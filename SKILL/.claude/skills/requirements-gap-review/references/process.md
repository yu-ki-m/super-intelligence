# 要求分析の実行プロセス

情報収集、要求発見、統合、検証、判断、報告を分けて実行する。実装の振る舞いを起点とし、仕様・要件・要求を上位へ遡って見直す。各工程は前工程の成果物を受け取り、後工程へ渡す。[逆向きレビュー](reverse-review.md) を全工程に適用し、分析モデルは [分析手法](analysis-methods.md)、記録欄は [報告形式](report-format.md) を使う。

## P1 情報収集と分析対象の定義

**入力**：レビュー依頼、利用可能な要求・業務資料、既存と変更後のコード・設計・テスト・設定、運用・障害・問合せ履歴、IF・契約・判断記録。

1. 変更目的、比較基準、対象工程、対象利用者・業務・環境、重要な損失を整理する。
2. 情報源を、人、文書、コード、稼働・利用実態、外部制約に分けて探す。利用者だけでなく、前後業務、運用、サポート、管理、連携先を含める。
3. 情報源に `SRC-*` を付け、場所・版・調査状態・適用範囲・得られた事実を記録する。アクセスできない、未提供、未調査、対象外を分ける。
4. [差分と実行経路](change-analysis.md) を調べ、比較基準とレビュー対象の版を特定する。対象コードから条件・状態・結果・副作用・暗黙の前提を復元し、文書上の仕様と分ける。変更前の動作、意図した変更、維持する条件、矛盾を区別し、根拠がない維持条件は候補に留める。
5. 業務境界、主体、状態、データ、外部依存と影響先を地図にする。12分析軸に対応する既知の値域と未定義を列挙する。情報源が足りず発見できない領域も記録する。

6. 変更の種類から、P2で深く掘る重点を決める。どの種類でも6系統と全分野の一次選別は省略せず、深さの配分だけを変える。複数の種類にまたがる変更は、該当する重点をすべて含める。

| 変更の種類 | 深く掘る重点 |
|---|---|
| 軽微な表示変更 | 対象の画面・表示条件・アクセシビリティ。表示と保存・出力の意味の一致 |
| 既存機能の改善 | 既存の仕様、変える条件と変えない条件、回帰の影響先 |
| 新規の業務機能 | 目的、業務フロー、状態、データ、例外、品質 |
| 権限・認証の変更 | 主体、資源、操作、認可の境界、攻撃経路、すべての情報の出口 |
| 外部連携の変更 | IF契約、異常系、再試行、整合性、互換性 |
| データ移行 | 既存データ、変換規則、整合性、復旧、運用への影響 |

たとえばAPIの応答に項目を追加するなら、既存の利用側が知らない項目をどう扱うかを確かめる。すべてのAPIを最初から詳しく調べる必要はなく、変更対象との依存関係から調べる範囲を決める。

**出力**：情報源台帳、範囲と比較状態、実装から復元した仕様と前提、業務・システムの概略、事実と仮定、未取得情報、変更・維持条件、変更の種類と深掘りの重点。

**次工程への渡し方**：共通の範囲と事実を6系統へ渡す。各系統が重点的に読む情報源を指定する。資料がない領域も空欄にせず調査課題として渡す。開始できないほど対象が不明なら、その特定に必要な質問をする。

## P2 6系統で要求候補を発見する

**入力**：P1の共通事実と系統別の調査材料。最初の系統の結論を残りの系統の前提にせず、異なる材料・モデルから検討してから照合する。各系統で実装上の前提を問い直し、文書にない必要条件も業務・状態・損失から導出する。コードと設計・テストの一致だけで探索を終えない。

| 系統 | 重点入力 | 実施する分析 | 必ず残す出力 |
|---|---|---|---|
| D1 業務・目的 | 目的、関係者、業務フロー、規程、運用上の補完 | M01〜M03。目的→必要能力→成立条件、正常・代替・例外・逆操作、直接利用しない関係者 | 目的の分解、業務シナリオ、未定義の分岐、候補 |
| D2 状態・条件 | 状態モデル、権限規則、条件分岐、入力定義、時刻・競合 | M04〜M05。状態遷移表、決定表、境界、禁止操作、順序逆転 | 条件と値域、期待結果、未定義セル、不変条件、候補 |
| D3 データ・連携 | スキーマ、データの読書き、IF、イベント、バッチ、データ管理 | M06〜M07。CRUD・ライフサイクル、正・派生データ、契約と失敗・再送 | データフロー、IF契約、欠落・重複・鮮度・互換の候補 |
| D4 異常・脅威 | 信頼境界、認証認可、障害履歴、依存、危害・損失 | M08〜M10。故障と業務影響、危険な制御、脅威・誤用、検知・封じ込め・復旧 | 故障・脅威シナリオ、損失経路、安全制約・対処の候補 |
| D5 品質特性 | 利用環境、負荷、品質基準、運用・保守・移行条件 | M11。[カタログ](quality/index.md)の全分野を一次選別し、関連・不明の詳細を対象へ適用 | 品質台帳、適用根拠、測定条件・未決定値、候補 |
| D6 変更影響 | 変更前後、呼出関係、共有データ・設定、利用元、判断履歴 | M13。直接・間接影響、未変更経路、新旧混在、切戻し、時間経過 | 影響一覧、変更前後の反例、維持条件、候補 |

どの系統も「確認済み」だけで閉じない。調査対象・参照材料・作ったモデル・候補ID・未確認を残す。適用対象がない場合は対象構成の証拠と理由を記す。時間や資料が足りなければ、未実施・一部実施を明示する。

時間や資料が限られて全部を同じ深さで進められないときは、次の順に深さを配分する。どの系統も一次の記録は残し、浅くした範囲を未実施・一部実施として報告する。

1. 情報源の探索（M01）と、要求の根拠の管理（候補の由来・根拠の記録）
2. 目的・業務フロー・状態・条件から、正常系以外の候補を出すこと（M02〜M05）
3. 実装から要求までの双方向の追跡（M12）と変更影響（M13）
4. 故障・脅威（M08〜M10）と品質特性（M11）の深掘り。実際に漏れが多い領域や重大な損失がある領域から
5. 形式的なモデル検査（[検証と評価](verification.md)）。表や具体例で判断できない並行性・状態の衝突があるとき

この順は検出範囲と負荷から考えた目安で、実証された順位ではない。

### 各系統の候補の記録

候補に `C-D1-001` のような系統別IDを付ける。候補ごとに次を記す。

- 要求・要件・仕様のどの層か、誰にとって何が必要か。
- 由来：明示／導出／推定／現状観測。導出なら前提と推論を、推定なら検証すべき仮説を記す。
- 適用条件、具体的なシナリオ、守るべき不変条件または観測したい結果。
- 対象の実行経路と現在の結果、そこから遡る仕様・要件・要求・目的、変更が必要な層の候補。
- 調査した `SRC-*` と位置、使用した分析モデル・品質観点ID。
- 期待が未定義なのか、仕様・実装の不充足なのか、まだ必要性自体が不明なのか。
- 影響、既知の対処・反証、追加調査または判断が必要な事項。

品質カタログを引用しただけでは、対象で必要なことの根拠にはならない。候補を既存の要求の表現へ書き換えるだけで終えず、今までなかった条件・主体・状態・情報源を探す。

**出力**：6系統の候補リスト、モデル・シナリオ、未確認事項。これらがP3の入力になる。

## P3 候補を統合し、根拠と対応を確定する

**入力**：6系統の候補と分析結果、P1の根拠。

1. 同義の候補を統合要求 `R-*` へまとめ、統合前ID→統合後IDを保存する。用語だけが違うものと、適用条件・対象・期待が違うものを区別する。
2. 重複候補にある追加の主体、失敗条件、タイミング、影響先は失わない。採用しない候補も不採用理由と根拠を残す。
3. 要求の由来を維持し、必要性の根拠と、実装で起きることの証拠を分ける。一般論の推定を明示要求に変更しない。
4. 実装・設定→仕様→要件→要求→業務目的・発言・判断記録を結び、その選択が妥当か検討する。次に要求から逆方向へたどり、必要条件の集合を仕様・実装・検証が満たすか確認する。リンクの存在だけで十分性を判定しない。
5. 候補間の矛盾を関連付ける。たとえば即時削除と保存義務、最新認可とキャッシュの両方を残し、どの条件で衝突するか示す。
6. 各統合要求に採否（根拠で確定／要判断／不採用）と充足（確認／不充足／矛盾／未確認）を独立して付ける。
7. 不足ごとに変更が必要な最上位の層と、仕様・実装・テスト・運用などへの波及先を特定する。期待が未確定なら決定事項と条件付き修正案を分ける。

**出力**：統合要求台帳、統合前後の対応、要求の双方向対応表、矛盾一覧、必要性・期待・事実が未確認の一覧。

**次工程への渡し方**：統合済みという理由で合格にしない。P4へ根拠、導出前提、モデル、期待結果、対応先をまとめて渡す。

## P4 検証工程

**入力**：P3の統合結果と、P1〜P2の情報源・モデル。候補を出したときとは別の確認パスとして実行する。

### 最初に3層の不足を調べる

| 層 | 検証すること | 不足した場合 |
|---|---|---|
| L1 情報源 | 誰・どの文書・経路を調べるべきか。未知の関係者・資料が残っていないか | P1へ戻り追加探索。取得不能なら未確認領域として残す |
| L2 発見と導出 | 目的・状態・条件・データ・異常等から必要条件を取り出したか | 該当D系統へ戻りモデル・候補を補う |
| L3 仕様と検証への反映 | 導出した条件が仕様・実装・受入条件へ届き、上位の期待を満たすか | P3の対応を補い、仕様不足・実装不足・検証不足を区別して指摘 |

### 10項目の検証

各項目を **充足を確認／不充足／判定不能／対象外** で記録し、対象ID、証拠、反例または限界、次の行動を付ける。対象外は適用しない根拠が必要。

| ID | 検証 | 実際に確認すること | 未解決となる条件 |
|---|---|---|---|
| G01 | 根拠 | 参照先が実在し本文が主張を支持するか。導出の全前提が成立するか | 確定要求に根拠がない、出典と意味が違う、前提が未確認 |
| G02 | 分析範囲 | 情報源・主体・条件・品質・影響先の台帳を突合 | 必要な領域が未分析、未確認を対象外扱い、分母から黙って削除 |
| G03 | 業務条件 | 決定表の条件値域・組合せ・期待結果・除外根拠 | 必要な組合せの期待結果がない、境界や条件軸が不足 |
| G04 | 状態遷移 | 許可・禁止・中断・再開・競合の遷移と不変条件 | 必要な遷移が未定義、反例がある、現状状態を表現できない |
| G05 | 整合性 | 要求同士、用語・単位・時点・責任・既存決定との整合 | 同一条件で両立しない要求、暗黙の優先順位、根拠の競合 |
| G06 | 追跡性と充足性 | 実装→仕様→要件→要求・目的の妥当性と逆向きの充足、下位条件の集合の十分性 | 対応がない、仕様どおりでも業務が成立しない、同じ生成前提を根拠に循環している |
| G07 | 検証可能性 | 前提・操作・観測結果・合否基準と期待の根拠 | 合否を決められない、未決定値を創作、未実行を実行済み扱い |
| G08 | 変更影響 | 呼出・データ・設定・利用元・運用・展開・切戻しの影響 | 未変更の影響先が未分析、旧データや混在版を見落とす |
| G09 | セキュリティ | 適用する認証認可・情報保護・悪用対策を全経路で確認 | 必要な信頼境界・情報出口が未分析、UI非表示だけで充足扱い |
| G10 | 品質特性 | 適用する品質条件、運用・移行・保守・安全、測定条件 | 必要な副特性が未定義、項目確認のみで期待・証拠がない |

記録の空欄やID欠落はスクリプトで検査できる。根拠の意味、矛盾、目的への十分性は内容を読んで判定する。[品質台帳の検証](coverage-workflow.md) だけでG01〜G10を完了したとはしない。

別の共通層・DB制約・設定・外部保証・承認済み変更を探して候補を反証する。根拠不足なら「欠落確定」を「要確認」へ修正する。期待が確定し不充足なら、要求・要件・仕様・実装・検証・運用のどこに問題があるかを特定する。

反証後の各指摘に、根拠、確度（%）とその理由、推奨する修正、受入・回帰条件を付ける。確度は [報告形式](report-format.md) の定義で評価する。観測事実が明確でも、その条件が業務上必要か未確認なら、その不確実性を指摘の区分・確度・修正案へ反映する。

有限の状態・組合せを機械検査する場合は [検証手順](verification.md) に従い、範囲と前提、入力モデル、実行結果、反例を残す。使っていないツールや未実行の検査を証跡にしない。

**出力**：L1〜L3とG01〜G10の結果、確認できた指摘、反証で解消した候補、未確認・矛盾・未分析、検証証跡。

## P5 エスカレーションと再分析

**入力**：P4の未決定事項・矛盾・重要な不確実性。

既存の決定や追加調査で解決できるものを先に解決する。業務ルール・品質水準・互換性破壊・責任範囲・許容損失など、判断が必要な事項は具体的な質問にする。

[エスカレーション票](report-format.md) に、関連R・指摘ID、状況と根拠、選択肢の振る舞いと業務・運用・費用への影響、推奨案と前提、判断先、必要な時点、未決定で止まる作業と続けられる作業をまとめる。

回答がないことを承認と扱わない。回答待ちでも確定範囲を進め、未回答は未確認としてP6へ渡す。回答で前提が変わったら影響するD系統・R・仕様・受入条件を更新し、対応するG項目を再検証する。議事録への回答だけで実装不充足を解消済みにしない。

修正も依頼されている場合は対象の版を更新して、原因となった反例と未変更の影響先を再確認する。根本の層の修正、下位成果物への反映、検証証拠がそろってから解消とする。分析のみなら、この再確認を指摘ごとの完了条件として提出する。

## P6 結果を報告する

**入力**：全工程の成果物と最新の決定状態。

最初に重要な指摘と判断事項を **HTMLの表** で示す。全行に根拠・確度（%）・推奨する修正を表示し、[HTML出力手順](html-output.md) で必須欄と表の表示を確認する。次の5群は本文または参照先で混ぜずに報告する。

1. 根拠で確定した要求・要件・仕様と、その充足・不充足。
2. 必要性・期待結果・事実の確認が残る要求候補。
3. 両立しない要求・根拠・仕様と、必要な判断。
4. 調べていない領域、情報源不足、今回範囲外と残余リスク。
5. 条件表・遷移表・対応表・品質台帳・実行結果等の検証証跡。

6系統の実施記録、統合前後の対応、L1〜L3・G01〜G10の結果を添える。指摘ゼロでも調査範囲と未検証を省略しない。大きな表は別ファイルにできるが、結論から根拠へたどれる参照を付ける。

追加探索できる範囲を終え、残る不確実性と次の行動を明記できたら、その時点の分析を提出できる。未確認がゼロになるまで無期限に待たず、未確認を合格へ変えない。リリース判断への影響は、対象の版、未解決事項、業務上の影響、必要な修正・決定・検証を示す。条件付き進行・該当作業の保留推奨・判定不能の対象と理由を区別する。

## P7 検出能力を評価し、観点を更新する

実際に後から見つかった漏れを、L1の情報源不足、L2の発見・導出不足、L3の反映・検証不足へ分類する。誤検出は根拠の誤読、適用の誤認、意図した変更の見落とし等へ分類する。

過去の漏れの発見前資料、人工的な欠落、正しく満たされる対照事例を使う。正解と修正内容は評価時まで分離する。正解集合と裁定がある場合だけ既知欠陥への再現率・正確率を算出し、未裁定、重大な見逃し、確認負荷も残す。

今回の入力に評価データがなければ「検出能力は未評価」と記録する。指摘数・観点数・台帳の処理率を性能の代わりにしない。改善は実際の失敗に対応する工程へ戻し、無関係な必須要件を増やさない。
