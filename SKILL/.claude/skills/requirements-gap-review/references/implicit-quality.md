# 暗黙の品質と分析観点

本資料の12軸と質問例は分析の枠組み。品質の詳細は [9品質特性・40副特性のカタログ](quality/index.md) と [605観点の一覧](quality/viewpoints.md) を使い、本資料だけで品質観点の確認を完了しない。[台帳手順](coverage-workflow.md) に沿って未分析を残す。

## 期待の根拠

ここでの「当たり前品質」は一般的な品質分類に限定しない。利用者・関連部門が業務上依存し、明文化されなくても開発側の確認対象になる期待を含む。ただし、開発側が調査する責任と、すべてを実装する義務は分ける。

| 期待の由来 | 探す証拠 | 要件化するときの注意 |
|---|---|---|
| 明示された約束 | 承認済み要求、契約、運用規程、変更決定 | 対象、版、有効期間、例外を確認 |
| 業務成立の必要条件 | 業務フロー、目的、後工程、失敗時の損失 | 前提と導出を明示。目的達成に必要か検証 |
| 組織固有の慣行 | 手順、過去の承認、問い合わせ、サポート対応 | 繰り返された運用か、一時的な例外かを区別 |
| 既存の依存・互換性 | 呼出側、テスト、利用実態、データ、公開仕様 | 現行挙動だけで恒久的な保証としない |
| 人が補っている条件 | 再処理、手修正、Excel補正、目視照合 | 自動化・仕様変更後に誰が補うか。自動化を勝手に要求しない |
| 故障・誤用からの導出 | 障害履歴、境界条件、到達可能な失敗経路 | 具体的な損失と回避・検知・回復の条件を示す |
| 一般的な期待 | 品質モデル、業界慣行、類似機能 | 発見の手掛かり。適用根拠がなければ未確認候補 |

根拠の優先順位を一律に「コード優先」「最新文書優先」としない。適用範囲と明示された変更・承認・失効を調べ、解決しない矛盾を残す。

## 組織の品質前提

利用可能な資料から次を短く整理する。全部を初回質問にせず、不足が重大な判断に効く箇所をエスカレーションする。

- 誰の業務をどこまで開発側が支えるか。運用・サポート・外部サービスとの責任境界。
- 絶対に避けたい損失と、許容される縮退・手作業・遅延。根拠のあるものと未確認を区別。
- 利用者、組織・テナント、端末、利用時間帯、データ量、業務上重要な締め・期限。
- 維持すべき既存の約束、過去の重大な漏れ、よくエスカレーションされる事項。
- 品質基準、例外の承認経路、実装側で決められる範囲、業務側の判断が必要な範囲。

既存の品質基準があれば利用する。今回の分析で新たな全社方針を確定・保存したことにしない。

## 分析観点表

各軸を対象に照らして選別し、関連する領域を深掘りするための表。項目数を増やすことは目的ではない。具体的な条件と期待結果が決まるところまで展開する。

| 軸 | 探す条件と期待 | 調査の手掛かり |
|---|---|---|
| A 主体と責任 | 利用者、代理操作、管理者、運用者、自動実行、別組織 | 誰が開始・承認・復旧し、誰に影響するか |
| B 目的と業務 | 前後工程、代替手段、例外、完了条件、手作業 | 正常終了でも業務が終わらない場面 |
| C 業務状態 | 開始、途中、承認待ち、完了、取消、再開、禁止遷移 | 状態機械、画面・APIのガード |
| D データ状態 | 未入力、null、空、境界値、不正、重複、旧形式、削除済み | スキーマ、実データの制約、正規化・丸め・単位 |
| E 許可・成立条件 | 主体×資源×操作、所有者、テナント、目的制限 | 認可層、業務規則、UIとAPIの差 |
| F 結果と副作用 | 成功、失敗、一部成功、成功したが応答を失った状態 | 画面表示、保存、課金、通知、履歴の一致 |
| G 時間・順序 | 競合、再送、逆順応答、期限、日付境界、タイムゾーン | ロック、冪等性、時刻・締め処理、非同期 |
| H 外部依存 | 遅延、停止、制限、仕様変更、認証期限、応答不正 | タイムアウト、再試行、縮退、二重処理 |
| I 品質 | 性能、使いやすさ、アクセシビリティ、信頼性、保守性等 | 利用環境、測定条件、業務目的への寄与 |
| J ライフサイクル | 導入、初期データ、運用、移行、復旧、切戻し、廃止 | 展開順序、バックアップ、監視、復旧手順 |
| K 既存の約束 | API、形式、順序、識別子、既定値、通知先、運用 | 利用側と混在版、既存テスト、承認された廃止 |
| L 異常・危険・悪用 | 誤操作、越境、改ざん、過負荷、障害連鎖 | 信頼境界、障害実績、検知できず放置される失敗 |

この12軸は分析用の整理であり、国際標準の項目番号ではない。

## 広い当たり前品質を具体化する質問

関連する領域だけを掘る。ここにある条件を無条件に追加仕様にしない。

- **業務の一貫性**：画面、検索、一覧の件数、帳票、出力、通知が同じ意味・権限・状態を扱うか。片方だけ古いと誰が誤判断するか。
- **処理の一度性と完了**：二重クリック、タイムアウト後の再試行、イベント再配信で同じ業務が重複するか。受付済みと完了済みを利用者が区別できるか。
- **情報の鮮度と境界**：権限剥奪・削除・訂正後にキャッシュ、検索索引、要約、ログ、出力へ反映される条件は何か。内容以外の件数や存在も情報にならないか。
- **途中状態の扱い**：一部だけ保存・通知された後に止まると誰が何を直すか。再開・補償・手修正の整合条件は何か。
- **運用の成立**：失敗を誰がどう知り、識別・調査・再処理するか。監視があっても対応責任や復旧条件が空白でないか。
- **変更と継続性**：旧クライアント、旧データ、新旧サービス混在、段階展開、フラグ切替、切戻しで意味が変わらないか。
- **利用環境**：IME入力中、キーボード、支援技術、弱い通信、古い端末など、実際の対象利用者の条件で業務が成立するか。
- **データの意味**：金額・税・丸め・数量の単位、日付・締め・時差、識別子の一意性や再利用は何を前提としているか。
- **容量と性能**：件数・同時数・外部待ち・大きな入力によって、応答やリソースがどう変わるか。数値目標の根拠と測定境界はあるか。
- **誤操作からの回復**：取消、確認、やり直し、入力保持が必要な場面と、不可逆な操作の責任範囲は何か。
- **長期運用**：保存・削除・監査・バックアップ・復元が矛盾しないか。期限切れの鍵・証明書・依存サービスで継続できるか。
- **費用と支援負荷**：再試行や再計算が無制限にならないか。手作業の増加や問い合わせ増が運用能力を超えないか。

法令・契約・標準の適用は、対象地域・業務・データ・版を確認する。最新性が必要なら一次資料で確認し、アクセスできなければ未確認とする。一般的な知識だけで法的義務や規格適合を確定しない。

## 掛け合わせで欠落を発見する

全軸の無差別な直積を作らない。対象の不変条件に影響する軸を選ぶ。例えば「誰にも他組織の本文を開示しない」なら、主体×組織×情報の出口×権限変更時点を調べる。「重複して処理しない」なら、再送×部分成功×競合×再起動を調べる。

例：類似検索で候補30件、表示最大10件なら、閲覧可能件数が0・1・9・10・11・30の場合と認可・切捨ての順序を比較する。「最大10件」は常に10件を埋める義務ではない。一方、10件を満たす約束があって候補に閲覧可能なものが9件しかなければ、取得範囲と約束の矛盾として判断が必要になる。

「起票の補助機能が失敗しても起票できる」は有力な候補だが、検索が必須チェックを兼ねる業務もある。業務目的から必要性を確認し、既定で採用しない。

## 過剰仕様を防ぐ反証

候補ごとに、適用の証拠、既存の充足手段、意図的な除外、より小さい対処、採用しないときの具体的損失を確認する。「便利そう」だけなら改善提案へ分ける。理由が未確認なら対象外にせず未確認にする。

既知の品質基準を満たす複数の設計がある場合、特定技術の採用を要件と同一視しない。例えば整合性の保証方法としてロック・楽観制御・直列化などを比較できても、根拠なしにロックだけを必須としない。
