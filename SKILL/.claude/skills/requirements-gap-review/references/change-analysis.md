# 変更・コード分析

## 比較する二つの状態を固定する

ユーザー指定の基準を優先する。Gitならリポジトリのルート、作業ツリーの状態、基準コミット、対象コミット、未コミット変更の包含範囲を記録する。ブランチ名だけでなく解決したコミットIDを保存する。

読み取りの例。Bashツールで実行し、引数のパス・参照名を正しく引用する。日本語のパスが `\346\227\245...` のように表示される場合は `git -c core.quotepath=false` を付ける。差分が大きいときは `--stat` や `-- <path>` で範囲を絞って読み、表示が打ち切られた部分を読んだことにしない。

```text
git rev-parse --show-toplevel
git status --short
git diff --name-status -M
git diff --cached --name-status -M
git ls-files --others --exclude-standard
git diff --name-status -M <base> <target>
git diff --find-renames <base> <target> -- <path>
git show <base>:<path>
```

- コミット間、ステージ済み、未ステージ、未追跡の変更を区別する。`git diff` 一つだけで「全変更を確認した」としない。
- PRの変更範囲を見たい場合は、意図されたマージ先が特定できればその参照とのmerge-baseを使う。指定された二時点比較を勝手にmerge-base比較へ変えない。
- マージ先を `main` と決めつけない。基準が不明ならHEADと作業ツリーの差を暫定範囲として示し、コミット済み変更は判定対象に含めていないと書く。
- 最新状態との比較が必要なのに参照が古い場合は鮮度の不足を示す。リモート更新やチェックアウトを黙ってレビューの前提にしない。
- `git diff <base>` で基準から作業ツリーまで比較しても未追跡ファイルは含まれない。対象に関連する未追跡ファイルは別途読む。
- 追加、削除、リネーム、型・設定・依存更新、DB移行、テスト削除も見る。生成物なら生成元を調べる。
- 大きな差分の表示打切り、バイナリ、サブモジュール、アクセス不可ファイルは未確認として残す。
- Gitがない場合は、渡された旧版と新版を比較する。旧版がなければ変更起因性を確定せず、現状の整合性分析に切り替える。

ユーザーの作業状態を保持する。比較のためにreset・stash・checkoutや本番操作を行う必要はない。

## 差分から実行経路へ進む

1. 変更した入口、公開関数、型、設定、テーブル、イベント、業務ルールを特定する。
2. 呼出元、呼出先、ルート登録、DI、ミドルウェア、DB制約までたどり、実際に到達する条件を確認する。
3. 同じデータを読む・書く・公開する経路を探す。UI以外のAPI、バッチ、通知、エクスポート、管理画面を含める。
4. 既存テストと運用・障害記録から期待される動作を抽出する。テストが存在しても、入力とassertが問題の条件を検証しているか読む。期待値が現実装や同じ生成時の仮定をなぞるだけなら、業務目的を裏付ける証拠としては扱わない。
5. 前後の動作を具体例で比較し、目的・制約・データ整合性に生じる差を記録する。

Grep・Glob ツールや言語の参照検索で候補を集め、Read で該当ファイルの文脈を読む。検索ヒット数だけで依存の有無を決めない。動的登録、リフレクション、設定経由や外部利用側で追跡が途切れたら、その境界を記載する。

| 変更の起点 | 影響をたどる先 | 見落としやすい必要条件 |
|---|---|---|
| 認可・公開範囲 | 検索、件数、キャッシュ、通知、出力、要約 | 本体以外の漏えい、権限変更後の再評価 |
| DB型・意味・必須化 | 旧データ、書込元、移行、集計、連携先 | 既存null、桁・丸め・単位、混在版 |
| APIの入出力 | 全クライアント、ページング、署名、SDK | 省略とnull、順序、厳密なデシリアライズ |
| 同期から非同期 | 応答、ジョブ、再試行、監視、取消 | 受付と完了の区別、重複、順序、部分失敗 |
| 削除・保存 | 子データ、添付、索引、バックアップ、履歴 | 保全との衝突、残存、復元・再処理時の復活 |
| UIの状態・入力 | 保存、入力中データ、支援技術、端末 | 古い応答、二重送信、フォーカス、離脱 |
| 設定・依存・配置 | 環境差、既定値、起動、展開順、切戻し | フラグ両状態、新旧サービス混在、互換性 |

表にない経路も実システムの構成から補う。見つけた依存ごとに、影響あり／影響なしの根拠／未確認を残す。

## 変更前後を結ぶ証拠

各重要変更に、現行の根拠・意図された変更・変更後の実装または設計・影響先・検証条件を結ぶ。既存に問題があった場合は維持を提案せず、変更意図と業務影響を確認する。変更後に問題が解消していると分かれば指摘しない。

次に [逆向きレビュー](reverse-review.md) に従い、実装が採用したルール・制約・例外時の結果を仕様として言語化し、仕様→要件→要求・業務目的を遡る。変更された行だけでなく、変更で到達可能になった状態、共有処理、前後の業務まで含める。設計との一致と業務目的の充足を別々に判定する。

実装を読んだ結果と実行した結果は分ける。テスト実行が有用ならリポジトリの手順と対象を確認し、関連する最小の検証を行う。実DB書換え、外部送信、環境依存で実行できなければ静的な根拠と未検証事項を報告する。

## 設計書を比較するとき

画面・APIの本文だけでなく、表、脚注、図の矢印、入出力定義、例外、用語定義、運用・移行手順を読む。PDFや画像を含む文書で抽出できない箇所を、読んだものとして扱わない。

設計中の「適切に」「速やかに」「必要に応じて」「既存と同様」は、誰がどの条件で何を観測すれば合格かに展開する。「既存と同様」なら参照先の版と引き継ぐ範囲を特定する。

コードと設計書が矛盾しても、どちらが正かを独断で決めない。有効な決定・変更履歴を探し、見つからなければ両方の根拠と業務上の差を提示する。設計のみのレビューでは実装・テストの不在を欠陥として数えず、次工程で確認する義務として残す。
