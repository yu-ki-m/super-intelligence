# Q07 保守性(Maintainability)

このカタログを、案件固有の要求候補を発見するために使う。各項目の適用条件・必要性・代替手段を確認し、一律に必須要件としない。技術例や数値をそのまま採用せず、案件の根拠に基づいて判断する。規格・法令・期限を判断に用いる場合は適用範囲と最新性を確認する。

項目IDを使って案件の根拠・要求候補・指摘・検証条件を結び付ける。

<a id="Q07-01"></a>
## Q07.01 モジュール性(Modularity)

### Q07.01.001 コンポーネント間の疎結合

- `Q07.01.001.01` 他モジュールの内部実装への依存(DB 直参照等)の排除
- `Q07.01.001.02` インターフェース経由での連携の徹底
- `Q07.01.001.03` 結合度・依存本数の計測

### Q07.01.002 モジュール内の高凝集

- `Q07.01.002.01` 関連する処理・データの同一モジュールへの集約
- `Q07.01.002.02` 雑多な共通モジュール(utils 等)の肥大化防止
- `Q07.01.002.03` 単一責任から逸脱したモジュールの検出

### Q07.01.003 ドメイン境界(業務領域の区切り)の明確さ

- `Q07.01.003.01` 業務ドメインに沿った境界(境界づけられたコンテキスト)の定義
- `Q07.01.003.02` 境界を跨ぐデータ・用語の変換の明示
- `Q07.01.003.03` 境界と実装構造(パッケージ、サービス)の一致

### Q07.01.004 インターフェース(契約)の明確さ

- `Q07.01.004.01` 公開 API と内部実装の区別
- `Q07.01.004.02` 契約(入出力、例外、事前条件)の文書化
- `Q07.01.004.03` 契約変更時の影響管理のプロセス

### Q07.01.005 依存関係の明確さ・循環依存の有無

- `Q07.01.005.01` 依存グラフの可視化
- `Q07.01.005.02` 循環依存の検出と解消
- `Q07.01.005.03` 意図しない依存の混入防止(アーキテクチャテスト)

### Q07.01.006 共有 DB 経由の暗黙的結合の有無

- `Q07.01.006.01` 複数システムからの同一テーブル直接参照の排除
- `Q07.01.006.02` データの所有者(オーナー)の明確化
- `Q07.01.006.03` スキーマ変更時に影響先を把握できること

### Q07.01.007 レイヤー構造・依存方向の一貫性

- `Q07.01.007.01` レイヤー定義と依存方向のルール化
- `Q07.01.007.02` レイヤー違反(飛び越し・逆流)の検出
- `Q07.01.007.03` ルールの自動チェック(静的解析)への組み込み

### Q07.01.008 アーキテクチャ様式(モノリス/マイクロサービス)の適切さ

- `Q07.01.008.01` チーム規模・変更頻度に応じた様式の選択
- `Q07.01.008.02` 分割しすぎ/巨大化しすぎの兆候の把握
- `Q07.01.008.03` 様式の変更(分割・統合)の判断基準

### Q07.01.009 チーム構造とモジュール境界の整合(コンウェイの法則)

- `Q07.01.009.01` モジュールごとのオーナーシップ(担当チーム)の明確化
- `Q07.01.009.02` チームを跨がないと完了しない変更の頻度の把握
- `Q07.01.009.03` 組織変更時の境界の見直し

### Q07.01.010 機能単位での独立デプロイ可能性

- `Q07.01.010.01` モジュール単位でのビルド・デプロイの可否
- `Q07.01.010.02` 他モジュールとの同時リリース強制の有無
- `Q07.01.010.03` 互換性を保った独立リリースの運用

### Q07.01.011 変更頻度が異なる部分の分離

- `Q07.01.011.01` 頻繁に変わる部分(UI、業務ルール)と安定部分の分離
- `Q07.01.011.02` 変更頻度の計測(ホットスポット分析)
- `Q07.01.011.03` 安定部分への変更波及の抑制

### Q07.01.012 変更影響範囲の局所化

- `Q07.01.012.01` 1 つの変更で触るモジュール数の少なさ
- `Q07.01.012.02` 依存の追跡による影響分析のしやすさ
- `Q07.01.012.03` 局所化を壊す実装(グローバル状態等)の排除

## Q07.02 再利用性(Reusability)

### Q07.02.001 汎用部品の切り出し(複数箇所で使える単位への部品化)

- `Q07.02.001.01` 複数の機能・システムで繰り返し現れる処理の特定と部品化
- `Q07.02.001.02` 業務固有の処理と汎用的な処理の分離
- `Q07.02.001.03` 再利用の想定範囲(単一システム内/チーム内/全社)の明確化

### Q07.02.002 共通化の判断基準とタイミング

- `Q07.02.002.01` 共通化に踏み切る基準(同じ処理が 3 回現れたら等)の合意
- `Q07.02.002.02` 見た目が似ているだけで変更理由が異なる処理の共通化の回避
- `Q07.02.002.03` 共通化で生じる依存(利用者間の結合)とのトレードオフ評価

### Q07.02.003 インターフェースの汎用性(特定の利用者に依存しない設計)

- `Q07.02.003.01` 特定の呼び出し元の事情を前提としない引数・戻り値の設計
- `Q07.02.003.02` 利用者ごとの差異を設定・パラメータ・拡張ポイントで吸収する仕組み
- `Q07.02.003.03` 使われないオプションの増殖(過度な汎用化)の回避

### Q07.02.004 環境・文脈への非依存性(別の環境へ持ち込めること)

- `Q07.02.004.01` ホスト名・パス・接続先などのハードコードの排除
- `Q07.02.004.02` グローバル状態・暗黙の初期化処理への依存の排除
- `Q07.02.004.03` 動作に必要な前提(ランタイム、OS、ミドルウェア)の明示

### Q07.02.005 依存関係の最小化(持ち込んだ先の負担の軽さ)

- `Q07.02.005.01` 再利用資産が引き込む推移的依存の少なさ
- `Q07.02.005.02` コア部分の特定フレームワークからの独立
- `Q07.02.005.03` 依存ライブラリのバージョン指定を利用者に強制しない設計

### Q07.02.006 業務ルール・計算ロジックの一元化と共用

- `Q07.02.006.01` 税計算・料金計算など全社共通ルールの単一実装
- `Q07.02.006.02` 画面・バッチ・API で同じ業務ロジックを共用できる構造
- `Q07.02.006.03` 業務ルールの外部化(ルールエンジン、設定テーブル)の検討

### Q07.02.007 共通基盤・共通サービスの提供(認証、ログ、通知、帳票等)

- `Q07.02.007.01` 横断的な機能(認証・ログ・通知・帳票出力)の共通サービス化
- `Q07.02.007.02` 共通サービスで賄えない個別要件への対応手段
- `Q07.02.007.03` 共通基盤の障害・性能劣化が全利用システムへ波及するリスクの評価

### Q07.02.008 API・サービスとしての再利用(画面以外からの利用)

- `Q07.02.008.01` 画面専用ではなく他システムからも呼べる API の設計
- `Q07.02.008.02` 社内向け API の公開範囲・利用条件の定義
- `Q07.02.008.03` 利用元・利用量の計測(誰がどれだけ使っているか)

### Q07.02.009 データ・マスタの再利用(共通マスタ、データ定義の標準化)

- `Q07.02.009.01` 顧客・商品・組織など共通マスタの一元管理

- `Q07.02.009.03` 項目名・意味・コード値を定めたデータ辞書の整備

### Q07.02.010 UI コンポーネント・デザインシステムの再利用

- `Q07.02.010.01` 共通 UI コンポーネントライブラリの整備
- `Q07.02.010.02` 色・余白・文字サイズ等のデザイントークンの一元管理

### Q07.02.011 設計資産・ひな形(テンプレート)の再利用

- `Q07.02.011.01` 画面・帳票・バッチのひな形の整備

### Q07.02.012 インフラ構成・CI/CD 定義の再利用
