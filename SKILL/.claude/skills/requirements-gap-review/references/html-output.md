# HTMLの指摘一覧を作る

P6では [報告形式](report-format.md) に従い、全指摘の根拠・確度（%）・推奨する修正が表の同じ行に見えるHTMLを作る。根拠以外は1列1項目とし、各JSONキーを独立した列へ表示する。標準の出力先は対象作業領域の `requirements-gap-review.html`。分析台帳は別ファイルにできるが、必須欄を参照先だけに置かない。

## 同梱の出力スクリプト

Python 3の標準ライブラリだけで動く [render_findings.py](../scripts/render_findings.py) を使用できる。下表の形式を読んでから、入力JSONを Write ツールで出力先に作り、Bashツールでスクリプトを実行する。`<SKILL_DIR>` はスキルのフォルダ（SKILL.md に示した実パス）。Windowsでは `python`、ほかは `python3` を使い、パスは二重引用符で囲む。

```text
python -X utf8 "<SKILL_DIR>/scripts/render_findings.py" --input "<project-dir>/review-findings.json" --output "<project-dir>/requirements-gap-review.html"
```

エラーが出たら、表示された欄を入力JSONで直して再実行する。欄を埋めるために根拠や判断先を創作しない。既存ファイルは上書きしない。同じレビューの更新であると確認できる場合だけ `--overwrite` を付ける。出力先の親フォルダが無ければ作成する。スクリプトの絶対パスを使えば、対象プロジェクト等の別ディレクトリからも実行できる。

終了コード0は構造検査とHTML生成の成功、1は入力・ファイル操作のエラー。指摘の正しさ、根拠の実在、修正案の妥当性、リリース可否は検査しない。P4の内容検証を別途行う。

## JSON形式（schema_version: 2）

ルートはオブジェクトとする。全ての文章はHTMLではなくプレーンテキストで渡す。

| キー | 型 | 内容 |
|---|---|---|
| schema_version | 整数 | `2` |
| title | 空でない文字列 | レビュー名 |
| target | 空でない文字列 | 対象コード・設計の版、未コミット範囲や調査時点 |
| baseline | 空でない文字列 | 比較基準の版。ない場合はその旨と変更起因性の限界 |
| scope | 空でない文字列 | 調査した業務・機能・経路・検証 |
| summary | 空でない文字列 | 結論と重要な未解決事項 |
| limitations | 文字列配列 | 未確認・未分析・未実行・残余リスク。項目なしは `[]` |
| artifacts | 文字列配列、省略可 | 工程の記録、対応表、品質台帳、決定票等の場所と説明 |
| findings | オブジェクト配列 | 下記の指摘。0件は `[]` |

各指摘に次のキーを全て持たせる。空の文字列・空白だけの値は不可。

| キー | 型 | 表示内容 |
|---|---|---|
| id | 文字列 | 重複しない指摘ID |
| title | 文字列 | 条件を含む指摘の要点 |
| status | 文字列 | `確認できた不足`／`要判断`／`分析不能`／`矛盾`／`解消・対象外` |
| severity | 文字列 | `重大`／`高`／`中`／`低` |
| impact | 文字列 | 業務への影響。到達条件と損失の規模を具体化する |
| scenario | 文字列 | 前提、主体、操作・障害、到達条件 |
| observed | 文字列 | 現在の結果 |
| expected | 文字列 | 必要な結果。採否未確定・推定ならその旨を記す |
| layers | 文字列 | 修正が必要な最上位の層と波及先 |
| reverse_trace | 文字列 | コード・実行経路→仕様→要件→要求・業務目的の対応。欠ける根拠も明示 |
| evidence | オブジェクト | 下記3種類の根拠 |
| confidence_pct | 整数 | `0`〜`100`。`95` と書き、文字列 `"95%"` や小数は不可 |
| confidence_reason | 文字列 | 確度の理由、裏付けの強さ、未確認の前提 |
| recommended_fix | 文字列 | 推奨する修正。層・対象・具体ルール・関連成果物・判断条件 |
| verification | 1件以上の文字列配列 | 修正後の受入・回帰条件。既存の検証結果と混同しない |
| next_action | 文字列 | 次に実施する具体的な行動 |
| decision_role | 文字列 | 判断先の人物または役割。必要だが不明なら未定、不要なら該当なしと理由 |
| decision_timing | 文字列 | 判断が必要な時点。根拠のない日付は作らない。必要だが不明なら未定、不要なら該当なしと理由 |

次の行動・判断先・判断が必要な時点は、それぞれの欄に分けて書く。判断先や時点が分からないときに、文章から担当や期限を推定して埋めない。

`evidence` には次の3キーを持たせ、それぞれ1件以上の文字列配列とする。

- `behavior`：コード・設計の位置と版、静的確認／実行結果の別、何を示すか。
- `necessity`：必要性の業務根拠と位置。導出なら前提と推論、推定なら仮説と確認方法。
- `counterevidence`：確認した別経路・共通層・承認された変更、主張の限界。反証未確認なら理由と未確認範囲を明記する。

文章内の改行は表示にも反映される。根拠が不足する場合に位置を創作して欄を埋めない。「対象を調査したが根拠未取得、要判断」など事実を記し、区分・確度を調整する。

## 出力を確認する

1. 入力とHTMLの指摘件数・ID・区分が一致すること、全行に根拠・確度（数値と%）・推奨する修正が表示されることを確認する。根拠以外は入力の各項目が独立列に入り、他項目の値や小見出しが混ざっていないことも確認する。
2. 確度を「高」だけで書いていないか、発生確率と混同していないか、修正案が具体的な条件と結果を含むかを読む。
3. 日本語、コード記号、`<`・`>`・`&`、引用符を含む根拠が文字として表示されることを確認する。対象コードや文書の文字列をHTMLとして埋め込まない。
4. ブラウザーを操作できるツール（Claude in Chrome など）が使えれば、HTMLを開いて表の折返し、横スクロール、見出し、全列への到達を確認する。表示確認できなければその限界を記録する。
5. 外部のスクリプト・画像・フォントへ依存させない。HTMLだけを開いて表が見えることを確認する。0件でも未確認範囲を省略しない。

Pythonが利用できない場合は同じ列と必須条件でHTMLを直接作成してよい。表は `<table>`・`<thead>`・`<tbody>`・`<th scope="col">` を使い、UTF-8と日本語の言語指定を含め、`<`・`>`・`&`・引用符はすべて文字参照に変換する。
