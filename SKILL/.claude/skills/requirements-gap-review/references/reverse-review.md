# 実装から仕様・要件・要求を問い直す

主な入力は、レビューする時点の実装と、利用可能な変更前コード・設計・業務情報である。実装を先に調べることは、実装の選択を正当化することではない。事実を復元するパスと、必要な挙動を業務から導くパスを分け、最後に突き合わせる。

## 1. 観測した振る舞いを仕様として言語化する

重要な入口と変更の影響先について、次をコード・設定・DB制約・外部契約から復元する。

- 主体、対象、操作、前提、分岐条件、権限、実行時点。
- 入力と既定値、正常・境界・例外時の戻り値、保存状態、副作用。
- 確定の時点、トランザクション境界、非同期完了、再実行、競合、途中停止。
- UIが伝える結果と、保存・送信・集計・後続業務で実際に成立する結果。
- 前提としているデータ量、データの新旧、利用環境、運用による補完。

「更新する」なら、何をいつ更新し何を更新しないかまで書く。未実行のコード読解、実行で観測した結果、設計の記載、推測を分ける。到達可能性と共通層の保証を確認し、読んでいない経路の挙動を補完しない。

## 2. 各振る舞いを上位へ遡る

| 遡る段階 | 確認すること | 根拠がないとき |
|---|---|---|
| 実装→仕様 | どの具体ルールを実現しているか。文書と差があるか、文書にない選択は何か | 実装から復元した仕様として記録し、正式な仕様と区別 |
| 仕様→要件 | どの能力・制約・品質条件を満たすか。その条件の集合で十分か | 必要性と不足条件を導出し、未確認の前提を残す |
| 要件→要求 | 誰のどの成果・損失回避に必要か。対象外の関係者へ負担を移していないか | 目的・利用実態・業務責任を探索し、候補または矛盾として残す |
| 要求→業務目的 | その成果自体が業務を成立させるか。前後業務や例外でも目的を果たすか | 目的の欠落・衝突を判断事項にし、機能追加へ短絡しない |

逆向き対応は「コード位置・条件→実装上の仕様→必要条件とその由来→要求・目的→業務上の差→修正する層」で残す。対応先がないことだけで欠陥と断定しない。過去の決定や暗黙の必要性を調べる。

## 3. 業務から独立に反例を作る

P2の6系統で、実装に存在しない条件も候補に含める。提示された正常系や生成済みのテストの入力だけを分析範囲にしない。

- **業務の完結**：受付から確定、引継ぎ、取消、差戻し、再開、訂正、照合まで。成功表示だけで、資源・金額・履歴・後続処理が不整合にならないか。
- **関係者と責任**：本人、代理、承認者、後続部門、管理、運用、サポート。誰も担当しない例外処理や、処理権限のない人に復旧を要求する前提がないか。
- **業務時間と状態**：締め、期限、順序、重複、並行、権限変更、過去日訂正。正常時だけ成立する前提が残っていないか。
- **失敗時の仕事**：途中失敗、結果不明、依存停止、再試行、復旧時に、処理済みか判断できるか。入力や確定済みの仕事が失われないか。手作業への切替が現実に実施可能か。
- **導入後の成立**：旧データ、新旧版の混在、移行・切戻し、通常負荷と繁忙、問い合わせ対応、保守。運用が恒常的に補うことを暗黙に要求していないか。

各反例は「前提→操作・障害→実際の状態・結果→影響を受ける業務→必要条件」にする。品質カタログと横断条件で補うが、対象にない機能や技術を一律に追加しない。

実装・設計・テストが同じ依頼文や生成時の仮定を共有していれば、一致していても見落としを共有し得る。テストの期待値を業務根拠へ遡り、別の情報源や条件から検証する。生成時の説明は意図の情報源として扱い、実際の挙動や業務上の正しさの証明にはしない。

## 4. 修正の出発点と波及先を決める

| 見つかった差 | 推奨する修正の組み立て方 |
|---|---|
| 妥当な仕様に実装が従わない | 実装・設定・データの修正箇所と回帰条件を示す |
| 実装と仕様は一致するが要件を満たさない | 具体ルールを変える仕様案と、実装・テスト・運用への反映先を示す |
| 記載要件は満たすが業務が成立しない | 成立に必要な条件を導出し、要件の追加・変更と仕様案を示す。未確認の業務判断を分離する |
| 目的・対象者・責任・優先順位が不足または衝突する | 要求の見直し案、選択肢、業務上の得失、判断先を示す。決定後に変える下位成果物を列挙する |
| 期待も挙動も確認できない | 調査範囲と不足する証拠、確認方法、判断に応じた修正案を示す。不具合確定とはしない |

各指摘で最上位の修正対象と波及先を示す。すべてを要求変更扱いにせず、コード修正だけで上位の矛盾を隠さない。「要確認」「テスト追加」だけで修正案を終えず、期待するルール・結果とその検証方法を書く。

## 5. 修正後とリリース判断へつなぐ

分析の依頼では、修正案と確認すべき条件を提出する。実装修正も依頼されている場合は、その範囲で修正して再レビューする。

1. 指摘ID、決定内容、変更対象の層、確認する受入条件を対応させる。
2. 修正した版を特定し、該当経路と共有処理・データ・未変更の影響先を再確認する。
3. 原因となった反例が成立しなくなった証拠と、必要な回帰確認を残す。コードを変更した事実だけで解消にしない。
4. 更新した仕様・要件・要求と実装・検証を照合する。判断が変わった場合はP1〜P4の影響範囲へ戻る。
5. 対象の版、残存指摘、未決定の業務条件、未検証範囲をリリース判断材料にする。更新後の版へ古い評価を無条件に引き継がない。

静的な推論による確認と実行による確認を区別する。未確認が解消できない場合も、対象・影響・必要な判断を残して報告する。指摘の確度や品質台帳の処理率をリリース可否の自動判定に使わない。
