# 品質観点を省略しないための台帳

## 広さを確認してから深さを決める

同梱の [カタログ](quality/index.md) に9品質特性・40副特性・605観点・1,833確認項目がある。[実行プロセス](process.md) のP2・D5で要求候補を発見し、P3の統合とP4の品質検証へつなぐ。要約だけから観点を再生成しない。

1. [40副特性の一覧](quality/index.md) と [605観点の一次選別一覧](quality/viewpoints.md) を一巡し、変更機能と影響先、既存環境に照らして適用候補を探す。セキュリティ・性能など目立つ分野だけを選ばない。
2. 関連あり・適用不明の観点は、下記「詳細確認項目を読む」の `show` で詳細確認項目を読む。無関係と判断するには対象の構成・責任範囲・利用条件などの証拠が必要。資料がないだけなら不明とする。
3. 各確認項目を対象の要求・要件・仕様・コード・運用へ対応付ける。同じ項目が複数機能へ適用される場合、IDに対象機能・条件を付けて別の分析行に展開するか、個別結果を別表に持つ。元ID一行の「充足」で全機能を代表させない。
4. 正常系だけでなく、境界・失敗・時間・権限・新旧混在など [横断分析](cross-checks.md) と掛け合わせる。
5. 項目ID、適用条件、根拠、期待結果、確認結果、関連指摘、未確認時の次の調査を残す。確認項目に「機能がある」と記載するだけで、その必要性・十分性を確認したことにしない。

小変更でも一次選別の記録を残し、深掘りする範囲を調整する。ユーザー指定の部分レビューならその境界を尊重し、外側の項目は「今回範囲外」とする。時間・情報・コンテキストの制約で読めなかった項目は「未分析」で残す。「影響が小さそう」を理由に未分析を対象外へ変えない。

## カタログの文言と要件の区別

カタログは多様な領域の検討材料と具体策の例を含む。たとえばMCP、特定の認証、マルチリージョン、テスト手法、印刷、AI支援、具体的な指標や閾値が書かれていても、全システムに必須とはしない。「なぜその条件が必要か／代替策で満たすか／どの判断が未決定か」に変換する。

規格・法令、期限・年次、特定技術を採用判断に使う場合は、一次資料・契約・社内基準で版と適用範囲を確認する。カタログへの記載だけで適用を確定しない。クローラー除外を認可の代替としない等、例示が目的を満たすかも検証する。

## 詳細確認項目を読む

`<SKILL_DIR>` はスキルのフォルダ（SKILL.md に示した実パス）。Bashツールから実行し、Windowsでは `python`、ほかは `python3` を使う。パスは二重引用符で囲む。

```text
python -X utf8 "<SKILL_DIR>/scripts/quality_coverage.py" show --ids Q03.01.011 Q06.01 Q05.03.002
python -X utf8 "<SKILL_DIR>/scripts/quality_coverage.py" show --ids @"<review-dir>/quality-read-viewpoints.txt" --ledger "<review-dir>/quality-coverage.json"
```

- `--ids` には観点ID（`Q03.01.011`）か副特性ID（`Q06.01`、配下の全観点）を渡す。確認項目ID（`Q03.01.011.01`）は受け付けない。
- 出力はMarkdownで、指定した観点の確認項目を全件表示し、最後に表示した観点IDの一覧を出す。この一覧を `<review-dir>/quality-read-viewpoints.txt` に追記して、詳細を読んだ観点の記録にする。
- `@ファイル` で、ファイルに書いたIDを渡せる。1行に複数のIDを空白区切りで書いてよく、`#` 以降は注記として無視する。
- `--ledger` を付けると各項目の台帳上の判定を併記する。会話の要約後に、どこまで判定したかを確かめるのに使う。
- 9分野の詳細ファイル（`quality/q01.md`〜`q09.md`）にも同じ内容があるが、大きいので丸ごと読まない。

## 台帳の作成

出力先はレビュー対象の作業領域を指定する。`init` は既存ファイルを上書きしない。

```text
python -X utf8 "<SKILL_DIR>/scripts/quality_coverage.py" init --output "<review-dir>/quality-coverage.json"
python -X utf8 "<SKILL_DIR>/scripts/quality_coverage.py" update --ledger "<review-dir>/quality-coverage.json" --input "<review-dir>/quality-updates-Q04.03.json"
python -X utf8 "<SKILL_DIR>/scripts/quality_coverage.py" validate --ledger "<review-dir>/quality-coverage.json" --read @"<review-dir>/quality-read-viewpoints.txt"
```

`scope`、`baseline`、`target` に実際のレビュー範囲を記入する。基準のない設計なら「新規設計・比較基準なし」など実態を書く。全1,833項目は初期状態 `unreviewed`。最初から合格や対象外にしない。

### 判定を台帳へ記入する

台帳は約340KBあるため、Read で開いたり Edit で直接書き換えたりしない。副特性などの単位で判定を小さなJSONファイルに書き、`update` で反映する。

```json
{
  "scope": "注文取消API と在庫引当の後続処理",
  "baseline": "abc1234（main）",
  "target": "def5678 と未コミット変更（2026-11-01 時点）",
  "updates": [
    {
      "ids": ["Q01.01.008.01", "Q01.01.008.02"],
      "status": "gap",
      "reason": "取消しても在庫の引当が解除されない",
      "expected": "取消の確定時に引当を解除し、再注文で同じ在庫を使える",
      "evidence": ["src/orders.py:42 cancel() 静的確認"],
      "finding_ids": ["F-001"],
      "next_action": "解除の時点を業務担当に確認"
    }
  ]
}
```

- `scope`・`baseline`・`target` は省略できる（台帳の値をそのまま残す）。
- `ids` には確認項目ID（`Q01.01.008.01` の形）を1件ずつ列挙する。観点ID・副特性IDやワイルドカードで配下をまとめて処理しない。
- 1件の更新は、列挙した各IDの記録全体を置き換える。省略した欄は空になる。
- 不明なID・キー、同じファイル内で同じIDの重複、記入後の行が下表の必要な記録を満たさない場合は、何も書き込まずにエラー（終了コード1）を返す。成功時は `validate` と同じ集計を返す。

### 反映する時期

- D5で詳細確認項目を読んだら、項目ごとの判定案をD5の記録に残す。`unknown`・`covered`・`not_applicable`・`out_of_scope` のように指摘IDが要らない判定は、D5の時点で `update` してよい。
- `gap`・`conflict` は指摘ID（`finding_ids`）が必須。P3で候補を統合して指摘IDを決めてから、P4のG10で `update` する。仮の指摘IDを先に書き込まない。
- 指摘IDが統合や反証で変わったら、関係する行を `update` で記録全体ごと書き直す。
- 記録・報告に書く件数は手で数えず、`show` の見出し（観点数・確認項目数）と `validate` の `status_counts`・`by_subcharacteristic`・`read_check` から転記する。`read_check` が一致していれば、`unreviewed` 以外の `status_counts` が詳細を読んだ項目の判定の内訳になる。転記した件数と記録の内容が合わなければ、記録の側を直す。

| status | 意味 | 必要な記録 |
|---|---|---|
| unreviewed | 未分析・未読・後回し | 不足のまま保持。必要なら理由を補記 |
| unknown | 分析したが適用・期待・事実が未確定 | 理由、次の調査・判断。資料不足の範囲 |
| covered | 記録した期待と対象範囲で充足の証拠を確認 | 期待条件、根拠位置、確認方法と範囲 |
| gap | 適用条件に不充足を確認 | 期待、根拠、指摘ID、次の行動 |
| conflict | 適用する条件や根拠が競合 | 競合条件、両方の根拠、指摘ID、次の行動 |
| not_applicable | 案件に適用しないことを確認 | 対象構成等の証拠と対象外理由 |
| out_of_scope | 案件には関係し得るが今回の依頼範囲外 | 範囲指定の根拠、除外理由、残る確認 |

`reason` は結論の理由、`expected` は期待条件または受入条件、`evidence` は参照位置の配列、`finding_ids` は報告の指摘への対応、`next_action` は次の調査・判断・是正を記載する。

「covered」は確認範囲付きの判定。設計の充足を確認しても実装済み・試験済みとは書かない。複数の対象に展開した項目のうち一つでも未分析・未確認が残るなら、元ID全体をcoveredにしない。既知のgapと未確認が同居する場合はgapとして未確認範囲と次の調査も記載する。

同じ根拠で複数項目を処理する場合は、対象ID集合と共通する前提を明示して各行へ展開してよい。ただし一つの観点に証拠があるだけで、その配下の確認項目すべてを処理済みにしない。たとえば画面のないAPIでも相互運用性・API利用者支援・エラー表現・自動化経由の利用は検討対象になり得る。

JSONを利用できない環境では同じIDと状態をMarkdown等で管理してよい。その場合も全項目との突合、未記載の発見を行い、機械検証済みとは言わない。要約報告は40副特性単位で集計できるが、判断の根拠となる詳細台帳を残す。

## 検証の意味

検証スクリプトは全IDとの一致、重複、未分析、根拠や次行動の未記入、カタログの版の不一致を検査する。根拠の実在性や意味の十分性は別に読む。実装、モデル、規格適合、潜在要求の完全性は判定しない。

`validate` の終了コード0は台帳構造が妥当という意味で、未知項目や不充足があっても0になる。`--require-complete` を付けた場合は、未分析・未確認・今回範囲外が残ると終了コード2になる。構造エラーは1。

`--read` に詳細を読んだ観点・副特性のIDを渡すと、結果に `read_check` が加わる。`unreviewed_in_read` は読んだ観点の配下で未判定のまま残った項目、`reviewed_outside_read` は詳細を読んだ記録のない観点で判定した項目。どちらかがあれば終了コード3（構造エラーの1を優先し、2より優先）。3になったら、未判定の項目を判定するか、読んだ記録を補うか、根拠なく判定した行を見直す。`read_check` が一致しても、判定の内容が正しいことは示さない。不充足・矛盾は処理状況が確定していても未解決の指摘として別に出る。どの終了コードも製品の合格やリリース承認ではない。

**全カタログの処理状況と、今回範囲内の品質判断を別に報告する。** 未確認を減らすために根拠のない対象外を付けない。項目が重複する分野は指摘を統合してよいが、対応するIDは残す。

## 同梱カタログの整合確認

```text
python -X utf8 "<SKILL_DIR>/scripts/quality_coverage.py" check-catalog
```

`check-catalog` は同梱JSONの版・階層・ID・内容のハッシュを検査し、さらに同梱Markdown（`index.md`・`viewpoints.md`・`q01.md`〜`q09.md`）がJSONから生成される内容と1バイトも違わないことを確かめる（結果の `markdown_checked`）。外部ファイルとの照合は不要で、スキルのフォルダだけで整合を確かめられる。Markdownが食い違うと終了コード1になる。Markdownを手で直さず、カタログの保守として `render` で生成し直す。スクリプトは自身の配置場所からカタログを読むため、レビュー対象の作業フォルダーから絶対パスで起動しても使える。`catalog.json`（約420KB）は Read で開かず、項目の内容は `show` で読む。Pythonが利用できない場合は同梱Markdown（`q01.md`〜`q09.md` の該当観点の節を Grep で探し、Read の offset・limit で読む）を使って同じ工程を実行し、読んだ観点と判定の突合は手作業で行う。機械検証済みとは言わない。

カタログの版や内容が変わったときは、同じIDでも内容・適用前提を確認して旧台帳を移行する。カタログの追加・変更はスキルの保守作業であり、案件レビュー中に判定を通すために削除・改変しない。
