# 要求・要件・仕様の考慮漏れ分析

利用者の依頼：$ARGUMENTS

（空のときは、会話の内容から対象・比較基準・資料・出力先を読み取る。）

実装が選んでいる振る舞いと前提を取り出し、仕様・要件・要求の妥当性を業務目的から検証する。コードの不具合に加えて、仕様どおりに動いても業務が成立しない条件、未定義の例外、関係者・運用への負担を発見する。修正が必要な層と判断の根拠を特定し、変更後に確かめる受入条件までつなぐ。

## 実行に必要なもの

このスキル一式と、レビュー対象のコード・差分・設計・要求・業務資料のうち利用できるものを使う。分析手順と品質カタログはすべて同梱している。特定の資料名、固定の作業フォルダー、作成者の環境を前提にしない。

対象資料が不足していても、存在する資料から開始する。比較基準や重要な業務判断を変える不明点だけを確認し、それ以外の分析を進める。コードがなければ設計レビュー、変更前がなければ現状の整合性レビューとして範囲を明示する。

## Claude Code での実行

### スキルのフォルダとスクリプト

- このスキルのフォルダは `${CLAUDE_SKILL_DIR}`（このSKILL.mdがあるフォルダ）。参照資料の中の `<SKILL_DIR>` はこのパスに読み替える。参照資料どうしのリンクは、このフォルダからの相対パス。
- スクリプトはPython 3の標準ライブラリだけで動く。Bashツール（WindowsではGit Bash）から、Windowsでは `python`、ほかは `python3` で実行し、日本語を正しく入出力するため `-X utf8` を付ける。スキルや対象のパスには日本語・空白が入り得るので、パスは二重引用符で囲む。Pythonがなければ、各参照資料の「Pythonが利用できない場合」の手順で同じ工程を行う。

```text
# 同梱カタログの整合確認（JSONのハッシュと、同梱Markdownとの一致）
python -X utf8 "${CLAUDE_SKILL_DIR}/scripts/quality_coverage.py" check-catalog
# 関連あり・不明と選んだ観点（または副特性）の詳細確認項目を読む（P2のD5）
python -X utf8 "${CLAUDE_SKILL_DIR}/scripts/quality_coverage.py" show --ids Q03.01.011 Q06.01
# 品質台帳の作成（P2のD5）
python -X utf8 "${CLAUDE_SKILL_DIR}/scripts/quality_coverage.py" init --output "<出力先>/quality-coverage.json"
# 判定の反映（指摘IDの要らない判定はD5、gap・conflictはP3で指摘IDを決めた後のP4）
python -X utf8 "${CLAUDE_SKILL_DIR}/scripts/quality_coverage.py" update --ledger "<出力先>/quality-coverage.json" --input "<出力先>/quality-updates-<副特性ID>.json"
# 台帳の検査と、詳細を読んだ観点との突合（P4のG10）
python -X utf8 "${CLAUDE_SKILL_DIR}/scripts/quality_coverage.py" validate --ledger "<出力先>/quality-coverage.json" --read @"<出力先>/quality-read-viewpoints.txt"
# HTMLの指摘表の生成（P6）
python -X utf8 "${CLAUDE_SKILL_DIR}/scripts/render_findings.py" --input "<出力先>/review-findings.json" --output "<出力先>/requirements-gap-review.html"
```

各コマンドの意味と入力形式は [品質台帳](references/coverage-workflow.md) と [HTML出力手順](references/html-output.md) にある。どの終了コードも、構造の検査結果であり、指摘の正しさやリリース可否を示さない。

### 大きなファイルの読み方

- Read は1回に約25,000トークンまでしか返さず、超えると途中で打ち切って続きの offset を示す。打ち切られたら、示された offset から続きを読み、最後の行まで読み終えてから次へ進む。途中までの内容で判断しない。
- `references/quality/catalog.json`（約420KB）と、`init` で作る品質台帳（約340KB）は Read で開かない。台帳への記入は `update`、状況の確認は `validate` の集計（`by_subcharacteristic`）と `show --ledger` を使う。
- `references/quality/viewpoints.md`（605観点の一次選別一覧、約811行）は全体を読む。1回では打ち切られるので、2回以上に分けて最後の `Q09.05.009` まで読む。
- 詳細確認項目は、一次選別で関連あり・不明とした観点（または副特性）のIDを `show --ids` に渡して読む。`q01.md`〜`q09.md` を丸ごと読まない。表示の最後に出る観点IDを、作業フォルダの `quality-read-viewpoints.txt` に追記していく（1行に複数ID可、`#` 以降は注記）。読んでいない観点の確認項目は台帳で `unreviewed` のまま残す。

### 品質台帳へ反映する時期

- D5では、詳細確認項目ごとの判定案をD5の記録に残す。`unknown`・`covered`・`not_applicable`・`out_of_scope` のように指摘IDが要らない判定は、この時点で `update` してよい。
- `gap`・`conflict` には指摘ID（`finding_ids`）が必要なため、P3で候補を統合し指摘IDを決めてから、P4のG10で `update` する。指摘IDを仮に作って先に書き込まない。
- G10では `validate --read` で、詳細を読んだ観点の配下に未判定（`unreviewed`）が残っていないこと、読んでいない観点の項目を判定していないことを確かめる（不一致なら終了コード3）。
- 記録・報告に書く件数（読んだ観点数・確認項目数、判定ごとの項目数、副特性ごとの集計）は手で数えない。`show` の見出しの件数と、`validate` の `status_counts`・`by_subcharacteristic`・`read_check` から転記する。転記した件数と記録の内容が合わなければ、記録の側を直す。

### ツールの使い方

- コードと資料の探索は Grep・Glob・Read を使う。Git は Bash で読み取りのコマンドだけを使い（[コード・差分分析](references/change-analysis.md)）、reset・stash・checkout など利用者の作業状態を変える操作はしない。
- 依頼から開始できないほど対象・比較基準が不明なときだけ、AskUserQuestion で最小限を聞く。業務ルール・品質水準など判断が必要な不明点で分析を止めず、P5のエスカレーション票に回して、確定できる範囲を進める。
- 出力先は最初に決める。利用者の指定を優先し、なければレビュー対象の作業領域（リポジトリのルートなど）とする。既存の `requirements-gap-review.html` が別のレビューのものなら上書きせず、対象名を付けたファイル名にする。

### 長い分析を途切れさせない

このレビューは長く、途中で会話が要約（コンパクション）されることがある。記憶だけに頼らず、ファイルを正とする。

1. 出力先に作業用のフォルダ（例：`requirements-gap-review-work/`）を作る。情報源台帳、系統ごとの記録（D1〜D6は別ファイル）、統合要求台帳、L1〜L3・G01〜G10の結果、エスカレーション票、品質台帳と `quality-read-viewpoints.txt`、`review-findings.json` を、工程を終えるたびに書き出してから次の工程へ進む。
2. 進捗ファイル（例：`progress.md`）に、対象と比較基準の版、終えた工程、次にやること、未確認の一覧を書き、工程ごとに更新する。
3. 会話が要約された後、または利用者が「続き」「再開」と言ったときは、進捗ファイルと成果物を読み直してから続ける。このSKILL.mdの「判断原則」と、次の工程の参照資料も読み直す（要約で規則の細部が失われるため）。
4. 対象のコードの版が記録と変わっていたら、変わったファイルを確かめ、影響を受ける分析をやり直す。古い評価を新しい版へそのまま引き継がない。

### 6系統の分担（サブエージェント）

6系統は、参照材料と分析モデルを分けて実施する。既定では一人で順に実行し、系統ごとの記録を別のファイルに残す。先に終えた系統の結論を、後の系統の前提にしない。

利用者がサブエージェントによる分担・並列実行を求めた、または許可している場合は、Agent ツールで系統ごとに起動してよい。

- サブエージェントは会話の文脈もこのスキルも引き継がない。P1の共通事実のファイル、担当系統の重点入力（[実行プロセス](references/process.md) のP2の表）、読む参照資料の絶対パス（`${CLAUDE_SKILL_DIR}/references/...`）、出力ファイルのパス、候補の記録形式（同P2「各系統の候補の記録」）、「判断原則」をプロンプトで渡す。
- 独立性を保つため、他の系統の候補は渡さない。返答は要約にとどめさせ、候補と根拠はファイルに書かせる。
- P3の統合とP4の検証は独立した工程として必ず行う。サブエージェントの「確認済み」を検証済みとして扱わない。P4を別のサブエージェントに任せる場合は、候補を出していないエージェントにする。

## 工程

まず [実行プロセス](references/process.md) と [実装からの逆向きレビュー](references/reverse-review.md) を読み、以下の工程を実行する。主経路は実装後のレビューとする。工程の入力・成果物・検証結果を追跡し、手法名や観点名を列挙しただけで完了しない。

```text
P1 対象実装の版を特定・実行経路と実装上の仕様を再構成・情報源探索
  ↓ 共通の事実と、系統ごとに異なる調査材料
P2 実装の前提を問い直す6系統の要求発見
   業務・目的／状態・条件／データ・連携
   異常・脅威／品質特性／変更影響
  ↓ 各系統の要求候補・根拠・モデル・未確認
P3 候補の統合・根拠関連付け・実装から要求までの逆向き対応
  ↓ 統合要求台帳・修正すべき層・矛盾・未確認
P4 検証工程
   根拠／範囲／条件／遷移／整合性／追跡性
   受入条件／変更影響／セキュリティ／品質特性
  ├─ 発見・導出・根拠の不足 → 該当するP1〜P3へ戻る
  ↓
P5 エスカレーション・修正方針・修正後の影響再検証
  ↓ 未回答は未確認として保持
P6 HTML指摘表と、確定要求・未確認要求・矛盾・未分析領域・検証証跡
  ↓ 後から判明した漏れ・誤検出
P7 検出能力の評価と改善
```

## 判断原則

- 組織の用語を優先する。区別がなければ、要求＝誰が何をなぜ達成したいか、要件＝満たすべき振る舞い・制約・品質条件、仕様＝実現・検証可能な具体ルールとする。
- 書かれていないことを不要とも必須とも即断しない。利用実態・目的・制約・損失シナリオから必要性を調べる。
- 既存コード・テストの動作は現状の証拠。正しい要求や維持義務とは限らない。承認済みの変更、過去の不具合、利用側の依存と照合する。
- コード・設計・テストが一致していても、期待そのものが不足していないか調べる。同じ生成過程や同じ仮定に由来する成果物の一致を、業務上の妥当性の独立した裏付けに数えない。
- 性能値、保存期間、承認者、契約義務を創作しない。カタログの技術例を一律に要件化しない。
- 要求の由来、採否、充足状態を分ける。推定のまま正式要求にせず、実装済みでも必要性が未確認ならその状態を残す。
- 対象が試作・検証用など本番と位置付けが違うときは、資料からその範囲を確かめる。範囲の中の業務条件（試作で成り立たせると決めた目的・制約）の不足は通常どおり指摘する。範囲の外にある本番向けの条件（本人確認・監査・性能・運用など）が無いことは、試作の不充足とはしない。本番化で必要になる条件として区分を「要判断」にし、いつ・誰が要件に加えるかを判断事項にする。範囲の記載が無ければ、範囲そのものを確認事項にする。
- 全指摘に **根拠・確度（0〜100%の整数と理由）・推奨する修正** を必須とする。具体的な条件・操作列・影響と、変更する層を記す。確度は指摘の妥当性への証拠に基づく評価であり、発生確率・重大度・網羅率とは別である。
- 未分析、未確認、対象外、今回範囲外を区別する。有限モデル・登録項目の処理率を潜在要求全体の網羅率とは呼ばない。

スキルの手順・カタログ・スクリプトはこのフォルダの中だけで完結し、外部の資料を読まなくても実行できる。

同梱カタログは9品質特性・40副特性・605観点・1,833確認項目を持つ。全分野を見渡し、未確認を残したうえで、影響のある領域を深く調べる。カタログの点検はP2の一系統であり、業務や既存コードからの要求発見、候補統合、P4の意味的な検証を省略しない。

## 成果物と完了判断

小規模なら一つのレビュー文書に統合し、大規模なら台帳やモデルを分ける。少なくとも次の情報をつなぐ。

1. 情報源台帳と比較範囲、現状・変更・維持条件。
2. 6系統の実施記録、統合前の候補と未確認。
3. 候補から統合要求への対応、実装→仕様→要件→要求・業務目的の対応と、その逆向きの充足確認。
4. 10検証項目の結果と証拠、品質観点の処理状況、反例・未検証範囲。
5. **HTMLの表による指摘一覧**、エスカレーション票、残余リスク、修正・再レビュー条件。

指摘一覧は出力先に `requirements-gap-review.html` として保存する。各行に「根拠」「確度（%）」「推奨する修正」を表示する。**根拠以外は1列1項目**とし、ID・指摘・区分、重大度・影響、確度・理由、検証条件・次の行動などを同じ列にまとめない。Markdown表・JSON・文章だけで代替しない。分析台帳は別ファイルにできる。指摘ゼロでも同じ列を持つ表と未確認範囲を出す。

**情報源は十分か／必要条件を導出したか／仕様・検証へ反映したか**の3層をそれぞれ判定する。資料不足や未回答があっても結果は提出し、未確認を解決済みにしない。分析が完了したことと、設計・実装・リリースが承認されたことを区別する。

最終応答では、HTMLの絶対パス、重要な指摘と判断事項、未確認・未分析の範囲を短く示す。HTMLの内容を応答に貼り直さない。

判断資料の作成を越える外部送信・チケット登録・正式要件への採用・製品コードの修正は、分析依頼だけから実行しない。別途許可されている作業はその範囲で続ける。

## 依頼例

- `/requirements-gap-review 実装結果から仕様・要件・要求を見直し、業務上の考慮漏れと修正案をHTMLの指摘表にして`
- `/requirements-gap-review 基準コミット abc1234 からの変更と未変更の影響先を調べ、暗黙の品質条件まで分析して`
- 「要求書がない機能の改善案を、既存の業務・コード・運用から分析して。考慮漏れがないか見てほしい」
- 「AIに実装させた予約機能、仕様どおりだけど業務で困るところがないかリリース前に確認して」
