# FlowTS Skill Designer

## 目的

スキルの手順を FlowTS で書き、図にして、手順の流れと抜けを目で確かめられるようにする。

自然文の SKILL.md は、どこで分かれるのか、失敗したらどこへ行くのか、誰（AI・ツール・人）がやるのかがあいまいになりやすい。
FlowTS で書くと、ステップごとの行き先・条件・担当・結果の型を書かざるをえないので、あいまいな所がそのまま見つかる。
さらにスクリプトの検査が、行き先の無い goto、上限の無い繰り返し、終わりにたどり着けないステップなどを機械的に出す。

順序は必ず「flow.ts を書く → 検査する → 図にする」。図は flow.ts からスクリプトが作り、AI は HTML を書かない。
作成・改善では、正は SKILL.md（Claude が実際に読んで動くのは SKILL.md）で、flow.ts は設計図としてスキルの中に残す。

## モード

| 依頼 | モード |
|---|---|
| 既存スキルを図にしたい、流れを見たい、FlowTS で表してほしい | 可視化 |
| 新しいスキルを作りたい、設計したい | 作成 |
| 既存スキルを直したい、抜けを見つけたい、手順をレビューしたい | 改善 |

どれか分からないときは、依頼の言葉で決める（「見たい」「表して」は可視化、「直したい」「良くしたい」は改善）。それでも決まらないときだけ利用者に聞く。

## 保存先

| モード | flow.ts と HTML の置き場所 |
|---|---|
| 可視化 | 作業フォルダーの `.skill-flow/<スキル名>/<スキル名>.flow.ts` と `<スキル名>.flow.html`。スキル本体には何も足さない |
| 作成・改善 | `<スキルのフォルダー>/flow/<スキル名>.flow.ts` と `<スキル名>.flow.html`。改善前の版は `<スキルのフォルダー>/flow/history/<YYYYMMDD-HHMM>.flow.ts` |

同期・配布されたスキル（`~/.claude/skills/synced/` の下、プラグインのスキルなど）は直接書き換えない。
改善するときは、作業フォルダーの `.skill-flow/<スキル名>/skill/` に写してから写しを直し、そのことを利用者に伝える。

HTML はローカルのファイルとして保存し、パスを伝える。claude.ai の Artifact には公開しない。

## スクリプト

```bash
node <このスキルのフォルダー>/scripts/flow-view.mjs <file.flow.ts> --title "<スキル名>" [--out <file.html>] [--before <改善前.flow.ts>] [--typescript <TypeScript の場所>] [--no-tsc] [--no-html]
```

- 出力の `Findings` にエラーと注意が出る。エラーが1件でもあると終了コード1（HTML は書き出す）。
- 検査は、FlowTS 仕様 10 章のうち構文から確かめられるもの（goto の行き先・ラベルの重複・禁止された位置からの goto・宣言の飛び越え・goto の引数の数・ラベルの引数の書き方と名前・引数のあるラベルへの流れ込み・`実施` の型引数と担当・能力・`async`・戻り値）と、手順の抜けの注意（たどり着かないステップ、終わりにたどり着けないステップ、上限の見当たらない繰り返し、初期値の無い変数）。
- 型検査は、goto を TypeScript の制御構造に置き換えてから `tsc --strict` で行う（行番号は flow.ts と同じ）。goto で渡す値の型も、引数の式の位置で確かめる。TypeScript は flow.ts のフォルダー・作業フォルダー・グローバルから探す。見つからなければ型検査を省き、出力の `Type check` にその理由が出る。TypeScript のインストールは利用者の了承なしに行わない。
- `--before` を付けると、改善前と比べて、追加・変更したステップを図で色分けし、変更の表を足す。
- `--title` にはスキル名を渡す（HTML にローカルのパスを出さないため）。
- 図は、関数本体の直下のラベル付きブロックと、ラベルの外の文のまとまりを1つの箱にする。箱の中に作業（担当の印付き）・条件・行き先を字下げして並べる。

## 手順：可視化

1. 対象のスキルのフォルダーを確かめ、SKILL.md を全部読む。手順が `references/` にあれば読む。スクリプトは全部を読まず、引数と出力の行だけを確かめる。
2. [スキルを flow.ts に表す書き方](references/skill-to-flow.md) を読む。構文に迷ったら [FlowTS 仕様書](references/flowts-spec.md) を読む。
3. flow.ts を書く。スキルに無い手順や決まりは足さない。足してよいのは、型と前提の確認（`null` の確認）だけにする。
   繰り返しの上限や、失敗したときの行き先がスキルに無くても、足さずにそのまま写す。足すと、図と検査からスキルの抜けが消えてしまうためである。
   写すときに自分で決めたこと（条件の境目など）には「スキルに記載なし」とコメントする。
4. `flow-view.mjs` を実行する。エラーは写し方の誤りなので、flow.ts を直して再実行する（エラー0件まで）。
   注意は、写し方の誤りなら直し、スキルそのものの抜け（上限の無い繰り返しなど）ならそのまま残して報告する。
5. 写し漏れを確かめる（書き方の手引きの4章）。SKILL.md の手順・禁止事項・完了条件を1つずつ、flow.ts のどこに表したかを対応させる。
6. 報告する。

## 手順：作成

1. 作りたいスキルについて、次をはっきりさせる。会話の中に答えがあればそれを使い、足りないことだけを1〜3問ずつ聞く。
   - 何をするスキルか。いつ使うか（利用者が言いそうな言い方）。
   - 入力（依頼文・ファイル・オプション）と、最後に返すもの（成果物・報告の項目）。
   - 各段階を誰がやるか（AI の判断・スクリプトやツール・人の確認）。
   - 失敗したとき・決められないときにどうするか。人に確かめる所はどこか。
2. `assets/template.flow.ts` を元に flow.ts を書く。決まっていないことは、該当する所に「未決定：…」とコメントする。
3. `flow-view.mjs` で検査し、エラーを0件にしてから図を作る。注意（上限の無い繰り返しなど）は設計の穴なので、直すか、直さない理由を利用者と決める。
4. 図のパスを伝え、主な流れ・分岐・人の確認・繰り返しを数行で説明して、直したい所を聞く。直したい所があれば flow.ts を直して図を作り直す（合意するまで繰り返す）。
   利用者が「確認なしで最後まで進めてよい」と言っている場合は、ここで止めずに先へ進め、報告で図を見るよう伝える。
5. [flow.ts から SKILL.md を書き起こす書き方](references/flow-to-skill.md) に従い、SKILL.md を書く。tool の作業のうち決まった処理は `scripts/` のスクリプトにする。
6. flow.ts と SKILL.md を照合し（書き起こしの手引きの2章）、食い違いを直す。
7. flow.ts と HTML を `<スキルのフォルダー>/flow/` に置く。
8. 報告する。テストや説明文の調整をする場合は skill-creator を使えることを伝える。

## 手順：改善

1. 対象のスキルのフォルダーを確かめる。同期・配布されたスキルなら、作業フォルダーへ写して写しを直す。
2. `<スキルのフォルダー>/flow/<スキル名>.flow.ts` があれば読み、今の SKILL.md と食い違っていないかを確かめる（SKILL.md の方が新しいことがある）。食い違っていれば、今の SKILL.md に合わせて直す。
   無ければ、可視化の手順1〜5で今の flow.ts を書く。
3. 今の flow.ts を `flow/history/<YYYYMMDD-HHMM>.flow.ts` に写す。
4. 今の flow.ts の図を作り、検査の結果と次の観点で、改善点を挙げる。各改善点には、場所（ステップ）・何が起きうるか・直し方を書く。
5. 改善した flow.ts を書き、`--before flow/history/<…>.flow.ts` を付けて図を作る。検査のエラーは0件にする。
6. 図のパスと改善点の一覧を示し、どれを採るかを利用者と決める（「全部直してよい」と言われていれば、そのまま進める）。
7. 採った改善を SKILL.md（必要ならスクリプト・references）に入れる。直すのは改善に要る所だけにし、`name` は変えない。
8. flow.ts と SKILL.md を照合し、最終の図を作り直す。
9. 報告する。

### 改善の観点

| 観点 | 確かめること |
|---|---|
| 終わり方 | すべてのステップに行き先か終わりがあるか。失敗したとき（コマンドの失敗・検査の不合格）の行き先があるか |
| 繰り返し | 戻る経路に上限と、上限に達したときの終わり方があるか |
| 判断 | 条件が自然文の判断のままになっていないか（型の決まった結果を得てから分けているか）。判断の基準が書かれているか |
| 担当 | コマンドの結果・ファイルの中身・人の回答を、AI が作れる書き方になっていないか |
| 確認 | 取り消せない操作・外への送信・利用者の物を書き換える前に、人の確認があるか |
| 入力と出力 | 各作業の結果の形が決まっているか。最後に返す報告の項目が決まっているか |
| 検証 | 作ったものを確かめるステップがあるか。確かめ方が機械的にできる所はスクリプトになっているか |
| 再開 | 長い作業で、途中の結果をファイルに残して続きから再開できるか |
| 無駄 | 同じことを二度していないか。使われないステップ・決まりは無いか |
| 粒度 | 1つの作業に複数の目的を詰めていないか。1つのステップが大きすぎないか |

## 報告

最後に次を伝える。

- HTML のパスと flow.ts のパス（作成・改善では SKILL.md のパスも）。
- フロー関数とステップの数、作業の数（AI・ツール・人・サブフロー）。
- 検査の結果：エラーの件数（0件のはず）と、残した注意とその意味。型検査をしたか（していなければ理由）。
- 可視化：flow.ts に写すときに自分で決めたこと（スキルの書き方があいまいだった所）と、見つかった抜け。
- 作成：書いた SKILL.md の要点と、照合で直した食い違い。
- 改善：採った改善と採らなかった改善、変更の数（`Diff` の行）。

## 禁止事項

- HTML を手で書いたり直したりしない。直すのは flow.ts で、図は `flow-view.mjs` で作り直す。見た目を変えたいときはスクリプトを直す。
- flow.ts を書かずに図や SKILL.md を作らない（順序は flow.ts → 検査 → 図）。
- 可視化で、スキルに無い手順を注記なしに flow.ts へ足さない。図がスキルの実際と違ってしまう。
- 検査のエラーを残したまま完了にしない。
- 改善で、利用者と決めていない変更を SKILL.md に入れない。
- 同期・配布されたスキルを直接書き換えない。
- HTML を claude.ai の Artifact に公開しない。
- TypeScript が無くても、利用者の了承なしにインストールしない。

## 完了条件

- flow.ts があり、`flow-view.mjs` がエラー0件で終わり、HTML が書き出されている。
- 可視化：SKILL.md の手順・禁止事項・完了条件が、flow.ts のどこかに表されている（表せないものはコメントに残している）。
- 作成：SKILL.md があり、flow.ts と照合して食い違いが無い。flow.ts と HTML が `<スキルのフォルダー>/flow/` にある。
- 改善：改善前の flow.ts が `flow/history/` にあり、`--before` 付きの図がある。採った改善が SKILL.md に入り、flow.ts と照合して食い違いが無い。
- 報告の項目を伝えている。
