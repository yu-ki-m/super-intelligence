# flow.ts から SKILL.md を書き起こす書き方と、照合のしかた

作成・改善で、図で合意した flow.ts を SKILL.md に書き起こすときに読む。
Claude が実際に読んで動くのは SKILL.md なので、正は SKILL.md にする。flow.ts は設計図として `<スキル>/flow/` に残す。

## 1. 書き起こしの対応

| flow.ts | SKILL.md |
|---|---|
| 入口の関数の目的、モードの分かれ方 | frontmatter の `description`（何をするか＋いつ使うか）と、本文の「目的」「モード」 |
| 引数の型 | 「入力」：受け取る依頼文・オプション・前提 |
| フロー関数ごとのステップの並び | 「手順」：モードごとの番号付きの手順。ステップ1つが手順1つ（大きければ小見出し） |
| ブロックの末尾から次へ進む | 番号の順に進む（書かなくてよい） |
| `goto` で飛ぶ・戻る | 「〜なら手順 N へ戻る」「〜なら手順 N へ進む」と番号で書く |
| `goto ステップ名(値)` と、引数付きのステップ | 「〜なら、〜（値）を持って手順 N へ進む」。手順 N の冒頭に「この手順は〜を受け取る」と、受け取るものを書く |
| 戻る `goto` と回数の上限 | 「〜まで繰り返す。N 回やっても〜なら、〜して止める」 |
| `if` / `switch` の条件 | 「〜なら〜する」。判断の基準（何を見て決めるか）を具体的に書く |
| `実施`（model） | 「〜を決める」「〜を書く」。判断の基準と、守ること（作らない・推測しない）も書く |
| `実施`（tool, shell.exec） | 実行するコマンドをそのまま書く（コードブロック）。確かめる終了コードと出力の行も書く |
| `実施`（tool, file.read / file.write） | 読む・書くファイルのパスと、読む範囲 |
| `実施`（human） | 「ユーザーに確認する」。何を、どの選択肢で聞くか。答えが得られるまで先へ進まないこと |
| `Promise.all` | 「〜を並行して行う」（サブエージェントで並べる場合はそう書く） |
| 戻り値の型 | 「報告」：最後に利用者へ伝える項目 |
| 禁止事項などの定数 | 「禁止事項」「書き方」。それぞれに理由を添える |
| 完了の確かめ（`if` と `実施<判定>`） | 「完了条件」 |
| 「スキルに記載なし」のコメント | 書き起こすときに、スキルの決まりとして入れるかを利用者と決める |

書き方は、利用者の既存のスキル（`~/.claude/skills/*/SKILL.md`）に合わせる。
常体で、何を・どこで・どうするかを具体的に書き、「適切に」のようなあいまいな言葉を使わない。
決まりには、なぜそうするのかを一言添える（理由が分かると、手順に無い場面でも正しく判断できる）。

`description` は、何をするかと、いつ使うか（利用者が言いそうな言い方）を書き、使わない場面も書く。
スキル名を言われなくても使われるよう、言い方を多めに挙げる。

SKILL.md は500行以内を目安にし、長い決まりや例は `references/` に分けて、どの手順で読むかを本文に書く。
決まった処理（ファイルの列挙・変換・検査など）は、手順に書くより `scripts/` のスクリプトにする。flow.ts では tool の作業になっているはずである。

## 2. 照合のしかた

書き起こした後に、flow.ts と SKILL.md が食い違っていないかを2つの向きで確かめる。

1. flow.ts → SKILL.md：ステップ・`goto`・`実施`・定数を1つずつ見て、SKILL.md のどこに書いたかを対応させる。
2. SKILL.md → flow.ts：SKILL.md の手順・決まりを1つずつ見て、flow.ts のどこにあるかを対応させる。

対応の付かないものが見つかったら、どちらが正しいかを決めて、もう一方を直す。
図で利用者と合意した内容は flow.ts にあるので、迷ったら flow.ts に合わせる。
照合の結果（対応の付かなかったものと、どう直したか）は報告で伝える。

## 3. その後の保守

SKILL.md を直したら、flow.ts も直して `flow-view.mjs` で図を作り直す。
直す前の flow.ts は `<スキル>/flow/history/` に残し、`--before` で差を図と表に出す。
