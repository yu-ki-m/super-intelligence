# スキルを flow.ts に表す書き方

既存のスキルを可視化するとき、新しいスキルを設計するとき、どちらもこの書き方で flow.ts を書く。
構文と意味は [FlowTS 仕様書](flowts-spec.md) に従う。迷ったら仕様書を読む。
書き上がりの例は [example-codebase-guide.flow.ts](example-codebase-guide.flow.ts)、白紙から書くときの雛形は `assets/template.flow.ts`。

## 目次

1. ファイルの組み立て
2. スキルの書き方と FlowTS の対応
3. 書くときの決まり
4. 既存スキルを写すときの手順と、写し漏れの確かめ方
5. よくある検査のエラーと直し方

## 1. ファイルの組み立て

上から次の順に書く。

1. 先頭のコメント：どのスキルを表したか、正は SKILL.md であること、使う能力の一覧と意味。
2. 引数と結果の型：スキルの入口が受け取るもの（依頼文・オプション）と、最後に利用者へ返すもの（報告の項目）。
3. 作業の間で受け渡す型：コマンドの結果、AI の判断の結果、人の回答など。
4. 作業に渡す決まり：禁止事項・書き方・完了条件などを `const` の配列にする。
5. 補助関数：ラベルを持たない通常の関数（コマンドの組み立て、`実施` を1つ包むだけの関数など）。
6. 入口のフロー関数（`export async function`）と、モードごとのフロー関数。

フロー関数の本体は「共有する変数の宣言 → ステップ（ラベル付きブロック）の並び」にする。
ステップの名前は、その段階でやることを表す短い名詞句にする（例：「依頼の解釈」「下準備」「件数の確認」）。
図ではステップが1つの箱になるので、1つのステップに1つの段階だけを入れる。
1つのフロー関数のステップは15個程度までにし、それを超えるならモードや段階ごとにフロー関数を分ける。

## 2. スキルの書き方と FlowTS の対応

| スキルの書き方 | FlowTS での表し方 |
|---|---|
| 手順の段階（見出し・番号付きの手順） | 関数本体の直下のラベル付きブロック（ステップ） |
| 次の段階へ進む | 何も書かない（ブロックの末尾から次の文へ進む） |
| 戻る・やり直す・別の段階へ飛ぶ | `goto ステップ名;` |
| 値を持って別の段階へ飛ぶ（失敗の理由を持ってやり直しへ、など） | 行き先を `ステップ名(引数: 型): { … }` にし、`goto ステップ名(値);` で渡す |
| 「〜まで繰り返す」 | 後ろ向きの `goto` と、回数の変数・上限の比較 |
| モード・場合分け | `if` / `switch`。自然文の判断が要るなら、先に `実施` で型の決まった結果を得てから分ける |
| スクリプト・コマンドの実行 | `担当: "tool", 能力: "shell.exec"`（補助関数 `コマンド実行` に包む） |
| ファイルを読む・語を探す | `担当: "tool", 能力: "file.read"` |
| ファイルを書く・直す | `担当: "tool", 能力: "file.write"` |
| 利用者に確かめる・承認を得る | `担当: "human", 能力: "user.ask"`（承認なら `"approval.request"`） |
| 解釈する・判断する・文章を書く | `担当` を省く（model） |
| コードを読みながら原因を考える | `担当: "model", 能力: "file.read"` |
| 並行して行う | `Promise.all(一覧.map(x => 実施<T>(…)))` |
| サブエージェントに任せる | `担当: "tool", 能力: "agent.run"`（結果の型を決める） |
| 出力の形・報告の項目 | 入口の関数の戻り値の型 |
| 禁止事項・守ること | `const 禁止事項 = [...]` にして、関係する `実施` の入力に渡す |
| 完了条件 | 機械的に確かめられるもの（終了コード・件数・ファイルの有無）は `if` で、判断が要るものは `実施<判定>` で確かめる |
| 参照する手引き（references） | 読む作業（`file.read`）にし、読んだ内容を後の `実施` の入力に渡す |

能力の名前は、上の表のものを使う。ほかに要るときは `領域.動作`（例：`browser.open`、`slack.post`）の形で決め、先頭のコメントの一覧に足す。

## 3. 書くときの決まり

- **条件は、実行時に決まっている値で書く。**
  「問題がありそうなら」のような自然文の判断は、`実施<{ 問題あり: boolean; 理由: string }>` で結果を得てから `if` で分ける。
  こうしておくと、どこで AI が判断しているかが図に出る。
- **観測と承認を AI に作らせない。**
  コマンドの結果やファイルの中身は tool、利用者の回答は human の作業にする。
  AI の作業の指示に「実行した結果を返す」のような書き方をしない。
- **繰り返しの上限は、モードで扱いを分ける。**
  検査は、後ろ向きの `goto` で戻る経路に、回数を数えて上限と比べる変数が無いと「注意」を出す。
  作成・改善では、回数の変数と上限の比較を置き、上限に達したときの終わり方も書く。上限の値はスキルの引数か定数にする。
  可視化では、スキルに上限が書かれていなければ足さない。注意をそのまま残し、スキルの抜けとして報告する（足すと抜けが図から消える）。
- **スキルに無いことを足したら、コメントに「スキルに記載なし」と書く。**
  可視化では、スキルに無い手順を足さない。足すのは、型と前提の確認（`null` の確認）だけにする。
- **共有する変数は、最初のステップより前で宣言し、初期値を入れる。**
  後で決まる値は `T | null = null` で始め、使うステップの先頭で `if (x === null) throw new Error("…");` と確かめる。
  これは型を絞るための前提の確認で、図では条件として扱わない。
- **行き先でしか使わない値は、goto の引数で渡す。**
  「失敗した理由」のように、どこから来たかで中身が変わり、行き先のステップでしか使わない値は、共有の変数にしない。
  行き先を `失敗の対処(問題: string[]): { … }` のように引数付きのステップにし、`goto 失敗の対処(結果.問題);` で渡す。
  どの経路で何を渡すかが図の行き先に出て、渡す値の型も型検査で確かめられる。
  複数のステップで使う値や、繰り返しの間で持ち越す値（回数など）は、これまでどおり共有の変数にする。
- **引数のあるステップには、goto でだけ入る。**
  直前のステップの末尾から流れ込むと引数が決まらないので、直前のステップは `return`・`throw`・`goto` で必ず終わらせる。関数本体の先頭にも置かない。
  引数名には、関数の引数や関数直下の変数と同じ名前を使わない。引数は `名前: 型` の形だけで書き（既定値・`?`・`...` は使えない）、ステップの中で再代入しない。
- **goto で宣言を飛び越えない。**
  ステップの間で使う値を、`goto` の行き先より後ろで宣言しない。
  後ろへ戻る `goto` の範囲に、関数直下の宣言を置かない。
- **1つの `実施` には1つの目的だけを書く。**
  指示は「何をするか」と「守ること（作らない・推測しない）」を短く書く。
  詳しい決まりは定数にして入力で渡す。
- **出力の読み取りと実行を分ける。**
  コマンドの実行は tool、その出力から件数などを読み取るのは model の作業にする。
  読み取りの指示には「出力に無い値は作らない」と書く。
- **AI の書いた値を上書きできるものは上書きする。**
  依頼文・範囲・フラグなど、フローの中で決まっている値は、AI に書かせた結果をそのまま使わず、決めた値で上書きする。

## 4. 既存スキルを写すときの手順と、写し漏れの確かめ方

1. SKILL.md を全部読む。手順が references にあれば、それも読む。
2. スクリプトは全部を読まない。受け取る引数と、出力する行（件数・結果の行）だけを `grep` で確かめる（例：`grep -n "console.log\|process.exit\|opt('--" scripts/*.mjs`）。
3. 入口の分かれ方（モード）を決め、モードごとにフロー関数を作る。
4. 各モードの手順を、段階ごとにステップへ写す。
5. 禁止事項・完了条件・書き方の決まりを定数に写す。
6. 写し漏れを確かめる。SKILL.md の見出しと手順・禁止事項・完了条件を上から1つずつ見て、flow.ts のどこに表したか（ステップ名・定数・コメント）を対応させる。
   表せないもの（見た目の好み、背景の説明など）は、先頭のコメントか該当するステップの直前のコメントに残す。
7. スキルの書き方があいまいで、flow.ts に写すときに自分で決めたこと（条件の境目、失敗したときの行き先など）を控えておき、報告で伝える。
   これがスキルの改善点の候補になる。

## 5. よくある検査のエラーと直し方

| 出る内容 | 直し方 |
|---|---|
| goto の行き先が無い | ステップ名の打ち間違い。ラベルが関数本体の直下にあるかも確かめる |
| try・catch・finally の中から goto している | `try` の中で失敗の印（`let 失敗 = false`）を立て、`try` の外で `if (失敗) goto …;` する |
| 関数やコールバックの中から goto している | `.map` などのコールバックの外へ出し、結果を見てから `goto` する |
| goto が宣言を飛び越え… | 飛び越えた宣言を、最初のステップより前の共有の宣言へ移す。行き先でしか使わない値なら、goto の引数で渡す |
| goto 〜 の引数が N 個ある（ラベルの引数は M 個） | goto で渡す値の数を、行き先のステップの引数の数に合わせる |
| 引数の無いラベルに、goto で引数を渡している | 行き先のステップに引数を足すか、goto の引数を消す |
| 引数のあるラベルに、goto を通らずに入る経路がある | 直前のステップの末尾を `return`・`throw`・`goto` で終わらせる。引数のあるステップを関数の先頭に置かない |
| ラベルの引数は「名前: 型」の形で書く | 既定値・`?`・`...`・分割代入をやめ、`名前: 型` にする |
| ラベルの引数が、関数の引数か関数直下の変数と同じ名前 | 引数の名前を変える |
| 型検査：型 X の引数を型 Y のパラメーターに割り当てることはできません | goto で渡す値の型が、行き先のステップの引数の型と合っていない |
| 後ろへ戻る goto で、関数直下の宣言をもう一度評価… | その宣言をステップの中へ入れるか、最初のステップより前へ移す |
| 関数の終わりまで return せずに届く | 最後のステップの末尾に `return` を書く。分岐の漏れがないかも見る |
| 型検査：割り当てられる前に使用されています | 共有変数に初期値を入れる（`= null` など） |
| 型検査：'x' は 'null' の可能性があります | ステップの先頭で `if (x === null) throw new Error("…");` と確かめる |
| 型検査：暗黙的に 'any' 型（TS7022） | 戻る `goto` のある流れで、`実施` の結果を同じ共有変数へ戻している。結果の変数に型を書く（`const 回答: T = await 実施<T>(…)`） |
| 型検査：名前が見つからない | 型・定数・補助関数の宣言が抜けている。flow.ts の中で宣言する |
| 上限の見当たらない繰り返し（注意） | 回数の変数を足して上限と比べる。スキルの改善点として報告する |
| 関数の先頭からたどり着かない（注意） | 使われないステップ。消すか、どこから来るのかを書く |
