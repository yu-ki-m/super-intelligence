# 段4・5の書き方と点検

## 1. ストーリーマップ（段4）

### 1.1 形

- 背骨：活動を、左から右へ時間の順に並べる。活動は、体験の流れの時期、またはユースケースの大きなまとまり。
- 手順：各活動の下に、ユースケースの正常の流れの手順を並べる。複数のシナリオで同じ手順は、1つにまとめて由来を並べる。
- ストーリー：各手順の下に、その手順を実現するストーリーを、重要な順に並べる。代わり・例外の流れは、同じ手順の下に別のストーリーとして置く。
- 切れ目：リリースごとに、どのストーリーを含めるかを決める。

Markdown では、2次元の図の代わりに、活動 → 手順 → リリースごとのストーリーの入れ子で書く（`assets/story-map.md`）。

### 1.2 リリースの切れ目

- 最初の切れ目は、主シナリオが端から端まで、安全に完了する最小の組にする。主シナリオの手順のすべてに、最低1つのストーリーを置く。最初は人の手作業で代わりにできる手順は、手作業でよい。そのときは、手作業で行うことを書く。
- 「安全に」は外さない。主シナリオを壊しうるシナリオのうち重いもの（権限、誤りに気づくこと、取り消し）への最小の備えは、最初の切れ目に入れる。
- 2つ目以降は、壊しうるシナリオへの備え → 運用のシナリオ → 広げるシナリオ → 便利さ、の順を目安にする。
- 切れ目ごとに、そのリリースで何が確かめられるか（どの仮置きを確かめるか）を書く。最初の切れ目で、最も危ない仮置き（多くは「利用者が本当に使うか」）を確かめられるようにする。作ってから使われないと分かるのが、一番高くつくため。
- Claude がおすすめの切れ目を、理由と決め手つきで示す。決めさせない。相談者が何も言わなければ、おすすめで進める。

### 1.3 点検

- 手順・代わり・例外の流れのすべてに、ストーリーか対象外（理由）がある。
- ストーリーのすべてに、由来（手順・代わり・例外の流れの ID）がある。
- 最初の切れ目で、主シナリオが端から端まで完了する。
- 最初の切れ目に、重い壊しうるシナリオへの最小の備えがある。

## 2. ストーリーの形

```
### US-001 〔タイトル：利用者の行動で〕

- ストーリー：〔役割・状況〕として、〔したいこと〕したい。それは〔得たい価値〕のためだ。
- 由来：S1-2（〔手順の名前〕）、S1-機1
- 受入条件：
  - 〔前提〕のとき、〔操作〕すると、〔観察できる結果〕になる。
  - （例外）〔前提〕のとき、〔操作〕すると、〔観察できる結果〕になる。
- 依存：
- 確からしさ・仮置き：
- メモ（分ける候補・実装の候補・未確定）：
```

- 役割は、属性ではなく状況で書く（「販促担当として」より「展示会の前でデモの準備を急いでいる販促担当として」）。
- 「得たい価値」は、上の段の課題・価値から取る。したいことの言い換えで終わらせない（「データを入力するために、入力したい」は価値になっていない）。
- 受入条件は、ユースケースの終わりの条件と、その手順の代わり・例外の流れから作る。観察できる結果で書く。「適切に」「素早く」「分かりやすく」は、数値か状態に直す。数値が分からなければ〔仮置き〕にする。
- 画面の部品や技術の作り方は、ストーリーと受入条件に書かない。思いついたら「メモ」に「実装の候補」として書く。

## 3. ストーリーの分け方

次のどれかなら、大きすぎる。分ける。

- 1回の開発の区切り（スプリントなど）に収まりそうにない。
- 受入条件が7つ以上ある。
- ストーリーの文に「と」「または」が入る。

| 分け方 | 例 |
|-|-|
| 手順で | 「欲しいデータを伝える」と「出てきたデータを確かめる」 |
| 正常と例外で | 正常の流れを先に、例外の流れを後に |
| データ・対象の種類で | 製品のデータと、顧客のデータ |
| 役割で | 販促担当と、管理者 |
| 程度で | まず1件ずつ、次に一括で |
| 手作業を残して | 最初は人が確かめる、後で自動にする |
| 決まりごとで | 単純なルールを先に、例外のルールを後に |

分けた後も、それぞれが利用者にとって意味のある価値を持つようにする。技術の層（画面だけ、データだけ）で分けない。層で分けると、どのストーリーも単独では利用者の価値を確かめられないため。

## 4. バックログの点検

### 4.1 ストーリーごと

| 点検 | 見ること |
|-|-|
| 独立している | ほかのストーリーなしで、価値を確かめられるか。依存があれば書いたか |
| 話し合える | 作り方を固定していないか |
| 価値がある | 利用者か事業にとっての価値が書けているか |
| 見積もれる | 何をするかが分かるか。分からなければ、調べるためのストーリーを別に置いたか |
| 小さい | 1回の開発の区切りに収まる見込みか |
| 確かめられる | 受入条件が、観察できる形か |

### 4.2 全体

- すべてのストーリーに由来がある。由来のないストーリーは、上の段に元を足すか、消す。
- 主シナリオの手順のすべてに、リリース1のストーリーがある。
- マップのストーリーが、すべてバックログにある。バックログのストーリーが、すべてマップにある。
- 横断の条件（5章）を書いた。
- 仮置きに頼るストーリーに、印と確かめ方がある。

## 5. 横断の条件

バックログの末尾に、すべてのストーリー、または多くのストーリーにかかる条件をまとめる。

- 例：応答は3秒以内〔仮置き〕。誰が何をしたかの記録を残す。キーボードだけで操作できる。顧客のデータは、権限のある人にしか見せない。
- 観点：速さ・量、権限、記録・監査、使える人の広さ（見やすさ・キーボード・読み上げ）、データの扱い（保存・削除・外部への送信）、止まったときの扱い。
- それぞれに、由来（どのシナリオ・どの課題から来たか）と、確かめ方を書く。
- 悪化させてはいけないもの（思考ノートの成果の輪の「悪化させないもの」）も、ここに書く。
