# 曖昧な依頼を価値ある成果に変えるための企画・要求分析ガイド

**版**：1.1（2026-10-17）  
**用途**：新規事業・製品機能・システム開発・業務改善・サービス導入・組織施策・運用変更・調達・研究開発など、依頼内容が十分に具体化されていない仕事全般  
**利用者**：企画担当、業務分析者、PM/PO、エンジニア、コンサルタント、営業企画、業務責任者、意思決定者  
**適用原則**：依頼に応える／価値から逆算する／根拠を残す／定量的な成果仮説を置く／対象外を明示する／漏れを検出する／未検証事項を放置しない

> **このガイドの目的**は、曖昧な依頼から「何を、なぜ、誰のために、どこまで実現するか」を導き、選択肢を比較して合意し、検証可能な要求と実行計画に落とし込むことである。チェック項目を埋めること自体を目的にしない。
>
> **注意**：どの手法でも未知の要求の「漏れゼロ」は証明できない。本ガイドで目指すのは、発見経路を多重化し、対象範囲内の未検証・未対応・不整合を可視化して、許容不能な漏れを合意前に解消すること。

---

## 1. 作業を開始する前の基本原則

### 1.1 「依頼された解決策」と「解決すべき問題」を分ける

依頼が「ツールを作ってほしい」「AI化してほしい」「マニュアルを作ってほしい」であっても、それは**解決手段の指定**であり、目的・成果・成功条件を意味しない。指定された解決手段は尊重しつつ、目的との整合性、代替手段、成立条件を検証する。

最初に以下の5層を区別する。

| 層 | 中心となる問い | 例（汎用） |
|---|---|---|
| 事業・組織上の目的 | なぜ実施するか | 対応遅延を減らす |
| 利用者・関係者の成果 | 誰が何を達成するか | 担当者が案件の状況を即時把握する |
| 必要な能力 | 何ができればよいか | 複数データ源を照合し、最新状況を表示できる |
| 実現手段・設計 | どう実現するか | UI、プロセス変更、API、AI、教育など |
| 検証可能な成果 | 何をもって成功とするか | 対象作業の所要時間を現状比で何％削減するかなどを、基準値・目標値・測定条件とともに定義する |

### 1.2 情報の確からしさを区別する

すべての記述に可能な限り次の状態を付ける。

- **事実（F）**：資料・ログ・観察などで裏付けられた情報。出典と確認日を記録。
- **申告（S）**：関係者が述べた内容。発言者・日時・確認要否を記録。
- **仮説（H）**：現時点で説明として妥当だが未検証の考え。
- **提案（P）**：分析者が推奨する選択肢。根拠・他案・副作用を示す。
- **決定（D）**：権限者が承認した内容。決定者・日付・前提を記録。
- **未確認（U）**：検証が必要な論点。責任者・調査方法・期限を持つ。

「不明」は欠陥ではないが、**重要な不明を根拠なく確定扱いすること**と、**未確認のまま期限なく放置すること**を禁止する。

### 1.3 三つの品質を同時に満たす

1. **妥当性**：そもそも正しい問題を解いているか。価値・目的に合うか。
2. **完全性**：必要な利用シーン、関係者、条件、影響、例外を十分に捉えたか。
3. **明確性・検証可能性**：曖昧語や暗黙の前提がなく、達成を確認できるか。

これに**実現可能性、費用対効果、リスク許容性**を加えて判断する。

### 1.4 作るものの形を最初に限定しない

機能開発が唯一の対策とは限らない。制度変更、業務手順変更、教育、組織体制、委託、既存ツールの設定変更、運用改善、何もしないことまで比較する。

## 2. 分析の全体プロセスと品質ゲート

各段階は反復してよい。ただし、段階ごとの結論・保留・根拠を記録する。

| 段階 | 主な仕事 | 必須アウトプット | 次に進む条件 |
|---|---|---|---|
| 0. 受領・初期整理 | 明示された依頼と曖昧さを整理 | 依頼分析票、確認課題 | 解決策と目的を混同していない |
| 1. 事業・目的分析 | 背景・機会・価値・成果を明確化 | 問題定義、定量的な成果仮説 | 改善対象の業務単位・指標・現状値または取得計画が明らか |
| 2. 関係者・対象範囲分析 | 利用者・非利用者・権限者・境界を把握 | ステークホルダー図、スコープ図 | 主要関係者と責任境界が明示される |
| 3. 現状分析 | 現行の行動・仕組み・根本原因を確認 | As-Is、作業別ベースライン、問題・原因一覧 | 改善対象の作業量・時間・件数・品質を把握または測定計画化 |
| 4. 望ましい状態・利用シーン | To-Beと通常・例外ケースを構築 | ユースケース群、業務フロー | 利用者が成果を得る道筋が説明できる |
| 5. 解決案の発散と比較 | 複数案・代替案・非採用理由を検討 | 定量効果を含む代替案比較、採用方針 | 効果・費用・不確実性を同条件で比較できる |
| 6. 要求の導出と構造化 | 明示・潜在・派生・移行要求を抽出 | 要求台帳、要求モデル | 各目的・ユースケースに要求が紐づく |
| 7. 影響・網羅性分析 | 非変更箇所、境界、横断条件を点検 | 影響分析、カバレッジ表 | 高リスクの未対応セルがない |
| 8. 実現性・リスク評価 | 技術・運用・予算・組織・法務を調査 | 実現性評価、リスク台帳 | 許容不能リスクの対処方針が決まる |
| 9. 成果・品質検証設計 | 受入基準と成果測定を定義 | 受入条件、作業別改善率・総効果・KPI検証計画 | 単位・母数・期間・目標根拠・測定方法が明瞭 |
| 10. 優先順位・計画化 | MVP、依存関係、費用、導入段階を設計 | ロードマップ、見積前提 | 必須・延期・対象外が明瞭 |
| 11. 合意・引き継ぎ | 判断・責任・残課題を正式化 | 提案書、決定記録、引継書 | 意思決定者と実行責任者が合意 |
| 12. 実行後の再評価 | 成果・副作用・追加要求を検証 | 事前事後比較、目標達成率、改善バックログ | 実測の改善率と予測との差異・原因を評価する |

### 2.1 どの段階でも行う6つの確認

1. **根拠はあるか**：観察、業務資料、規則、ヒアリングなど何に基づくか。
2. **対象は誰か**：利用者だけでなく、管理者、運用者、被影響者、意思決定者を含むか。
3. **前後関係は何か**：前提・結果・下流影響を追ったか。
4. **反例は何か**：失敗、少数派、最大負荷、誤操作、禁止条件を検討したか。
5. **別解は何か**：依頼どおりの手段が最適か、代替案と比較したか。
6. **どう確かめるか**：検証方法・受入基準・責任者・期限があるか。

## 3. 段階別の具体的な実施手順

### 0. 受領・初期整理

**行動**：依頼文を「確定依頼」「背景推測」「手段指定」「利用シーン」「制約」「未決定事項」に分解。誰が依頼し、誰が承認するか確認。納期・予算・法定期限などの固定条件と希望条件を区別。

**問い**：なぜ今回この話が出たか／今やらないと何が起こるか／実施しない選択肢はあるか／何を納品すれば満足するか／依頼者自身も把握していない条件は何か。

**出口**：重要な未確認事項を優先順に並べ、追加調査の担当と期限を設定。

### 1. 事業・目的分析

**行動**：課題を現象・原因・影響に分解し、目的と手段の因果関係を描く。便益を利用者・組織・顧客・社会など受益者ごとに分ける。定量指標の現状値が未取得なら測定計画を作る。成果は「どの作業・利用者・対象範囲が、何を、いつまでに、何％改善するか」の形でも仮置きし、数値の出典と確度を明示する。

**問い**：何を改善するか／誰にどんな便益があるか／何が犠牲になるか／解決を阻む真因は何か／成功を数値と観察でどう判定するか／優先順位の根拠は何か。

**出口**：問題定義（背景→現象→原因仮説→影響）、成果仮説、対象指標を揃える。

### 2. 関係者・対象範囲分析

**行動**：直接利用者、管理者、周辺業務、承認者、運用・保守、問い合わせ先、法務・セキュリティ、顧客・取引先などを洗い出す。権限・期待・懸念・利害対立を記録。組織・業務・データ・システム・場所・期間の境界を明示する。

**問い**：誰が得をし誰に負担が移るか／利用できない人は誰か／例外を承認するのは誰か／費用負担者と責任者は誰か／どの部門・契約・組織境界をまたぐか。

**出口**：影響を受ける重要な関係者の未調査をなくす。対象外の根拠と合意者を記録。

### 3. 現状（As-Is）分析

**行動**：実業務の観察、操作ログ、問い合わせ、事故・クレーム、現行規程、既存仕様、データ、手作業の例外対処を照合。文書化された正規手順と、現場の実際の手順を区別する。業務を作業単位に分解し、1件当たりの作業時間・件数・待ち時間・手戻り・品質・人員構成・季節変動を測定し、ベースラインを作る。

**問い**：作業開始のきっかけは何か／前段階から何を受け取るか／どこで滞るか／非公式な回避策は何か／現状でも保持すべき価値は何か／少数・まれなケースは何か。

**出口**：観察・申告・推測を区別した現状モデルと、改善対象ではない「保持すべき既存能力」を定義。

### 4. 目標状態（To-Be）とユースケース分析

**行動**：理想状態を利用者の行動・業務成果として描く。開始条件→主要手順→判断・分岐→完了条件→後処理まで追跡。通常・代替・例外・失敗・中断・取消・再開・復旧・権限不足・競合を検討。低頻度だが重大なケースも取り上げる。

**問い**：全体の仕事が完了するか／途中で人に戻す条件は何か／完了後に誰が何を確認するか／誤って実行したらどうなるか／無関係な利用者の業務に影響しないか。

**出口**：主要ユースケースごとに、開始条件、結果、正常・例外パス、関係者、制約を記述。

### 5. 解決案の発散・比較・提案

**行動**：「現状維持」「業務変更」「教育・運用改善」「既存機能活用」「外部サービス利用」「新規開発」「複合案」を含む複数案を作成。同じ母数・測定期間・費用条件で、作業別改善率、年間換算効果、コスト、期間、リスク、可逆性、拡張性、運用負荷を比較。反対意見を自ら構成する。

**問い**：この手段が必要十分か／小さく試せるか／先送り可能か／取り返しのつかない副作用はないか／別案を選ばない根拠は何か。

**出口**：推奨案を一つ以上示し、非採用案・前提・残る弱点を明記する。

### 6. 要求の抽出・導出・構造化

**行動**：最初の依頼の内容だけでなく、利用シーン・既存仕様・法令・品質・運用・例外・依存関係から要求を導出。要求を以下に分類する。

- **BR（ビジネス要求）**：組織・事業が達成する成果。
- **SR（ステークホルダー要求）**：利用者や関係者が必要とする成果・能力。
- **FR（機能要求）**：システム・業務プロセスが実現する振る舞い。
- **NFR（品質・非機能要求）**：性能、安全性、使いやすさ、復旧性などの必要水準。
- **DR（データ・情報要求）**：内容、品質、権利、更新・保持・削除の規則。
- **TR（移行・導入要求）**：教育、データ移行、切替、並行運用、撤退。
- **CR（制約・遵守要求）**：予算、納期、契約、法規、技術制約。

**要求の由来**として「明示」「分析による導出」「影響・リスクから導出」「既存能力の維持」「外部規則」を別記する。要件を満たすための設計案と要件そのものを混同しない。

**出口**：要求を原子化し、ID、根拠、主語、事前条件、望ましい結果、検証方法を持たせる。矛盾・重複・孤立要求を検査。

### 7. 影響・網羅性分析

**行動**：業務、組織、データ、関連システム、非変更機能、運用、利用者権限、財務・法務をまたぐ依存グラフを作る。「変更箇所」だけでなく、変更によって意味・挙動・負荷・責任が変わる「非変更箇所」を洗う。次節の網羅性マトリクスで再点検。

**問い**：誰も修正しない既存機能に副作用はないか／仕様上つながる上流・下流はどこか／データ共有先はどこか／契約や説明資料が古くならないか。

**出口**：影響対象と非影響判断に根拠を持たせ、未確認の高リスク影響を保留理由ごと管理する。

### 8. 実現可能性・リスク分析

**行動**：技術、業務、体制、予算、契約、法務、安全性、調達、運用、スケジュールについて成立条件を調べる。各リスクには発生要因、影響、兆候、予防、検知、対処、責任者、残余リスクを設定。必要に応じ小規模実証で確認する。

**問い**：その方式は本当に使えるか／外部依存が崩れたらどうするか／失敗したときの損失上限は／人手で代替できるか／誰が最終リスクを受容するか。

**出口**：重大な実現性仮説に証拠または検証計画がある。許容不能リスクは解決・計画変更・中止のいずれか。

### 9. 成果指標・受入条件・検証計画

**行動**：業務成果指標と手段の動作品質指標を分ける。各要求を、正常・異常・境界・権限・利用者行動まで検証できる形にする。改善対象の作業別に、現状値・目標値・改善率（％）・年間換算効果・算定根拠・不確実性を定義する。導入前の基準値、母数、測定時期、データ収集方法、季節性、観察バイアス、比較可能性を考慮。

**問い**：「作った」ではなく「目的を達成した」をどう示すか／誰がどの証拠で合格を認めるか／悪化してはいけない指標は何か。

**出口**：各必須要求の受入条件が揃い、改善対象の各業務には基準値（未取得の場合は取得計画）、目標値、改善率、対象件数、算式、測定責任者、目標の設定根拠がある。非金銭便益や実測不能な効果は無理に金額換算せず、評価方法を決める。

### 10. 優先順位・計画・費用

**行動**：法令・安全・契約などの不可欠条件を先に分離し、残りは価値、緊急性、費用、依存関係、失敗時影響、不確実性で比較する。MVPは「機能数が少ない版」ではなく「特定の利用シーンを安全に完了できる最小の提供単位」とする。リリース後の保守・教育・運用費も見積もる。

**問い**：なくすとユースケースが完了できなくなる要求は／後回しで生じる負債は／フェーズ分割でデータや利用者が困らないか。

**出口**：今やる・後でやる・対象外を根拠付きで分類。依存関係と成立条件を計画へ反映。

### 11. 提案・合意・実行への引き継ぎ

**行動**：依頼者には質問の羅列でなく、選択肢、推奨、根拠、決めるべき論点を提示する。要求IDを設計・タスク・テスト・受入・運用へ引き継ぐ。変更要望が来たら目的と影響を再評価し、決定記録を更新する。

**問い**：誰が何を承認したか／見積もりの前提は何か／残課題の責任者と期限は／実行担当が同じ解釈を持てるか。

**出口**：スコープ、非対象、受入基準、責任分担、残リスク、変更ルール、次のアクションに合意。

### 12. 実行後の効果検証・改善

**行動**：提供開始後、業務成果、利用状況、障害、追加負担、想定外利用、当初仮説との差を確認。実施前後の同条件比較から作業別改善率、全体改善率、実際の年間換算効果、費用対効果、品質への副作用を算出する。成果が出ない場合は「要求の誤り」「導入・周知の問題」「設計・実装の問題」「測定の問題」に切り分ける。

**出口**：続ける・改善する・縮小する・やめるを判断し、結果を次の企画へ還元。

## 4. 漏れを検出するための横断チェック体系

### 4.1 全案件共通の「20の分析レンズ」

各レンズを **対象／対象外（理由）／未確認（担当・検証期限）** のいずれかに必ず分類する。対象の場合は該当する要求・業務・リスクへのリンクを付ける。

| # | レンズ | 見るべき対象・問い |
|---|---|---|
| 01 | 目的・成果 | 改善対象の作業、現状値、目標値、改善率（％）、ビジネス効果、成功条件、副作用 |
| 02 | ステークホルダー | 直接利用者、非利用者、管理者、運用者、顧客、第三者 |
| 03 | 人・権限・責任 | 役割、能力差、代理、承認、責任分界、利益相反 |
| 04 | 業務起点・終点 | 開始のきっかけ、入力、完了状態、後処理、引継ぎ |
| 05 | 業務手順・判断 | 分岐、承認、判断基準、待ち、手戻り、例外 |
| 06 | 状態・ライフサイクル | 作成、更新、保留、取消、履歴、廃棄、再開 |
| 07 | データ・情報 | 正確性、鮮度、出所、整合性、個人・機密情報、保持・削除 |
| 08 | 物・設備・資源 | 現物、場所、設備、在庫、人的能力、容量・供給 |
| 09 | 接点・利用環境 | チャネル、UI、端末、現場、地域、ネットワーク、アクセス手段 |
| 10 | 時間・負荷・規模 | 日時、締切、ピーク、同時数、地域差、季節性、継続時間 |
| 11 | 外部・内部連携 | 上流、下流、他部門、外部サービス、取引先、委託先 |
| 12 | 既存仕様と不変条件 | 変更しない機能、暗黙の契約、互換性、現行保証、歴史的経緯 |
| 13 | 正常・代替・異常 | 失敗、停止、再試行、競合、欠損、誤入力、復旧、悪用 |
| 14 | 品質・人間特性 | 利便性、可用性、信頼性、安全性、アクセシビリティ、説明可能性 |
| 15 | セキュリティ・プライバシー | 権限、監査、脅威、機微情報、外部送信、悪意ある利用 |
| 16 | 法務・契約・倫理 | 法令、規制、社内規程、約款、権利、顧客期待、公平性 |
| 17 | 経済性・実行資源 | 作業別削減量、年間効果、実現する現金節減と余力創出の区別、投資・維持費、ROI、予算、要員、採算 |
| 18 | 導入・組織変化 | 教育、移行、周知、抵抗、並行運用、サポート、手順変更 |
| 19 | 運用・保守・監視 | 担当者、監視、障害、変更管理、問い合わせ、継続・撤退 |
| 20 | 将来・変化・終了 | 拡張、利用者増減、規則変更、技術更新、終了・データ返却 |

**案件別の拡張レンズ**：ITならAPI契約・テナント・バージョン・非機能、製造なら品質・安全・トレーサビリティ、販促なら顧客セグメント・ブランド・法令、調達なら契約・SLA・サプライチェーン、公共・医療なら固有の法規・安全性を加える。共通表は専門家によるドメイン追加チェックの代わりにはならない。

### 4.2 六方向から同じ要求を検査する

1. **縦方向（Why→What→How→Test）**：目的から実装・検証までつながるか。逆向きにも「不要な機能」がないか。
2. **横方向（End-to-End）**：上流→自分の担当範囲→下流と他部門まで仕事が完結するか。
3. **時間方向（Before→During→After）**：導入前、実行中、完了後、維持、撤退まで含むか。
4. **境界方向（Inside↔Outside）**：組織・システム・契約・権限・環境の境界で漏れないか。
5. **反例方向（Normal↔Abnormal）**：成功だけでなく失敗、拒否、中断、復旧、誤操作、悪用、想定外を見たか。
6. **変更方向（Change↔Non-change）**：直接変更しない部分への間接影響、不変条件、既存利用者への影響を見たか。

### 4.3 網羅性をマトリクスで証拠化する

少なくとも以下の関係を作り、各セルを「対応済み／対象外（理由）／未確認（検証計画）」で管理する。

- **利用者・役割 × ユースケース**：誰の仕事が見落とされているか。
- **ユースケース × 正常・代替・例外・中断・取消・復旧**：成功パスしか設計していないか。
- **業務対象 × 状態遷移**：作成・変更・無効化・削除などの抜け。
- **ユースケース × 入力・出力・前提・後処理**：前後の条件の抜け。
- **業務・機能 × 上流・下流・非変更箇所**：影響の見逃し。
- **要求 × 根拠 × 設計 × 検証 × 運用**：孤立・未実装・未検証要求の検出。
- **リスク × 予防 × 検知 × 復旧 × 責任者**：対処不在の重大リスク。
- **効果指標 × 対象作業 × 単位・母数 × 基準値 × 目標値・改善率 × 根拠 × 測定手段 × 責任者**：数値の定義・算出・検証不能の検出。
- **作業別改善効果 × 実施件数・頻度 × 追加作業・費用 × 最終成果**：改善率の単純平均、作業漏れ、効果の二重計上、年間換算の誤りを検出。

**空欄は「問題なし」を意味しない。** 空欄と「調査して対象外と判断した」を分け、欠損を見えるようにする。

### 4.4 特に漏れやすい「非変更箇所への影響」13分類

1. **意味の変化**：同じ項目・機能でも解釈や業務ルールが変わる。
2. **入力の変化**：上流から届くデータ、形式、頻度、品質が変わる。
3. **出力の変化**：下流の集計・画面・通知・帳票の前提が崩れる。
4. **状態遷移の変化**：既存フローが新しい状態・順序に対応できない。
5. **認可の変化**：今までアクセスできなかった／できたものが変わる。
6. **量・頻度の変化**：負荷、容量、コスト、作業量が増減する。
7. **タイミングの変化**：締切、非同期、順序、整合性が変わる。
8. **障害連鎖**：故障時の影響範囲や復旧順序が変わる。
9. **操作習慣の変化**：誤操作、期待不一致、教育・案内不足が発生する。
10. **監査・説明の変化**：記録主体、証跡、顧客説明、契約内容が合わなくなる。
11. **データ寿命の変化**：保存・削除・バックアップ・移行に副作用が出る。
12. **責任分界の変化**：問い合わせ、監視、承認、障害対応の担当が曖昧になる。
13. **後方互換の変化**：既存の利用者・連携先・手順が静かに破綻する。

### 4.5 主要な発見手段を独立に組み合わせる

- **発言ベース**：依頼者・現場・管理者・非利用者へのヒアリング。
- **証拠ベース**：ログ、規則、仕様、申請書、事故記録、業務データ。
- **行動ベース**：現場観察、作業同行、ユーザーテスト、現物確認。
- **構造ベース**：プロセス図、状態遷移、責任分界、依存・データフロー。
- **反証ベース**：失敗例、レッドチーム、プレモーテム、逆方向の追跡。
- **外部ベース**：顧客・取引先・専門家、競合・標準・法規の確認。

一人の依頼者の発言だけで完結させず、重要論点は可能な限り異なる情報源でクロスチェックする。

## 5. 要求の品質を判定するルール

要求ごとに、以下の基準を満たすか確認する。

| 観点 | 判定質問 |
|---|---|
| 必要性 | どの目的・業務・制約を満たすために必要か |
| 正確性 | 業務実態・規則・データと一致するか |
| 明確性 | 異なる人が読んでも同じ解釈になるか |
| 単一性 | 一要求に複数の独立した条件を詰め込んでいないか |
| 完全性 | 主語、事前条件、入力、期待結果、例外を必要な範囲で書いたか |
| 整合性 | 他要求・既存仕様・制約と矛盾しないか |
| 実現可能性 | 技術・費用・期限・法務・運用上、実現の見通しがあるか |
| 検証可能性 | 客観的な観察、テスト、実測で合否を判断できるか |
| 追跡可能性 | 根拠・目的・設計・検証・責任者へ辿れるか |
| 優先度・状態 | 必須／任意、提案／合意、未確認／検証済みを区別できるか |
| 変更可能性 | 影響範囲を特定し、変更時に更新対象が分かるか |
| 妥当性 | その要求で利用者・組織の成果につながるか |
| 定量性（成果要求） | どの作業・集団・期間に対し、現状の何をどれだけ（絶対値・％）改善するかを判定できるか |
| 数値の根拠（成果要求） | 基準値・目標値・改善率の計算式・母数・出典・確度が明示されているか |

**曖昧語の例**：「簡単に」「高速」「柔軟」「適切に」「自動で」「リアルタイム」「安全に」「すべて」。利用者、条件、基準、許容範囲に分解する。

**要求の記述型**：`〔主体〕は、〔前提・条件〕において、〔対象〕に〔振る舞い／制約〕を適用でき、その結果〔観測可能な状態〕となること。`  
ただし、事業・組織施策などシステム以外の要求には状況に合わせて表現を調整する。

## 6. 定量的な成果仮説・改善率・投資効果の標準分析（原則必須）

この章はIT開発だけでなく、業務改善、販促、調達、組織施策、サービス改善にも適用する。**「便利になる」「生産性が上がる」で止めず、どの作業・成果が何％改善するかを、数値の根拠とともに示す。** 効果が金額では表せない場合も、適切な定量・定性指標を組み合わせる。

### 6.1 定量化の対象を「作業→業務→事業成果」に分解する

1. **業務の範囲を決める**：始点・終点・対象者・対象組織・対象件数・実施頻度・対象期間を記録する。
2. **作業に分解する**：準備、入力、確認、承認、待機、手戻り、例外処理、後片付け、運用・維持まで含める。
3. **各作業の現状値を得る**：1件当たり作業時間、処理件数、エラー・差戻し率、コストなどを記録。平均だけでなく中央値・分布・ばらつき・繁忙期も必要に応じ確認する。
4. **改善のメカニズムを説明する**：「操作をなくす」「入力を再利用する」「手戻りを減らす」など、改善率が実現する理由を特定する。
5. **作業別目標と業務全体の目標を設定する**：作業を取り除いた結果、他の作業が増えないかも考慮する。
6. **事業・組織の成果へつなぐ**：創出した余力が、追加対応件数、納期短縮、売上・品質向上、現金支出削減などにどう寄与するかを検討する。

**必須の記述型**：`〔対象者・対象業務・作業〕について、〔測定期間・対象条件〕の〔現状値・単位〕を〔目標値・単位〕に改善する（〔削減率／増加率〕％）。根拠は〔測定／試行／推計〕であり、〔施策が効くメカニズム〕による。〔検証時期〕に〔方法〕で判定する。`

### 6.2 目的に合う指標を選ぶ

| 改善の種類 | 代表的な指標 | 取り違えてはいけないこと |
|---|---|---|
| 時間・工数削減 | 1件当たり作業分数、月間工数、リードタイム | 作業時間と待ち時間、削減工数と人件費削減は異なる |
| 処理能力向上 | 単位時間の処理件数、稼働率、完了率 | 件数増と1件当たり効率改善は同義ではない |
| 品質向上 | 誤り率、差戻し率、手戻り時間、再作業件数 | エラーの定義と検出能力が変わると単純比較できない |
| 顧客・利用者体験 | 解決率、完了時間、満足度、離脱率 | 回答率・利用率の向上が課題解決の向上とは限らない |
| 売上・事業成長 | 成約率、継続率、平均売上、粗利益 | 売上増と利益増は異なる。外部要因を除外する必要がある |
| コスト・資源 | 支払費用、処理単価、設備・資源消費量 | 現金支出削減と計算上の労務費相当額を区別する |
| 安全・安定性 | 事故率、停止時間、復旧時間、重大インシデント数 | 発生頻度が少ない指標は短期間では検証が難しい |

**指標のセット**：最終成果指標（アウトカム）＋施策が働く過程の指標（先行指標）＋悪化させない制約指標（ガードレール：品質・安全・負荷・公平性など）。一つの数値だけで成功を判定しない。

### 6.3 改善率（％）の計算ルール

同じ対象・単位・母数・条件・観測期間で比較する。ベースラインを `B`、目標値または実測導入後の値を `T` とする。

- **小さいほど良い指標の削減率（％）**：`(B - T) / B × 100`。例：60分→15分なら **75％削減**。
- **大きいほど良い指標の増加率（％）**：`(T - B) / B × 100`。例：月100件→130件なら **30％増加**。
- **達成率・不良率など％値の変化**：`15％→10％` は **5パーセントポイント低下**、基準値に対する相対削減率は **約33.3％**。必ず両者を区別する。
- **削減絶対量**：`B - T`（分／件、時間／月など）。改善率と絶対量の両方を示す。
- **対象業務全体の改善率**：`(改善前の総工数 - 改善後の総工数) / 改善前の総工数 × 100`。**作業別の改善率を単純平均しない**。作業時間や件数で重み付けした実工数に基づき計算する。
- **基準値が0または不明**：相対改善率を安易に算出しない。絶対差、目標到達率、基準値取得計画などで扱い、必要に応じ「％算定不可」と明記する。

比較対象と分母を必ず明記する（例：「1件当たり」「作業者1人・1か月当たり」「全利用者の月間総工数」）。利用者数・案件難易度・件数の構成が変わる場合は層別集計や条件調整を行う。

### 6.4 年間効果・金額・投資判断への換算

**標準の算定経路**：`作業別の1件当たり削減量 × 対象件数 × 期間内の実施頻度 = 期間削減量`。導入後に発生する確認・修正・運用作業は差し引く。複数作業・部門を合計するときは、同じ効果を二重計上しない。

| 区分 | 計算・確認方法 | 記録する注意点 |
|---|---|---|
| 作業時間の削減 | `Σ（現状時間 - 導入後時間）× 件数` | 追加作業・例外・教育・定常運用を含める |
| 労務費相当額 | `削減時間 × 評価用時間単価` | 原則、**創出余力の評価額**であり、現金支出が減ったとは限らない |
| 実際の現金削減 | 廃止した外注費・実際に減る支払額など | 実現が確認できる部分だけを現金削減として計上 |
| 追加利益・売上効果 | 追加収益に対する粗利益等 − 増分費用 | 追加工数・需要制約・因果関係を検証。売上総額を利益と混同しない |
| 総保有コスト（TCO） | 初期費＋利用期間の運用・保守・利用料・教育・移行費等 | 比較期間・一時費用と継続費用・税等の扱いを統一 |
| 単純ROI | `(金額換算した期間便益 - 同期間の総費用) / 同期間の総費用 × 100` | 比較期間と便益の種類を明記。金額換算できない便益は別欄で扱う |
| 投資回収期間 | 累積の**実現可能な金銭便益**が累積費用を上回るまで | 単純な労務費相当額だけから現金の回収期間を主張しない |

必要に応じ、複数年度の割引キャッシュフロー・NPV、リスクによる期待損失、実施しない場合の機会損失も評価する。

### 6.5 目標値の根拠・実現可能性・不確実性

すべての主要な数値に、**値／単位／分母／対象期間／対象集団／情報源／算定式／確度／責任者**を付ける。

- **実測値**：作業ログ、タイムスタディ、会計記録など。取得日・対象件数・欠測・ばらつきを記録。
- **実験・試行値**：プロトタイプや限定導入の結果。条件・参加者・サンプルの偏りを記録。
- **推計値**：工程分解や専門家見積もりに基づく数値。前提と算式を記録。
- **目標・仮定値**：達成を目指す数値。実測や予測であるかのように提示しない。

改善率が実現する根拠を「削除される作業時間」「短縮される処理」「削減される手戻り」のように分解し、重要な仮定が外れた場合の影響を検討する。効果見積もりは必要に応じ **保守／標準／楽観** の3シナリオを設け、対象件数・導入率・品質・運用負荷を変数として感度分析する。

### 6.6 測定計画と成功判定

- **事前**：ベースラインを採る。定義・単位・測定期間・担当者・サンプル規模を決める。未取得なら試算値を実測と混ぜず、取得期限を設定する。
- **途中**：利用率、処理件数、追加作業、エラー、対象範囲の変化を継続記録する。導入が進まなければ理論上の削減量は実現しない。
- **事後**：同じ条件・定義・母数で測定する。可能なら比較群や段階導入を用い、季節性・業務量・習熟・人員構成・他施策の影響を検討する。
- **判定**：目標値、実測値、改善率、達成・未達、効果の差の説明、ガードレールの悪化有無を示す。不確実性が大きければ幅・暫定判定・追加検証条件を示す。

**禁止事項**：根拠のない「〇％改善」を確定効果として記載する／分母を示さない／改善率だけで総効果を推測する／削減工数をそのまま現金節減にする／増加した作業を除外する／品質悪化を伏せる／同じ効果を複数施策に重複計上する。

### 6.7 数値化が難しい領域の扱い

法令順守、重大事故の回避、公平性、信頼、利用者の尊厳などは、安易な金額換算や単一指標への還元をしない。**必要条件・禁止条件・定性的証拠・代理指標・検証頻度**を設定する。「未測定／推計不能」は理由と検証方法を示して管理し、数字がないことだけで価値がないと判断しない。

## 7. 合意に向けた意思決定と優先順位

### 7.1 依頼者へは「質問」より「検証可能な提案」を持っていく

提案書は次の順に並べる。

1. **問題の理解**：依頼内容と、解決すべき課題の仮説。
2. **目標**：達成したい成果と、対象作業の現状・目標・改善率（％）・達成時期・測定方法。
3. **対象者・ユースケース**：誰がどこまで仕事を完了するか。
4. **選択肢**：少なくとも現状維持と、実行可能な代替案を比較。
5. **推奨案**：作業別改善率、年間効果、必要投資、ROI等の根拠と不確実性、デメリット、成立条件、なぜ他案でないか。
6. **提供範囲**：今回／次回／対象外、スコープ境界。
7. **リスク・不確実性**：重要な未検証事項、調査・緩和策。
8. **意思決定依頼**：何を誰がいつ決めるか。

### 7.2 優先順位は安全制約と価値の評価を混ぜない

- **まず前提条件**：法令、安全、必須契約、データ保護など欠くと提供不可なものを先に判定。
- **そのうえで価値比較**：作業別改善率（％）、対象者数、対象件数・利用頻度、年間効果、初期費・維持費、ROI、緊急性、依存関係、不確実性を同じ条件で比較。
- **点数は補助**：スコアが高いから必ず実施するわけではない。仮定の偏り・少数者への重大影響・不可逆な損失を別途審査。
- **延期・対象外も決定**：単に優先度を低くするのではなく、選ばなかった理由と再評価条件を残す。

### 7.3 決定記録の最低項目

`決定ID／論点／選択肢／推奨案／採用案／根拠・証拠／却下理由／前提／副作用・残リスク／決定者／日付／再検討条件`

## 9. 複雑な仕事での追加ルール

### 9.1 大量の既存資産がある場合

仕様書やソースコード、業務規程を一度に全量読んで理解した前提にしない。まず**資産目録→関連性グラフ→重要箇所の証拠抽出→周辺依存の探索→未調査範囲の表示**で進める。

- 資産目録：資料、機能、利用者、データ、外部連携、規則、オーナー、更新日。
- 関連性グラフ：変更候補から参照先・呼び出し元・下流利用先・責任者を辿る。
- 証拠単位：出典、版、該当箇所、判断、反証可能性をセットで残す。
- 探索範囲：変更箇所の周辺だけでなく非変更の影響先へ広げる。
- 未調査表示：「全体を確認した」と言わず、確認済み・未確認の資産集合を明示する。

### 9.2 領域横断・多部門の場合

部門ごとに個別最適化せず、端から端までの業務を一つのフローとして評価する。受け渡しのたびに情報欠落、権限不一致、責任の空白、重複、遅延がないか検査する。利害衝突は両者の要求とトレードオフを明示して決裁者に委ねる。

### 9.3 AIを分析支援に利用する場合

AIには「候補の発散」「反例生成」「依存関係の探索」「文章・要求の曖昧さ検出」「欠落セルの検出」「作業別定量効果の算式と前提の監査」を担わせる。ただしAIの推測は証拠ではない。原資料からの抽出とAIが導出した仮説を分離し、重要要求・法務・安全性・事実認定は適切な担当者が検証する。

**推奨するAIへの指示**：

> この依頼を目的・利用者・業務・要求・制約・リスクに分解し、明示された情報と仮説を区別してください。20の分析レンズと六方向の漏れチェックを適用し、既存の非変更箇所への影響も洗い出してください。依頼者の記載だけに限定せず、導出要求を提示してください。各候補には根拠、確認方法、優先度、見落とした場合の結果を付け、未確認を確定事項として扱わないでください。改善対象を作業に分解して現状値・目標値・改善率（％）・削減絶対量・年間効果を提示し、分母、単位、対象件数、改善のメカニズム、根拠・確度、算出不能な点を明記してください。年間労務費相当額と実際の現金削減額は分けてください。最後に定量比較可能な複数案、推奨案、意思決定が必要な論点を提示してください。

## 10. 汎用的な簡易適用例（依頼：「月次レポートを自動化して」）

1. **手段指定と目的を分離**：「自動化」が手段。目的は集計時間の短縮か、誤集計の防止か、意思決定の迅速化かを確認する。
2. **業務を端から端まで確認**：収集→加工→確認→承認→配布→読解→意思決定→訂正まで対象として観察する。
3. **代替案を比較**：現行手順改善、テンプレート統一、既存BI活用、新規自動化を比較する。
4. **導出要求を発見**：データ欠損検知、例外の人手確認、閲覧権限、過去数値との差分検証、訂正履歴、配布失敗時の再送など。
5. **非変更箇所を確認**：既存の承認規則、配布先、経営会議の締切、過去レポートとの比較可能性を保持する。
6. **成果を数値で検証**：例えば合計の作業時間が120分／件→72分／件なら、48分／件・40％削減。月80件なら64時間／月、年間768時間の削減という**仮説**になる。実測で検証し、導入・確認・例外処理による追加時間、差戻し率、締切遵守率、レポート利用者の意思決定時間や品質も確認する。
7. **合意する**：初回対象の部署・帳票・期間、除外例外、移行方法、受入条件、運用担当を決める。

この進め方は「何かを開発する」以外に、組織改革、販促施策、調達、研修、運用変更にも適用できる。

## 11. 見落としを減らす最終レビュー（独立レビュー推奨）

### A. 価値と範囲
- [ ] 依頼をそのまま実装するのでなく、背景と目標を確認した。
- [ ] 課題、原因、成果、手段を混同していない。
- [ ] 対象・対象外・制約・暫定仮定が記録されている。
- [ ] 便益だけでなく副作用、負担の移転を検討した。
- [ ] 現状維持と複数案を比較した。

### B. 利用者と業務
- [ ] 主要利用者、非利用者、運用・承認・被影響者を確認した。
- [ ] 業務の開始前から完了後まで検討した。
- [ ] 標準、例外、失敗、拒否、中断、取消、再開、復旧を確認した。
- [ ] 多様な利用環境、習熟度、権限、頻度、規模を検討した。

### C. 仕様・影響
- [ ] データ、状態、上流・下流、外部連携を確認した。
- [ ] 非変更箇所に影響する既存仕様と保持すべき目的を確認した。
- [ ] 明示要求以外の派生要求を抽出した。
- [ ] 要求相互の矛盾、重複、孤立、不足を検査した。
- [ ] 20レンズの全項目に対応・対象外理由・未確認管理のいずれかがある。

### D. 実現・検証・合意
- [ ] 技術・組織・運用・法務・費用・期間の成立条件を確認した。
- [ ] 安全・セキュリティ・権利・重大リスクに対処方針がある。
- [ ] 必須要求を客観的に検証できる。
- [ ] 改善対象作業の現状値・目標値・改善率（％）・絶対量が定義されている（未測定なら理由と取得計画がある）。
- [ ] 全体の改善率を同一母数の総量から計算し、年間件数・頻度・追加工数を反映した。
- [ ] 金額効果は労務費相当と現金支出削減を分け、TCO・ROIの前提が明示されている。
- [ ] 成果指標の根拠・確度・測定時期・実施者・副作用指標が明らかである。
- [ ] 意思決定者が推奨・非採用・残リスクを理解している。
- [ ] 未確認の重要事項は所有者・期限・対応方針が決まっている。

### 原則として合意・着手を止める条件

- 解決する問題や成功条件を重要関係者が共有できていない。
- 法令・安全・機密・重大な権限問題に対して判断者も対処方針も存在しない。
- 業務の主要な正常・異常ケースの実現可能性が確認されていない。
- 受入基準のない必須要求が存在する。
- 実行の可否を左右する未確認事項に担当者・期限・検証方針がない。
- 重大な非変更箇所への影響を確認せず、「影響なし」と記述している。

ただし**調査・実証そのものを目的とする限定PoC**は、仮説、時間・費用・影響範囲、安全上の制約、停止条件を明記することで開始してよい。

|---|---|---|
| ライト | 低リスク・短期・影響範囲が限定 | 依頼分析票、目的・対象、代表ユースケース、20レンズ簡易判定、受入・残課題 |

### 分析の終了（Definition of Ready for Decision）

次の全条件を満たしたとき、「提案・要求を意思決定できる状態」とみなす。

1. 対象業務と目的が、利害関係者に説明できる。
2. 主要ユースケースに開始条件、成功・失敗・完了条件がある。
3. 対象範囲の20レンズと主要マトリクスに、未説明の空欄がない。
4. すべての必須要求が目的と根拠へ遡れ、検証条件を持つ。
5. 重大影響と残リスクは判断者・対応方針を持つ。
6. 不明事項は検証済み、期限付き管理、または理由付き対象外であり、着手可否を阻む未解決事項がない。
7. 推奨案と代替案、採否理由、MVP、非対象範囲が明示される。
8. 改善対象の作業別に基準値・目標値・改善率（％）と絶対量、対象件数、算定根拠と確度、計測方法が決まっている。未測定は測定計画、定量化不能は理由・代替評価が管理されている。
9. 承認者が情報とトレードオフを理解し、次の実行を承認している。

## 付録B. 分析者の最後の自問

- 依頼者から一切言及されなかった重要な要求を、どの方法で探したか。
- この施策の失敗を最も困るのは誰か。その人に聞いたか。
- 誰も変更しない既存業務・機能に、どのような副作用があるか。
- 成功例だけを見て、失敗・境界条件を切り捨てていないか。
- 解決策の採用理由よりも、解決する問題の妥当性を強く検証したか。
- 今回実現する価値と、将来の可能性を区別できているか。
- 要求一覧だけを見れば、分析から導出された要求まで確認できるか。
- 未確認を「問題なし」と扱わず、検証責任を置いているか。
- 反対者・専門家・現場・下流担当者によるレビューに耐えるか。
- 完了後に、当初約束した成果が得られたか確認する仕組みがあるか。
- どの具体的な作業を何％改善するか、現状値・目標値・絶対量・分母と対象期間を説明できるか。
- 作業別の改善が全体工数と年間効果にどう積み上がるか、追加負担や効果の重複計上を除いて説明できるか。
- 目標改善率の根拠と不確実性を示し、想定と実測の差を検証できるか。
