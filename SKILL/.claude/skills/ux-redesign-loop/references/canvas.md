# 画面一覧キャンバスの作り方

画面一覧キャンバスは、プロトタイプの画面を、スクロールした先まで含めた 1 画面の全体として 1 枚ずつのフレームに描き、1 つの作業面（キャンバス）に並べて見せる HTML である。Figma で、画面をフレームとしてキャンバスに並べて全体の構成を見るのと同じ見方を、プロトタイプから作る。部品は `<SKILL_DIR>/screen-canvas/`（`canvas.css`・`canvas.js`）にあり、見本は `<SKILL_DIR>/sample-demo/` の `画面一覧_*.html` にある。

呼び方について。Figma では、画面を置く作業面を「キャンバス」、1 つの画面の枠を「フレーム」と呼ぶ。「デザインスタジオ」は、チームで短時間に案をスケッチして見せ合い、批評し合うワークショップの進め方の名前であり、画面を並べる場所の名前ではない。このスキルでは、この機能を「画面一覧キャンバス」と呼ぶ。

## 1. 目的

プロトタイプやデモでは、画面を 1 つずつしか見られない。1 つずつ見ていると、「この情報は別の画面にもある」「この画面だけ判断の根拠が下の方に埋もれている」「最初に見える範囲に、次の操作が入っていない」といった、画面どうしの関係や配置の問題に気付きにくい。画面一覧キャンバスは、全画面を同じ縮尺で並べ、どの情報がどこにあるかを番号の印で示すことで、画面の構成をまとめて見直せるようにする。チームが付箋やテキストを貼って、気付いたことをその場に残すこともできる。

デモ（`references/demo.md`）が「人と状況の時間の流れ」を追うのに対し、画面一覧キャンバスは「画面の空間の配置」を俯瞰する。同じプロトタイプから両方を作れる。

| 項目 | デモ | 画面一覧キャンバス |
|---|---|---|
| 見るもの | 1 画面ずつ、場面の順に | 全画面を同時に、全体の長さで |
| 主に分かること | 誰が何を言い、何を思い、どう操作するか | どの情報がどの画面のどこにあるか、画面どうしのつながり |
| 書き込み | 場面・仮説ごとのメモ | 付箋とテキストを好きな所に貼る |

## 2. 作る時期と前提

- ユーザーが頼んだときに作る（「全画面を並べて見たい」「画面の構成を一覧で見たい」「画面一覧に付箋を貼りたい」「Figma のように画面を並べたい」など）。反復の D でプロトタイプを作ったあと、E（検証）の前に、情報の配置を見直す材料としても使える。
- 操作できるプロトタイプが必要である。プロトタイプには、デモと同じく `window.uxDemoApply` と `demo-bridge.js` が要る（`references/prototype.md` の「デモとの連携」）。
- 結果は、反復の B（最適化）の「判断地点に判断根拠があるか」「情報量が 10 倍でも構造が成り立つか」の点検に使う。付箋に書かれたことは、デモのメモと同じく [推論] として扱う。

## 3. 出力

```
ux-design/<YYYY_MMDD>_<案件名>/
├── demo/player/demo-bridge.js        # プロトタイプが読み込む連絡役（デモを作らない場合も置く）
├── canvas/
│   ├── screen-canvas/                # <SKILL_DIR>/screen-canvas/ の複製（canvas.css・canvas.js）
│   └── 画面一覧_<案ID>.html           # 台本（window.UX_CANVAS）と部品を読み込むキャンバス
└── iter-NN/proto-<案ID>-v<NN>.html   # 今の版
```

キャンバスの HTML は、DS の `tokens.css`・`components.css`・`components.js` と、`screen-canvas/canvas.css`・`canvas.js` を読み込む。見本の `<head>` を写し、パスだけを変えると早い。

## 4. 台本の書き方

```js
window.UX_CANVAS = {
  id: 'K-01',                                   // キャンバスの ID
  title: '…',
  refs: { case: 'C-02', iteration: 'iter-01' },
  prototype: '../iter-01/proto-C-02-v03.html',  // キャンバスの HTML から見たプロトタイプ（今の版）のパス
  device: 'pc',                                 // pc（1280 × 800）・phone（360 × 780）・tablet-portrait（800 × 1280）・tablet-landscape（1280 × 800）。{ w, h, label } でも書ける
  screens: [{
    id: 's-review', row: 0,                     // row は行。同じ行の画面は左から順に並ぶ
    title: '検査の結果', desc: '47 行に問題',     // フレームの見出し
    state: { screen: 'review', file: true },    // その画面のプロトタイプの状態（デモと違い、前の画面から引き継がない）
    prototype: '…',                             // 省略可。この画面だけ別のプロトタイプにするとき
    marks: [{ sel: '#summary', text: '取り込める行と、直す必要がある行の数', color: '#e11d74' }]   // 情報の位置の印
  }],
  flows: [                                      // 画面の移り方の矢印
    { from: 's-upload', to: 's-checking', label: '取り込む前に検査する', trigger: '#check-btn' },   // trigger：押すと移るボタン。そこから矢印を出す
    { from: 's-checking', to: 's-review', label: '検査が終わる', auto: true }                      // auto：押す操作ではなく、時間や出来事で移る（点線）
  ],
  notes: [                                      // 最初から貼っておく付箋とテキスト
    { type: 'text', near: 's-upload', dx: 0, dy: -420, text: '見出し' },
    { type: 'sticky', near: 's-review', dx: 1660, dy: 60, color: 'pink', text: '…' }   // near の画面の左上からの位置。x・y で絶対の位置にもできる
  ]
};
```

- **画面を選ぶ。** 状態表の状態ごとに 1 枚を基本にし、シートやダイアログが開いた状態、失敗・空・大量の状態も入れる。正常な流れだけを並べると、例外の画面で情報が欠けていることに気付けないためである。
- **印を付ける。** その画面で利用者が判断に使う情報と、主な操作に印を付ける。印の説明には、その場所に何があり、何のためにあるかを書く。印の対象には、プロトタイプの側で `id` を付けておく。印の数は 1 画面に 2〜5 個を目安にする。多すぎると、どれが大事かが分からなくなるためである。
- **行を分ける。** 1 つの流れを 1 行にし、別の流れ（失敗のとき、翌日の再開など）は次の行にする。矢印は、縦と横の線を角を丸めてつなぐ形で引かれる。右の画面へは横に進み、下の行へは行の間を通って相手の上から入り、左へ戻るときは下を回って相手の下から入る。
- **移り方の起点を書く。** ボタンを押して移るときは、`trigger` にそのボタンのセレクターを書く。ボタンの右端に丸の印を付け、そこから矢印を出す。どの操作でどの画面へ移るかが、画面の中の位置まで分かるようにするためである。ボタンではなく、処理の終わり・時間の経過・他の人の操作で移るときは `auto: true` を書く。矢印は点線になり、利用者が押さなくても移ることが分かる。起点のないときは、画面の右端（下の行へは下端）から出る。説明の札の列があるときは、札より下の高さを通して札に重ねない。

## 5. 表示と操作

| 操作 | 結果 |
|---|---|
| ドラッグ、ホイール | キャンバスを動かす |
| Ctrl（Mac は ⌘）＋ホイール、上の帯の − ＋ | 拡大・縮小 |
| Shift＋1、「全体を表示」 | 全画面が収まる大きさにする |
| フレームの見出しをドラッグ | フレームを動かす（位置は保存される） |
| フレームの「触る」 | その画面を実際に操作する。もう一度押すと、台本の状態に戻る |
| 「付箋」「テキスト」 | 見ている範囲の中央に足し、すぐ書ける |
| 付箋をダブルクリック、Enter | 書き直す（Esc で終える） |
| 付箋を押して、Delete | 消す。押すと出る帯で色を変えられる |
| 「表示と保存」 | 印・矢印・最初に見える範囲の線・付箋の表示の切り替え、付箋のテキストでのコピー、JSON の書き出しと読み込み、台本の状態に戻す |

各フレームには、端末の 1 画面の高さの所に「ここまでが最初に見える範囲」の線を引く。スクロールしないと見えない所に、判断の根拠や主な操作が入っていないかを確かめるためである。

付箋・テキスト・フレームの位置は、そのブラウザの中にだけ保存される。チームで共有するときは「付箋と配置を書き出す（JSON）」で書き出し、相手は「書き出したものを読み込む」で開く。「付箋をテキストでコピー」は、付箋を近い画面ごとにまとめた Markdown を作るので、設計の記録に貼れる。

## 6. 仕組みと制約

キャンバスは、フレームごとにプロトタイプを iframe で開き、`demo-bridge.js` に状態と印のセレクターを送る。`demo-bridge.js` は次のことをして、ページ全体の高さと印の位置を返す。

- スマートフォン版 DS の端末の枠（時刻の帯・下の帯・キーボードなど）を外す。
- スクロールする欄（`overflow: auto` の要素）を、中身の高さまで伸ばす。
- 動きを止める。

この伸ばし方は、スクロールする欄の作りによっては合わないことがある。たとえば、高さを `100vh` から計算して決める要素が中身を囲んでいると、フレームの高さに合わせて伸び続けることがある。キャンバスは 4 回で測り直しを打ち切るので画面は止まるが、その場合は、プロトタイプの側で `html[data-ux-canvas]` のときの高さを指定する。

各フレームは、端末の 1 画面の高さより短くはしない。中身が短い画面でも、端末の 1 画面の大きさで見せるためである。

## 7. 確かめること

1. キャンバスを開き、すべてのフレームの見出しに警告（「プロトタイプから応答がない」「印の対象が見つからない所がある」「矢印の起点のボタンが見つからない」）が出ていないことを確かめる。
2. 全体を表示した画像と、印を付けた画面を拡大した画像を撮り、印が対象に重なっているか、説明の番号と印の番号が合っているかを見る。
3. スクロールした先まで描けているか（フレームの下端に、ページの最後の要素が入っているか）を見る。
4. 付箋を 1 枚足して書き、再読込しても残ることを確かめる。
