# UI崩れの検査と修正

反復の D2（SKILL.md 3章）で、プロトタイプの今の版を、画面の大きさ・文字・データ・状態を変えて開き、UI が崩れていないかを検査して、崩れていれば直す手順である。

## 目次

1. この段を置く理由
2. 崩れとして扱うもの
3. 試す条件

## 1. この段を置く理由

E（検証）のシナリオ走査は、各手で「見つけられるか・意味が分かるか・正しく判断できるか・操作できるか」を判定する。表示が崩れていると、たとえばボタンが画面の外に出て「操作できない」になる。そのとき、原因が体験の構造にあるのか、表示の崩れにあるのかを分けられず、戻る工程を誤る。そこで E の前に、表示の崩れだけを取り除く。

C でプロトタイプを作ったときに確かめていても、D で文言を省くと文字の長さが変わり、折り返しや並びが変わる。そのため、D の後の版で確かめる。また、プロトタイプは作り手の画面の大きさ（多くは 1 種類）で作られやすく、利用者の画面が狭い・低い・拡大している場合の崩れは、意識して大きさを変えないと見えない。

## 2. 崩れとして扱うもの

崩れは、設計した構造とは関係なく、表示が壊れている状態である。

| 種類 | 例 | スクリプトで拾えるか |
|---|---|---|
| ページの横はみ出し | 狭い幅で、上の帯の検索欄やボタンが右へはみ出し、ページ全体に横スクロールが出る | 拾える |
| 画面の外の操作要素 | 切り取られた入れ物の外にボタンがあり、送っても届かない | 拾える |
| 文字の切れ | 省略記号なしに、名前の後ろが切れている | 拾える |
| 縦に潰れた文字 | 幅が足りず、見出しが1行に1〜2文字ずつ折り返す | 拾える |
| 操作要素の重なり | 2つのボタンが重なり、片方を押せない | 拾える |
| 覆われた操作要素 | 下に固定した帯、端末の枠の下の帯やキーボードが、送信ボタンを覆う | 拾える |
| 下が切れて届かない | 画面の高さに固定した入れ物の下の部分が、送っても見えない | 拾える |
| 画像・アイコンの欠け | 読み込めない画像、ページの中に無いアイコンを指している | 拾える |
| 文字どうし・部品どうしの重なり | 見出しと数値が重なって読めない | 画像で確かめる |
| 並びの乱れ | そろうべき列がずれる、一覧の行の高さがばらばらで読みにくい | 画像で確かめる |
| 余白の崩れ | 余白が無くなって部品が接する、片側だけ極端に空く | 画像で確かめる |
| フォーカスの枠の欠け | Tab で移った先の枠が、入れ物に切られて見えない | 画像で確かめる |

次は崩れとして扱わない。ただし、記録には「意図どおり」として残す。

- 表など、横に送る入れ物を意図して置き、その中で横スクロールする場合。
- 省略記号で長い名前を省く場合。ただし、長い名前どうしを区別できるか、全文を見る手段（詳細の画面、フォーカスでも出る表示など）があるかを画像で確かめる。区別できなければ崩れとして扱う。

## 3. 試す条件

対応する画面の大きさは、`01_設計ブリーフ.md` の対象ユーザー・状況（使う端末、外出先で使うか、など）から決める。書かれていなければ、下の表の既定の値を [仮定] として置き、確認事項にする。

| 観点 | PC の画面 | スマートフォンの画面 | タブレットの画面 |
|---|---|---|---|
| 幅 | 1920・1440・1280・1024px と、ブラウザで200%に拡大したときに当たる 640px | 320・360・375・390・430px（540px 以下では端末の枠が消え、実機と同じ表示になる） | 端末の枠つきで、ブラウザを 1024・1280・1440px |
| 高さ | 600px（ノートPCでブラウザの帯を除いた高さに近い）と 1080px | 568px（小さい機種）と 932px | 768px と 1024px |
| 向き | なし | 縦と横（例：667 × 375px） | 縦と横の枠（`data-orientation="landscape"`） |
| 文字の間隔 | 行の高さ1.5倍・字間0.12em・語間0.16em・段落の後2em に広げる（WCAG 2.2 の 1.4.12 の条件） | 同じ | 同じ |
| データ | 検証用パネルのシナリオ（通常・大量・空・失敗・長い名前）を切り替える | 同じ | 同じ |
| 状態 | シート・ダイアログ・メニュー・通知を開いた状態、処理中・失敗の表示、一覧の最後までスクロールした先 | 同じに加えて、入力欄に焦点を当てて端末のキーボードを出した状態 | 同じ |
| 見た目 | DS が明るい画面と暗い画面、または見た目を切り替えられる場合は両方 | 同じ | 同じ |
| キーボード | Tab で順に移動し、フォーカスの枠が切れたり隠れたりしないか | 外付けのキーボードを使う想定がある場合だけ | 同じ |

端末の枠を使う画面（スマートフォン版の DS の `.dv-phone`）では、枠の中の大きさは固定で、枠ごと縮む。そのため、ブラウザの幅と高さを変えて確かめるのは、枠が台に収まるかと、枠の中で部品が端末の帯やキーボードに隠れないかである。枠の中の画面そのものの幅による崩れは、540px 以下の幅（枠が消える表示）で確かめる。

すべての組み合わせを試す必要はない。組み合わせを全部試すと数百通りになり、同じ崩れを何度も見るだけになるためである。次の順に広げる。

1. 状態表の状態ごとの画面（検証用パネルのシナリオ）を、幅の一覧のすべてで、標準の高さで開く。
2. 低い高さ・向き・キーボードを出した状態は、入力や下の操作がある画面だけで試す。
3. 文字の間隔・暗い画面・大量・長い名前は、幅の最小と最大で試す。

文字の間隔を広げるには、ページに次の CSS を足す（Playwright MCP なら `browser_evaluate` で `<style>` を足す）。

```css
* { line-height: 1.5 !important; letter-spacing: 0.12em !important; word-spacing: 0.16em !important; }
p { margin-bottom: 2em !important; }
```

## 4. 検査スクリプトの使い方

`<SKILL_DIR>/layout-check/check-layout.js` は、開いているページの、今の幅と高さでの崩れの候補を返す、ページの中で実行する関数である。2章の表で「拾える」とした種類を、要素の位置と大きさから機械的に探す。

使い方（Playwright MCP の場合）：

1. `browser_resize` で幅と高さを決める。
2. `browser_navigate` でプロトタイプを開く。シナリオは URL のハッシュ（例：`#scenario=large`）か、検証用パネルの操作で切り替える。`file://` が開けない設定なら、保存先で `python -m http.server <空いているポート> --bind 127.0.0.1` を立てて開き、終わったら止めて、そのプロセスが残っていないことを確かめる。ほかの作業のサーバーが同じポートを使っていることがあるので、開いたページの題名で、目的のプロトタイプが開けたかを確かめる。
3. `browser_evaluate` の `function` に、`check-layout.js` の中身（先頭のコメントを含めてよい）をそのまま渡す。
4. 結果の `問題` が空でなければ、`browser_take_screenshot` で画面を撮り、候補ごとに画像で確かめる。問題が空でも、各条件で1枚は撮って、2章の「画像で確かめる」種類を見る。画像は `iter-NN/screens/layout/` に、`<版>_<幅>x<高さ>_<条件>.png` の名前で保存する。

結果の形は次のとおりである。

```json
{ "幅": 360, "高さ": 667, "件数": 2,
  "問題": [ { "種類": "ページの横はみ出し", "詳細": "ページの幅 616px が画面の幅 360px を超える",
              "要素": ["label.ds-topnav__search（右端 382px）", "…"] } ] }
```

スクリプトが返すのは候補であり、崩れの判定ではない。意図した横スクロールや省略も候補に出るので、画像で確かめて「崩れ・意図どおり・構造の問題」に分ける。検証用パネルの中は、製品の画面ではないので検査から外している（`data-ux-panel` 属性か `ux-panel` のクラス、または「検証用」を含む `aria-label` を付けたパネル）。プロトタイプの中身を `<iframe>` に入れている場合は、その iframe の中で実行する。

## 5. 進め方

1. `iter-NN/UI崩れ記録.md`（書式は `references/templates.md` の17章）に、試す条件の表を作る。幅・高さ・向き・文字の間隔・データ・状態の組み合わせを、3章の順で選ぶ。
2. 案ごとに、今の版を各条件で開き、スクリプトを実行して画面を撮る。
3. 候補と画像を見て、崩れを L-01… の ID で記録する。種類、条件、場所、画像、判定（崩れ・意図どおり・構造の問題）を書く。
4. 崩れがあれば、6章の決まりで直し、新しい版のファイルにして、`04_プロトタイプの版.md` に一行足す（反復と段は「反復NN D2」）。
5. 直した版で、崩れた条件と、1で選んだほかの条件をもう一度試す。直した所が別の幅や状態で崩れることがあるためである。
6. 2〜5 を、崩れが無くなるか、直して確かめる巡が3回に達するまで繰り返す。3回で残った崩れは「未解決」として記録し、E に進む。E のシナリオ走査では、その崩れが関わる手に注記し、判定がその崩れによるものかを分けて書く。上限を置くのは、ある幅を直すと別の幅が崩れる、という行き来で反復が止まらなくなるのを防ぐためである。
7. 「構造の問題」と判定したものは、直さずに F（全体再評価）に渡し、次の反復の A・B で扱う。

## 6. 直し方の決まり

- 直すのは表示だけ（CSS、部品の組み方、折り返しや並びの指定）にする。機能・作業・画面・状態・操作・判断の材料は削らない。
- 崩れた要素を隠して直さない（表示しない、切り取って見えなくする、画面の外へ出す）。崩れは消えても、利用者がその情報や操作にたどり着けなくなるためである。
- 文言を削って収めない。文言を減らすのは D の役目で、ここで削ると、意味を担う所と復元条件の記録（`省いた文言.md`）が無いまま文言が消えるためである。収まらないのは配置の問題として直す。
- 検証用のデータ（長い名前、50件以上、失敗、空）を短く・少なくして直さない。E で長い名前や大量の件数での見落としを確かめられなくなるためである。
- 省略記号で省くときは、長い名前どうしを区別できるか、全文を見る手段があるかを確かめる。
- DS を使っている場合は、DS のトークンと部品の範囲で直す。部品の制約で直せない場合は、`デザインシステム対応.md` でその要素を「最善のものがない」として判定し直し、追加提案を作るか見直す（SKILL.md 7章の「DS に合わせて体験を曲げる」）。
- 比べる案が同じ見た目の基盤（共通の CSS）を使っている場合、基盤の側で直したら、ほかの案にも同じ直しを当てる。案どうしの違いを構造に限るためである（`references/prototype.md` の「案どうしの公平さ」）。
- 量が多すぎて一覧が成り立たない、画面の幅で一覧と詳細を並べられない、など、構造を変えないと直らない崩れは、ここで直さず「構造の問題」として F に渡す。情報の配置と量に耐える構造は B（最適化）の仕事で、D2 で表示の小手先で収めると、B で見直す機会を失うためである。

## 7. Playwright が使えない場合

実際の表示では確かめられないので、HTML と CSS を読んで、崩れやすい書き方を探して直す。

- 固定の幅（`width: 1200px` など）や、最小の幅が画面より広い指定
- 折り返さない指定（`white-space: nowrap`）が長い名前に当たる所
- 重ねた配置（`position: absolute` / `fixed`）が、ほかの部品やキーボードの位置と重なりうる所
- 切り取る指定（`overflow: hidden`）が、文字や操作要素を含む入れ物にある所
- 画面の高さに固定した入れ物（`height: 100vh` など）で、中身が送れない所

見つけたものは [机上] として記録し、`UI崩れ記録.md` に「Playwright が使えず、実際の表示では確かめていない」と書く。実ユーザー検証の前に、実際の画面の大きさで確かめることを `09_実装引継ぎ.md` の未検証事項に入れる。
