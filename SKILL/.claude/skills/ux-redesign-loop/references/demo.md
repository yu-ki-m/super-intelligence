# デモの作り方

デモは、プロトタイプの画面を場面に合わせて切り替えながら、その横に登場人物の発言・心の声・状況の説明を並べて見せる HTML である。再生の部品は `<SKILL_DIR>/demo-player/` にあり、見本は `<SKILL_DIR>/sample-demo/` に四つある。作り始める前に、作る画面に近いほうを開くと、完成形が分かる。

| 見本 | 画面 | 題材 | ファイル |
|---|---|---|---|
| D-01 | PC（`sample-design-system`、コンソールの見た目） | 顧客管理の CSV 取込で、一部の行が失敗し、翌朝に保留を片付ける | `仮説デモ_C-02_S-02.html`、`proto-C-02.html` |
| D-02 | スマートフォン（`sample-design-system-mobile`、端末の枠つき） | 外回りの課長が電車の中で経費の申請を承認し、途中で通信が切れ、夕方に経理から差し戻される | `mobile/仮説デモ_C-01_S-03.html`、`mobile/proto-C-01.html` |
| D-03 | 縦のタブレット（`sample-design-system-mobile`、枠を 800 × 1280 に広げる。1 列） | 工場の点検員が巡回しながら設備を点検し、異音を保全に送り、途中で呼ばれて中断する | `tablet-portrait/仮説デモ_C-01_S-02.html`、`tablet-portrait/proto-C-01.html` |
| D-04 | 横のタブレット（`sample-design-system-mobile`、枠を 1280 × 800 に広げる。一覧と詳細の 2 列） | 店頭受け取りのカウンターで、同じ名前の注文・一部の欠品・後ろの行列が重なる | `tablet-landscape/仮説デモ_C-01_S-04.html`、`tablet-landscape/proto-C-01.html` |

## 1. 二種類のデモと、このファイルで扱う範囲

デモには、見る人と目的の異なる二種類がある。

| 種類 | 見る人 | 目的 | 状態 |
|---|---|---|---|
| 仮説立案向け | 設計チーム（自分たち） | 利用者が何を言い、何を思い、どんな状況で画面を使うかを物語として追い、仮説を立て直す・疑う・確かめ方を決める | このファイルで扱う |
| お客さん向け | 顧客・依頼者 | 新しい体験を伝える | 未整備 |

お客さん向けのデモを頼まれた場合は、見せ方（設計チームの書き込みや根拠のラベルを見せるか、心の声をどう扱うか、架空の人物をどう断るか）がまだ決まっていないことをユーザーに伝え、確かめてから作る。仮説立案向けの台本は同じ形式で書いておけば、あとからお客さん向けに転用しやすい。

## 2. 仮説立案向けデモの目的

プロトタイプだけでは、画面の外の事情が見えない。たとえば「明日の朝に配信したい上司がいる」「会議に呼ばれて途中でやめる」「担当者マスタを触れるのは別の部署の人だけ」といった事情である。利用者が画面の上でどう判断するかは、こうした事情に強く左右される。現状ジャーニーで画面の外の作業を同じ時間軸に置くのと同じ理由で、デモでは、画面の切り替わりと、人の発言・心の声・状況を同じ時間軸に並べる。マニュアル工程6の表で、仕事の流れや分担が不確かな段階に挙げられている「シナリオ」と「役割演技」を、プロトタイプと組み合わせた形に当たる。

チームはデモを見ながら、「この人は本当にこう思うか」「別の解釈はないか」「この仮説が崩れるのはどんな場面か」を話し合い、場面や仮説ごとにメモを残す。デモが役立つのは、仮説を作り、疑い、確かめ方を決める場面である。

デモは検証の証拠にはならない。登場人物の発言と心の声は、設計チームが置いたものだからである。デモを見てチームが納得しても、それはチームの感想であり、記録では [推論] として扱う。「デモで確認した」「デモで使いやすさを確かめた」とは書かない。

## 3. 作る時期と前提

- ユーザーが頼んだときに作る（「デモを作って」「登場人物の会話つきで画面を見せたい」「チームで仮説を話し合う材料がほしい」など）。
- 操作できるプロトタイプが必要である。まだなければ、反復の D（`references/prototype.md`）で先に作る。
- 反復の中では E（検証）の補助になる。台本の場面は、検証記録のシナリオ走査を物語に書き直したものに近い。チームが書いたメモは、F（全体再評価）と次の反復の A に戻す（9章）。

## 4. 出力

```
ux-design/<YYYY_MMDD>_<案件名>/
├── demo/
│   ├── player/                       # <SKILL_DIR>/demo-player/ の複製（player.css・player.js・demo-bridge.js）
│   ├── 仮説デモ_<案ID>_<シナリオID>.html  # 台本と再生の部品を読み込むデモ
│   ├── screens/                      # 場面ごとのスクリーンショット（撮れた場合）
│   ├── 仮説メモ_<デモID>_<日付>.md     # チームが書き出したメモ（ユーザーから受け取った場合）
│   └── デモ記録.md                    # デモの目的、台本と根拠の対応、メモの反映先（書式は templates.md の13章）
└── iter-NN/proto-<案ID>.html          # demo-bridge.js を読み込み、window.uxDemoApply を持つ
```

`demo-player/` を複製する理由は、DS を `ds/` に複製するのと同じで、オフラインでも、スキルの部品が後で変わっても、同じように開けるようにするためである。デモの HTML は、DS の `../ds/tokens.css`・`../ds/components.css`・`../ds/components.js` と、`player/player.css`・`player/player.js` を読み込む。見本の `仮説デモ_C-02_S-02.html` の `<head>` を写し、パスだけを変えると早い。

## 5. 台本の作り方

台本は、デモの HTML の中で `window.UX_DEMO` に書く JavaScript のオブジェクトである。次の順に作る。

1. **シナリオを選ぶ。** 検証記録の重要シナリオ（S-01…）から、試したい仮説が多く関わり、失敗・中断・引継ぎ・他者の関与のどれかを含むものを選ぶ。正常に終わるだけの流れにしない。マニュアル8章の「デモでは魅力的だが実務で破綻する」を、デモ自体が起こさないためである。1つのデモは1つのシナリオにし、別のシナリオは別のデモにする。
2. **登場人物を決める。** 利用者本人と、その仕事に影響する人（上司、依頼者、管理者、引継ぎの相手、AI エージェントなど）を2〜4人にする。設計ブリーフの「対象ユーザー・状況」と現状と課題の観察記録から作り、役割・背景・根拠のラベルを付ける。根拠のない人物像は [仮定] とする。
3. **場面を分ける。** 将来ジャーニーの場面と状態表の状態に合わせて、6〜10場面にする。各場面に、時刻、場所、画面の名前（状態表の状態名と合わせる）、プロトタイプに当てる状態（`state`）を書く。時刻を書くのは、中断や翌日の再開のような時間の経過が、体験の負担を生むことが多いためである。
4. **手を並べる。** 1場面に3〜8手を置く。手の種類は次の6つで、場面の中で「状況 → 人の発言・心の声 → 画面の操作 → 結果への反応 → 仮説や未確認」の順になることが多い。

| 種類（type） | 表すもの | 見え方 | ラベル |
|---|---|---|---|
| situation | 状況の説明（時刻、締め切り、周りの出来事、画面の説明） | 全幅の灰色の札 | 世界についての主張なら付ける。画面の説明だけなら不要 |
| say | 人の発言 | 人物の印と吹き出し | 必須 |
| think | 心の声 | 点線の吹き出しと小さな丸 | 必須。[推論] か [仮定]。本人がインタビューなどで語った場合だけ [発言] |
| do | 画面の操作 | 操作の札。プロトタイプの対象を枠で強調する | 不要 |
| hypothesis | 設計チームの仮説（H-ID を参照） | 黄色の札。反証条件と確かめ方つき | 仮説の根拠の強さ |
| question | 未確認の前提・確かめたいこと | 点線の青い札。確認先つき | 不要（既定で [仮定]） |

5. **ラベルを付ける。** ラベルの意味は SKILL.md の「証拠の扱い」と同じである。画面では、実際の証拠（[観察] [発言] [資料]）を塗りの札、設計チームが置いたもの（[推論] [仮定] [机上] [AI模擬]）を点線の札で示し、見た人が両者を混同しないようにしている。架空の人物の発言は [仮定]、心の声は原則 [推論] である。一方、依頼者から聞いた事実（「取込の失敗は問い合わせの3割」など）は [発言] として状況の手に入れ、実際の根拠と架空の物語を見分けられるようにする。
6. **仮説の手を置く。** 仮説が試される瞬間、つまり利用者が判断する直前か直後に置く。台本の `hypotheses` に挙げた仮説は、すべて1回以上どこかの場面に出す。反証条件と確かめ方は、体験構造カードや仮説カードから写す。デモを作りながら別の説明（代替説明）を思い付いたら `alt` に書く。
7. **未確認の手を置く。** 台本を書く途中で分からなかったこと、置いた仮定、技術的に確かめるべきことを、その場面に置く。確認先も書く。デモを見たチームが、どの前提が物語を支えているかに気付けるようにするためである。
8. **強調する所を決める。** 操作の手には `highlight`（プロトタイプの要素の CSS セレクター）を付ける。画面のどこを見ればよいかが分からないと、会話と画面のつながりが伝わらないためである。対象の要素には、プロトタイプの側で `id` を付けておく。

台本の分量は、1つのデモで30〜50手を目安にする。多すぎると話し合いの時間がなくなり、少なすぎると中断や失敗の場面を省きがちになる。

## 6. 台本の形式

```js
window.UX_DEMO = {
  id: 'D-01',                                  // デモの ID
  title: '…',                                  // デモの題名
  refs: { case: 'C-02', scenario: 'S-02', iteration: 'iter-01' },
  prototype: '../iter-01/proto-C-02.html',     // デモの HTML から見たプロトタイプのパス
  purpose: '…',                                // このデモで考えたいこと（はじめの札に出る）
  disclaimer: '…',                             // 省略可。はじめの札の注意書きを差し替える
  cast: [{ id, name, initial, role, profile, label, tone, face }],   // tone は 1〜5（人物の印の色。顔の絵では服の色になる）
  // face：人物の印に描く顔。{ hair: 'short' | 'side' | 'long' | 'bob', hairColor: 'black' | 'brown' | 'gray' | 'dark' | 色,
  //        skin: 0〜3 | 色, glasses: true }。省くと id から決まる。face: false にすると initial（頭文字）を出す
  hypotheses: [{ id: 'H-01', text, falsify, check, alt, label }],
  scenes: [{
    id: 'sc-01', title, short, time, place,    // short は上の帯の場面の札に出す短い名前
    screen: '状態表の状態名',                   // 枠の上に「画面：…」と出る
    state: { … },                              // プロトタイプに当てる状態（下を参照）
    highlight, highlightLabel, spot,           // 省略可。場面の最初から強調する
    cast: ['sato', 'tanaka'],                  // 省略可。省くと、手に出てくる人物から作る
    beats: [
      { type: 'situation', when: '状況', text, label, state, screen, highlight },
      { type: 'say', who: 'sato', text, label },
      { type: 'think', who: 'sato', text, label },
      { type: 'do', who: 'sato', text, highlight: '#check-btn', tag, spot },
      { type: 'hypothesis', ref: 'H-01', text, falsify, check, label },   // text などを省くと hypotheses から写す
      { type: 'question', text, to }
    ]
  }]
};
```

- **状態の引き継ぎ。** プロトタイプに送る状態は、最初の場面から今の手までの `state` を順に重ねたものである。書いたキーだけが上書きされ、前の場面の値は引き継がれる。前の場面に戻ったときも、同じ計算で状態を作り直して送る。そのため、プロトタイプの `uxDemoApply` は、何度呼ばれても同じ結果になるように書く。値を入れ子のオブジェクトにすると一部だけを上書きできないので、キーは平らにする（`fixed: { phone: true }` ではなく `fixedPhone: true`）。
- **強調の引き継ぎ。** 強調は、同じ場面の中で次に `highlight` を書いた手まで続く。`highlight: null` で消える。場面が変わると消える。`tag` は枠の上に出す短い説明で、操作の手では省くと「人物名：操作」になる。`spot: true` にすると、枠の外を暗くする。
- **手の結果の書き方。** 操作の手では、ボタンを押す前の画面で対象を強調し、押した結果は次の手の `state` で当てる。押す前と押した後が別の手になるので、話し合いのときに「押す前に何が見えていたか」に戻れる。

## 7. プロトタイプの側の準備

プロトタイプには、次の三つを足す（`references/prototype.md` の「デモとの連携」）。

1. `window.uxDemoApply = function (state) { … }` を定義する。受け取った値を既定の状態に重ねて描画し直し、動いているタイマー（処理中の模擬など）を止める。
2. `<script src="../demo/player/demo-bridge.js" defer></script>` を読み込む。iframe の中で開かれたときだけ働き、単独で開いたときは何もしない。
3. 検証用パネルを `html[data-ux-demo]` のときに隠す。デモでは製品の画面だけを見せるためである。

デモは、次へを押すたびに状態を送り、プロトタイプは毎回描き直す。会話だけが進んで状態が前の手と同じときも描き直すが、`demo-bridge.js` が、描き直しで始まった動き（現れるときの浮かび上がり、選択の印の移動など）を最後の形まで進め、強調の枠も点滅させない。画面が変わらないのに動き直すと、見る人の目が会話から画面へ引っ張られるためである。強調する場所だけが変わる手では、枠が移って点滅し、画面の動きは出ない。会話の欄の「もう一度示す」は、同じ画面でも枠を点滅させる。プロトタイプの側で動きを止める処理を書く必要はない。

スマートフォン向けのプロトタイプは、端末の枠（`device.css`・`device.js`）に入れたまま iframe に表示する。端末の枠に入っていると、時刻の帯・下の操作の帯・親指の届く位置と画面の関係を、会話と一緒に見られるためである。このとき、次の五つに気を付ける（見本の `mobile/proto-C-01.html`。タブレットはこの下に続けて書く）。

- 端末の操作盤（`.dv-controls`）は検証用パネルと同じ扱いにし、`html[data-ux-demo]` のときに隠す。
- 端末の下の操作の帯は、3 つのボタン（戻る・ホーム・履歴）にする（`.dv-phone` に `data-nav="buttons" data-nav-fixed`）。戻るボタンが見えていると、利用者が「戻る」でどこへ戻るかを、会話と一緒に確かめられるためである。`data-nav-fixed` を付けないと、ブラウザに保存された端末の設定でジェスチャーの帯に替わることがある。
- 端末の戻るボタン（と、端から払う操作・Esc）は、`device.js` が DS の `ds.back()` を呼ぶ。下に書くとおりシートや画面を状態から描く場合は、`ds.back` を包み、開いているシートを閉じる・詳細から一覧へ戻る、をこの画面の状態で先に行う。戻れないとき（最上位の画面）だけ元の `ds.back` に任せる。包まないと、詳細の画面で戻るを押してもアプリを離れてホーム画面へ移ってしまう。
- 時刻の帯の時刻を、場面の時刻に合わせる。状態に `time` を持たせ、`uxDemoApply` で `.dv-phone` の `data-time` と `.dv-time` の文字を書き換える。場面の時刻と端末の時刻がずれると、見る人が時間の経過を追えなくなるためである。
- シートや画面の進む・戻るは、DS の `ds.open`・`ds.push` を使わず、状態から直接描く（シートは `.ds-scrim` と `.ds-sheet` を描き、詳細の画面では下のタブに `hidden` を付ける）。`ds.open`・`ds.push` は開いている順や戻り先を DS の中に覚えるので、デモで前の場面へ戻ったときに、描き直した画面とその記憶が食い違うためである。プロトタイプを単独で触るときの操作も、同じ描画の関数で動かす。

タブレット向けのプロトタイプも、スマートフォン版の DS と端末の枠を使う。指で押す部品と押せる大きさは、タブレットでも同じだからである。端末の枠は、`.dv-phone` に `data-device="tablet"`（縦、800 × 1280）を付け、横は `data-orientation="landscape"`（1280 × 800）も付ける。縮め方・時刻の帯・下の操作の帯は `device.js` が受け持つ。DS の中の例は `例_タブレット画面_縦.html` と `例_タブレット画面_横.html`、デモの見本は `tablet-portrait/` と `tablet-landscape/` にある。気を付けることは次の二つである。

- DS の `.ds-content` は、中身を幅 640px で中央に寄せる。タブレットの幅を使う画面では、この上限を外すか、一覧と詳細を左右に並べる組み方を画面の CSS で作る。左右に並べる組み方は DS に無いので、DS への追加の候補として記録する。
- 縦は片手で持って歩きながら、横は台やカウンターに置いて、というように、向きによって使い方が変わる。台本の状況の説明に、持ち方と置き場所を書く。押す場所が親指の届く範囲か、手袋のままで押せるか、といった論点は、持ち方から出てくるためである。

`demo-bridge.js` が必要な理由は、`file://` で開いたデモの画面からは、iframe の中のプロトタイプの要素に直接触れないことにある。そこで、デモの画面は `postMessage` で状態と強調する要素を送り、プロトタイプの側の `demo-bridge.js` が状態を当てて枠を描き、対象が見つかったかを返す。

## 8. 確かめること

デモを作ったら、次を確かめてから渡す。

1. デモを開き、「はじめに」の札に「台本の問題（作り手向け）」が出ていないことを確かめる。再生の部品は、人物や仮説の参照の誤り、ラベルの欠落、心の声に証拠のラベルを付けた誤りを、ここに出す。
2. 最初から最後まで一手ずつ進め、プロトタイプの枠の上に警告（「強調する対象が画面にない」「状態を当てられない」「プロトタイプから応答がない」）が出ないことを確かめる。Playwright が使える場合は、デモを開いて `ArrowRight` のキーを送りながら `.uxd-frame__warn` の表示を集めると、全手を機械的に確かめられる。Playwright の設定で `file://` が開けない場合は、保存先で `python -m http.server` などのローカルのサーバーを立てて開く。
3. 場面ごとに、URL の `#s=<場面>&b=<手>` で開いてスクリーンショットを撮り、`demo/screens/` に保存する。撮った画像を自分で見て、強調の枠が対象に重なっているか、会話の欄の文字が切れていないか、画面と会話の内容が食い違っていないかを確かめる。
4. ラベルを読み直す。心の声や架空の人物の発言が [発言] や [観察] になっていないか、逆に依頼者から聞いた事実が [仮定] に埋もれていないかを見る。
5. すべての仮説が1回以上出てくるか、失敗・中断・引継ぎのどれかの場面があるかを確かめる。
6. 台本とプロトタイプに、実在する会社・施設・人物の名前、使われている可能性のある電話番号やメールアドレスが入っていないかを確かめる。架空と分かる形にする決まりは `references/prototype.md` の「データ」にある。デモはプロトタイプより人に見せやすく、実在のものが載っていると誤解のもとになるためである。

## 9. チームで使うときの進め方

デモの画面の操作は、→ / Space で次へ、← で前へ、1〜9 で場面へ移る、P で自動再生、M でその場面へのメモ、C で会話の表示の切り替えである。上の帯の右の設定で、発言・心の声・設計チームの書き込み・根拠のラベル・画面の強調を、それぞれ隠せる。

会話の欄には、最初から台本の全体が並ぶ。今の場面は、これまでの手・今の手・この先の手の順に出し、この先の手は「この先（まだ進めていない）」の区切りの下に、薄く点線で出す。終わった場面とこれからの場面は畳んだ見出しになり、これからの場面には「これから ・ 何手」と付く。見出しを開けば中身を読め、「この場面から見る」か手そのものを押すと、その手へ移る。話し合いの途中で「この後どうなるか」を確かめたいときや、後の場面へ飛んで比べたいときに使う。開いた見出しは、進めても開いたままになる。

会話の欄の上の「会話と解説／解説だけ」で、発言と心の声をまとめて隠せる。「解説だけ」では、状況の説明・画面の操作・仮説・未確認だけが順に出て、画面はこれまでどおり場面に合わせて切り替わる。画面の流れと設計の論点だけを短く追いたいとき（台本の構成を見直すとき、仮説の置き場所を確かめるとき）に使う。隠した手で画面の状態や強調が変わる場合も、その変化は当てる。見せる手が 1 つもなくなる場面は飛ばさず、隠れていることを書いた札を出す。プロトタイプと会話の欄の境目をドラッグすると、会話の欄の幅を変えられる（境目に焦点を当てて ← で広げ、→ で狭める。Home で最大、End で最小、ダブルクリックか Enter で元の幅）。選んだ幅はブラウザに残り、次に開いたときも同じ幅になる。会話を読み込みながら話し合うときは広げ、画面の細部を見るときは狭める。

話し合いは、一人が操作し、場面の終わりごとに止めて行う。各場面で話すのは、次の三つである。

- この人は本当にこう言い、こう思うか。別の解釈はないか。
- この場面で仮説が崩れるとしたら、どんな条件のときか。
- 物語を支えている前提のうち、確かめていないものはどれか。

出た意見は、その場面のメモか、仮説の一覧のメモに書く。メモはブラウザの中にだけ残るので、終わったら「メモ」の欄から Markdown で書き出し、`demo/` に置いてもらう。

受け取ったメモは、次のように設計の記録へ反映する。新しい仮説や代替説明は次の反復の仮説へ、疑わしいと分かった前提は `02_現状と課題.md` の前提台帳へ、確かめるべきことは `00_進行.md` の未解決事項へ、画面や流れの問題は次の反復の A へ入れる。どれも [推論] として書き、反映した先を `デモ記録.md` に残す。チームの意見は実ユーザーの証拠ではないが、何を実ユーザーで確かめるべきかを決める材料になる。
