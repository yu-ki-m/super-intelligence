# UX・UI設計マニュアル

## 1. このマニュアルの目的

ユーザーの仕事を根本から見直し、複数の体験構造を比較しながら、斬新さと使いやすさを両立するための実務手順を定める。

本書の中心は、発散・統合・削減・検証を繰り返すことである。ただし、反復回数や案の数そのものを品質の証拠とはしない。各反復では、未検証の仮説を明確にし、観察結果によって設計判断を更新する。

T3CodeやOrcaは依頼の着想元であり、本書は両製品の制作過程を調査・再現したものではない。以下のAI開発支援ツールの例は架空の設計例である。実際のユーザー調査結果や測定結果ではない。

本書の工程、管理表、回数の例は、本依頼に合わせた実務提案である。発散と収束にはDesign Council、操作品質の点検にはNielsenのヒューリスティクス、アクセシビリティの検証にはWCAGを参考にする。出典の方法論が本書の全手順や数値を保証するわけではない。

## 2. 設計の基本方針

### 2.1 最適化する範囲

対象は、画面を開いてから閉じるまでではなく、ユーザーが必要性を感じ、準備し、作業し、結果を確認し、次の仕事に移るまでである。中断・再開、他者への引継ぎ、失敗後の復旧も含める。

たとえば、実行開始が1クリックになっても、終了後に10分かけて結果を確認する必要があるなら、全体の負担が減ったとは判断できない。

「全体最適」は唯一の最良解を証明する意味では使わない。対象ユーザー、利用状況、業務成果、制約を定めたうえで、工程間・役割間の負担移転まで評価する意味で使う。

### 2.2 新規性の扱い

新規性は、これまで難しかった仕事を成立させる仮説として扱う。見た目の珍しさは、それ自体では採用理由にならない。

たとえば、チャットを大きく表示することよりも、「依頼を送るたびに監視する仕事」から「判断が必要な案件だけを確認する仕事」への変更のほうが、体験構造の再設計に当たる。ただし、その変更が本当に有効かは検証が必要である。

### 2.3 複雑さの扱い

不要な作業はなくす。必要な複雑さは、適切な時点と場所に配置する。説明責任、権限、結果確認など、業務上必要な判断まで消さない。

表示を隠すことと、ユーザーの負担をなくすことは別である。折り畳んだ情報を毎回探さなければならないなら、負担は残っている。

### 2.4 変更する階層

| 階層 | 検討対象 | 変更例 |
|---|---|---|
| 成果・課題 | 誰が何を達成する必要があるか | 実行状況の監視から、成果物を安全に受け入れる判断へ |
| 体験構造 | 仕事の単位、役割、工程、中心概念 | 会話単位から案件単位へ |
| 情報構造・操作 | 何をどこで見て何を行うか | 根拠と承認操作を同じ場所に置く |
| 表現 | 文言、余白、色、動き、見た目 | 状態を色とテキストで示す |

下位の修正を繰り返しても問題が再発する場合は、上位の階層に戻る。中心概念が伝わらない問題を、ツールチップの追加だけで解決し続けない。

## 3. 運営と成果物

設計責任者は、各工程の判断と未解決事項を管理する。調査担当者は観察と解釈を分離する。実装担当者は、状態管理、性能、権限、復旧の実現可能性を早期に確認する。プロダクト責任者は、事業上の優先順位と制約を決める。小規模チームでは兼任してよい。

ユーザーの参加を、関係者の好みの投票で代替しない。AIによるレビューや仮想ユーザーの回答も、実際のユーザーの行動を観察した証拠とは区別する。

成果物は次の関係を追跡できるようにする。

観察記録 → 課題 → 体験仮説 → 設計案 → 検証結果 → 採否判断

例：O-12「再開時に履歴を読み直した」→ P-03「再開に必要な状態が分からない」→ H-02「変更点と未判断事項を先に示せば再開が早まる」→ D-04「再開サマリー」→ T-07「中断再開テスト」→ 決定記録。

変更のたびに文書を増やす必要はない。小規模案件では、一つの表にIDで関連付ければよい。重要なのは量ではなく、採用理由と反証条件を失わないことである。

## 4. プロセス全体

| 工程 | 主な作業 | 成果物 | 次に進む条件 |
|---|---|---|---|
| 0. 設計条件の設定 | 対象、成果、制約、判定基準を決める | 設計ブリーフ | 成功と失敗を判定できる |
| 1. 現状体験の観察 | 実際の仕事と周辺作業を記録する | 現状ジャーニー、観察記録 | 問題を具体的な場面で説明できる |
| 2. 課題と前提の再定義 | 目的、手段、制約、慣習を分ける | 課題一覧、前提台帳 | 維持する前提と変更可能な前提が分かる |
| 3. 体験構造の発散 | 異なる仕事の仕組みを複数作る | コンセプト案 | 案の差が配色や配置だけではない |
| 4. 全体体験の構成 | 開始から確認・復旧までを設計する | 将来ジャーニー、状態表 | 正常系と重要な例外がつながる |
| 5. 統合・削減 | 作業、概念、判断、表示を整理する | 削減記録、比較版 | 削減後も必要な判断と復旧が成立する |
| 6. プロトタイプ化 | 重要な仮説を試せる形にする | 検証用プロトタイプ | 説明に頼らず実際の課題を試せる |
| 7. 検証 | 行動、成果、誤り、回復を測る | 検証記録 | 仮説ごとの支持・反証・未判定が分かる |
| 8. 全体再評価 | 局所改善と全体の負担を比較する | 採否記録、次の検証計画 | 戻る工程か採用条件が決まる |
| 9. 実装・継続評価 | 実データと実環境で成立させる | 実装仕様、運用指標 | 実装後も体験の品質を確認できる |

工程0〜2は最初に実施し、以降も前提が崩れれば戻る。工程3〜8が反復の中心である。工程9で判明した問題も、必要な階層へ戻して扱う。

## 5. 工程ごとの手順と観点

### 工程0. 設計条件の設定

目的は、「誰にとって良い設計か」を決めることである。

手順：

1. 対象ユーザーと利用状況を定義する。職種だけでなく、頻度、熟練度、作業量、権限、中断の多さを記載する。
2. 対象業務の開始条件と完了条件を定める。
3. 現状の基準値を測定する。未測定なら、計測方法と時期を記載する。
4. 主指標と、悪化を認めない条件を定める。
5. 今回変更できる範囲と、確認が必要な制約を記載する。

観点：

- 初心者と熟練者で優先順位は異なるか。
- 操作者の時間短縮によって、確認者や管理者の仕事が増えないか。
- 成功は操作完了か、業務上正しい結果の確定か。
- 速度と正確性が衝突した場合、どちらを優先するか。
- 権限や技術上の制約は確認済みか、単なる思い込みか。

記載例：「複数のAI実行結果を確認する開発者が、中断後も未判断の案件を特定し、根拠を確認して受入可否を決められる。主指標は正しい判断までの時間。重大な誤承認は許容しない」。数値の閾値は、実測と業務上の損失を踏まえて別途設定する。

### 工程1. 現状体験の観察

目的は、画面の不満と、その背後にある仕事の問題を区別することである。

手順：

1. 最近の実例を、入力データ、成果物、履歴とともに再現してもらう。
2. 可能なら実際の仕事を観察する。
3. 画面内の操作と、メモ、コピー、他ツールでの確認、相談、待機を同じ時間軸に置く。
4. 各場面で、目的、必要情報、判断、操作、感情、失敗、回復を記録する。
5. 観察事実、本人の発言、設計者の解釈を別欄にする。

観点：

- ユーザーは何を覚えたまま移動しているか。
- 同じ情報をどこで再入力・再確認しているか。
- 仕事を始められない、止められない、再開できない原因は何か。
- 誤りが起きる前にどのような迷いや兆候があるか。
- 正常に完了したケースだけを見ていないか。
- システム外にある前後工程まで対象にしたか。

例：「一覧が見づらい」という発言に対して、列幅だけを変更しない。「自分が判断すべき案件が分からず、全件を開いている」という行動が観察されれば、優先して検証すべき仮説が変わる。

### 工程2. 課題と前提の再定義

目的は、既存UIを前提にした要求から、変更可能な体験仮説を導くことである。

手順：

1. 要望を「達成したい成果」「現在の手段」「制約」に分ける。
2. 各工程について、誰が、なぜ、それを行う必要があるかを確認する。
3. 前提を「確認済みの制約」「検証可能な仮説」「過去の慣習」に分類する。
4. 課題を、状況・妨げ・影響・望ましい状態で書く。
5. 解決すべき課題の優先順位を、頻度、損失、対象人数、根拠の確かさから決める。

観点：

- 手順を短くする前に、その手順自体をなくせないか。
- 人が判断すべきことと、システムが処理できることを混同していないか。
- 中心概念は会話、ファイル、案件、成果物のどれが仕事に合うか。
- 同期的な監視は本当に必要か。
- 今の組織や製品構成に由来する境界を、ユーザーにも強いていないか。

例：「進捗一覧を追加する」を、「複数案件の中から介入が必要なものを発見できる」に置き換える。前者は解決手段を固定するが、後者からは通知、優先一覧、自動停止、担当分担など複数の案を検討できる。

### 工程3. 体験構造の発散

目的は、異なる仕組みを比較できる状態を作ることである。

手順：

1. 最初は配色や精密なレイアウトを作らず、仕事の流れを文章や簡単な図で表す。
2. 一案につき、中心概念、人とシステムの分担、開始方法、完了確認、例外対応を記載する。
3. 発想軸を変えた案を作る。
4. 各案について、便益だけでなく、学習負担、成立条件、失敗する状況を記載する。
5. 構造が実質同じ案をまとめ、異なる仮説を残す。

発想の観点：

| 軸 | 問い | 案の例 |
|---|---|---|
| 中心となる対象 | 何を一単位として扱うか | 会話、案件、成果物、要判断事項 |
| 時間 | いつ関与すればよいか | 常時監視、節目の確認、例外時の介入 |
| 主導権 | 誰が次の行動を決めるか | 人が指示、システムが提案、範囲内で自動処理 |
| 情報配置 | 何を同時に見せるか | 全件一覧、対象と根拠の併置、概要から詳細へ |
| 作業単位 | 一件ずつ処理する必要があるか | 個別処理、比較、一括処理、条件による分類 |
| 継続性 | 作業を離れても何が残るか | 再開地点、変更点、未判断事項、担当者 |

初回の運用例として、異なる構造を3〜5案作り、重要な仮説の異なる2〜3案を試作する。これは案数の目安であり、多ければ品質が上がるという基準ではない。

### 工程4. 全体体験の構成

目的は、魅力的な一場面を、継続して使える体験につなぐことである。

手順：

1. 利用開始、準備、実行、介入、確認、完了、再開をつなぐ。
2. 各場面に、必要情報、選択肢、操作結果、次の行動を配置する。
3. 未開始、処理中、入力待ち、部分成功、失敗、取消、完了などの状態を定める。
4. 状態ごとに、責任者、許可される操作、保持するデータ、遷移条件を定める。
5. 重要な例外を、同じ概念モデルの中で説明できるか確認する。

観点：

- 現在の対象、状態、次に行うことを識別できるか。
- ユーザーの判断地点に、判断根拠があるか。
- 情報量が10倍になっても構造が成立するか。
- 中断、権限変更、通信切断、同時編集で何が起こるか。
- 初回利用と毎日の利用で、同じ説明を強制していないか。
- 他者への引継ぎで、経緯と未決事項が失われないか。

AI機能を含む場合は、提案と実行済み結果、推測と確認済み事実を区別する。実行範囲、変更対象、停止、取消可能性、失敗後の再試行を設計する。「何でもチャットで指示できる」だけでは、状態と権限の設計を代替できない。

### 工程5. 統合・削減

目的は、価値と判断可能性を保ちながら負担を減らすことである。

手順：

1. 作業、画面、概念、入力、判断、通知、設定を列挙する。
2. 各項目を、残す、統合する、自動化する、必要時に提示する、削除する、に仮分類する。
3. 削減によって負担が誰のどの工程へ移るかを記載する。
4. 変更前後の同じシナリオを比較する。
5. 根拠が弱い削減は、比較用の分岐案として保持する。

| 操作 | 適用条件 | 確認する副作用 |
|---|---|---|
| 残す | 判断、理解、復旧に必要 | 常時表示が必要か |
| 統合する | 対象、目的、権限、実行時点が近い | 画面密度や操作の意味が複雑にならないか |
| 自動化する | 判断基準と処理範囲が定義できる | 誤処理の検知、停止、修正が可能か |
| 必要時に提示する | 現時点で判断に不要 | 必要になった際に発見できるか |
| 削除する | 必要な成果への寄与がない | 周辺作業や手作業を発生させないか |

観点：

- 画面数ではなく、ユーザーが覚える概念数や判断回数が減ったか。
- 表示を消しても、操作結果を予測できるか。
- 確認を省略しても、誤処理を防ぐ別の手段があるか。
- 情報を一画面にまとめた結果、比較しにくくなっていないか。
- 熟練者の高速操作と、初心者が発見できる経路を両立できるか。

削減記録の例：「常時表示のログを概要表示へ変更。ログは失敗原因の確認時に必要。エラー箇所へ直接移動できる経路を残す。原因特定が遅くなれば再検討する」。

### 工程6. プロトタイプ化

目的は、最も不確かな仮説を、必要十分な精度で試すことである。

| 不確かな点 | 適した試作 | 確認できること |
|---|---|---|
| 仕事の流れや分担 | シナリオ、紙、役割演技 | 前後関係、不要な工程、引継ぎ |
| 概念や情報構造 | 低精度の画面遷移 | 用語理解、対象の発見、操作の予測 |
| 判断と操作 | 操作可能なプロトタイプ | 根拠確認、比較、取消、復旧 |
| 並列処理や大量データ | 実装に近い試作 | 状態更新、性能、情報密度、中断再開 |
| 視覚・アクセシビリティ | 実際のHTML等 | フォーカス、拡大、読み上げ、コントラスト |

観点：

- 比較案の作り込みに差があり、見た目だけで優劣が決まらないか。
- 長い名前、欠損、失敗、長時間処理、多数案件を含んでいるか。
- 重要な判断を、実装していない領域に隠していないか。
- 模擬動作と実際に動く部分を記録したか。

架空の成功結果だけを表示する試作では、誤りの検知や信頼の適切さを評価できない。意図的に不完全な結果も用意する。

### 工程7. 検証

目的は、「良さそう」という感想から、行動と成果に基づく判断へ移ることである。

手順：

1. 仮説、反証条件、対象者、課題、観察項目、合否基準を先に決める。
2. 代表的な通常業務に加え、中断再開、重要な失敗、引継ぎを試す。
3. 操作方法を教えず、達成すべき目的と利用状況を伝える。
4. 成否、時間、誤り、援助、迷い、戻り操作、判断根拠を記録する。
5. 終了後に、ユーザーが状態と操作結果をどう理解していたか確認する。
6. 観察事実と原因仮説を分けて整理する。

観点：

- 見つけられるか、意味を理解できるか、正しく判断できるか、操作できるかを分けて見る。
- 自信を持って誤判断していないか。
- 操作速度が上がっても、結果確認を省略しているだけではないか。
- 初回の理解と反復利用の習熟を別に確認したか。
- 設計者の説明がなければ成立しない箇所はどこか。

| 評価対象 | 測定例 | 解釈上の注意 |
|---|---|---|
| 業務成果 | 正しい結果まで到達した件数／試行数 | 操作完了と正しい成果を分ける |
| 時間 | 準備から結果確認までの経過時間、人の作業時間 | 待機時間を分離し、同じ条件で比較する |
| 判断 | 誤承認、見落とし、根拠確認 | 重大な誤りを平均値に埋めない |
| 継続性 | 中断から正しい操作に復帰するまでの時間 | 中断時間や課題の複雑さをそろえる |
| 学習 | 初回と再利用時の援助回数 | 同じ課題の暗記による改善を区別する |
| 回復 | 誤操作から復旧できた件数と時間 | 復旧不能な操作の有無を確認する |
| 主観 | 難しさ、安心感、負担の評価と理由 | 行動記録と照合する |

少人数の観察は問題の発見に使う。成功率や改善率を一般化するには、対象者構成、試行数、ばらつき、比較条件を考慮した別の評価設計が必要である。参加者数を固定の万能基準にしない。比較順による学習を抑えるため、順序の入替えや同等難度の別課題を使用する。

### 工程8. 全体再評価

目的は、局所改善による負担移転を検出し、次に戻る階層を決めることである。

手順：

1. 各案を、同じユーザー・シナリオ・判定基準で比較する。
2. 開始から確認、引継ぎ、再開、復旧までを再点検する。
3. 改善、悪化、未検証を分ける。
4. 採用、条件付き採用、再設計、棄却、保留を決定する。
5. 次の反復では、判断を最も変え得る未検証事項を優先する。

戻る工程の目安：

| 観察された問題 | 戻る工程 | 次に確かめること |
|---|---|---|
| 正しく使えても仕事が改善しない | 0〜2 | 課題と対象者を誤っていないか |
| 中心概念が理解されない | 2〜4 | 仕事の単位や役割分担が適切か |
| 次の行動や根拠が分からない | 4〜5 | 情報の配置や削減が適切か |
| ラベルや操作対象を誤認する | 5〜6 | 表現と操作の対応が明確か |
| 大量データや遅延で破綻する | 4・6 | 構造と技術条件が両立するか |

全体再評価の観点：

- 操作者の改善が、確認者や管理者の負担増になっていないか。
- 通常時の簡潔さが、障害時の復旧困難を生んでいないか。
- 初心者と熟練者、少量と大量、短時間と長時間で成立するか。
- 便利な例外機能の追加によって、全体の概念が矛盾していないか。
- 事前に定めた優先順位を、気に入った案のために変えていないか。

採用の最低条件は、主要な価値が支持され、重大な誤操作や回復不能な問題が解消され、重要なシナリオで大きな退行がなく、実装可能性が確認されていることである。未検証事項が残る場合は、公開範囲、監視項目、撤回条件を決める。

期限が来たことと品質条件を満たしたことを区別する。期限で終了する場合は、確認できた範囲を限定して記録する。

### 工程9. 実装・継続評価

目的は、試作で成立した体験を、実際の性能、データ、権限の下で保つことである。

実装へ渡す情報：

- ユーザー、目的、対象シナリオ、優先順位。
- 情報の意味、データの出所、更新時点。
- 状態一覧、遷移条件、処理中・失敗・空状態の表示。
- 操作可能条件、権限、取消・復旧の仕様。
- キーボード操作、フォーカス移動、読み上げに必要な情報。
- 大量データ、遅延、通信切断時の振る舞い。
- 採用理由、代替案を棄却した理由、未検証事項。
- 受入条件と、公開後に観察する指標。

観点：

- 実装都合の変更で、判断根拠や復旧経路が失われていないか。
- 実データでの視認性と応答性を確認したか。
- アクセシビリティを見た目だけで判定していないか。
- 操作ログだけでは分からない困難を、問い合わせや観察で補っているか。
- 継続利用で増えた設定や機能が、中心概念を崩していないか。

アクセシビリティはWCAG 2.2を参照し、対象範囲に応じた適合目標を定める。自動検査だけで完了扱いにせず、キーボード、読み上げ、拡大等による確認を組み合わせる。上記の点検項目だけでWCAGへの適合を主張しない。

## 6. 反復の具体例

以下は架空のAI開発支援ツールでの設計演習である。結果の欄は、実測結果ではなく、次の判断へ進む場合の例である。

| 反復 | 仮説と案 | 検証で判明し得る問題 | 次の変更 |
|---|---|---|---|
| 1 | 複数の会話を同時表示すれば監視しやすい | 表示量が増え、どこに介入すべきか分からない | 会話の一覧から案件と状態の一覧へ |
| 2 | 要判断案件を先頭にすれば介入先が分かる | 判断対象は分かるが、根拠を探すため画面を移動する | 判断項目、差分、検証結果を同じ文脈に置く |
| 3 | 判断情報を一画面にまとめれば速くなる | 情報が多すぎて、重要な差分を見落とす | 概要と重要な根拠を先に示し、詳細への経路を残す |
| 4 | 根拠を整理すれば短時間で承認できる | 中断後に、すでに確認した部分を再確認する | 前回確認位置、追加変更、未判断事項を保存する |
| 5 | 再開状態を保存すれば継続利用が安定する | 他者の更新により古い確認結果を使う | 更新時点と再確認が必要な差分を示す |

この例で積み重なるのは、機能数だけではない。仕事に関する理解、検証結果、採用理由が積み重なる。一方、検証で不要と分かった機能や前提は削除する。

各反復で、以前の重要シナリオも再確認する。新しい改善だけを確認すると、直前の版で成立していた体験を壊しても気付けない。

## 7. 再利用する記録様式

### 7.1 設計ブリーフ

| 項目 | 記入内容 |
|---|---|
| 対象ユーザー・状況 | 誰が、いつ、どの程度の頻度と量で利用するか |
| 達成する成果 | 何ができたら業務上の成功か |
| 対象範囲 | 開始条件、終了条件、含む例外 |
| 現状と根拠 | 観察記録、基準値、未測定事項 |
| 主指標 | 最も改善したい成果 |
| 悪化を認めない条件 | 正確性、復旧、権限、アクセシビリティ等 |
| 変更可能な前提 | 画面、工程、役割、データ、運用等 |
| 制約と確認先 | 確認済みか未確認かも記載 |

### 7.2 仮説カード

| 項目 | 記入内容 |
|---|---|
| 仮説ID・関連課題 | どの観察と課題に対応するか |
| 仮説 | 何を変えると、誰の何が、なぜ改善するか |
| 代替説明 | 改善しても別の理由ではないか |
| 反証条件 | どの結果なら仮説を見直すか |
| 試す案 | 比較する構造と、変えない条件 |
| 検証方法 | 対象者、課題、観察・計測内容 |
| 結果 | 事実、解釈、制約を分離 |
| 決定 | 採用・再設計・棄却・保留と理由 |

### 7.3 削減記録

| 対象 | 必要な価値 | 変更方法 | 負担の移転先 | 検証結果 | 復元条件 |
|---|---|---|---|---|---|
| 記入 | 誰の何の判断に必要か | 残す・統合・自動化・必要時提示・削除 | 誰のどの作業が増えるか | 観察された事実 | どの悪化で戻すか |

### 7.4 反復終了時の記録

毎回、次の七点を短く残す。

1. 今回解こうとした問題。
2. 比較した異なる仮説。
3. 実際に変更した体験と操作。
4. 観察された改善と悪化。
5. 残すもの、統合するもの、削るもの。
6. 未検証事項と、次に戻る工程。
7. 判断責任者と、判断を見直す条件。

## 8. レビューで防ぐ失敗

| 失敗 | 起きる理由 | 対応 |
|---|---|---|
| 画面案は多いが体験が同じ | 配色や配置だけを発散している | 中心概念、時間、主導権、作業単位を変える |
| 継ぎ足しで複雑になる | 個別要望だけを評価している | 概念と状態の整合性を毎回確認する |
| 簡潔だが使えない | 判断根拠や発見経路を削っている | 削減前後の同じ課題を比較する |
| デモでは魅力的だが実務で破綻する | 正常系と少量データしか扱わない | 中断、例外、大量データ、引継ぎを試す |
| 改善したという証拠が弱い | 感想、好み、クリック数だけで判断する | 正しい成果、確認、復旧まで計測する |
| 反復しても進展しない | 毎回同じ階層しか変更しない | 問題の定義と中心概念に戻る |
| 新しいUIをユーザーが理解できない | 新規性の利益と学習コストを比較していない | 慣れた経路との比較と再利用テストを行う |
| 終了できない | 合否基準も残存リスクの扱いもない | 採用条件、期限、保留範囲を先に定める |
