# 机上検証の方法

AIは実際のユーザーを観察できないため、ここでの検証は「問題を見つけること」が目的である。改善を証明するものではない。見つからなかった問題は、なかったのではなく、この方法では見えなかった可能性がある。

## 1. 重要シナリオを決める

最初の反復で、次の種類からシナリオを作り、ID（S-01…）を付ける。以後の反復でも同じシナリオを使い続ける。毎回同じシナリオを使うことで、反復の前後を比べられ、回帰にも気付けるため。

| 種類 | 例（AIエージェント管理ツールの場合） |
|---|---|
| 通常業務 | 朝、夜間に動いた8件の実行結果を確認し、受け入れるものを決める |
| 初回利用 | 初めて開いた人が、最初の依頼を出して結果を受け入れる |
| 中断からの再開 | 3件確認したところで会議に呼ばれ、2時間後に戻る |
| 重大な失敗 | 実行の1件が誤った変更を含み、テストは通っている |
| 引継ぎ | 休暇に入る人の未判断の案件を、別の人が引き継ぐ |
| 量が10倍 | 80件が同時に動いている |
| 他者による更新・権限 | 確認中に別の人が同じ案件を承認した |

各シナリオに、開始時の状態、ユーザーの目的、正しい成果（操作の完了ではなく、業務上正しい結果）を書く。

## 2. シナリオ走査

シナリオごとに、プロトタイプ上で一手ずつ進め、次の表を作る。

| 手 | ユーザーが知る必要があること | 画面にあるか（どこに） | 行う操作 | 起こりうる誤り | 回復手段 | 見つけられる | 意味が分かる | 正しく判断できる | 操作できる |
|---|---|---|---|---|---|---|---|---|---|

最後の四列は「○・△・×」で判定する。四つを分けるのは、原因によって戻る工程が違うためである。見つけられないなら情報配置（工程4〜5）、意味が分からないなら概念や表現（工程2〜6）、判断できないなら判断根拠の配置（工程4〜5）、操作できないなら操作の設計（工程5〜6）に戻る。

走査の終わりに、ユーザーがその時点の状態と操作の結果を正しく理解しているはずかを書く。「自信を持って誤判断する」場面（例：テストが通っているので誤った変更を承認する）を、とくに探す。

## 3. ヒューリスティクス点検

Nielsen Norman Group の10のヒューリスティクスで、見つかった問題だけを記録する。全項目に「問題なし」と書き並べる必要はない。

1. システム状態の可視性
2. システムと実世界の一致
3. ユーザーによる制御と自由（取消・やり直し）
4. 一貫性と標準（デザインシステムを使う場合は、同じ部品が同じ意味で使われているか、追加提案の部品が既存の部品と見分けにくく誤解を生まないかも見る）
5. エラーの防止
6. 記憶より認識
7. 柔軟性と効率（熟練者の近道）
8. 美的で最小限のデザイン
9. エラーの認識・診断・回復の支援
10. ヘルプとドキュメント

## 4. デザインシステムの追加提案の確認

デザインシステム（既定の DS を含む）を使い、追加提案（DS-01…）がある場合に行う。提案ごとに、検証用パネルで提案版と代用版を切り替え、提案に関係するシナリオを両方で走査する。走査表の四つの判定（見つけられる・意味が分かる・正しく判断できる・操作できる）と、一つの仕事を終えるまでの手数・判断の回数を並べて記録し、差がどの手で、なぜ出たかを書く。×だけでなく、△と○の差や、手数・判断の回数の差も差として扱う。提案版が代用版より良くならなければ、その提案は取り下げて代用にする。「既存の部品では最善にならない」という判定は、この比較で裏付けられて初めて提案として残す価値があるためである。

## 5. AI模擬評価

Agent ツールが使える場合に行う。別のエージェントを起動し、次だけを渡す。

- 利用者としての状況（職種、熟練度、今の目的）。シナリオの「開始時の状態」と「目的」をそのまま使う。
- プロトタイプのパスと開き方（Playwright が使えれば実際に開いて操作させる。使えなければスクリーンショットと、画面に表示される文字だけを渡す）。
- 検証用パネルは製品の一部ではないこと。

設計文書、仮説、設計意図は渡さない。HTML のソースコードを読ませる場合は、表示されない情報（コメントや非表示要素）を手がかりにしないよう指示する。

依頼する内容は、目的を達成するまで、各手で「今何が起きていると思うか」「次に何をするか、なぜか」「迷ったこと」を書きながら進むこと、そして最後に「今の状態」と「自分の操作の結果」を説明することである。マニュアル工程7の「操作方法を教えず、目的と状況だけを伝える」に当たる。

結果は [AI模擬] として記録する。AIは画面の構造を人より速く読み取り、人が持つ思い込みや疲れを持たないため、所要時間や成功率の推定には使わない。使うのは、設計者の説明がなければ成り立たない箇所や、言葉や状態表示の誤解を見つけるためである。

## 6. 仮説ごとの判定

| 判定 | 使う条件 |
|---|---|
| 机上で破綻なし | 関連するシナリオをすべて走査し、×がない |
| 机上で問題あり | ×があり、原因の見当が付いている（戻る工程を書く） |
| 未判定 | 実ユーザーの行動、実データ、性能や技術の確認がないと判定できない |

「支持された」「反証された」は、実ユーザーでの検証の結果にだけ使う。

## 7. 実ユーザー検証の計画に引き継ぐこと

机上検証の後、実ユーザーで確かめる項目をマニュアル工程7の表（業務成果、時間、判断、継続性、学習、回復、主観）から選び、`09_実装引継ぎ.md` の検証計画に書く。追加提案の部品がある場合は、それが説明なしに理解されるかも確かめる項目に含める。少人数の観察は問題の発見に使い、成功率や改善率の一般化には別の評価設計が要ることも書き添える。
