# プロトタイプの作り方

プロトタイプの目的は、最も不確かな仮説を、必要十分な精度で試すことである（マニュアル工程6）。見せるためのデモではなく、壊れる場面を見つけるための道具として作る。

## 精度の選び方

不確かな点に合わせて精度を選ぶ（マニュアル工程6の表）。仕事の流れや分担が不確かな段階なら、シナリオ文と簡単な画面遷移で足りる。判断・比較・取消・復旧が論点なら、操作できるHTMLが要る。並列処理や大量データが論点なら、件数と状態更新を模擬できるHTMLが要る。反復が進むほど精度を上げてよいが、論点と関係のない見た目の作り込みはしない。

## 形式

- 1案につき1ファイルの HTML（`iter-NN/proto-<案ID>.html`）。CSS と JavaScript はファイル内に書き、外部の CDN やフォントを読み込まない。オフラインでも、何か月か後でも同じように開けるようにするため。ただし、デザインシステム（既定の DS を含む）の CSS・JavaScript は、保存先の `ds/` に複製したものを相対パスで読み込む（`references/design-system.md` の7章）。複製なので、同じ目的は保たれる。
- フレームワークは使わず、素の HTML・CSS・JavaScript で書く。状態の切替えは、一つの状態オブジェクトと描画関数で行うと、シナリオの切替えが簡単になる。ただし、処理中の進み具合や経過時間のように、同じ画面のまま短い間隔（1 秒以下）で変わる値は、画面を丸ごと描き直さず、変わる所（数値、棒の長さ）だけを書き換える。丸ごと描き直すと部品が作り直され、DS の現れるときの動きや読み込み中の回転が毎回最初から動いて、画面がちらつくためである。
- ファイル冒頭のコメントに、案ID、反復番号、検証する仮説、模擬している部分（例：AIの実行結果は固定データ、待ち時間は setTimeout）、未実装の部分を書く。デザインシステムを使う場合は、基準にした DS と版、選んだ見た目、使った DS 外の部品（提案ID）、再現できなかった部分も書く。

## データ

架空の業務に即したデータを使い、ダミー文字列（lorem ipsum、「テスト1」など）は使わない。ダミーでは、名前の長さや情報の重要度の差が現れず、実際の見落としが起きないため。

ただし、実在する会社・団体・施設・製品の名前、使われている可能性のある電話番号やメールアドレス、実在の人物を使わない。プロトタイプやデモは社外の人にも見せることがあり、実在のものが載っていると、その会社や人の情報を扱っているように見え、問い合わせや誤解のもとになるためである。架空と分かる形にする。

- 会社・施設の名前：「サンプル精機株式会社」「見本ホール」のように、サンプル・見本・架空・例示などの語を含める。長さや英字の混在は、この形のまま作れる。
- 電話番号：市内局番を 0000 にする（例：03-0000-1007）。0 で始まる市内局番は割り当てられないためである。
- メールアドレス・URL：例示用に予約されたドメイン（example.com、example.org、example.net。RFC 2606）を使う。

依頼者から実データを受け取って使う場合は、この決まりに当たらないが、社外に見せる前に扱いを確かめる。画面には「見本」「架空のデータ」のような表示を出さない。架空であることは名前・番号・アドレスの形で分かり、画面に札や注記を足すと、製品の画面にない要素が増えて見る人の邪魔になるためである。

次を必ず含める。

| 種類 | 例 | 確かめること |
|---|---|---|
| 長い名前 | 60文字を超える案件名、英数字と日本語の混在 | 折返し・省略で区別できなくならないか |
| 欠損 | 担当者なし、説明が空、更新日時が不明 | 空欄の意味が分かるか |
| 失敗・部分成功 | 10件中3件が失敗、途中で停止 | 失敗に気付き、原因と回復手段にたどり着けるか |
| 長時間の処理 | 数十分かかる処理、進捗が止まって見える処理 | 待っている間に別の仕事ができるか |
| 大量 | 50件以上（JavaScript で生成してよい） | 構造が保てるか、優先すべきものが見つかるか |
| 空・1件 | 初回利用、すべて完了済み | 次に何をすればよいか分かるか |
| 他者による更新 | 確認中に別の人が変更した | 古い情報で判断しないか |
| 権限不足 | 承認権限がない人が開いた | できない理由と代わりの経路が分かるか |
| 意図的に不完全な結果 | AIの提案に誤りが混じる | 誤りを見抜ける根拠が画面にあるか |

## 検証用パネル

画面の端に、製品のUIとは見た目をはっきり変えた「検証用」パネルを置き、シナリオ（通常／初回／中断後の再開／重大な失敗／大量／空／他者による更新）を切り替えられるようにする。デザインシステムを使う場合は、DS 外の部品の一覧と、提案版・代用版の切替えもここに置く。キー操作（例：`Shift+?`）で隠せるようにし、スクリーンショットでは隠した状態も撮る。パネルがあると、シナリオ走査とAI模擬評価で同じ状況を何度でも再現できるため。AI模擬評価に渡すときは、パネルが製品の一部ではないことを伝える。

URL のハッシュ（例：`proto-C-01.html#scenario=failure`）でもシナリオを指定できるようにすると、Playwright で状態ごとのスクリーンショットを撮りやすい。

## 案どうしの公平さ

比べる案は、同じデータ、同じ基本スタイル（文字の大きさ、色、余白の基準）で作る。違いは、中心となる対象、情報の配置、操作の流れなど、構造に限る。片方だけ作り込むと、構造ではなく見た目の完成度で優劣が決まってしまうため。

## 見た目

見た目の基盤には、ユーザーが指定したデザインシステム、指定がなければ同梱の既定の DS（`<SKILL_DIR>/sample-design-system/`）を使う。読み込み方は `references/design-system.md` の「既定のデザインシステム」の節と7章に従う。ユーザーが DS を使わないと明示した場合だけ、落ち着いた中立の配色にし、装飾に時間をかけない。DS にない部品（追加提案）の作り方、製品の画面に「提案」と出さない理由、検証用パネルで代用版に切り替える方法は `references/design-system.md` の7章に従う。どちらの場合も、斬新さは構造で出す。状態は色だけでなく、テキストやアイコンでも示す。提案と実行済みの結果、推測と確認済みの事実は、表示の形（ラベル、枠、文言）で区別する。

## 基本的なアクセシビリティ

- 操作要素には `button`・`a`・`input` などの意味のある要素を使い、見出しは階層どおりに `h1`〜`h3` を使う。
- すべての操作をキーボードで行えるようにし、フォーカスが見えるようにする。
- 入力欄にはラベルを付け、状態の変化（処理の完了、失敗）は `aria-live` で伝える。
- 本文の文字と背景のコントラスト比は 4.5:1 以上を目安にする。
- 200% に拡大しても、横スクロールなしで主要な操作ができるようにする。

これらは最低限の点検であり、WCAG への適合を意味しない。

## 動かす範囲

仮説に関わる操作（判断、比較、取消、復旧、再開）は実際に動かす。動かない部分を残す場合は、画面上で「未実装（検証対象外）」と示す。重要な判断を、実装していない領域に隠さない。隠すと、検証で「問題なし」と判定してしまうため。

## デモとの連携

デモ（`references/demo.md`）を作る場合は、プロトタイプに次の三つを足す。デモを作らない場合は不要だが、最初から足しておくと、あとでデモを頼まれたときにプロトタイプを作り直さずに済む。

- `window.uxDemoApply = function (state) { … }` を定義する。受け取った値を既定の状態に重ねて描画し直し、動いているタイマー（処理中の模擬など）を止める。デモでは前の場面へ戻るたびに全体の状態が送られるので、何度呼ばれても同じ結果になるように書く。状態のキーは平らにする（入れ子にすると、一部だけを上書きできない）。
- `<script src="../demo/player/demo-bridge.js" defer></script>` を読み込む。iframe の中で開かれたときだけ働き、デモの画面から送られた状態を当て、強調する要素に枠を描く。単独で開いたときは何もしない。
- 検証用パネルは `html[data-ux-demo]` のときに隠す。デモでは製品の画面だけを見せるため。

デモで強調する要素（主な操作のボタン、判断に使う数値、状態の表示）には `id` を付ける。見本は `<SKILL_DIR>/sample-demo/proto-C-02.html`（PC）、`mobile/proto-C-01.html`（スマートフォン）、`tablet-portrait/proto-C-01.html`（縦のタブレット）、`tablet-landscape/proto-C-01.html`（横のタブレット）。スマートフォンとタブレットの場合の注意は `references/demo.md` の7章にある。

## 撮影と目視

Playwright（MCP やスクリプト）が使える場合は、`file://` でプロトタイプを開き、シナリオごとにスクリーンショットを `iter-NN/screens/` に保存する。撮った画像を自分で見て、文字の重なり、はみ出し、情報の密度、優先すべきものが目に入るかを確かめる。Tab キーを順に押してフォーカスの移動順も確かめる。使えない場合は、HTML を読んで走査し、目視していないことを検証記録に書く。
