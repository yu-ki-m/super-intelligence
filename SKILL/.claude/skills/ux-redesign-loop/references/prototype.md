# プロトタイプの作り方

プロトタイプの目的は、最も不確かな仮説を、必要十分な精度で試すことである（マニュアル工程6）。見せるためのデモではなく、壊れる場面を見つけるための道具として作る。

## 精度の選び方

不確かな点に合わせて精度を選ぶ（マニュアル工程6の表）。仕事の流れや分担が不確かな段階なら、シナリオ文と簡単な画面遷移で足りる。判断・比較・取消・復旧が論点なら、操作できるHTMLが要る。並列処理や大量データが論点なら、件数と状態更新を模擬できるHTMLが要る。反復が進むほど精度を上げてよいが、論点と関係のない見た目の作り込みはしない。

## 形式

- 1案につき1ファイルの HTML（`iter-NN/proto-<案ID>.html`）。CSS と JavaScript はファイル内に書き、外部の CDN やフォントを読み込まない。オフラインでも、何か月か後でも同じように開けるようにするため。
- フレームワークは使わず、素の HTML・CSS・JavaScript で書く。状態の切替えは、一つの状態オブジェクトと描画関数で行うと、シナリオの切替えが簡単になる。
- ファイル冒頭のコメントに、案ID、反復番号、検証する仮説、模擬している部分（例：AIの実行結果は固定データ、待ち時間は setTimeout）、未実装の部分を書く。

## データ

架空の業務に即したデータを使い、ダミー文字列（lorem ipsum、「テスト1」など）は使わない。ダミーでは、名前の長さや情報の重要度の差が現れず、実際の見落としが起きないため。次を必ず含める。

| 種類 | 例 | 確かめること |
|---|---|---|
| 長い名前 | 60文字を超える案件名、英数字と日本語の混在 | 折返し・省略で区別できなくならないか |
| 欠損 | 担当者なし、説明が空、更新日時が不明 | 空欄の意味が分かるか |
| 失敗・部分成功 | 10件中3件が失敗、途中で停止 | 失敗に気付き、原因と回復手段にたどり着けるか |
| 長時間の処理 | 数十分かかる処理、進捗が止まって見える処理 | 待っている間に別の仕事ができるか |
| 大量 | 50件以上（JavaScript で生成してよい） | 構造が保てるか、優先すべきものが見つかるか |
| 空・1件 | 初回利用、すべて完了済み | 次に何をすればよいか分かるか |
| 他者による更新 | 確認中に別の人が変更した | 古い情報で判断しないか |
| 権限不足 | 承認権限がない人が開いた | できない理由と代わりの経路が分かるか |
| 意図的に不完全な結果 | AIの提案に誤りが混じる | 誤りを見抜ける根拠が画面にあるか |

## 検証用パネル

画面の端に、製品のUIとは見た目をはっきり変えた「検証用」パネルを置き、シナリオ（通常／初回／中断後の再開／重大な失敗／大量／空／他者による更新）を切り替えられるようにする。キー操作（例：`Shift+?`）で隠せるようにし、スクリーンショットでは隠した状態も撮る。パネルがあると、シナリオ走査とAI模擬評価で同じ状況を何度でも再現できるため。AI模擬評価に渡すときは、パネルが製品の一部ではないことを伝える。

URL のハッシュ（例：`proto-C-01.html#scenario=failure`）でもシナリオを指定できるようにすると、Playwright で状態ごとのスクリーンショットを撮りやすい。

## 案どうしの公平さ

比べる案は、同じデータ、同じ基本スタイル（文字の大きさ、色、余白の基準）で作る。違いは、中心となる対象、情報の配置、操作の流れなど、構造に限る。片方だけ作り込むと、構造ではなく見た目の完成度で優劣が決まってしまうため。

## 見た目

落ち着いた中立の配色にし、装飾に時間をかけない。斬新さは構造で出す。状態は色だけでなく、テキストやアイコンでも示す。提案と実行済みの結果、推測と確認済みの事実は、表示の形（ラベル、枠、文言）で区別する。

## 基本的なアクセシビリティ

- 操作要素には `button`・`a`・`input` などの意味のある要素を使い、見出しは階層どおりに `h1`〜`h3` を使う。
- すべての操作をキーボードで行えるようにし、フォーカスが見えるようにする。
- 入力欄にはラベルを付け、状態の変化（処理の完了、失敗）は `aria-live` で伝える。
- 本文の文字と背景のコントラスト比は 4.5:1 以上を目安にする。
- 200% に拡大しても、横スクロールなしで主要な操作ができるようにする。

これらは最低限の点検であり、WCAG への適合を意味しない。

## 動かす範囲

仮説に関わる操作（判断、比較、取消、復旧、再開）は実際に動かす。動かない部分を残す場合は、画面上で「未実装（検証対象外）」と示す。重要な判断を、実装していない領域に隠さない。隠すと、検証で「問題なし」と判定してしまうため。

## 撮影と目視

Playwright（MCP やスクリプト）が使える場合は、`file://` でプロトタイプを開き、シナリオごとにスクリーンショットを `iter-NN/screens/` に保存する。撮った画像を自分で見て、文字の重なり、はみ出し、情報の密度、優先すべきものが目に入るかを確かめる。Tab キーを順に押してフォーカスの移動順も確かめる。使えない場合は、HTML を読んで走査し、目視していないことを検証記録に書く。
