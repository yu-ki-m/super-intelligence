# デザインシステムの扱い

デザインシステム（以下「DS」）を使う場合に読む。ユーザーが指定しなかった場合も、次の節の既定の DS を使うので読む。DS とは、製品群で共通に使うデザイントークン（色・文字・余白などの値）、コンポーネント（ボタン、表、ダイアログなどの部品）、パターン（フォーム、空状態、エラー表示などの組み合わせ方）、利用ガイドライン（どの場面で何を使うか）をまとめたものである。

## 1. 尊重の程度

このスキルでは、指定された DS を「尊重する」。尊重とは、次の二つを同時に守ることである。

- 画面要素を決めるときは、DS の既存のトークン・部品・パターンを第一候補にする。DS から外れるときは、必ず理由を記録する。
- ただし、DS に合わせることを、体験の質より優先しない。判定の基準は「既存の部品を適用できるか」ではなく「既存の部品が最善か」である。既存の部品に当てはめると、判断地点の根拠が欠ける、状態を区別できない、取消や復旧ができない、量が10倍で破綻する、設計ブリーフの「悪化を認めない条件」を破る、といった使えなくなる場合だけでなく、使えるが手数や判断の回数が増える、意味が分かりにくくなる、といった場合も、その部品を使わず、DS に新しいデザインを組み込むことを提案する。

この二つを両立させる理由は、DS の性質にある。DS は、それまでの製品の仕事に合わせて作られている。このスキルが体験構造を変えると、新しい仕事の単位（例：会話ではなく「要判断事項」を一単位にする）や、新しい状態（例：AIの提案と実行済みの結果の区別）を表す部品が、DS に存在しないことがある。それを既存の部品に無理に当てはめると、構造の変更が画面で伝わらず、反復で作った体験が実装の段階で失われる。反対に、DS を無視して独自の部品を増やすと、利用者は同じ操作を別の見た目で覚え直すことになり、製品内の一貫性と、実装・保守の効率（同じ部品を使い回せること）が損なわれる。そのため、既存の部品が最善である所は DS に従い、最善でない所は、理由と仕様を付けて DS の管理者に提案する。「一応使える」既存の部品で済ませると、利用者は毎日その小さな手間や迷いを負い続けるため、適用できることを DS に従う理由にはしない。

このスキルは DS のファイル（トークン定義、部品のコード、Figma など）を直接書き換えない。DS への追加を決めるのは DS の管理者であり、このスキルが出すのは提案である。

## 既定のデザインシステム

ユーザーが DS を指定せず、既存製品の DS も見当たらない場合は、このスキルに同梱した汎用のデザインシステム `<SKILL_DIR>/sample-design-system/`（以下「既定の DS」）を、指定されたものとして扱う。既存製品の DS が分かった場合は、既定の DS より既存製品の DS を優先する（下の表）。このファイルと SKILL.md で「DS が指定されている」と書く場合は、既定の DS を当てはめた場合を含む。

既定の DS を置く理由は二つある。一つは、DS がないと、どの状態をどの部品で表すかが決まらないまま実装へ渡り、実装者がそれを改めて決めることになるためである。もう一つは、DS がないと「既存の部品では最善にならない所」を見つける機会もなくなるためである。既定の DS は、業務画面と作業道具の画面のための部品（表、深刻度、判定、根拠の札、ターミナル、分割画面など）を持っているので、このスキルが扱う画面の多くに当てはめられる。

尊重の程度と、追加を提案する基準は、ユーザーが指定した DS と同じである（1章・5章）。既定の DS への追加提案の宛先は、この汎用 DS の管理者（このスキルの利用者）になる。

### 既定の DS を使わない場合

| 状況 | 扱い |
|---|---|
| ユーザーが別の DS を指定した | 指定された DS を使う |
| ユーザーが DS を使わないと明示した | DS を使わず、`references/prototype.md` の中立の見た目で作る。対応表と追加提案は作らない |
| 資料やコードから既存製品の DS が分かった（共通部品のパッケージ、トークンの定義ファイルなど） | 既存製品の DS を使う。既存の画面と見た目がそろい、実装で部品を作り直さずに済むためである。工程0の前の壁打ち（`references/kickoff.md`）の最初の応答で、それで進めると仮置きを示す。違うと言われなければ既存製品の DS で進め、[仮定] として記録し、確認事項に入れる |

既定の DS を使った場合は、`01_設計ブリーフ.md` の「デザインシステム」の行に「既定（ユーザー未指定のため同梱の sample-design-system を適用）」と書き、最終報告でも伝える。ユーザーが選んだ DS ではないことを後から区別でき、別の DS に替えたい場合に気付けるようにするためである。

### 既定の DS の読み方

2章の表の内容は、次の順に読むと分かる。

1. `README.md` を最初に読む。ファイルの構成、二つの見た目、原則、部品の一覧、動きと暗い画面の決まりが書かれている。
2. `tokens.css` で意味トークンの名前（`--ds-color-text-body` など）を確かめる。基本パレット（`--ds-neutral-*`、`--ds-primary-*`）は画面で直接使わない。直接使うと、見た目や明るさを切り替えても色が変わらないためである（README の決まり）。
3. 使う部品の HTML の作りは `index.html` で確かめる。大きなファイルなので、全文を読まず、使う部品のクラス名で検索して該当する節を読む。部品の組み合わせ方は `例_コンソール画面.html` と `例_作業台画面.html` を見る。

見た目は、README の表に沿って画面の性質で選ぶ。中身を読み書きする作業道具（エディター、AIツールなど）ならミニマル（既定）、一覧と設定が中心の業務画面（管理画面など）ならコンソール（`<html data-look="console">`）とする。選んだ理由をブリーフに書き、比べる体験構造案はすべて同じ見た目でそろえる。舞台（`stage.js`、タイトル画面の部品）は作業の前の入口の画面だけに使い、作業の画面には使わない（README の決まり）。

### プロトタイプでの読み込み

最初のプロトタイプを作るときに、`tokens.css`・`components.css`・`components.js`・`icons.svg` を保存先の `ds/` フォルダーに複製し、プロトタイプからは `../ds/tokens.css` のような相対パスで読み込む（7章）。複製した日付をブリーフの「デザインシステム」の行に版として書く。アイコンは、使う `symbol` を HTML の中に埋め込む。`file://` で開くと外部の `icons.svg` を読めないブラウザがあるためである（README）。

### スマートフォン向けの画面

設計する画面がスマートフォンで使われるもの（スマートフォンのアプリ、スマートフォンのブラウザで開く画面）の場合は、既定の DS として `<SKILL_DIR>/sample-design-system-mobile/`（スマートフォン版）を使う。PC 版の部品は、横に並べる幅・ホバー・マウスの細かい操作を前提にしているので、スマートフォンにそのまま当てはめると、押せる範囲が足りず、一覧と詳細を並べられないためである。スマートフォン版は PC 版と同じトークンの名前・色・見た目の切り替えを持ち、部品を指で操作する作りに置き換えている。PC 版の部品をどれに置き換えるかは、スマートフォン版の README の「PC 版との対応」にある。PC とスマートフォンの両方で使う製品では、両方の DS を使い、画面ごとにどちらで作ったかを対応表に書く。タブレットの画面も、指で操作するのでスマートフォン版を使い、幅を使う組み方（一覧と詳細を左右に並べるなど）は画面の側で作って、DS への追加の候補にする。端末の枠は `.dv-phone` に `data-device="tablet"`（横は `data-orientation="landscape"` も）を付けてタブレットにする。画面の例は、スマートフォン版の `例_タブレット画面_縦.html` と `例_タブレット画面_横.html` にある。

読み方は PC 版と同じで、`README.md` → `tokens.css` → `index.html`（使う部品のクラス名で検索）の順に読み、組み合わせ方は `例_スマホ画面.html` を見る。プロトタイプでは、上の 4 つのファイルに加えて `device.css`・`device.js` も `ds/` に複製する。これは、ブラウザで見せるときに画面を端末の枠（時刻の帯・カメラの穴・下の操作の帯・キーボード）の中に入れるための部品で、端末の帯やキーボードに中身が隠れないか、親指の届く所に操作があるかを、パソコンの画面で確かめられるようにするためである。プロトタイプは `.dv-stage` > `.dv-phone` > `.dv-screen` > `.dv-viewport` の中に `.ds-app` を置いて組む。同じ HTML を実機（幅 540px 以下）で開くと、枠は消えてアプリが画面いっぱいに出るので、実ユーザーの検証にもそのまま使える。ブリーフの「デザインシステム」の行には「既定（スマートフォン版の sample-design-system-mobile を適用）」と書く。

## 2. 工程0で読むもの

DS について、次を読む。読めた範囲と読めなかった範囲を `01_設計ブリーフ.md` の「デザインシステム」の行に書く。

| 対象 | 確かめること |
|---|---|
| トークン | 色（状態色を含む）、文字の大きさと太さ、余白の段階、角丸、影、動き |
| コンポーネント | 部品の一覧、各部品の状態（通常、ホバー、フォーカス、無効、読込中、エラー）、バリエーション |
| パターン | 一覧、フォーム、空状態、エラー表示、確認、通知、進捗表示の組み合わせ方 |
| 利用ガイドライン | 部品ごとに、使ってよい場面と使ってはいけない場面 |
| アクセシビリティの方針 | コントラスト、フォーカス表示、キーボード操作の規定 |
| 版 | どの版を基準にしたか |

DS の形式は、コードのパッケージ、CSS 変数、Storybook、文書サイト、PDF、Figma などさまざまである。Figma のように読めない形式しかない場合は、その旨を記録し、トークンの値や部品の一覧をユーザーに求める（工程0の前の壁打ちで一度伝える。使うのは反復の B からなので、壁打ちを止めて聞かない）。読めないまま推測で再現した部分は [仮定] とする。

## 3. 当てはめる時期

工程0〜3（設計ブリーフ、現状と課題、体験構造の発散）では、DS で案を狭めない。既存の部品で表せるかどうかを基準に体験構造を選ぶと、「いまの部品で作れる仕事の仕組み」しか出てこなくなり、根本からの見直しにならないためである。

ただし、工程3の案の比較では、DS との距離（その案を作るのに新しい部品がいくつ必要か）を、実装と学習の負担として比較表に書いてよい。DS との距離が大きいことだけを理由に案を棄却はしない。

DS を当てはめるのは、反復の B（最適化）で画面要素を決めるときからである。

## 4. 対応表

DS が指定されている場合、反復ごとに `iter-NN/デザインシステム対応.md` を作り、画面要素ごとに DS のどれを使うかを決める。書式は `references/templates.md` にある。判定は次の四つから選ぶ。

| 判定 | 意味 |
|---|---|
| そのまま使う | DS の部品・パターンを、利用ガイドラインどおりに使う |
| DS の範囲で調整 | 既存のバリエーション、部品の組み合わせ、ガイドラインが認める設定で対応する |
| 近いもので代用 | 部品の本来の用途とは少し違うが、5章の基準のどれにも当たらない（失うのは見た目の細部だけ）。失うものを必ず書く |
| 最善のものがない | 5章の基準に当てはまる。追加提案（DS-01…）を作る |

各要素には、その要素が担う仕事（状態表のどの状態、どのシナリオのどの判断・操作を表すか）を書く。担う仕事を書かないと、部品が「合っているか」を判断する基準がなくなり、見た目が似ているかどうかで選んでしまうためである。

## 5. 「最善のものがない」の判断基準

次の順に確かめる。

1. 既存の部品・バリエーション・組み合わせで、必要なことをすべて満たせるか。必要なこととは、状態表のすべての状態の表示、判断地点に置く情報、操作（取消・復旧を含む）、量が10倍になったときの構造、設計ブリーフの「悪化を認めない条件」である。
2. 満たすために、DS の利用ガイドラインに反する使い方をしていないか。たとえば、数秒で消える通知（トースト）に取り消せない重要な操作の結果を出す、画面の切替え用のタブを処理の状態の切替えに使う、などである。ガイドラインに反する使い方は、DS を使っているように見えて、DS が保証している意味を壊す。
3. 近いもので代用した場合に、関連するシナリオの走査で、四つの判定（見つけられる・意味が分かる・正しく判断できる・操作できる）のどれかが○にならないか（△も含む）。また、より適した表し方と比べて、一つの仕事を終えるまでの手数や判断の回数が増えないか。

1を満たせない、2で違反がある、3で○以外の判定が出るか手数・判断の回数が増える、のいずれかに当てはまれば「最善のものがない」と判定する。たとえば、AIの提案と確認済みの事実を、既存のバッジの色と文字で一応は区別できても、走査で利用者が見分けるのに迷う（△）なら、最善のものがないと判定する。

反復の B では、まだプロトタイプがないため、走査の結果を見込みで判定する。見込みで判断に迷う場合は、「最善のものがない」として提案を作り、E で提案版と代用版を比べて決める（8章）。迷った所を代用で済ませると、比べる機会がなくなり、最善でない部品が検証されないまま残るためである。不要な提案は8章の比較で取り下げられるので、迷った時に提案の側へ倒しても DS は膨らまない。

次は理由にしない。見た目だけの好み、新しさ、既存の部品が古く見えること。これらは使いやすさの差ではないため、追加を提案すると DS が案件ごとの例外で膨らみ、DS を持つ意味（一貫性と使い回し）がなくなる。反対に、使いやすさの差（判定の△、手数や判断の回数の増加）は、小さくても正当な理由として扱う。

DS の既存の規定そのものが「悪化を認めない条件」に反する場合（例：状態色の文字と背景のコントラスト比が 4.5:1 に届かない、フォーカス表示がない）も、既存の修正として提案する。

## 6. 追加提案

提案には次の種類がある。

| 種類 | 例 |
|---|---|
| 新しい部品 | 判断が必要な案件を、根拠と選択肢とともに一単位で示すカード |
| 既存部品の新しいバリエーション・状態 | 表の行に「部分成功」の状態を加える |
| 新しいパターン | 長時間の処理を待たずに別の仕事へ移り、完了後に戻るための組み合わせ |
| 新しいトークン | 「AIの提案」と「確認済みの事実」を区別する表示の値 |
| 既存の修正 | コントラストが不足する状態色の値の変更 |

提案ごとに、`references/templates.md` の追加提案カードを書く。とくに次の二つは省かない。

- 検討した既存の代替と、それぞれで失うもの。DS の管理者が「既存の部品で足りるのではないか」と判断できるようにするため。
- 提案が採用されなかった場合の代替。どの既存部品で代用し、何が失われ、それを文言や配置でどこまで補うかを書く。提案が採用されるまで実装が止まらないようにするため。

汎用性（この案件以外で使えそうな場面）は [推論] として書く。一つの画面でしか使わない見込みなら、そのことを明記し、DS には加えず製品の中の部品として留める選択肢も併記する。

提案は、反復の中で `iter-NN/デザインシステム対応.md` に書き、工程9で最終的に残ったものを `08_デザインシステム追加提案.md` にまとめる。

## 7. プロトタイプでの扱い

- DS の CSS・JavaScript がファイルとして手元にある場合（既定の DS を含む）は、保存先の `ds/` フォルダーに複製し、プロトタイプから相対パスで読み込む。CDN や元の DS の置き場所を直接読み込まないのは、オフラインでも、DS が後で変わっても、同じように開けるようにするためである（`references/prototype.md` の規則の目的と同じ）。既存の部品は、DS のクラスと HTML の作りをそのまま使う。
- DS が文書や Figma だけでファイルがない場合は、トークンの値をプロトタイプのファイル内の CSS 変数に写し、部品の見た目・状態・振る舞いを再現する。再現できなかった部分（動きの細部など）は、ファイル冒頭のコメントに書く。
- 追加提案の部品も、できるだけ DS の既存トークンで作る。新しいトークンが必要な場合は、その値に提案IDのコメントを付ける。
- 製品の画面には「提案」などの表示を出さない。AI模擬評価の評価者が、その部品を特別なものとして扱い、評価が偏るためである。代わりに、検証用パネルに「DS 外の部品」の一覧（提案ID、名前）を出す。
- すべての追加提案について、検証用パネルで「近いもので代用」した版に切り替えられるようにする。8章の比較を同じ画面で行うためである。
- 比べる体験構造案は、すべて同じ DS の基盤で作る。片方だけ DS から外れると、構造ではなく見た目の違いで優劣が決まってしまうため。

## 8. 検証

反復の E（検証）で、次を加える。

- ヒューリスティクスの「一貫性と標準」の点検で、DS の同じ部品が同じ意味で使われているか、追加提案の部品が既存の部品と見分けにくく誤解を生まないかを確かめる。
- 追加提案ごとに、提案版と代用版で関連シナリオを走査し、四つの判定（見つけられる・意味が分かる・正しく判断できる・操作できる）と、手数・判断の回数の差を記録する。×だけでなく、△と○の差、手数や判断の回数の差も「差」として扱う。提案版が代用版より良くならなければ（差がないか、提案版のほうが悪ければ）、その提案は取り下げて代用にする。最善のものがないと判断した根拠が、走査で裏付けられなかったことになるためである。
- 結果は [机上] または [AI模擬] であり、提案部品が実ユーザーに理解されるかは、`09_実装引継ぎ.md` の実ユーザー検証計画で確かめる項目に入れる。
