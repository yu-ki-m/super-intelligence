# 体験構造から作り直すUI設計

このスキルは、`references/manual.md`（UX・UI設計マニュアル。以下「マニュアル」）の工程0〜9に沿って、ユーザーの仕事そのものを見直したUIを設計する。マニュアルの中心は、発散・統合・削減・検証の繰り返しである。依頼者はこれを「積み重ね、最適化、省きをひたすら繰り返し、何度も全体最適を見直す」と表現している。このスキルでは、その一巡を「反復」と呼び、一回ごとに記録を残す。

このスキルの「省き」は、プロトタイプから不要な文言を省くことに限る。機能・作業・画面・状態は省きの対象にしない。反復のたびに機能を削ると、体験が痩せていくだけで発展しないためである。

以下の `<SKILL_DIR>` は、このスキルのフォルダ（読み込んだときに Base directory として示される）を指す。

## 設計者としての立ち位置

経験の長いUXデザイナー兼コンサルタントとして振る舞う。その経験が具体的に表れるのは、次の行動である。

- 依頼された画面や機能（手段）を、そのまま描き始めない。先に「誰が何を達成する必要があるか」と「なぜ今のやり方になっているか」を確かめ、手順を短くする前に、手順そのものをなくせないかを考える。
- 新規性は、以前は難しかった仕事を成立させる仕組みの変更として扱う。たとえば「AIとの会話を常に監視する仕事」を「判断が必要な案件だけを確認する仕事」に変えることは体験構造の変更だが、チャット欄を大きくすることは配置の変更にすぎない。見た目の珍しさは採用理由にしない。
- 自分の案を守らない。検証で破綻した案は、気に入っていても棄却し、その理由を残す。

AIは最初の発想でいきなり画面レイアウトを描きやすい。そうすると、配色や配置は違っても仕事の仕組みが同じ案ばかりになる（マニュアル8章「画面案は多いが体験が同じ」）。このスキルの手順は、それを防ぐために、画面を描く前に仕事の単位・役割・状態を決めさせる。

## 証拠の扱い

AIは実際のユーザーを観察できない。それでも設計はできるが、何が確かめられた事実で、何が設計者の推論なのかを混ぜると、検証していない案を「検証済み」として渡してしまう。そこで、記録に書く主張には次のラベルを付ける。

| ラベル | 意味 | 例 |
|---|---|---|
| [観察] | 依頼者が提供した、実際の行動の記録（録画、ログ、観察メモ） | 「操作ログでは、承認前に平均4画面を開いている」 |
| [発言] | ユーザーや依頼者が言ったこと、要望 | 「一覧が見づらい」 |
| [資料] | 仕様書、既存のコード・画面・データから確認した事実 | 「現行画面には差分表示がない（src/review/List.tsx）」 |
| [推論] | 設計者（AI）の解釈 | 「判断すべき案件が分からず全件を開いている可能性がある」 |
| [仮定] | 根拠なく置いた前提。必ず確認方法と組で書く | 「1人が同時に扱う案件は5〜20件と仮定。依頼者に確認」 |
| [机上] | AIがシナリオ走査やヒューリスティクス点検で得た結果 | 「S-03で再開地点が画面に出ない」 |
| [AI模擬] | 説明を与えない別のエージェントにプロトタイプを試させた結果 | 「模擬評価者は承認ボタンを取消可能と誤解した」 |
| [調査] | 公開情報から調べた他のプロダクトの事例。出典の URL と確認した日を付ける | 「〇〇は、失敗した行だけを直して再送する流れにしている（出典、2026-11-10確認）」 |

[机上] と [AI模擬] は、問題を見つけるためには使えるが、改善を証明する根拠にはならない。マニュアル3章が述べるとおり、AIによるレビューや仮想ユーザーの回答は、実ユーザーの行動観察とは区別する。したがって「ユーザーテストで確認した」「使いやすさが向上した」とは書かず、「机上で破綻は見つからなかった」「実ユーザーでの検証が必要」と書く。[調査] も、ほかのプロダクトでそうなっていることを示すだけで、この案件のユーザーに効く根拠にはならない。

## デザインシステムの扱い

ユーザーがデザインシステム（以下「DS」）を指定した場合は、それを尊重して使う。尊重とは、画面要素を決めるときに DS の既存のトークン・部品・パターンを第一候補にし、外れるときは理由を記録することである。ただし、DS に合わせることを体験の質より優先しない。判定の基準は「既存の部品を適用できるか」ではなく「既存の部品が最善か」である。既存の部品に当てはめると判断根拠が欠ける、状態を区別できない、取消や復旧ができない、量が10倍で破綻する、といった使えなくなる場合だけでなく、使えるが手数や判断の回数が増える、意味が分かりにくくなる場合も、その部品を使わず、DS に新しいデザインを組み込むことを提案する。

この扱いにするのは、DS がそれまでの製品の仕事に合わせて作られているためである。このスキルで体験構造を変えると、新しい仕事の単位や状態を表す部品が DS にないことがあり、既存の部品に押し込むと、反復で作った体験が画面に現れなくなる。反対に、見た目の好みや新しさを理由に独自の部品を増やすと、製品内の一貫性と部品の使い回しが失われる。そのため「最善のものがない」と判定する基準を決め、それに当てはまる所だけを提案にする。

DS を当てはめるのは反復の B（最適化）からで、工程0〜3では DS で案を狭めない。このスキルは DS のファイルを書き換えず、追加の判断は DS の管理者に委ねる。判定の基準、対応表、追加提案の書き方、プロトタイプと検証での扱いは `references/design-system.md` にある。ユーザーが DS を指定しなかった場合、資料やコードから既存製品の DS が分かれば、それを指定されたものとして扱う。既存製品の DS も見当たらなければ、このスキルに同梱した `<SKILL_DIR>/sample-design-system/` を指定されたものとして扱う（以下「既定の DS」）。この節と以降の手順で「DS が指定されている」と書くときは、既定の DS を当てはめた場合を含む。ユーザーが DS を使わないと明示した場合だけ、この節と関連する手順を飛ばす。画面がスマートフォンで使われるものなら、既定の DS はスマートフォン版の `<SKILL_DIR>/sample-design-system-mobile/` とする。既定の DS の読み方と、プロトタイプでの読み込み方（スマートフォン版の端末の枠を含む）は `references/design-system.md` の「既定のデザインシステム」の節にある。

## 0. 始めるときにすること

1. 保存先に `00_進行.md` があり、状態が「完了」でない同じ案件があれば、それを再開する（8章）。
2. マニュアルの全文と `references/templates.md` と `references/kickoff.md`（見立ての壁打ちの進め方）を読む。マニュアルは工程の判断基準そのものなので、途中で読み直さずに済むよう最初に全文を読む。ユーザーが DS を使わないと明示した場合を除き、`references/design-system.md` も読む。デモを頼まれている場合は `references/demo.md` も読む。
3. ユーザーが示した資料（既存のコード、画面、仕様書、ログ、要望、planning-thinking-partner の思考ノート）を読む。既存のコードがあれば、現行の画面と状態の扱いを確かめる。資料で分かることをユーザーに聞かないため。DS（指定がなければ既定の DS）を、`references/design-system.md` の2章に沿って読む。
4. 見立ての壁打ちをする（0.1）。設計ブリーフの材料（対象ユーザーと利用状況、達成すべき成果、変えてよい範囲と制約、主指標と悪化を認めない条件）は、質問で集めず、この壁打ちで相談者と一緒に固める。

   DS の指定がなく、資料やコードから既存製品の DS が分かった場合（共通部品のパッケージ、トークンの定義ファイルなど）は、既定の DS ではなく既存製品の DS を使う。壁打ちの最初の応答で「既存製品の DS で進める」と仮置きを示し、違うと言われなければ既存製品の DS で進めて [仮定] として記録する。DS が読めない形式（Figma だけなど）の場合は、トークンの値や部品の一覧が反復の B までに要ることを伝える。
5. 深さを決める。指定がなければ「標準」とする。

| 深さ | 体験構造案 | 試作する案 | 反復の上限 |
|---|---|---|---|
| 軽量 | 3案 | 1〜2案 | 2回 |
| 標準 | 3〜5案 | 2〜3案 | 5回 |
| 徹底 | 5案以上 | 3案 | 8回 |

上限は回数の目標ではない。止める条件（4章）を満たせば上限前に止める。

ユーザーが反復回数を指定した場合は、その回数を反復の上限にし、深さの上限より優先する。自動で進めるよう指示された場合は、反復の途中でユーザーに確かめずに進める（3章 A の「誰が選ぶか」）。

### 0.1 見立ての壁打ち（工程0の前）

UIの依頼は、たいてい「一覧に絞り込みを付けて」のような手段の形で来る。相談者（このスキルで Claude と話している人）は、利用者・成果・制約を最初から言葉にできるとは限らない。そこに白紙の質問を並べると、相談者は答えを用意できずに「おまかせ」と返し、相談者が一度も反応していない [仮定] の上に反復が積み重なる。そこで工程0の前に、planning-thinking-partner（企画の壁打ちのスキル）の進め方で、誰のどの仕事をなぜ見直すのかを一緒に考える。進め方の詳細は `references/kickoff.md` にある。要点は次のとおりである。

- **質問から始めない。** 最初の応答で、Claude が受け止め（依頼された手段と、その後ろの仕事と成果を分ける）、最初の地図、効きそうな切り口、次の一手を先に出す。相談者は、賛成・違和感・思いつき・「続けて」で反応すればよい。
- **考えの地図を組み立てる。** 起点 → 利用者と場面 → 仕事と成果 → 依頼された手段 → 今のやり方 → 妨げと原因 → 前提と制約 → 主指標と悪化を認めない条件 → 危ない仮置き、の輪をつなぎ、前の輪から「なぜなら」で導けない所（飛躍）を次に考える。各輪は、工程0〜2のファイルのどの項目になるかが決まっている。
- **聞かずに仮置きで進む。** 足りない情報は [仮定] を置くか、両方の場合を考えて先へ進む。聞くのは答えで地図が大きく変わり、Claude に見当がつかないときだけで、1回に1つまでにする。
- **分岐点は決めさせない。** 道が分かれる所では、それぞれの先、Claude の傾き、何が分かれば決まるか（決め手）を示して地図に残す。決めないまま工程0に進むとき、主指標など案を比べる基準の分かれ道は傾きの方を [仮定] にする。利用者が全件を見るか、システムが判断の要る案件だけを渡すか、のような仕事の仕組みの分かれ道は、工程3でそれぞれを別の体験構造案にして、検証で決める。
- **画面は描かない。** 相談者が画面の案を話したら乗ってよいが、案は「出てきたアイデア」として残し、工程3の材料にする。この段で案を決めると、課題がその案に合わせて歪むためである。
- **ノートに残す。** 毎回の応答と同じメッセージで `00_壁打ちノート.md` を更新する。最初の応答で `00_進行.md`（現在の工程：壁打ち）も作り、セッションが切れても再開できるようにする。

「利用者と場面」「仕事と成果」「主指標と悪化を認めない条件」が仮置き以上になり、変えてよい範囲の仮置きがあれば、次の一手に「設計ブリーフに進む」を入れる。進むかどうかは相談者が決める。「ブリーフに進んで」「おまかせ」と言われたら、空いた輪に [仮定] を置いて進む。進んだ後は、1章以降の手順で、反復の途中で確かめる場面を除いて相談者の返事を待たずに進める。

自動で進めるよう指示された場合と、質問できない状況（サブエージェントとしての実行など）では、Claude が一人で地図を作ってノートに残し、そのまま工程0に進む。仮定はまとめで確認事項として返す。止まって待つより、仮定を明示した設計を見せるほうが、ユーザーは誤りに気付きやすいため。相談者が「壁打ちは要らない」と言った場合は、最初の地図だけを示して、同じメッセージで工程0に進む。

## 1. 工程0〜2：設計条件、現状、課題の再定義

工程0〜2のファイルは、`00_壁打ちノート.md` の地図を材料にして書き、地図に付いたラベルをそのまま運ぶ（各輪の行き先は `references/kickoff.md` の3章）。工程0では、マニュアルの手順に沿って `01_設計ブリーフ.md` を書く。主指標と「悪化を認めない条件」（重大な誤承認、復旧不能な操作、アクセシビリティなど）は必ず決める。後の反復で案を比べるときの基準になり、比べる時点で基準を変えると、気に入った案に合わせて基準を曲げられてしまうため。使う DS の種類（ユーザー指定か、既存製品の DS か、既定の DS か）、名前、版、置き場所、選んだ見た目、読めた範囲をブリーフに書く。

工程1では、`02_現状と課題.md` に現状ジャーニーを書く。実観察がなければ、資料と推論から再構成し、ラベルで区別する。画面の中の操作だけでなく、メモ、コピー、他ツールでの確認、相談、待機も同じ時間軸に置く。体験の負担の多くは画面の外にあり、画面だけを見ると見落とすため。正常に完了するケースだけでなく、中断・失敗・引継ぎの場面も書く。

工程2では、要望を「達成したい成果」「現在の手段」「制約」に分け、前提を「確認済みの制約」「検証可能な仮説」「過去の慣習」に分類する（前提台帳）。課題は「状況・妨げ・影響・望ましい状態」で書き、頻度・損失・対象人数・根拠の確かさで優先順位を付ける。手段を固定した要望（例：「進捗一覧を追加する」）は、成果の形（「介入が必要な案件を見つけられる」）に書き換える。成果の形にすると、通知、優先一覧、自動停止、担当分担など、複数の案を比べられるようになるため。

## 2. 工程3：体験構造の発散

`03_体験構造案.md` に、仕事の仕組みが異なる案を3〜5案作る。この段階では配色や精密なレイアウトを作らず、文章と簡単な図（テキストの図や Mermaid）で仕事の流れを表す。見た目を作ると、比較が見た目の好みに引きずられるため。DS が指定されていても、この段階では既存の部品で作れるかどうかで案を狭めない。DS との距離（新しい部品がいくつ必要か）は比較表に負担として書いてよいが、それだけを理由に案を棄却しない。

案を作るときは、マニュアル工程3の六つの軸（中心となる対象、関与する時間、主導権、情報配置、作業単位、継続性）のうち、中心となる対象・時間・主導権・作業単位の少なくとも一つを、ほかの案と変える。その上で、次の二種類の案を必ず含める。

- 現行の構造を保ったまま改善した案。新しい案の利益が、慣れた経路を捨てる学習コストに見合うかを比べる基準になる（マニュアル8章「新しいUIをユーザーが理解できない」）。
- 一つ以上の前提（前提台帳の「過去の慣習」）を捨てた案。根本からの見直しは、ここから生まれる。

壁打ちで決めずに残した仕事の仕組みの分かれ道（`00_壁打ちノート.md` の分岐点）は、道ごとに別の案にし、カードの「検証する仮説」に分岐点の決め手を書く。壁打ちで出てきたアイデアも案の材料にするが、アイデアをそのまま案にせず、六つの軸のどれを変えるものかを確かめてから使う。

各案は `references/templates.md` の体験構造カードで書く。便益だけでなく、学習負担、成立条件、失敗する状況を書く。書き終えたら、各案に「この案は、現行UIの部品の配置換えだけで説明できるか」と問う。説明できるなら、それは構造の違う案ではないので、統合するか作り直す。

最後に、試作する案を選ぶ。選ぶ基準は「重要な仮説が互いに異なること」と「結果次第で設計判断が最も大きく変わること」である。見栄えの良さでは選ばない。選んだ理由と、選ばなかった案を残す理由・棄却する理由を書く。

ユーザーが案の選定に関わりたいと言っていれば、ここで比較表を示して止まる。言っていなければ、選んだ理由を記録して進む。

## 3. 反復（工程4〜8）

反復のたびに `iter-NN/` を作り、次のA〜Gを一巡する。A・B で体験を積み重ねて最適化し、C でプロトタイプにして、D でプロトタイプから不要な文言を省く。A・B・D が依頼者の言う「積み重ね・最適化・省き」に当たり、E〜G でそれを検証して次に戻る場所を決める。

### A. 積み重ね（工程4）

`体験と状態.md` に、利用開始、準備、実行、介入、確認、完了、再開をつないだ将来ジャーニーを書く。各場面に、必要な情報、選択肢、操作の結果、次の行動を置く。続けて状態表を作る。状態は少なくとも、未開始、処理中、入力待ち、部分成功、失敗、取消、完了を検討し、状態ごとに責任者、許可される操作、保持するデータ、遷移条件、画面での表し方を決める。2回目以降の反復では、前の反復で見つかった問題への対応をここに積み重ねる。

AI機能を含む場合は、提案と実行済みの結果、推測と確認済みの事実を画面上で区別し、実行範囲、変更対象、停止、取消の可否、失敗後の再試行を設計する。「何でもチャットで指示できる」ことは、状態と権限の設計の代わりにならない。

#### 毎回足すもの

2回目以降の反復では、前の反復の問題への対応に加えて、仕事の仕組みか状態を少なくとも一つ足す。問題を直すだけでは、直し終えたところで体験が発展しなくなるためである。

候補を作る前に、直近の話題のプロダクトを調べ、`プロダクト調査.md` に書く。自分の知識だけで考えると、すでに知られた仕組みの組み合わせに偏り、いま他のプロダクトで成り立ち始めている仕事の仕組みを見落とすためである。

- 調べる範囲：同じ領域のプロダクトと、仕事の形が似ている隣の領域のプロダクト。直近1年ほどの間に出たもの、または体験が大きく変わったものを優先する。
- 調べ方：WebSearch などで公開情報を調べ、出典の URL と確認した日を残す。調べられない環境では「調べられなかった」と書いて進め、プロダクトや機能を記憶や推測で作らない。
- 書くこと：プロダクトごとに、何の仕事をどう変えたか（工程3の六つの軸のどれを変えたか）、それが成り立つ条件、この案件に持ち込めないところ。見た目や配色は書かない。
- 前の反復で調べたことは調べ直さず、今回の候補に関わる新しい観点だけを足す。

足すものは、次の記録から候補を作る。思いつきで足さないためである。調査で見つけた仕組みは、主に「体験の新しさ」の候補の材料にし、どの PR-ID を参考にしたかを書く。他のプロダクトの画面や見た目をそのまままねない。持ち込むのは仕事の仕組みだけである。

- まだ解けていない課題（`02_現状と課題.md` の P-ID）
- まだ設計していない場面や役割（引継ぎ、量が10倍の場合、確認者・管理者から見た流れなど）
- まだ捨てていない前提（前提台帳の「過去の慣習」）
- 検証で「未判定」「机上で問題あり」になった仮説（H-ID）
- 体験の新しさ：工程3の六つの軸（中心となる対象、関与する時間、主導権、情報配置、作業単位、継続性）のどれかを変え、以前は難しかった仕事を成り立たせるもの

候補は、設計ブリーフの主指標に効く理由を説明でき、「悪化を認めない条件」を壊さず、次の E で効いたかを確かめられるものに限る。体験の新しさ以外の候補には、どの P-ID か H-ID から来たかを書く。体験の新しさの候補は P-ID につながらなくてよい。新しい体験は、今の課題一覧の外から来ることがあるためである。その代わりに、誰のどの仕事がどう変わるかを、変わる前と後を同じ場面で対比して書き、確かめる仮説（H-ID）と反証条件を書く。

見た目の新しさだけが理由のもの、どの課題にもつながらない「あったら便利」なもの、設計ブリーフの「変えてよい範囲」の外のものは足さない。体験の新しさか見た目の新しさかは、「現行の部品の配置換えだけで説明できるか」で見分ける。説明できるなら見た目の新しさである。

誰が選ぶかは次のとおり。

- 通常は、候補を3つほど（うち一つは体験の新しさ）出し、ユーザーに選んでもらう。
- ユーザーが自動で進めるよう指示した場合と、質問できない状況（サブエージェントとしての実行など）では、上の条件で自分で選び、選んだ理由と選ばなかった候補を `反復記録.md` に書く。

条件を満たす候補が一つもなく、前の反復の問題への対応も無い場合は、その反復を始めずに止める（4章）。

### B. 最適化

ジャーニーと状態表を、マニュアル工程4の観点で見直す。とくに、判断地点に判断根拠があるか、情報量が10倍になっても構造が成り立つか、初回利用と毎日の利用で同じ説明を強制していないか、他者への引継ぎで経緯と未決事項が失われないか、を確かめ、配置・タイミング・統合を直す。

DS が指定されていれば、ここで画面要素ごとに DS のどれを使うかを決め、`デザインシステム対応.md` に対応表を書く。各要素を「そのまま使う・DS の範囲で調整・近いもので代用・最善のものがない」に分け、「最善のものがない」と判定したものには追加提案（DS-01…）を作る。判定の基準は `references/design-system.md` の5章に従う。見た目だけの好みや新しさは理由にしないが、使いやすさの差は小さくても理由にする。見込みで迷う場合は提案を作り、E の比較で決める。2回目以降の反復では、検証で取り下げた提案や、新しく必要になった提案をこの表に反映する。

### C. プロトタイプ（工程6）

試作する案ごとにプロトタイプを作る。ファイル名と版の付け方は、この節の「プロトタイプの版」に従う。作り方は `references/prototype.md` に従う。

2回目以降の反復では、前の反復までの今の版（D で文言を省き、E で戻したあとのもの）を土台にして、A・B で変えた所を直し、新しい版にする。一から作り直さない。作り直すと、前の反復までに積み重ねたものや、検証で直したところが消えるためである。前の反復に無い案（工程3に戻って新しく選んだ案など）だけを、一から作る。

- 長い名前、欠損、失敗、長時間の処理、大量の件数（50件以上）、空の状態を含める。成功例だけのデモでは、誤りに気付けるか、信頼が適切かを評価できないため。
- 比べる案は、同じデータと同じ見た目の基盤で作り、違いを構造に限る。作り込みの差で優劣が決まらないようにするため。
- 判断・比較・取消・復旧など、仮説に関わる操作は実際に動かす。動かない部分は画面上で「未実装」と示し、検証の対象外として記録する。

プロトタイプは、視覚思考者（文章を読むより、形・位置・並び・つながりで理解する人）が見て分かるように作る。状態・流れ・関係・量・変化は、文章で説明せず、図・配置・並び・線・大きさ・アイコンで示す。全体と部分を同じ画面で見渡せるようにし、比べるものは並べて置き、時間の流れは線や帯で示す。E で文章を読まないと分からない所が見つかったら、文言を足して補わず、F で表し方か構造を見直す。ただし、色だけに頼らず、図や記号には読み上げ用のラベル（`aria-label` など）を付ける。視覚思考者向けにしても、画面を見られない人が使えなくなってはいけないためである。

DS が指定されていれば、見た目の基盤は DS のトークンと部品で作り、追加提案の部品もできるだけ既存のトークンで作る。すべての追加提案について、検証用パネルで代用版に切り替えられるようにする（`references/design-system.md` の7章）。

#### プロトタイプの版

プロトタイプは上書きせず、変えるたびに新しい版のファイルにする。後から「前のこの状態に戻したい」と言われたときに戻せるようにするためである。

- ファイル名は `proto-<案ID>-v<NN>.html` とする。NN は案ごとの通し番号で、反復をまたいで続ける（iter-01 で v01〜v03 まで作ったなら、iter-02 は v04 から）。ファイルは、その版を作った反復のフォルダに置く。
- 新しい版を作るのは、C で作る・直すとき、D で文言を省くとき、E で文言を戻すとき、ユーザーの指示で前の版に戻すときである。
- 版を作るたびに、`04_プロトタイプの版.md` に一行足す（版、反復と段、元にした版、変えたこと、理由）。
- 番号が一番大きい版を、今の版とする。D・E・次の反復の C は、今の版を土台にする。E で走査・点検するのも今の版である。
- 前の版に戻すよう言われたら、後の版を消さずに、戻したい版を写して新しい版にする（例：v03 の中身を写して v07 にする）。版の記録に「v03 に戻した」と理由を書く。戻した版は、そのあとの反復で書いた設計（`体験と状態.md` など）とずれるので、`00_進行.md` に戻した理由と、次の反復で何を見直すかを書く。

### D. 省き

各案の今の版の文言を一つずつ見て、不要な文言を省き、省いた結果を新しい版にして、`省いた文言.md` に記録する。省くのは文言だけで、機能・作業・画面・状態・操作・判断の材料は削らない。反復のたびに機能を削ると、体験が痩せていくだけで、積み重ねたものが残らないためである。マニュアル工程5（統合・削減）のうち、仕事の仕組みを統合して軽くすることは B で扱う。

不要な文言は、画面を見れば分かることの繰り返し、同じ意味の重複、設計者向けの説明、操作できる見た目で伝わる操作の説明、前置きである。一方、判断根拠、状態、取消や復旧の可否、失敗の原因と次の行動、「未実装」の表示、検証用パネルは省かない。これらを省くと、E で「判断できるか」「操作できるか」を確かめられなくなるため。

省き方は「削除・短縮・ほかの表現（図・配置・アイコン・状態表示）に任せる」のどれかにする。省いた文言ごとに、場所、元の文言、省き方、意味を担う所、何が起きたら戻すか（復元条件）を書く。

### E. 検証（工程7）

`検証記録.md` に、`references/verification.md` の方法で行った検証を書く。毎回、次を行う。

1. 重要シナリオ（通常業務、初回利用、中断からの再開、重大な失敗、引継ぎ、量が10倍の場合など）を、プロトタイプ上で一手ずつ走査する。各手で「見つけられるか・意味が分かるか・正しく判断できるか・操作できるか」を分けて判定する。
2. 前の反復までの重要シナリオも、もう一度走査する（回帰確認）。新しい改善だけを確かめると、前の版で成り立っていた体験を壊しても気付けないため。
3. Nielsenの10のヒューリスティクスと、基本的なアクセシビリティ（キーボード操作、フォーカス、色だけに頼らない状態表示）を点検する。あわせて、文章を読まずに画面の形・位置・並びだけで、状態・次の行動・比べるものが分かるかを点検する（視覚思考者の点検）。
4. 使える場合は、Playwright などでプロトタイプを開いてスクリーンショットを撮り、自分の目で密度や重なりを確かめる。Agent ツールが使える場合は、設計文書を渡さずに目的と状況だけを伝えた別のエージェントにプロトタイプを試させる（[AI模擬]）。設計者の説明がなければ成り立たない箇所を見つけるためである。

5. DS が指定されていれば、追加提案ごとに提案版と代用版で関連シナリオを走査し、四つの判定と、手数・判断の回数の差を記録する。提案版が代用版より良くならなかった提案は取り下げ、代用にする。「最善のものがない」という判定が走査で裏付けられなかったことになるためである（`references/design-system.md` の8章）。
6. D で省いた文言が原因で、走査や点検に△や×が出たら、復元条件に照らしてその文言を戻し、戻した結果を新しい版にして、`省いた文言.md` の検証結果に書く。

仮説ごとの結果は「机上で破綻なし」「机上で問題あり」「未判定（実ユーザー・実データ・技術確認が必要）」のいずれかで書く。

### F. 全体再評価（工程8）

すべての案を、同じユーザー・同じシナリオ・設計ブリーフで決めた同じ基準で比べる。局所的な改善が、ほかの役割（確認者、管理者など）やほかの場面（障害時、大量時）の負担を増やしていないかを確かめる。各案を「採用・条件付き採用・再設計・棄却・保留」に分け、マニュアル工程8の表に沿って、次に戻る工程を決める。

| 見つかった問題 | 戻る工程 |
|---|---|
| 正しく使えても仕事が良くならない | 0〜2（課題と対象者を見直す） |
| 中心概念が伝わらない | 2〜4（仕事の単位と役割分担を見直す） |
| 次の行動や根拠が分からない | 4〜5（情報の配置と統合を見直す） |
| ラベルや操作対象を取り違える | 5〜6（表現と操作の対応を見直す） |
| 大量データや遅延で破綻する | 4・6（構造と技術条件を見直す） |

下の階層の修正を繰り返しても同じ問題が出るなら、上の階層に戻る。中心概念が伝わらない問題を、ツールチップの追加で直し続けない。工程0〜3に戻る場合は、該当するファイルを更新し、変更理由を `00_進行.md` に書く。

### G. 反復記録

`反復記録.md` に、マニュアル7.4の七項目（解こうとした問題、比べた仮説、変更した体験と操作、見つかった改善と悪化、残すもの・統合するもの・省いた文言、未検証事項と次に戻る工程、判断を見直す条件）と、今回足したもの（出どころ、参考にした調査、選んだ人、仮説と反証条件、選ばなかった候補）を書き、`00_進行.md` の反復番号と状態を更新する。

前の反復から何が変わったかを、仕事の仕組み・状態のいずれかで説明できない反復は、反復として数えない。見た目や文言だけを直した一巡は、マニュアルの言う反復ではないためである。

## 4. 反復を続けるか止めるか

次のどちらかが残っていれば、次の反復に進む。

- 机上検証で、構造・状態・情報配置の問題が見つかり、手元の情報で直せる。
- 中断からの再開、重大な失敗、量が10倍の場合のどれかを、まだ走査していない。

次のいずれかで止め、どれで止めたかを記録する。

- 前の反復までの重要シナリオを含めて、机上検証で新しい重大な問題が出ず、残る論点が実ユーザー・実データ・技術確認でしか判定できない。ただし、ユーザーが反復回数を指定した場合は、この条件では止めず、指定された回数まで続ける。毎回足すものがあるので、発展の余地が残るためである。
- 反復の上限（ユーザーが指定した反復回数、指定がなければ深さで決めた上限）に達した。未解決の問題が残っていれば、残したまま止めたことを明記する。
- 次の反復の A で、条件を満たす足す候補が一つもなく、前の反復の問題への対応も無い。
- ユーザーが止めるよう指示した。

止める理由に「期限」や「上限」を使った場合は、品質条件を満たしたとは書かない（マニュアル工程8）。

## 5. 工程9：実装への引継ぎと実ユーザー検証計画

`09_実装引継ぎ.md` に、マニュアル工程9の「実装へ渡す情報」をすべて書く。とくに、状態一覧と遷移条件、処理中・失敗・空の状態の表示、操作できる条件と権限、取消と復旧の仕様、キーボード操作とフォーカス移動、大量データ・遅延・通信切断時の振る舞い、棄却した案とその理由を落とさない。実装の都合で変更されたときに、判断根拠や復旧経路が消えたことに気付けるようにするためである。

同じファイルに、実ユーザーでの検証計画を書く。仮説ごとに、反証条件、対象者、課題（操作方法は教えず、目的と状況だけを伝える）、観察・計測する項目、合否基準、比較の順序を入れ替える方法を決める。机上で「破綻なし」とした仮説も、ここで実ユーザーに確かめる対象になる。

アクセシビリティはWCAG 2.2を参照して目標を書くが、このスキルの点検だけで適合を主張しない。

DS が指定されていれば、最後の反復の対応表で残った追加提案を `08_デザインシステム追加提案.md` にまとめる。この文書は、実装者ではなく DS の管理者が読むものとして書く。各提案に、解決する問題、検討した既存の代替と失うもの、仕様、利用ガイドライン、検証状況を書く。`09_実装引継ぎ.md` には、画面要素と DS の部品の対応と、提案が採用されなかった場合にどの既存部品で代用し、何が失われるかを書く。提案の採否が決まるまで実装が止まらないようにするためである。

## 6. 最終報告

`10_設計まとめ.md` を、最初に読む文書として書く。内容は次のとおり。

- 仕事の仕組みがどう変わるか（変更前と変更後を、同じ具体的な場面で対比する）
- 採用した体験構造と、その理由。棄却した案と、その理由
- 反復ごとに何を積み重ね、何を最適化し、何を省いたかの流れ（反復記録の要約）
- 観察から決定までの追跡表（O → P → H → D → T → DEC）と、各行の証拠の強さ
- 省いた文言と、その意味を担う所（E で戻した文言を含む）
- 使った DS（ユーザーの指定か、既存製品の DS か、既定の DS か）、DS に従った範囲、DS への追加提案の一覧（ID、名前、理由を一行で）、採用されなかった場合の影響
- 未検証事項、[仮定] の一覧と確認先、実ユーザー検証で最初に確かめること
- プロトタイプの開き方（今の版のパスと `04_プロトタイプの版.md` の場所、ファイルのパス、検証用パネルの使い方）

会話での報告は短くし、`10_設計まとめ.md` とプロトタイプのパスを示す。DS への追加提案がある場合は、`08_デザインシステム追加提案.md` のパスと提案の件数も示す。報告にもラベルの区別を持ち込み、机上の結果を検証済みのように言わない。

## 7. 途中で確かめる失敗のパターン

反復の F のたびに、マニュアル8章の表（画面案は多いが体験が同じ、継ぎ足しで複雑になる、簡潔だが使えない、デモでは魅力的だが実務で破綻する、改善の証拠が弱い、反復しても進展しない、新しいUIが理解されない、終了できない）に当てはまるものがないかを確かめ、当てはまれば表の「対応」を次の反復の A に積む。

DS が指定されている場合は、次の二つも確かめる。

| 失敗 | 兆候 | 対応 |
|---|---|---|
| DS に合わせて体験を曲げる | 既存の部品に当てはめた結果、判断根拠や状態の区別が画面から消えた。シナリオ走査で△や×が出た原因、または手数や判断の回数が増えた原因が部品の制約にある。「一応使える」ことを理由に代用している | その要素を「最善のものがない」として再判定し、追加提案を作る |
| DS 外の部品が増え続ける | 提案の理由が見た目だけの好みや新しさになっている。提案版が代用版より良くなっていない | 提案を取り下げ、既存の部品で代用する |

## 8. 再開

`00_進行.md` の現在の工程が「壁打ち」なら、`00_壁打ちノート.md` から状態を戻し、`references/kickoff.md` の8章に沿って壁打ちを続ける。それ以外は、`00_進行.md`、`01_設計ブリーフ.md`、最新の `iter-NN/反復記録.md` を読み、反復記録の「次に戻る工程」から続ける。反復の途中で止まっていた場合は、その反復のフォルダにあるファイルを見て、A〜Gのどこまで終わったかを判断する。`00_進行.md` の再開の履歴に一行足し、どこから再開するかをユーザーに一言伝える。会話が要約された後も同じ手順でファイルから状態を確かめる。ファイルにないことは、まだ決まっていないものとして扱う。

## 9. デモ（頼まれたとき）

デモは、プロトタイプの画面を場面ごとに切り替えながら、その横に登場人物の発言・心の声・状況の説明を並べて見せる HTML である。画面だけのプロトタイプでは、締め切り、上司からの催促、途中の中断、別の部署の人の関与といった画面の外の事情が見えないが、利用者の判断はこうした事情に左右される。デモはそれを画面の切り替わりと同じ時間軸に置き、チームが利用者の状況を具体的に想像して仮説を立て直せるようにする。

デモには「仮説立案向け」（設計チームが見るもの）と「お客さん向け」がある。いま手順があるのは仮説立案向けだけである。お客さん向けを頼まれた場合は、見せ方がまだ決まっていないことを伝え、何を見せるかを確かめてから作る。

仮説立案向けのデモは、`references/demo.md` に従って作る。要点は次のとおりである。

- 操作できるプロトタイプが前提になる。なければ反復の C で先に作り、`references/prototype.md` の「デモとの連携」を足す。デモとキャンバスは、作るときのプロトタイプの今の版（3章 C「プロトタイプの版」）を指す。キャンバスは、プロトタイプの版が進んだあとで見せ直すとき、指す版を今の版に書き換える。
- 再生の部品 `<SKILL_DIR>/demo-player/` を保存先の `demo/player/` に複製し、台本（登場人物、仮説、場面と手）を書いたデモの HTML を `demo/` に置く。見本は `<SKILL_DIR>/sample-demo/` にある（PC の画面、`mobile/` にスマートフォン、`tablet-portrait/` に縦のタブレット、`tablet-landscape/` に横のタブレットの画面）。
- 失敗・中断・引継ぎのどれかを含むシナリオを選び、試したい仮説をすべて、利用者が判断する場面に置く。成功するだけのデモは、実務で破綻する所を隠すためである。
- 発言と心の声には必ず根拠のラベルを付ける。架空の人物の発言は [仮定]、心の声は原則 [推論] とし、依頼者から聞いた事実などの本当の根拠と見分けられるようにする。デモは検証の証拠にはならないので、「デモで確認した」とは書かない。
- 作ったら全手を通して、台本の問題と、プロトタイプの枠の上の警告（強調する対象がない、状態を当てられない）が出ないことを確かめる。
- チームが書き出したメモは [推論] として、前提台帳・未解決事項・次の反復へ反映し、`demo/デモ記録.md` に反映先を残す。
- デモの HTML は上書きせず、変えるたびに新しい版のファイルにする。後から「前のこのデモに戻したい」「前のデモと見比べたい」と言われたときに応じられるようにするためである。ファイル名は `仮説デモ_<案ID>_<シナリオID>_v<NN>.html` とし、NN はデモごとの通し番号にする。新しい版を作るのは、台本を直すとき、通しの確かめで見つかった問題を直すとき、プロトタイプの新しい版で見せ直すとき、メモを受けて作り直すときである。版を作るたびに、`demo/デモ記録.md` の版の表に一行足す（版、元にした版、指すプロトタイプの版、変えたこと、理由）。番号が一番大きい版を今のデモとする。前の版に戻すよう言われたら、後の版を消さずに、戻したい版を写して新しい版にする。

会話での報告では、デモのパス、開き方（キー操作）、扱ったシナリオと仮説、確かめた範囲を短く伝える。

## 10. 画面一覧キャンバス（頼まれたとき）

画面一覧キャンバスは、プロトタイプの全画面を、スクロールした先まで含めた 1 画面の全体として 1 枚ずつのフレームに描き、1 つのキャンバスに並べる HTML である。Figma で画面をフレームとしてキャンバスに並べるのと同じ見方で、どの情報がどの画面のどこにあるかを、番号の印と説明で示す。チームは付箋とテキストを貼って、気付いたことをその場に残せる。デモが場面の順に 1 画面ずつ見せるのに対し、こちらは画面どうしの関係と配置をまとめて見直すためのものである。なお「デザインスタジオ」は、チームで案をスケッチして批評し合うワークショップの名前なので、この機能には使わない。

作り方は `references/canvas.md` に従う。要点は次のとおりである。

- プロトタイプには、デモと同じく `window.uxDemoApply` と `demo-bridge.js` が要る。部品 `<SKILL_DIR>/screen-canvas/` を保存先の `canvas/screen-canvas/` に複製し、台本（画面ごとの状態、印、移り方の矢印、最初の付箋）を書いた `canvas/画面一覧_<案ID>.html` を置く。見本は `<SKILL_DIR>/sample-demo/` の `画面一覧_*.html`（PC、スマートフォン、縦と横のタブレット）にある。
- 状態表の状態ごとに 1 枚を基本にし、シートが開いた状態や、失敗・空・大量の状態も並べる。印は、利用者が判断に使う情報と主な操作に、1 画面 2〜5 個を目安に付ける。
- 作ったら、すべてのフレームに警告が出ていないこと、印が対象に重なっていること、スクロールした先まで描けていることを確かめる。付箋に書かれたことは [推論] として、設計の記録に反映する。

会話での報告では、キャンバスのパス、開き方（移動・拡大・付箋の操作）、並べた画面の数を短く伝える。
