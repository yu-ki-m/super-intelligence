# 知見の共有：聞き手に持ち帰ってもらう発表

技術カンファレンスやコミュニティでの発表、LT（ライトニングトーク）、社内勉強会での事例紹介、講演に使う。
発表の後に聞き手にしてほしいことは、紹介したやり方を自分の現場で試す、考え方を変える、
資料やコードを見に行く、話し手に声をかける、といったことである。

## 聞き手と始点

聞き手は、売り込まれることを想定していない。
その代わりに、「自分の仕事に使える何かがあるか」「聞いていて面白いか」を基準に、聞き続けるかを決めている。
同じ時間帯に別の発表や手元の仕事があることも多く、最初の数十秒で聞く価値がないと感じると、注意が離れる。

始点の「△△だと思っていた」には、次のようなものが多い。

- その問題は、もっと良い道具や、もっと多くの手間で解決するものだ。
- 自分の現場は事情が違うので、他の人のやり方は使えない。
- そのやり方は知っている。もう試した。

LTのように売り込みのない発表では、interestingを優先する考え方がある。
聞き手は話し手が何かに気づいていく過程を楽しめるので、話し手に実際の失敗談があれば、funnyはそこから取りやすい。

## 展開の段階

この型の並びは、Randy Olsonが科学の伝え方として示した「And（そして）・But（しかし）・Therefore（だから）」の構造を下敷きにしている。
背景を共有し（And）、そこで起きた問題やつまずきを示し（But）、そこから分かったことと、やり方を示す（Therefore）。
そこに、意外な結果を先に見せる掴みと、聞き手の現場への一般化と、持ち帰ってほしいことの回収を加えた。
段階の名前と数は目安であり、持ち時間に合わせて、まとめたり省いたりしてよい。

| 段階 | 聞き手の頭の中 | 入れるもの | ログの発表の例（仮） |
| --- | --- | --- | --- |
| 1. 掴み | 聞く価値がある話か | interesting：直感と違う結果を先に見せる。funny：あるある | 「障害の調査を速くしようとして、ログを10倍にしました。原因が見つかるまでの時間は、2倍になりました」 |
| 2. 背景 | どんな状況の話か。自分と同じか | 聞き手も経験している状況として描く | 障害のたびに「ログが足りない」と言われ、出せるものは全部出すことにした |
| 3. つまずき | 自分もやりそうだ | funny：あるあるの誇張。話し手の実際の失敗談があれば使う | 「1日に出たログは、社内のドキュメントを全部合わせたより多くなりました。読んだ人はいません」 |
| 4. 原因の発見 | そういうことだったのか | interesting：見方の転換。聞き手に一度考えてもらってから答える | ログが多すぎたのではなく、調べるときに答えたい問いが決まっていなかった |
| 5. やり方 | どうすればいいのか | 発見した原因に対応するやり方として出す | 障害のときに答えたい問い（どのリクエストが、どこで、何秒かかったか）から逆算して、出すログを決める |
| 6. 結果と証拠 | 本当に効いたのか | interesting：前後を比べられる数字、実物、デモ | ログの量は5分の1になり、原因が見つかるまでの時間は半分になった |
| 7. 一般化 | 自分の現場ではどうか | 具体的な一件から原則へ。当てはまらない条件も言う | 「ログ」を「監視の項目」や「会議の議事録」に置き換えても同じことが起きる |
| 8. 回収と持ち帰り | 明日何をすればいいか | funny：冒頭の回収。持ち帰ってほしいことを一つに絞る | 「ログを10倍にする前の私に言いたいです。増やす前に、問いを一つ書け、と」 |

## 時間の配分

5分のLTでは、8つの段階を全部話す時間はない。
仮に、掴みに30秒、背景とつまずきに1分、原因の発見に1分、やり方と結果に1分30秒、一般化と回収に1分といった配分になる。
5分で伝えられることは一つと考え、持ち帰ってほしいことを一つに絞ってから、それに必要な段階だけを残す。

20〜40分の発表なら、8つの段階を全部使える。
仮に30分なら、段階1に2分、段階2〜3に7分、段階4に4分、段階5に6分、段階6に5分、段階7に4分、段階8に2分といった配分になる。
技術の詳細（段階5）を長くしがちだが、聞き手が「なぜそうするのか」を納得するのは段階3と4なので、ここを削らない。

## 段階ごとの考え方

### 1. 掴みで、意外な結果を先に見せる

紹介や提案と違い、知見の共有では、結果を先に見せても空白が残る。
「なぜそうなったのか」「どうすればそうならないのか」が分からないからである。
直感と違う結果を先に見せると、空白が大きくなり、聞き手は過程を聞く理由を持つ。
自己紹介は、台本に入れない。
聞き手が知りたいのは話し手の経歴より、この話を聞く価値があるかどうかだからである。

### 2・3. 背景とつまずきで、聞き手を当事者にする

背景は、聞き手も経験している状況として、短く描く。
社内の固有名詞や経緯は、外の聞き手には分からないので、聞き手の言葉に置き換える。

成功したやり方だけを説明すると、聞き手には手順の一覧にしか聞こえない。
実際の最初のやり方と失敗があると、聞き手はそれを自分がやりそうな間違いとして受け取り、後で出すやり方の理由が分かる。
話し手自身の失敗は、誰も傷つけない笑いになる。
ただし、一緒に作業した同僚の失敗として話すと、本人がいない場でもその人を笑うことになるので、「私たちは」「私は」で話す。
依頼文や資料に失敗がなければ、作らない。
そのときは、よくあるやり方だとどこで困るのかを一般の状況として描き、話し手がしたこととしては話さない。

### 4. 原因の発見をストーリーの山にする

段階4は、interestingの中心である。
答えを出す前に「なぜ、ログを増やしたのに遅くなったと思いますか」と問い、聞き手に少し考えてもらう。
聞き手の多くが考えそうな答え（ログを読む道具が遅い、量が多すぎた）の裏にある、別の原因を示す。
見直した原因は、段階5のやり方につながっていなければならない。
原因が「量が多すぎた」なら、対策はログを減らすことになり、問いを決める必要はない。
原因が「答えたい問いが決まっていなかった」なら、問いから逆算する仕組みが必要になり、それが紹介するやり方の役割になる。

### 5・6. やり方と結果は、比べられる形で示す

やり方は、段階4の原因に対応させて出す。
原因に対応しない工夫や、使った道具の細かい設定は、資料やリポジトリに回す。

結果は、前と後を比べられる形にする。
数字には、期間、対象の規模、比べる前の状態を付ける。
コードの画面や設定を見せるときは、台本では読まず、どこを見てほしいかを言う。

### 7. 一般化で、聞き手の現場に置き換えられるようにする

聞き手の現場は、話し手の現場と違う。
具体的な一件の後で、どの条件なら同じことが起きるかを示すと、聞き手は自分の現場に置き換えて考えられる。
当てはまらない条件（規模が小さい、問いが毎回変わる）も言うと、話を盛っていないという信頼につながる。

### 8. 持ち帰ってほしいことを一つにする

最後は、冒頭の意外な結果や、段階3の場面に戻って締める。
持ち帰ってほしいことは一つにし、明日すぐにできる形で言う。
「明日、自分のサービスのログを一つ選んで、それで答えたい問いを一つ書き出してみてください」のように言う。
資料やコードの場所を示すときは、スライドにQRコードや短いURLを出し、台本では「資料はスライドのQRコードから見られます」と言う。

## funnyとinterestingの比重

interestingを中心にし、funnyを多めに入れてよい。
funnyは段階1、3、8に置き、段階3では、実際の失敗談があれば使い、なければあるあるの誇張を使う。
失敗談が、誰かに迷惑をかけた出来事（障害、納期の遅れなど）なら、先に影響と謝罪を言い、笑うのは自分の判断の甘さまでにする。
迷惑をかけたかどうかが依頼文や資料から分からないときは、謝罪を書かず、影響を「確かめてほしいこと」で聞く。
詳しくは story-principles.md の「笑いを入れるときの作法」にある。
interestingの山は段階4に置き、段階1の意外な結果で空白を作る。
内輪ネタ（社内の固有名詞、特定のコミュニティだけで通じる言い回し）は、外の聞き手には通じないことがある。
社内の勉強会でも、部署をまたぐ場では、聞き手の誰もが知っている状況に置き換える。

## 起きやすい失敗

| 失敗 | 起きる理由 | 直し方 |
| --- | --- | --- |
| 自己紹介と会社紹介から始まる | 話し手の信頼を先に示そうとしている | 意外な結果から始め、自己紹介と会社紹介は台本に入れない |
| 背景が長い | 話し手にとっては全部が大事な経緯である | 聞き手が自分の状況と重ねられる部分だけを残す |
| 実際にあった失敗を省く | 失敗を話すと評価が下がると考えている | 実際の最初のやり方と失敗を段階3に置き、やり方の理由として使う |
| 技術の詳細を全部話す | 正確に伝えたいので、省くと嘘になると感じている | 段階4の原因に対応する部分だけを話し、残りは資料に回す |
| 「いかがでしたか」で終わる | 締め方を決めていない | 冒頭を回収し、持ち帰ってほしいことを一つ言う |

## 下敷きにした考え方

- Randy Olsonの「And・But・Therefore」の構造（『Houston, We Have a Narrative』）：背景、問題、帰結の順で話を組む
- 情報ギャップ理論（George Loewenstein）：意外な結果を先に見せて空白を作る
