# 発表のストーリー設計と話し言葉の台本

このスキルは、発表の聞き手に「面白い」と思ってもらいながら、発表の後に行動してもらうためのストーリーを設計し、
話し手がそのまま声に出せる台本を書く。
面白さは二つに分けて扱う。
funny（笑える）は、聞き手の警戒や緊張をほどき、場面を記憶に残す。
interesting（知的好奇心を刺激する）は、聞き続ける理由を作り、話し手の結論を聞き手自身に納得させる。
どちらも、聞き手の認識を発表前の状態から発表後の状態へ動かすために置く。
笑いや驚きが起きても、聞き手の認識が動かなければ、発表としての成果はない。

## 作るもの

| ファイル | 中身 |
| --- | --- |
| Markdown | 発表の条件、聞き手に起こしたい変化、展開、ネタ、問いと答え、台本、確かめてほしいこと。利用者が直接直せる元のファイル |
| HTML | Markdownから scripts/render_html.py で作る閲覧用のファイル。台本を段階ごとに「見せるもの」と「話すこと」に分けて並べ、段階ごとの台本の長さの目安を展開の表に足す |

保存先は、利用者が指定した場所にする。
指定がなければ、作業フォルダーに「〈発表の短い名前〉_台本.md」を作り、同じ名前の .html を作る。
直したときは同じファイルを上書きし、HTMLも作り直す。
前の版を残したいと言われたときだけ、名前に版を付けて別に保存する。

## 受け取る人が知らない前提の扱い

成果物を受け取る人は二人いる。
台本を耳で聞くのは聞き手で、Markdown、HTML、チャットを読むのは話し手（このスキルの利用者）である。
どちらに向けた文でも、受け取る人が知らない可能性のある事柄を、知っているものとして扱わない。
知らない言葉や前提が説明なしに出ると、受け取る人はその意味を推測しながら先へ進むことになり、
その言葉に支えられた主張の根拠を受け取れない。
とくに聞き手は、聞き返すことも、手元で調べることもできない。

説明なしで使ってよいのは、受け取る人の業界で一般に使われている言葉と知識だけである。
業界の中で職種を問わず通じる言葉と、仕事をする人なら誰でも使う言葉が、これに当たる。
厳密な定義は言えなくても、業界の誰もがおおよその意味を分かっている言葉は、説明しない。
それ以外の言葉と前提は、初めて出る所で、その文脈で何を意味するのかを説明する。
社内の言葉（社内のシステムやツールの呼び名、プロジェクトやチームの名前、社内の略語、社内の会議や手続きの名前、社内だけの言い回し）も、説明する対象である。
社内に向けた発表でも説明する。
社内の言葉は、入ったばかりの人や別の部署の人には通じないことがあり、部署によって指すものが違うこともあるからである。
同じ業界の中でも、特定の職種の人しか使わない専門用語は、聞き手にその職種以外の人がいれば説明する。
迷ったときは、その言葉が、ニュースや他社の人とのやりとりでも、説明なしで使われているかで決める。
使われていれば、特定の職種から出た言葉でも、仕事をする人が広く使う言葉として扱い、説明しない。
「リリース」「アップデート」「バグ」は、ニュースでも説明なしで使われるので、営業や経理の人に向けた発表でも説明しない。
「プルリクエスト」「リファクタリング」は、開発の人どうしの会話でしか使われないので、開発の人以外がいれば説明する。
社内の言葉は、ニュースにも他社とのやりとりにも出てこないので、いつも説明する側に入る。

仮に、開発チームに向けた発表なら、「回帰テスト」は説明しなくてよい。
同じ言葉を事業部長への提案で使うなら、
「リリースの前に毎回3日かけて、前から動いていた機能が壊れていないかを手で確かめる作業」のように、
その提案の中で何を指すのかを言う。
一方、社員に向けた発表で「VPN」は言い換えても、「ログイン」「パスワード」は説明しない。
説明するかどうかは、言葉の難しさではなく、その言葉が聞き手の業界で一般に使われているかで決める。

業界の一般の言葉まで説明すると、話が遅くなるうえに、受け取る人は知らない人として扱われたと感じる。
「これを〜と呼んでいます」「〜とは〜のことです」のような定義の文を、業界の一般の言葉に使うと、とくにそう受け取られやすい。

反対に、説明する言葉と前提は、全員が知らない場合も、一部の人だけが知らない場合も、初めて出る所ではっきり説明する。
説明を言葉の前の修飾にまぎれさせず、何を指すのかを、それだけを言う一文で言う。
仮に、全社に向けた発表で、開発チームが「ミハリ」と呼んでいる監視の仕組みの話をするなら、
「システムが止まっていないかを、24時間見張っている仕組みがあります。」「社内では、ミハリと呼んでいます。」と言う。
「24時間見張っているミハリが、止まりました」のように言うと、知らない人は、ミハリが何の名前なのかを聞き取れない。
名前でない社内の言葉も同じである。
社内で、当日中に返事が要る問い合わせを「黄色」と呼んでいるなら、
「当日中に返事が要る問い合わせを、社内では『黄色』と呼んでいます。」と言ってから使う。
上の目安でも決めきれない言葉は、説明したうえで「確かめてほしいこと」に挙げ、聞き手が知っていれば消せるようにする。
ニュースでも説明なしで使われている言葉は、決めきれない言葉として扱わない。

説明が要る前提は、専門用語だけではない。

| 前提 | 説明が要る例（仮） |
| --- | --- |
| 受け取る人の業界の外の専門用語と略語 | 事業部長への提案での「回帰テスト」 |
| 社内の言葉と、話し手の側だけで通じる経緯 | 社内のツールの愛称、プロジェクトの名前、社内の略語や言い回し、「前回の件」 |
| 同じ業界でも、特定の職種の人しか使わない専門用語 | 開発の人以外もいる場での「プルリクエスト」 |
| 主張の根拠になる仕組み | テストを自動にすると、なぜ不具合が翌朝に分かるのか |
| 数字や指標の意味 | 経営層への報告での「一次解決率」が、何を何で割った割合か |
| 比喩や類似の元にする事柄 | 野球のルールを知らない聞き手への「スクイズのようなものです」 |
| このスキルの中だけで使う言葉 | 話し手に向けた文での「interestingの山」「回収」「ト書き」 |

聞き手に説明する前提は、手順2で決めて、Markdownの「聞き手に説明する前提」の表に書き、手順7で台本の言葉にする。
台本での説明の仕方は、references/spoken-script.md の「聞き手が知らない前提は、初めて出る所で言う」にある。

## 手順

### 1. 進め方を選んでもらう

依頼文で進め方が決まっていなければ、作り始める前に、次の三つから選んでもらう。
AskUserQuestion が使えればそれで聞き、使えなければ番号付きの選択肢で質問して、返事を待つ。

| 進め方 | すること |
| --- | --- |
| 仮置きで一気に作る | 依頼文と資料から、設計と台本をまとめて作る。足りない条件やネタは【仮】と書いて進め、最後に確かめてほしいことを並べる |
| 骨子を確かめてから台本 | 変化の一文、展開、ネタの候補、問いと答えを先に見せる。利用者が選んだり直したりしてから、台本を書く |
| 先に質問してから作る | 足りない条件と手元のネタを先に質問し、答えがそろってから設計と台本を作る |

「一気に作って」「まず構成だけ見せて」「質問してから作って」のように依頼文で分かるときは、聞かずにその進め方で始める。
発表の型（手順3）が依頼文から決められないときは、同じ質問の中で型も聞く。
型の選択肢は、依頼文から考えられるものを四つまでに絞る。

どの進め方でも、スキルが考えたネタの候補は【仮】と書き、事実として台本に書かない。
ネタ（あるある、失敗談、当事者の言葉、数字、デモ）は、話し手の実体験から取ったものが最も効く。
聞き手が自分の経験と照らして本当だと感じられるからである。
また、作った事例や数字を事実として話すと、後で確かめられたときに、発表全体が信用されなくなる。

### 2. 発表の条件をそろえる

依頼文と、渡された資料（製品の説明、企画書、スライド、過去の発表、データ）から、次の条件を読み取る。

| 条件 | 条件から決まること |
| --- | --- |
| 聞き手 | 誰の「あるある」を使い、どの問いなら答えられるか。どの言葉を説明なしで使えるか |
| 場 | 対面かオンラインかで変わる、笑いの確かめ方と問いかけのやり方 |
| 持ち時間 | 段階の数と、台本の長さ |
| 発表の後にしてほしいこと | ストーリーの終点。一つに絞る |
| 話す題材 | 紹介する製品、提案する施策、共有する知見、教える手順、報告する結果 |
| 手元のネタ | あるある、慣れてしまった不便、直感と違う事実、失敗談、当事者の言葉、数字と条件、デモ |
| 制約 | 決裁者が多い、安全や信頼が重視される、業界や国が違う聞き手がいる、話してはいけないことがある |

条件を読み取ったら、聞き手の業界や職種と、題材についての知識から、台本で説明する前提を決め、
「聞き手に説明する前提」の表に書く。
題材の資料や依頼文には、話し手の側の言葉（製品の機能の名前、社内の略語やツールの愛称、開発の用語）が、
説明なしで書かれていることが多い。
話し手にとっては毎日使う言葉でも、聞き手にとっては初めて聞く言葉であることがある。
資料の言葉を台本に移す前に、その言葉が聞き手の業界で一般に使われている言葉かを一つずつ確かめる。
社内の言葉は、社内に向けた発表でも表に入れる。
立場の違う人が混ざる場では、特定の職種の人しか使わない言葉は、その職種でない人がいれば表に入れる。
迷う言葉は、ニュースや他社の人とのやりとりでも説明なしで使われているかで決め、使われていれば表に入れない。
業界の一般の言葉は表に入れない。
入れると、台本に要らない説明が増える。

足りない条件の扱いは、進め方で変わる。

- 仮置きで一気に作る：足りない条件は、題材からもっともらしい内容を【仮】で置いて進める。
- 骨子を確かめてから台本：仮置きして骨子を作り、骨子と一緒に確かめてもらう。
- 先に質問してから作る：足りない条件と手元のネタを、一回の質問にまとめて聞き、答えを待つ。依頼文や資料で分かることは聞かない。「分からない」と言われた項目は【仮】で置いて進める。

質問するときの項目は次のとおりで、足りないものだけを聞く。
答えられるものだけでよいこと、分からない項目はスキルが【仮】で置くことを、質問に添える。

1. 聞き手は誰か（立場、業界や職種、人数、題材についての知識）
2. 場はどこか（展示会、社内会議、勉強会など。対面かオンラインか）
3. 持ち時間は何分か（質疑を含むか）
4. 発表の後に、聞き手にしてほしいことは何か（一つ）
5. 話す題材の要点は何か
6. 聞き手が毎日経験している「あるある」や、慣れてしまった不便はあるか
7. 聞き手が当然と思っているが、実は違うことはあるか（データや事例があれば出典も）
8. 話し手や作り手の失敗談、最初の勘違いはあるか
9. 顧客、利用者、現場の人が実際に言った言葉はあるか（引用してよいか）
10. 使える数字と、その条件（期間、規模、比べる前の状態）はあるか
11. その場で見せられるデモや実物はあるか

### 3. 発表の型を決める

発表の後に聞き手にしてほしいことから、型を一つ選ぶ。
型によって、聞き手が最初に持っている前提と、展開の段階と、funnyとinterestingの比重が変わる。
選んだら、その型のファイルを読む。

| 型 | 発表の後にしてほしいこと | 場面の例 | 読むファイル |
| --- | --- | --- | --- |
| 紹介 | 試す、申し込む、問い合わせる、応募する | 製品やサービスの紹介、展示会のセミナー、ウェビナー、営業の場、採用説明会、チーム紹介 | references/types/introduce.md |
| 提案 | 承認する、予算を付ける、試行を許可する | 社内の企画提案、予算や人員の申請、方針変更の提案、顧客に導入の判断を求める場、投資家へのピッチ | references/types/propose.md |
| 知見の共有 | 自分の現場で試す、考え方を変える | 技術カンファレンス、LT、勉強会での事例紹介、講演 | references/types/share.md |
| 教える | 教えた手順や考え方を使い始める | 研修、新人研修、ハンズオン、制度や手順の説明会 | references/types/teach.md |
| 報告 | 結果を理解して判断する、支援する、広げる | 成果報告、試行の結果報告、振り返り、調査結果、障害報告 | references/types/report.md |

どれにも当てはまらないときは、してほしいことが最も近い型を選び、段階の名前を読み替える。
二つの型にまたがるとき（顧客に製品を紹介して導入の判断を求める、など）は、聞き手が最後にすることで主の型を決め、
もう一方の型のファイルも読んで、必要な段階を借りる。

### 4. 聞き手に起こしたい変化を一文にする

references/story-principles.md を読み、「〇〇な人が、△△だと思っていたが、□□だと気づき、☆☆する」の形で一文を書く。
始点の「△△だと思っていた」は、聞き手が今のやり方を続けている理由であり、終点の「☆☆する」が発表の目的である。
この一文が、ネタを選ぶ基準と、funnyとinterestingを置く場所を決める基準になる。
始点には、型のファイルの「聞き手と始点」にある思い込みを参考に、この聞き手が実際に持っていそうな考えを書く。

### 5. ネタを集めて選ぶ

references/story-principles.md の「ネタを見つける観点」の七つの観点で、手元の材料と題材の周辺から候補を集める。
候補のうち、一文の始点から終点への流れに合うものを選ぶ。
選ぶときに次を確かめる。

- 誇張してよいのは状況の描写だけで、数字や事実は誇張しない。
- 笑う対象は、状況、仕組み、話し手自身にする。聞き手、聞き手の同僚や部下、顧客、競合の担当者を笑わない。
- 笑いのネタは、主張と同じ方向を向いている。
- 数字と事例は、出典と条件が分かるものだけを事実として使う。分からないものは【仮】と書き、ネタの表の「出どころ」に差し替え方を書く。
- 当事者の言葉を引用するときは、引用の許可を確かめてほしいことに書く。

### 6. 展開を組む

型のファイルの段階を元に、持ち時間に合わせて段階をまとめたり省いたりして、展開を組む。
段階ごとに、時間、前の段階からのつなぎ、聞き手の頭の中、funny、interesting、話すことを決める。
組んだら次を確かめる。

- 題材の中身（製品、提案、やり方、手順）が出る前の段階に、聞き手が必要性を感じるための時間を取っている。
- interestingの山（原因の見直し、予想と違った結果など）から、話し手の結論が導ける。
- funnyの量が、型の比重と場に合っている。決裁者が多い場、損害が出た出来事を扱う場では控える。
- 出した問いには、すべて答える場所がある。問いと答えの組を「問いと答え」の表にする。
- 「聞き手に説明する前提」の表の前提ごとに、説明する段階がある。
  説明は、その前提を使う主張や問いより前に置く。
  問いに要る前提を説明しないまま問うと、聞き手は予想を立てられない。
- 隣り合う段階が、「だから」「ところが」「では、なぜ」のどれかでつながる。
  「それと」「次に」でしかつながらない段階は、並べる順番か中身を直す。
  つなぎ方は、展開の表の「前の段階からのつなぎ」に一文で書く。
  意図して話を飛ばす段階は、そう書き、同じ段階の中のどこでつなぐかも書く。
- 最後に冒頭を回収し、してほしいことを一つだけ、その場で行動できる手段と一緒に頼む。

「骨子を確かめてから台本」の進め方では、ここで止まる。
台本の節を除いたMarkdownを assets/template.md の形で書き、HTMLを作ってから、チャットで次を見せて確かめてもらう。

- 聞き手に起こしたい変化の一文
- 展開の段階ごとの、funnyとinterestingの置き場所
- 意図して話を飛ばす所があれば、その場所と、どこでつなぐか
- ネタの候補。【仮】のものは、実体験に差し替えられるかを聞く
- 聞き手に説明する前提。聞き手が実際にその言葉を知っているかは話し手の方が分かるので、多すぎないか、足りないかを聞く
- 決めかねている点。二つの案があるときは、両方と、それぞれを選んだときの違い

返事を受けたら、骨子を直してから手順7に進む。

### 7. 台本を書く

references/spoken-script.md を読み、assets/template.md の形でMarkdownを書いて、展開の段階ごとに台本を書く。
書く前に、段階ごとの話す言葉の字数の目安を決める。
段階の予定の秒数から、デモ、ワーク、聞き手の反応を待つ秒数を引き、5を掛ける（1分300字は1秒5字）。
仮に、4分の段階でデモに1分かかるなら、話す言葉は900字前後になる。
目安に合わせて書くと、書いた後に長さを合わせ直す手間が減る。
要点は次のとおりである。

- スライドの文を読み上げず、耳で聞いて分かる話し言葉で別に書く。表、URL、コード、細かい数字の一覧は読まず、意味を言う。
- 「聞き手に説明する前提」の表の前提は、初めて出る所で、その発表の中で何を指すのかを一、二文で言う。
  一部の聞き手だけが知らない前提も、修飾にまぎれさせず、はっきり言う。
  聞き手の業界で一般に使われている言葉は、説明しない。
- 1行に1文を書き、一文で一つのことを言う。まとまりの最初の文で、何の話かが分かるようにする。ただし、問いで引っ張る場面では答えを先に言わない。
- テーマを切り替える所では、黙って次の話を始めない。
  前の話を締め、次の話に移る理由を言い、次の話が何の話かを言う。
  展開の「前の段階からのつなぎ」は、段階の最初の二、三文で声にする。
- 数字の条件と、仮であることは、声でも言う。台本とスライドを矛盾させない。
- 話す言葉以外は、行全体を〔 〕で囲んだト書きにする。問いの後と笑いを狙ったセリフの後には〔間〕を書く。時間がかかるト書きには時間を書く。
- 笑いのセリフは、ずれを文の最後に置き、笑いが起きなくても情報が伝わる形にする。

### 8. テーマの切り替わりを確かめる

台本を書いたら、次のコマンドで、テーマが切り替わる所（段階の切り替わりと、スライドの切り替わり）ごとに、前の文と次の文を抜き出す。

```
python "<このスキルのフォルダー>/scripts/render_html.py" "<Markdownのパス>" --joints
```

切り替わりごとに、前の文から次の文までを続けて声に出したつもりで読み、
聞き手が「なぜこの話になったのか」を、次の話の最初の二文までで分かるかを確かめる。
次のどれかに当たる所は、黙ってテーマを切り替えているので、直す。

- 前の話に触れず、次の話をいきなり始めている。
- 「本題の前に」「さて」「次に」「もう一つ」のように、切り替えたことだけを言い、理由を言っていない。
- 問いを出したり、手を挙げてもらったりした後に、その問いに触れずに次の話へ移っている。
- 自己紹介のような挟み込みを、問いと答えの間に入れているか、前の話との関わりを言わずに入れている。
- 段階の切り替わりで、展開の「前の段階からのつなぎ」が、台本の言葉になっていない。

直すときは、前の話を締める一文、次の話に移る理由、次の話が何の話かを足すか、文や段階の順番を入れ替える。
段階の切り替わりでは、合わせて二、三文にする。
同じテーマの中でスライドを替えるだけの所では、つながりの一文でよい。
足した分だけ長くなるときは、同じ段階の別の文を削り、段階の長さを保つ。

意図して話を飛ばす所も、黙っては飛ばさない。
前の話を締めてから飛び、飛んだ直後に前の話とつながることだけを言い、同じ段階の中でつながりを明かす。
展開にそう書いていない飛び方は、意図したものとして扱わない。

コマンドが「※」で示す所は、候補の目安である。
印がない所も同じように確かめる。
印があっても、前の話を自然に受けている所は、そのままでよい。
Pythonが使えないときは、台本を段階ごとに読んで、同じことを確かめる。

### 9. 見直す

references/story-principles.md の「ストーリーを見直す観点」と、references/spoken-script.md の「台本を見直す観点」で全体を見直し、
見つかった問題は直す。

前提知識の見直しでは、聞き手が知っていることだけを頼りに、台本を頭から読む。
説明なしに出てくる言葉、社内の名前や経緯、主張の根拠になる仕組みが見つかったら、
「聞き手に説明する前提」の表に足し、台本の初めて出る所に説明を入れる。
表にある言葉が、何を指すかを言われないまま修飾にまぎれていれば、一文で言い直す。
反対に、聞き手の業界で一般に使われている言葉を定義している文があれば、消す。
Markdownのほかの節と、チャットで話し手に伝える文も、話し手が知らない言葉（このスキルの中だけで使う言葉など）を
説明なしで使っていないかを確かめる。

見直しの記録は成果物に書かない。
直したうえで残る、話し手にしか決められないこと（【仮】の差し替え、引用の許可、デモの予備、数字の出典、
聞き手が知っているか判断がつかなかった言葉など）だけを、「確かめてほしいこと」に書く。

### 10. 書き出す

次のコマンドでHTMLを作る。

```
python "<このスキルのフォルダー>/scripts/render_html.py" "<Markdownのパス>"
```

コマンドは、Markdownと同じフォルダーに同じ名前の .html を書き、段階ごとの予定の時間と台本の長さの目安を表示する。
使い方はここに書いたとおりなので、scripts/render_html.py の中身を読む必要はない。
「直すこと」が出たら、Markdownを直してから、もう一度コマンドを実行する。
合計の長さが予定から1割以上ずれているときは、台本を削るか足す。
合計が1割以内に収まっていれば、段階ごとの長さのずれは、配分の意図が崩れているとき（題材の説明が予定の倍になっている、など）だけ直す。
「切り替わりの候補」が出たら、手順8と同じように確かめる。
「確かめる候補」は、1行に2文ある行、長い文、声に出せない書き方などである。
話し言葉として直すべきものは直し、意図して残すものはそのままでよい。
Pythonが使えないときは、HTMLを作らずにMarkdownだけを渡し、そのことを伝える。

最後にチャットで、次を短く伝える。

- 作ったファイルの場所
- 聞き手に起こしたい変化の一文と、funnyとinterestingの主な置き場所
- 確かめてほしいことのうち、発表の前に必ず決める必要があるもの

## 直すとき

利用者から直す点を言われたら、Markdownを直してHTMLを作り直す。
【仮】のネタを実体験に差し替えたときは、そのネタを使う段階のセリフと、最後の回収のセリフが合っているかを確かめる。
冒頭の問いや笑いを変えたときは、最後の回収も合わせて直す。
段階を足したり削ったり、順番を変えたりしたときは、「問いと答え」の表と時間の配分を直し、
前後の段階のつなぎを書き直してから、手順8の方法で切り替わりを確かめる。
持ち時間が変わったときは、型のファイルの「時間の配分」に戻り、段階をまとめたり省いたりしてから台本の長さを合わせる。
聞き手が変わったとき（社内向けの発表を社外向けにする、など）は、「聞き手に説明する前提」の表を作り直し、
台本の説明を足したり削ったりする。
