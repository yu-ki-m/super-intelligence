# 版と変更の印

変更設計・新規設計・コードレビュー用の仕様差分で読む。直すたびに版を残し、どこを変えたかを文書に示す。

目次

2. 直すときの決まり

## 1. 版の進め方

部品のディレクトリの隣の `versions/` に、版ごとの部品と `history.json` を残す。`build` は今の部品を v1（基準）と前の版と比べて、変更の印と「変更履歴」のタブを作る。

```bash
D="${CLAUDE_SKILL_DIR}/scripts/ddoc.py"
python "$D" rev <出力先>/parts --kind 基準 --note "現行コードから書き起こした"     # 直し始める前に、基準を保存する
# …部品を直す…
python "$D" rev <出力先>/parts --kind 指示 --note "指示 1「更新に楽観ロックを入れたい」"
python "$D" build <出力先>/parts -o <出力先>/<名前>.html --title "…" --src-root <ソースのルート>
```

- **変更の印を手で書かない。** 部品に `ins`・`del` を書かず、ふつうに文を直す。`build` が比べて付けるので、付け忘れが起きない（書くと `check` が警告する）。
- `--kind` はきっかけ：`基準`・`指示`・`補完`・`指示＋補完`・`コミット`。`--note` には利用者の指示の文をそのまま、または補った内容を書く。「変更履歴」のタブに載り、後から「なぜ変えたか」を読める。
- `rev` せずに `build` すると、最後の版との差分を「作業中」として表示する。利用者に見せる区切りごとに `rev` する。
- 「すべての変更」は v1 からの差分、「今回の変更だけ」は前の版からの差分。

指示を受けたときの流れ：① 部品を直す ② `rev --kind 指示 --note "指示の文"` ③ `build`・`check` ④ 変えた行（No.）と補った所を報告する。指示の文には番号を付け（指示 1, 指示 2…）、根拠の欄から指せるようにする。

**版の保存と検証の順。** 部品を直し、`build`・`check` を通してから `rev` で版を保存する。その後に `build`・`check` をやり直し、結果を検証記録に書く。検証記録と一覧（`data-sec="toc"`）は版の比較の対象外なので、`rev` の後に直しても「作業中」にならず、新しい版も要らない。

## 2. 直すときの決まり

- **既存の行の No. を振り直さない。** 行を足すときは `31a`、`31b` のように枝番にする。行を消すときは行を消すだけでよい（`build` が取り消し線で残す）。No. を変えないので、「No.33 を直して」という指示がずれず、変更していない行に印が付かない。
- **直すのは変わる所だけ。** 文を言い換えると、内容が同じでも変更の印が付く。読み手は印の無い所を読み飛ばすので、変えていない内容の文を触らない。
- **根拠の欄**：変えない行はファイル:行のまま。足した・変えた行は、指示・要件の番号（`指示 1`、`要件 R2`）や、実装があるならファイル:行。根拠の欄と行番号だけの違いは変更の印にならない。
- **共通のグループを変えるときは、同じ `data-key` の処理をすべて直す。** 共通と書いた行が処理の間で違うと `check` がエラーにする。共通のままにできないなら、変える処理のグループを分ける（`writing-rules.md` 12.4）。

## 3. AI の補完

指示や要件に無いことを AI が補った行には、`<span class="sup" data-why="補った理由">〔補完〕</span>` を付ける。「変更履歴」のタブの「AI が補った所」に、理由と一緒に載る。

- 設計を前へ進めるために補うのはよいが、黙って決めない。利用者が確かめられるように必ず印を付ける。
- 利用者が確認したら印を消す（新しい版になる）。
- 補うより利用者に聞くべきこと（業務の判断、データの持ち方など）は、未確認事項（未決）に載せる。

## 4. 新規設計

コードはまだ無い。読み手が後で実装できるように、現行の書き起こしと同じ粒度で書く。

1. 要件を番号付きで整理する（R1, R2…）。足りない所は、補って 〔補完〕 を付けるか、未確認事項に載せる。
2. 既存のコードを使う部分（共通の認証など）は、ソースを読んで現行の書き起こしと同じように書く。根拠はファイル:行。
3. 新しい部分は、根拠の欄に要件・指示の番号を書く。SQL は `data-kind="design"`（設計SQL）で、`data-src` に要件の番号を書く。
4. 初版を `rev --kind 基準` で保存し、指示と補完で直していく。

検証では、ソースとの照合の代わりに、要件・指示がすべて行に入っているか、行に要件・指示・〔補完〕のどれにも当たらない内容が無いかを確かめる（`verification.md`）。

## 5. 変更設計

1. 基準（v1）を作る。コードがあれば、変える処理を現行の書き起こしと同じ手順で書く。このフォーマットの設計書があれば、その部品を使う。別の形式の設計書しかなければ、読んで書き起こす（書かれていないことはコードか利用者に確かめる）。
2. `rev --kind 基準` で保存する。
3. 指示どおりに部品を直す。変える文の SQL は `data-kind="design"` にする。
4. 変更の影響を、共通のグループ・まとめの表（異常時の応答・データ変更とトランザクション）・他の処理の順に確かめる。

## 6. 仕様差分（コードレビュー用）

あるコミットを基準に、対象のコミットまでで変わった仕様を見せる。レビューする人は、コードの差分だけでは分からない「どの仕様が変わったか」を、変更の印の付いた行で読む。

```bash
D="${CLAUDE_SKILL_DIR}/scripts/ddoc.py"
# 1. 変わった所を調べる
python "$D" gitscope <基準> <対象> --repo <リポジトリ>
# 2. 基準のコミットのソースを別の場所に取り出す（今の作業ツリーを変えない）
git -C <リポジトリ> worktree add <出力先>/base-src <基準>
# 3. 影響する処理を、基準のソースから書き起こして保存する
python "$D" rev <出力先>/parts --kind 基準 --commit <基準> --note "基準のコミット"
# 4. 部品を対象のコミットの内容に直して保存する（書き直さない。変わった所だけ直す）
python "$D" rev <出力先>/parts --kind コミット --commit <対象> --note "<コミットの件名>"
# 5. 組み立てて、git の差分と突き合わせる
python "$D" build <出力先>/parts -o <出力先>/<名前>.html --title "仕様差分：…（<基準> → <対象>）" --src-root <リポジトリ>
python "$D" check <出力先>/<名前>.html --src-root <リポジトリ> --git-base <基準> --git-head <対象> --coverage
# 6. 取り出したソースを片付ける
git -C <リポジトリ> worktree remove <出力先>/base-src
```

- **影響する処理の決め方**：`gitscope` の関数から呼び出し元をたどり、起点（エンドポイント・ジョブ）を決める。共通の定数・型・ミドルウェアの変更は、多くの処理に影響する。変わっていない処理は文書に入れなくてよい。
- **対象の版は、基準の部品を直して作る。** 別々に書くと、文の言い回しの違いがすべて変更に見える。
- 「変更のある行だけ表示」は最初は無効のままにする（`--only-changes` は利用者が頼んだときだけ付ける）。有効にして渡すと、行が隠れていることに読む人が気づけない。読む人がチェックすると、変更の無い行、例外経路・非同期経路、節（逐次処理・入力項目・レスポンス・データ変更）が隠れ、変更のある所と処理の概要が残る。リンクで移った先は隠れない。チェックを外すと全行に戻る。変更のある行の字下げの親（分岐・繰返・try・「〜のとき」行）は、どの条件の中の変更かが分かるように色なしで残る（git の差分の前後の行と同じ）。グループの範囲の ▼ ▲ は、見えている最初と最後の行に出る。build が付けるので、部品には何も書かない。
- 根拠は対象のコミットの行番号にする。行番号だけの変化は印にならない。
- **一覧の先頭に「変わった仕様」の表を置く。** レビューする人は、行を読む前に何が変わったかを知りたい。`00-toc.html` の先頭に、見出し「<基準> → <対象> で変わった仕様」、変更の目的（1〜2 文）、表（変わった仕様｜基準｜対象｜該当する行）を書く。「該当する行」は `p3 No.31a` の形で書く（リンクになる）。判断が要る点（呼び出し元への影響、DB の移行など）は未確認事項に載せ、表の下から触れる。
- 削除した行の No. は参照できない（`check` の REF エラー）。文中で触れるときは No. を書かない。
- コミットごとに版を分ければ（`rev` をコミットの数だけ）、「今回の変更だけ」で最後のコミットの差分を見られる。

**`check --git-base` の読み方**

| コード | 意味 | 対応 |
|---|---|---|
| GIT（WARN）「どの行の根拠にも無い」 | コードの変更に、対応する行が無い | 仕様への影響を確かめ、行を足す。影響が無い（ログの文言など）なら理由を報告する |
| GIT（WARN）「文は変わっていない」 | 根拠にしている行のコードは変わったのに、行の文が同じ | 仕様が変わらない変更か確かめる。変わるなら文を直す |
| GITROW（INFO） | 行の文は変わったが、根拠が git の差分に無い | 根拠の指定漏れか、書き間違いの修正か確かめる |

import・コメント・空行だけの変更は、仕様に関係しないので対象にしない。

## 7. 確定する

利用者が「確定して」と言ったら、今の内容を新しい基準にする：`versions/` を別の名前に変えて残し、`rev --kind 基準 --note "確定"` で保存し直す。印は消える。No. の振り直しは、求められたときだけ行い、参照がずれていないことを `check --refs` で確かめる。
