# 品質検証チェックリスト — Phase 5

HTML を利用者に渡す前に、次の順で検証する。機械的に確かめられることはスクリプトで、
内容の正しさはソースとの突き合わせで確かめる。**実施していない検証を実施したと報告しない。**

## 1. 機械検証（必須）

```bash
node "${CLAUDE_SKILL_DIR}/scripts/seqdiag.cjs" validate <model.json>
node "${CLAUDE_SKILL_DIR}/scripts/seqdiag.cjs" build <model.json> -o <out.html>
node "${CLAUDE_SKILL_DIR}/scripts/seqdiag.cjs" verify <out.html> --screenshots <dir> --sizes 1600x900,1280x800 --full
```

| 確認項目 | 合格条件 |
|---|---|
| モデルの検証 | エラー 0。警告はすべて読み、直すか、直さない理由を説明できる |
| 根拠の照合 | ファイル未検出 0・行番号範囲外 0・記号不一致 0（ソースが手元にある場合） |
| 描画 | 全図・メソッド単位／クラス単位の両方で描画成功 |
| 対応付け | メッセージ・注記・枠・ライフラインがすべて「描画数 = 期待数」 |
| 文字の重なり・はみ出し | 0 件（出たら、ラベルを短くする・分岐条件を簡潔にする・図を分割する） |

`verify` はヘッドレスの Chrome / Edge / Chromium を使う。ブラウザが無い場合は、Playwright などのブラウザ操作ツールで
`<out.html>?verify=1` を開き、`window.__SEQDIAG_VERIFY__`（または `#seqdiag-verify-result` 要素の JSON）を確認する。
どちらもできない場合は「表示検証は未実施」と利用者に伝える。

スクリーンショットの撮り方：

- `--full`：図全体（大きい図は縮小されて細部が読めないので、全体の形の確認用）
- `--diagram <図ID> --select <ステップID>`：指定したステップを選んだ状態の画面（そのステップの周辺を等倍で確認でき、詳細パネルの内容も見られる）。
  気になる箇所はこれで拡大して確認する
- 画像はライトテーマで撮られる。`--theme dark` でダークテーマ（色の見分けが心配な場合に確認）
- ファイル名は `<図ID>@<幅>x<高さ>.png`、`--select` 付きは `<図ID>@<ステップID>@<幅>x<高さ>.png`（初期表示の画像を上書きしない）

## 2. 処理の正確性（ソースと突き合わせる）

解析した各メソッドについて、ソースを開き直してモデルと 1 行ずつ照合する（台帳 `*.analysis.md` があればそれを使う）。

- [ ] 呼び出し元・呼び出し先は正しいか（インターフェースの実装解決を含む）
- [ ] 呼び出しが欠落していないか（集約・省略したものは meta.omissions にあるか）
- [ ] 引数・戻り値の名前・型・意味は正しいか。戻り値が後続処理でどう使われるか書いたか
- [ ] 自己メッセージの粒度は適切か（重要な計算・状態変更・判定が残っているか、冗長でないか）
- [ ] 条件分岐の条件と各分岐の処理は正しいか。else・空の分岐・早期 return を落としていないか
- [ ] 例外の発生箇所・種類・捕捉場所・伝播経路・finally・再送出は正しいか
- [ ] DB 操作（種別・テーブル・条件・ロック・発行タイミング）は正しいか
- [ ] 処理の順序は正しいか（特に finally、コミット後のイベント、flush）
- [ ] 実行されない処理を追加していないか。推測で補った要素に inferred / unverified が付いているか
- [ ] 非同期と並列を取り違えていないか。critical は排他制御が確認できる箇所だけか
- [ ] トランザクションの範囲・伝播・ロールバック条件は正しいか

## 3. Mermaid の妥当性

生成器が正式な構文だけを出力し、描画で検証済みなので、通常は追加作業は不要。次の場合だけ確認する。

- [ ] モデルの構造（入れ子）がコードの構造と一致しているか（分岐の内側／外側の取り違えは構文上は正しく描けてしまう）
- [ ] Mermaid タブ（またはエクスポートした .mmd）で、意図しない `rect` / `Note` が無いか

## 4. 表示の確認（スクリーンショットを見る）

`verify --screenshots` の画像を Read で確認する（`@full.png` は図全体、`@1600x900.png` は画面）。

- [ ] 横長のビューア（上部ツールバー・中央の図・右の詳細パネル）になっている
- [ ] ライフライン・矢印・枠が欠けていない。枠の範囲（どこからどこまでが分岐・繰り返しか）が読み取れる
- [ ] 文字が重なっていない・読める大きさで表示される（初期表示は 80〜100%）
- [ ] 例外・非同期・DB の矢印が色と形で区別できる
- [ ] 推定・未確認の表示が意図どおり
- [ ] 枠の条件文・ライフライン名が不自然に折り返していない（verify は重なりを検出するが、折り返しは検出しない）

可能ならブラウザ操作ツールで、メッセージのクリック→詳細パネル、詳細参照のクリック→詳細図、検索→移動、ズーム、全体表示も試す。

## 5. 独立レビュー（推奨）

サブエージェントが使える場合は、作成者とは別のエージェントに次の 2 つを依頼する（並列でよい）。

- **構造レビュー**：モデル JSON とソースを渡し、「2. 処理の正確性」の観点で誤り・欠落・推測の混入を指摘させる。
  指摘には根拠行（ファイル:行）を付けさせる。
- **表示レビュー**：HTML のパスとスクリーンショットを渡し、「4. 表示の確認」の観点と操作性を確認させる。

指摘は採否を判断して反映し、build / verify をやり直す。サブエージェントが使えない場合、または利用者の指示・実行環境の方針で
サブエージェントの起動が制限されている場合（その方針がこのスキルより優先する）は起動せず、自分で 2〜4 を時間を置いて
もう一度行い、「独立レビューは未実施（理由）」と報告する。自己点検の最低限：

- 台帳（無ければモデルの全 call・throw）の各行について、根拠の行を開き直して呼び出し先・条件・例外名を照合した
- 分岐ごとに「どこで終わるか（return / throw / 合流）」をソースと照合した
- 全図の `@full.png` と、例外・TX・並列の箇所を `--select` で撮った画像を目で見た

報告にはこのうち実施したものを書く。

verify では検出できない見た目の問題もある（ライフライン名の詰まり、注記の行間、色の見分けにくさなど）。スクリーンショットは必ず目で見る。

## 6. 報告

利用者への報告に含めるもの：

- HTML のパス（と、モデル JSON のパス）
- 図の一覧（図名・メッセージ数）
- 検証結果（validate / verify の結果、レビューの有無と主な指摘・対応）
- 推定・未確認の件数と、利用者に確認してほしい事項（meta.unresolved）
- 集約・省略・対象外にしたもの
