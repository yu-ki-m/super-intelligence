# 出荷指示バッチ 処理仕様書（第1.2版）

## 1. 概要

入金済みの受注について、倉庫管理システム（WMS）へ出荷指示を登録するバッチ。

- 起動：ジョブスケジューラから毎日 6:00 に起動する（ジョブ名 `SHIP_INSTRUCTION`）。
- 処理単位：受注 1 件ごとにコミットする。途中で異常終了しても、処理済みの受注は確定させる。

## 2. 処理の流れ

### 2.1 対象受注の抽出

1. 受注テーブル（`orders`）から、次の条件をすべて満たす受注を受注日時の昇順で取得する。
   - `status = 'PAID'`
   - `ship_date <= 処理日`
2. 1 回の取得件数は最大 500 件とし、対象がなくなるまで繰り返す。
3. 対象が 0 件の場合は、7 章の処理結果通知のみ行って終了する。

### 2.2 受注ごとの処理

抽出した受注 1 件ごとに、次の処理を行う。

1. WMS の在庫照会 API（`GET /v1/stocks?sku=...`）で、受注明細の全商品の引当可能数を確認する。
2. 1 商品でも引当可能数が不足している場合：
   1. 受注の `status` を `'BACKORDER'` に更新する。
   2. 顧客への出荷遅延のお知らせメールを、メール送信キュー（`mail_queue` テーブル）に登録する（テンプレート `SHIP_DELAY`）。
   3. この受注の処理を終え、次の受注へ進む。
3. 全商品の在庫が足りる場合：
   1. WMS の出荷指示 API（`POST /v1/shipments`）に出荷指示を登録する。応答の出荷指示番号を受け取る。
   2. 出荷テーブル（`shipments`）に、受注番号・出荷指示番号・登録日時を登録する。
   3. 受注の `status` を `'SHIPPING'` に更新する。
4. 受注 1 件の処理が終わるたびにコミットする。

### 2.3 WMS 呼び出しの異常時

1. WMS の API がタイムアウト（30 秒）または 5xx を返した場合は、10 秒間隔で最大 3 回まで再試行する。
2. 再試行しても失敗した場合は、その受注の更新をロールバックし、バッチエラーテーブル（`batch_errors`）に受注番号とエラー内容を登録して、次の受注へ進む。
3. WMS が 4xx を返した場合は再試行せず、2. と同様にエラーとして記録して次の受注へ進む。

## 3. 処理結果の通知

すべての受注の処理が終わったら、処理件数（出荷指示・入荷待ち・エラー）を運用チームの Slack チャンネル（`#ops-shipping`）へ通知する。
エラーが 1 件以上ある場合は、メッセージにエラー一覧画面の URL を含める。

## 4. 未決事項

- 同じ受注が二重に処理されないための排他制御（同時起動の防止）の方式は検討中。
