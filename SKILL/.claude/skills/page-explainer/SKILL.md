# HTML に解説の案内を付ける

このスキルは、任意の HTML に、そのページを解説する案内を付ける。
案内は、ページの部分（見出し・表・図・列・ボタンなど）を 1 つずつ枠で囲んで指し、その横に出す吹き出しで、その部分が何で、何を示し、どう読み、どう使うのかを説明する。
対象のページは、報告書・設計書・分析のレポート・図のように読んで理解するページでも、業務の画面やツールのように操作するページでもよい。

案内の届け方は、依頼者が何を渡したかで 2 つに分かれる（依頼者の指示）。
HTML ファイルを渡されたときは、そのファイルに案内を埋め込む（この SKILL.md の「進め方」）。
URL を渡されたときは、Playwright でそのページを開いて案内を差し込み、読み手が「次へ」を押すたびに、クリックや入力を自動で行って別のページへ移り、移った先の画面も解説する（「URL を渡されたとき」と [ライブの案内](references/live-tour.md)）。

案内の説明は、一言の付け足しではない。
ページの分野を知らない読み手が、前提を知らなくても理解できるところまで説明する。
依頼者は、前提や論理の展開を省いた説明を理解しにくいと述べており、案内の読み手にも同じ人が多いと考えるためである。
このスキルの成果物の中心は、説明の文章である。
吹き出しのエンジンは、その文章を正しい部分の横に出すための入れ物にすぎない。

## 読み手から見た案内

案内を付けたページを開くと、読み手には次のものが見える。
依頼者への報告で使い方を説明するときにも、この表を使う。

| 部分 | 動き |
|---|---|
| 「解説」ボタン | 画面の隅（既定は右下）にある。押すと案内が始まり、案内を閉じたあとも残る。途中でやめていれば「続きから」か「最初から」を選べる。文字は、どのページでも「解説」にする（依頼者の指示。この案内は、操作の使い方だけでなく、ページに書かれている内容の解説にも使うため）。`launcher.label` で変えられるが、依頼者が別の文字を指定したときだけ変える |
| 案内への誘い | そのブラウザーで初めて開いたときだけ、ページが何のためのものかを述べる 1〜2 文と、案内の進め方を出す |
| 枠と暗幕 | 指す部分の周りを青い枠で囲み、ほかの部分を少し暗くする（ページの全体が読める薄さ）。案内を開いている間、ページは操作できない |
| 吹き出し | 指す部分の横（置く場所が無ければ上下、狭い画面では下か上に敷く形）に出る。上から「手順 n / N」「説明の細かさ k / K」「目次」、題名、冒頭の 1〜2 文（札を付けずに強調する）、「詳細」のボタン、「やめる」「戻る」「次へ」の順に並ぶ |
| 「詳細」 | 手順を開いた直後は、冒頭の 1〜2 文だけが見える。「詳細」を押すと、残りのまとまり（「前提」「言葉の意味」「例」「なぜそうなるか」「操作と結果」「注意」の札付き）と、その最後に「分からない」の行が開き、ボタンは「詳細を閉じる」に変わる。開いた手順は、戻ってきたときも開いたまま出る |
| 「分からない」 | 依頼者の指示で、詳細の中の最後に置く（詳細を開くまで見えない）。押すと、同じ手順の 1 段細かい説明に、詳細を開いた状態で切り替わり、細かい段では隣に「前の細かさに戻る」が出る。最も細かい説明で押すと、Claude Code や作った人に送る質問文を出す |
| 言葉の点線 | 前の手順で意味を説明した言葉に点線が付き、押すとその場で意味が出る |
| 目次 | 手順の一覧（押すとその手順へ移る）と、言葉の意味の一覧 |
| キー操作 | → で次へ、← で戻る、Esc で閉じる。案内の中で押したキーは、ページのキー操作には届かない |

URL のページを解説するライブの案内では、さらに次の動きが加わる。

| 部分 | 動き |
|---|---|
| 次の操作の予告 | 次の手順の前に自動で行う操作があると、吹き出しに「「次へ」を押すと、案内が次の操作を自動で行う。」と、操作の一覧が出る |
| 自動の操作 | 「次へ」を押すと、解説のときと同じ暗幕のまま、照らす所が操作する部分へ動き、橙の枠で囲む。横の吹き出しに「自動で操作中」と操作の中身（例：「検索」を押す）を出し、少し待ってから、クリックや入力を行う（依頼者の指示。急に画面が変わって驚かないようにするため）。暗幕・枠・吹き出しはクリックを受け取らないので、操作はページの部分にそのまま届く。操作が終わった画面（別のページでもよい）に、次の手順の吹き出しが出る |
| 戻る | 最初の画面から、その手順までの操作をやり直してから、その手順を出す |
| 自分で操作する手順 | 暗幕を出さず、吹き出しを開いたまま、読み手がページを操作できる。ページが移ると、移った先で吹き出しが出直す |

## 説明の決まり

案内の文章は、依頼者が示した次の 12 の決まりに従って書く。

1. 最初に、それが何なのかを 1〜2 文で説明する。
2. 専門用語を使う場合、その用語がこの文脈で何を意味するのか説明する。
3. 抽象語だけで説明しない。
4. 「A によって B が可能になる」と書く場合、A の何が B を可能にするのか説明する。
5. 主語を省略しない。「誰・何が、何を、どうする」の形を基本とする。
6. 前提知識を暗黙に要求しない。説明に必要な前提を先に示す。
7. 抽象的な説明の直後に具体例を 1 つ示す。
8. 複数の概念を一度に説明せず、1 つずつ説明する。
9. 「柔軟」「高度」「効率的」「最適化」など、具体的な意味が不明な形容を避ける。
10. 結論に至るまでの因果関係を飛ばさない。
11. 用語の羅列で説明しない。
12. 「分からない」と言われた場合、同じ説明を言い換えるだけではなく、説明の粒度を 1 段階下げる。

依頼者の指示で、案内の文には「つまり」という語を使わない。
冒頭の 1〜2 文にも札を付けず、要点を言い直す前置きを置かずに、指した部分が何かをそのまま書く。
検査（`guide.py validate`）は、「」の中の画面の文字の引用を除いて、この語を問題として示す。

もう 1 つの依頼者の指示で、吹き出しは、手順を開いた直後には冒頭の 1〜2 文だけを見せ、残りのまとまりと「分からない」のボタンは「詳細」を押すまで隠す。
読み手の多くは、冒頭の文だけを読んで次へ進む。
そのため、冒頭の 1〜2 文は、それだけを読んでも、指した部分が何で、何を示す（何をする）ものかが分かるように書く。
詳細の側では、冒頭の文を言い直さず、前提・言葉の意味・理由・例・読み方や使い方を足す。

案内のデータの形は、この決まりを守りやすいように作ってある。
例えば、各段の最初のブロックは必ず、指した部分が何かを述べる 1〜2 文で（決まり 1）、言葉の意味は 1 ブロックに 1 語で（決まり 2・8）、例は説明の直後に 1 つ置き（決まり 7）、因果は段ごとに矢印でつないで出し（決まり 10）、読み方や操作は「あなた」と「結果」の組で書く（決まり 5）。
決まり 12 は、手順ごとの「説明の細かさ」の段と「分からない」のボタンとして形にしてある。

書き始める前に、次の 2 つを必ず読む。
決まりの意味と悪い例・良い例は、ここにしか書いていない。

- [案内の文章の決まり](references/writing-rules.md)：12 の決まりを、案内の文章に当てはめたときの意味と書き方
- [説明の細かさの段の作り方](references/granularity.md)：「粒度を 1 段下げる」とは何をすることか、同じ手順を 3 段で書いた例

データの形は [案内のデータの形](references/guide-format.md) にある。

## URL を渡されたとき

`http://` か `https://` の URL を渡されたときは、[ライブの案内](references/live-tour.md) を読み、その進め方に従う。
`file:///` の URL は手元の HTML ファイルなので、ページを移りながら操作して解説してほしいと言われたのでなければ、次の「進め方」で埋め込む。
説明の決まり、「詳細」、説明の細かさの段は、埋め込む案内と同じである。

ライブの案内は、依頼者の本物のサイトを、依頼者のアカウントで操作する。
そのため、次の 2 つを必ず守る。

- データを送る・変える操作（送信・保存・削除・購入・確定・承認など）は、台本に書かない。
  その操作の手前までを見せ、押した結果は「操作と結果」の文で説明する。
  依頼者が、その操作を案内で行ってよいと明示したときだけ、その操作に `"allow_change": true` を付ける。
- パスワードを尋ねない・書かない・入れない。
  ログインが要るサイトは、`live-tour.mjs --login` で開いたブラウザーで、依頼者が自分でログインする。

流れは、画面を調べる（`live-tour.mjs --outline`）→ 台本を 1 手順ずつ書き足す（`--outline --at K` で、操作のあとの画面を確かめる）→ 検査（`guide.py validate`）→ 読み手役の点検 → ブラウザーで確かめる（`live-tour.mjs --check`）→ 依頼者のために案内を開く（`live-tour.mjs`、背景で実行）→ 報告、である。

## 進め方

この節は、HTML ファイルに埋め込む案内の進め方である。
コマンドは、このスキルのフォルダー（この SKILL.md があるフォルダー）を基準にした相対パスで書いている。
別のフォルダーから実行するときは、絶対パスにする。
必要なものは、Python 3.10 以上、Node.js 22 以上、Chrome か Edge である（外部のパッケージは使わない）。

作業用のファイル（案内のデータの JSON、点検用の文章、確認のスクリーンショット）は、ページのフォルダーではなく、作業用の一時フォルダー（以下 `WORK`）に置く。
セッションにスクラッチパッドのフォルダーがあれば、そこを使う。
依頼者のフォルダーに、案内の作業の跡を残さないためである。
案内のデータは HTML の中に埋め込まれるので、あとで直すときは HTML から取り出せる。

### 1. ページを読み、事実を集める

案内に書くことは、すべてページの事実に基づく必要がある。
そのため、最初にページの全体を調べる。

1. 指せる部分の候補と、ページの見た目を出す。

   ```sh
   node scripts/check-guide.mjs --outline PAGE.html --out WORK/outline
   ```

   候補の一覧には、見出し・領域・表・ボタン・入力欄ごとに、ページの中で 1 つに決まるセレクター、表示の文字、位置、どの画面の大きさで見えるかが出る。
   `WORK/outline` の `page-1440x900.png`・`page-390x844.png`（縦に長いページなら `page-full-1440x900.png`）を見て、読み手が見る画面を把握する。
2. HTML を、ページの性質に合わせて読む。
   - 読むページ（報告書・設計書・図）では、本文・見出し・表・図・凡例・記号やラベルの意味を読み、何についての文書で、結論はどこにあり、それぞれの結論がどの表や図の、どの値に支えられているかをつかむ。
   - 操作するページ（業務の画面・ツール）では、表示の文字だけでなく、スクリプトも読み、ボタンを押したとき・入力したときに、ページが実際に何をするのかを確かめる。
   大きなファイルは、候補の一覧のセレクターや文字で検索して、関係する所を読む。
3. コードから動きが分からない部分は、ブラウザーで操作して確かめる（Playwright などが使える場合）。
   確かめられなければ、その動きを事実として案内に書かない。
4. 次のことを `WORK` にメモする。
   ページの目的、誰が何のために読む（使う）か、読む順（使う順）、部分ごとの役割（何を示すか・何をするか）と、根拠（セレクターや本文の箇所・コードの行）。
   確かめた事実と、推測を分けて書く。

### 2. 読み手と範囲を決める

依頼者が読み手を指定していれば、それに従う。
指定が無ければ、読み手を「このページを初めて開き、〈ページの分野〉の言葉や前提を知らない人」とする。
パソコンの基本操作（押す、文字を入れる、画面を送る）はできるが、分野の言葉は知らない人である。
この想定は `reader` に書き、報告でも伝える。

案内が説明するのは、ページの読み方と使い方である。
読むページなら、各部分が何を示し、どの順にどう読めば、結論とその根拠をたどれるか。
操作するページなら、どこを見て、何を判断し、何を押すと何が起きるか、それはなぜか。
どちらも、ページの中身（表の全行、文書の全段落）を言い換えて並べ直すことではない。
ページの目的がどうしても分からないときだけ、依頼者に尋ねる。

### 3. 順路を決める

順路とは、どの部分を、どの順番で指すかである。
説明を書く前に順路を決めるのは、前提になる部分や言葉を、それを使う手順より前に置くためである。
順番が逆だと、読み手は、まだ説明されていない言葉で書かれた説明を読むことになる。

1. 1 つ目の手順は `target: null` にし、ページ全体を説明する。
   ページが何のためにあるか、誰が何のために読む（使う）か、この案内がどの順で部分を説明するか、を書く。
   読み手は、ここで全体像をつかんでから、部分の説明に進む。
2. 2 つ目からの並べ方は、ページの性質で決める。
   - 読むページは、理解を積み上げる順に並べる。
     多くの文書では、「全体の結論と構成 → 読むのに要る前提・凡例・記号 → 各章の主張と、それを支える表や図 → 限界・まだ分からないこと・次にすること」の順になる。
     ページの並び順と違ってもよい（凡例がページの最後にあるなら、凡例を使う表より先に指す）。
   - 操作するページは、読み手が実際に仕事をする順に並べる。
     多くの画面では、「最初に見る所 → 判断に使う所 → 操作する所 → 結果を確かめる所」の順になる。
3. 1 つの手順では、1 つの部分と、それに関わる 1 つの考えを説明する。
   ページの大きな領域ではなく、見出し・1 つの表・表の 1 つの列・図・ボタンのように、小さな部分を指す。
   大きな領域を指すと、吹き出しを置く場所が無くなり、指した部分に重ねて置くことになる。
4. 手順の数は、ページの読み方と使い方を一通り理解するのに要る数にする（多くのページで 5〜15）。
   8 より多くなったら、章（`chapters`）に分ける。
5. 一部の状態でしか見えない部分は、次のように扱う。
   - タブや開閉の見出しの中にある部分は、`reveal` に、見せるために押す部分を書く（押してよいのは、表示を切り替えるだけの部分に限る）。
   - 狭い画面で隠れる部分は、`missing` に、見えるようにする方法を書く。
   - 元に戻せない操作（送信、確定、削除）のあとにだけ出る部分（確認の画面、結果の知らせ）は、指さない。
     その操作をする部分の手順の「操作と結果」で説明する。
     案内のために、元に戻せない操作を押させない。
6. 順路を、表にして `WORK` に書く。
   列は、手順の id、題名、指す部分、説明する 1 つの考え、その手順で初めて意味を書く言葉、である。
   表を上から読み、どの手順も、それより前の手順で説明した言葉と部分だけで読めるかを確かめる。

### 4. 説明を書く

[案内の文章の決まり](references/writing-rules.md) と [説明の細かさの段の作り方](references/granularity.md) に従って、案内のデータ（`WORK/guide.json`）を書く。

1. まず、すべての手順の細かさ 1 を書く。
   そのあとで細かさ 2、必要な手順の細かさ 3 を書く。
   段ごとにまとめて書くと、同じ言葉を同じ意味で使い続けやすい。
2. 各手順の細かさ 1 には、多くの場合、次を書く。
   すべてが要るとは限らないが、抜くときは、読み手が困らないことを確かめてから抜く。
   - 冒頭の 1〜2 文：指した部分が何で、何を示す（何をする）ものか
   - 前提と言葉の意味：この手順を読むのに要るもの
   - 役割と理由：この部分が、ページの中で何のためにあり、読み手はここから何を知る（何をする）のか
   - 読み方・使い方：どこを見て、何と比べると何が分かるか（読むページ）、何を押すと何が起きるか（操作するページ）。どちらも「操作と結果」（`do`）のブロックで、あなたがすることと、その結果を組にして書ける
   - 例：このページに実際に出ている値・文で 1 つ
   - 注意：読み違えやすい点、元に戻せない操作
3. ページが示していること・ページが実際にすることとして書くのは、1 で確かめた事実だけにする。

### 5. 検査する

```sh
python scripts/guide.py validate WORK/guide.json
```

検査は、決まりのうち、文の形から判定できるものを確かめる。
冒頭が 1〜2 文になっているか、例があるか、例が続いていないか、細かい段が前の段より細かいか（文と文字の数が増えているか）、`added` があるか、「つまり」「柔軟」「高度」「効率」「最適」などを使っていないか、などである。
「問題」が 0 件になるまで直す。
「注意」（主語が無いかもしれない文、意味を書く前に使った言葉、言葉を並べた文、「〜によって〜できる」の文 など）は、1 件ずつ該当する文を読み、決まりに反していれば直す。

### 6. 読み手役で点検する

検査は文の形しか見ないので、「この言葉は読み手が知らない」「ここで因果が飛んでいる」という意味の問題は見つけられない。
[読み手役の点検](references/reader-review.md) に従い、ページのコードを読んでいない読み手の役に、案内の文章だけを読んでもらい、分からない所を挙げてもらう。
挙がった点を直し、もう一度検査を通す。

### 7. HTML に付ける

```sh
python scripts/guide.py inject PAGE.html --guide WORK/guide.json
```

`inject` は、検査に通ったデータだけを、エンジン（`assets/guide-engine.js`・`guide-engine.css`）と一緒に、`</body>` の直前に埋め込む。
埋め込んだ部分は、始まりと終わりの印（HTML のコメント）で囲まれる。
印の外側は 1 バイトも変えないので、`remove` で外すと、付ける前のファイルと同じになる。
すでに案内が付いていれば、前の案内を置き換える。

- 既定では、ページのファイルそのものに付ける（依頼が「このページに付けて」だからである）。
  依頼者が元のファイルを残したいと言ったときは、`--out` で、同じフォルダーの別の名前に書き出す。
  別のフォルダーに書き出すと、ページが相対パスで読む CSS や画像が見つからなくなる。
- ページが、別の道具（ほかのスキルのビルドなど）で作り直されるファイルなら、作り直すと案内は消える。
  そのことを報告に書く。

エンジンは、ページの要素には手を加えない。
ページに足すのは、`<html>` の直下の `<page-explainer>` という要素 1 つだけで、吹き出し・暗幕・ボタンはその中の Shadow DOM に作る。
そのため、ページの CSS は案内に届かず、案内の CSS もページに届かない。
例外として、指す部分へ画面を送る瞬間だけ、その要素に `scroll-margin-top` を付け、すぐに元へ戻す（指す部分の上に余白を空けて送るため）。

### 8. ブラウザーで確かめる

```sh
node scripts/check-guide.mjs PAGE.html --out WORK/check
```

確認の道具は、見えないブラウザー（Chrome か Edge のヘッドレス）を自分で起動し、終わると閉じる。
画面の大きさ 1440×900・1024×768・390×844 で全手順を出し、次を確かめる。
吹き出しやボタンの位置は、実際に見えている範囲を基準に判定する（幅の広いページを狭い画面で開くと、ブラウザーは見えている範囲だけをずらすことがあるため）。

- 指す部分が見つかり、見えているか。
- 吹き出しが画面に収まり、指す部分に重なっていないか。中身が横にはみ出していないか。
- 案内を付けても、ページの大きさとエラーが変わらないか（案内を止めたページと比べる）。
- 案内を開くボタンが、見えている範囲の中にあり、ページのボタンや文字に重なっていないか。
- 手順を開いた直後は冒頭の 1〜2 文だけが見え（「分からない」も見えない）、「詳細」で残りと「分からない」が開閉するか。
- 初めて開いたときの誘い、→・←・Esc、「分からない」と「前の細かさに戻る」、目次、続きから、最も細かい段での質問文、が動くか。

「直すべき問題」が 0 件になるまで直す。
よくある問題と直し方は次のとおりである。

| 出たもの | 直し方 |
|---|---|
| 指す部分が見つからない | 候補の一覧（1 の outline）からセレクターを選び直す。文字で探す書き方にする |
| 狭い画面で部分が見えていない | その画面で見えるようにする方法を `missing` に書く。または、狭い画面でも見える部分を指す |
| 部分が大きく、重ねて置いた（注意） | 領域の中の見出し・表・列・ボタンなど、小さな部分を指す |
| 吹き出しが指す部分に重なっている | `placement` で向きを変える。小さな部分を指す |
| 案内を開くボタンがページの部分に重なる（注意） | `launcher.position` を、重ならない隅に変える |
| 案内を付けたページにだけ出たエラー | エラーの文を読み、案内のデータかページとの相性を直す |

数字の確認だけでは、枠が意図した部分を囲んでいるか、吹き出しの文が指している部分と合っているかは分からない。
そのため、`WORK/check` のスクリーンショット（一覧は `index.html`）を見る。
スクリーンショットの名前は、`s<手順>-l<細かさ>-<画面の大きさ>.png` が手順を開いた直後（冒頭の 1〜2 文と「詳細」だけ）、`-open` が付くものが詳細を開いた状態である。
少なくとも、誘い（`welcome-*.png`）、1440×900 の全手順の開いた直後と詳細を開いた状態、390×844 の数手順、細かさ 2 以降を 1 つ、質問文（`handoff-*.png`）、暗い画面（`dark-*.png`）を見る。

### 9. 報告する

報告も、説明の決まりに従って書く。
最初に、何をしたかを 1〜2 文で書き、続けて次を書く。

- 案内を付けたファイルの場所と、開き方（案内を開くボタンの位置と文字、初めて開いたときの誘い、キー操作）
- 順路（手順の題名の一覧と、各手順の細かさの段の数）
- 想定した読み手（2 で決めたもの）
- 確かめたこと：検査の結果、読み手役の点検で直した点の数と主なもの、ブラウザーでの確認の結果（画面の大きさ、手順の数、残った注意とそのままにした理由）
- 確かめられなかったこと、推測で補わずに省いたこと
- 案内の直し方と外し方（下の「案内を直す・外す」のコマンド）
- スクリーンショットの一覧の場所（`WORK/check/index.html` の絶対パス）

## 「分からない」と言われたとき

- 案内からコピーした「【案内で分からない所】」で始まる文を貼られたときは、[説明の細かさの段の作り方](references/granularity.md) の 6 章に従い、その手順に 1 段細かい説明を足す。
  言い換えた説明を足すのではなく、つまずいた原因（知らない前提、飛んでいる段階、まとめて書いた操作）を書き出した段を足す。
- 依頼者が、会話の中で Claude の説明に「分からない」と言ったときも、同じ 7 章の考え方で、前の説明の粒度を 1 段下げて答える。

## 案内を直す・外す

```sh
# 付けた案内のデータを取り出す（直すときは、これを直して inject し直す）
python scripts/guide.py extract PAGE.html --out WORK/guide.json
# 読み物の文章にする（依頼者や読み手役に見せるとき）
python scripts/guide.py text PAGE.html --out WORK/guide.txt
# 案内を外す（付ける前と同じバイト列に戻る）
python scripts/guide.py remove PAGE.html
```

ページの中身が変わったときは、付け直す前に `check-guide.mjs` を流し、指す部分が見つかるかを確かめる。

## 道具とファイル

| ファイル | 役割 |
|---|---|
| `assets/guide-engine.js` | 案内のエンジン。データを読み、Shadow DOM の中に吹き出し・暗幕・ボタンを作り、指す部分の位置に合わせて毎コマ置き直す。`window.pageExplainer`（`open(手順)`・`close()`）でページの側からも開ける |
| `assets/guide-engine.css` | 吹き出しの見た目。どのページに付けても同じ見た目になるよう、ページの CSS や変数を借りない |
| `scripts/guide.py` | 検査（validate）・埋め込み（inject）・取り外し（remove）・取り出し（extract）・文章化（text） |
| `scripts/check-guide.mjs` | 見えないブラウザーでの確認と、指せる部分の候補の一覧（`--outline`） |
| `scripts/live-tour.mjs` | ライブの案内。Playwright でブラウザーを開いて案内を差し込み、台本の操作を行いながら案内する。確かめる（`--check`）、画面の部品の一覧（`--outline`）、依頼者が自分でログインするためのブラウザー（`--login`）も受け持つ |
| `scripts/outline-js.mjs` | 指せる部分の候補を、ページの中で集める式（`check-guide.mjs` と `live-tour.mjs` が使う） |
| `references/` | 文章の決まり、細かさの段の作り方、データの形、読み手役の点検、ライブの案内の進め方（`live-tour.md`） |

エンジンを直したときは、性質の違う 2 つ以上の HTML（明るいページと暗いページ、読むページと操作するページ、狭い画面より幅の広いページ）に案内を付けて、`check-guide.mjs` を通す。
ページの作りによって、部分の位置の測り方や、キー操作の受け取り方が変わるためである。

## 制約

- 案内が指せるのは、ページの文書の中の部分だけである。`iframe` の中の部分は指せない。
- ページの Content-Security-Policy がインラインのスクリプトを止めていると、案内は動かない（`inject` が注意を出し、確認の道具がエンジンの不在を問題として出す）。
- 1 つの HTML に、案内は 1 つだけ付けられる。複数のページにまたがって、操作しながら解説するときは、ライブの案内にする。
- 埋め込む案内では、読み手の進み具合（どこまで読んだか、誘いを出したか）は、そのブラウザーの localStorage に残る。ほかのブラウザーやほかの人には引き継がれない。ライブの案内は、サイトの localStorage に何も書かない。
- 動くブラウザーは、2022 年以降の Chrome・Edge・Firefox・Safari である（モーダルの dialog と Shadow DOM を使う）。
