# 読み手役の点検

案内を書いた本人は、ページのコードと分野の知識を持っているので、自分の文の前提の抜けに気づきにくい。
そこで、ページのコードを読んでいない読み手の役を立て、案内の文章だけを読んでもらい、分からない所を挙げてもらう。
検査（`guide.py validate`）が見るのは文の形だけで、「この言葉は読み手が知らない」「この因果は飛んでいる」という意味の問題は、読み手の目でしか見つからない。

## 進め方

1. 案内を、読み物の文章にする。

   ```sh
   python scripts/guide.py text guide.json --out guide.txt
   ```

2. サブエージェントを起動できるなら、下の依頼文で、読み手役を別のエージェントに頼む。
   ページの HTML やコードの場所は渡さない。
   渡すと、読み手役がコードから前提を補ってしまい、抜けに気づかなくなる。
   ブラウザーでの確認（SKILL.md の 8）を先に済ませていれば、スクリーンショットのフォルダーを渡してよい。
   読み手が実際に見る画面と、吹き出しの文を見比べられる。
   サブエージェントを起動できないときは、自分で下の観点を、1 手順ずつ、細かさ 1 から順に当てはめる。
3. 挙がった点を、1 つずつ直す。
   直さない点は、理由を 1 文で書けるものだけにする（例：「画面に書かれている言葉で、意味は前の手順で説明済み」）。
4. 直したら、検査を通し直す。

## 依頼文

〈 〉の中を埋めて渡す。

```text
あなたは、次の案内を初めて読む人の役をする。
あなたは〈reader（例：このページを初めて開き、脆弱性の調査をしたことがない人）〉である。
パソコンの基本操作（押す、文字を入れる、画面を送る）はできるが、このページの分野の言葉や仕事の流れは知らない。
このページのコードは読んでいない。〈スクリーンショットがあれば：吹き出しを出した画面は、次のフォルダーの sNN-l1-1440x900.png にある。〉

案内の文章は 〈guide.txt の場所〉 にある。
手順ごとに、細かさ 1 から順に読み、次の観点で、分からない所・引っかかる所を挙げる。
自分の知識で補って読まず、その文が書かれた時点までに案内が説明したことだけで読めるかを判定する。

1. 各手順の冒頭の 1〜2 文だけを読んで、その部品が何で、何をするものかが分かるか。
2. 意味が書かれていない言葉（分野の言葉、略語、画面のボタンや見出しの名前）。
3. 読む前に知っている必要があるのに、それより前に書かれていない事柄（前提の抜け）。
4. 「だから」「ため」「ので」「すると」の前後で、途中の段階が飛んでいる所。
5. 抽象的な説明だけで、直後に例が無い所。例が、何の例か分からない所。
6. 誰・何が（主語）が分からない文。読み手がするのか、画面がするのかが分からない文。
7. 1 つの文や 1 つのまとまりで、新しい考えを 2 つ以上出している所。
8. 「柔軟」「高度」「効率的」「最適化」「便利」のように、具体的に何が変わるのかが分からない形容。
9. 言葉を並べただけで、それぞれが何をするかが書かれていない所。
10. 細かさ 2・3 が、前の細かさの言い換えになっていて、新しく分かることが無い所。
11. 画面を見ても確かめられない断定（「〜に保存される」「〜に通知される」など）。
12. 手順の順番のせいで、後の手順で説明する言葉や部品を、先の手順で使っている所。

結果は、手順ごとに次の形で書く。問題が無い手順は「問題なし」と書く。
- 手順 N「題名」/ 細かさ K /「引用（その文の一部）」
  観点：番号
  何が分からないか：読み手として、何が分からず、何を知りたいか
  足すとよいもの：前提・途中の段階・例・言葉の意味のどれを、どこに足すか

最後に、案内全体を読み終えて、このページで自分が何をすればよいか（どこを見て、何を判断し、何を押すか）を、3〜5 文で書く。
書けないところがあれば、それがどの手順の不足によるかを書く。
```

最後の「何をすればよいかを書く」は、案内全体が、部品の説明の寄せ集めではなく、読み手の仕事の流れとしてつながっているかを確かめるためである。
読み手役が仕事の流れを書けなければ、最初の手順（ページ全体の説明）か、手順の順番に問題がある。
