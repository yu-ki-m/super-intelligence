# review-viewer：成果物のレビュー画面

エージェントの成果物をターミナルに貼ったりパスを並べたりするだけでは、利用者は複数の成果物を見比べにくく、HTML や画像はその場で見られない。感想をチャットに書き写す手間もかかり、どの成果物への感想かが曖昧になる。このスキルは、成果物をブラウザの画面に1件ずつ並べ、成果物ごとに判定欄とコメント欄を置く。エージェントは「どれを残し、どれを何のために直すか」を、自由記述を推測せずに構造化されたデータ（feedback.json）として受け取れる。

仕組みは3つの部品からなる。

| 部品 | 役割 |
| --- | --- |
| review.json（エージェントが書く） | 何をレビューしてもらうか。項目ごとの説明・ファイル・グループと、判定の選択肢 |
| `scripts/review_server.py` | review.json と成果物を読み、`assets/viewer.html` に埋め込んで返すローカルサーバー（127.0.0.1 のみ、Python 標準ライブラリだけ）。ブラウザを再読み込みするたびに読み直すので、成果物を直したら利用者は再読み込みするだけでよい |
| feedback.json（サーバーが書く） | 利用者の判定とコメント。入力のたびに自動保存（`in_progress`）され、「レビュー完了」で `complete` になってサーバーが終了する |

形式の詳細は `references/manifest-schema.md` にある。review.json を書く前に一度読むこと。

## 使わない場面

成果物が1つで短く、チャットに貼れば読める場合や、はい／いいえで答えられる質問は、チャットで聞く方が利用者の手間が少ない。レビュー画面は、見比べる対象が複数ある、HTML や画像のように見ないと判断できない、項目ごとに判定やコメントを集めたい、のどれかに当たるときに使う。

## 手順

### 1. レビュー対象を決めて review.json を作る

レビュー用のフォルダを、版（ラウンド）ごとに作る。例：`<作業フォルダ>/review/round-1/review.json`。同じフォルダでサーバーを起動し直すと、前回の feedback.json がそのまま「今回の入力」として画面に復元されるため、新しい版は新しいフォルダにする。成果物そのものは元の場所に置いたままでよい（パスは review.json からの相対パスか絶対パスで書く）。

各項目の `description` には、利用者に何を見て何を判断してほしいかを書く。利用者は説明を読んでから成果物を開くので、ここが曖昧だと判定の基準が項目ごとにぶれる。例えば「確認してください」ではなく、「初めての利用者が迷わずログインボタンまでたどり着けるか。要修正ならどこで迷うかを書いてください」のように、観点と判定の意味を書く。

判定の選択肢は、何も指定しなければ「採用／要修正／不採用」になる。作業に合わない場合は `verdict.options` で変え（例：見出し案の選定なら「残す／残さない」）、判定が要らない場合（文章への感想だけがほしいときなど）は `"verdict": false` にする。

```json
{
  "title": "ログイン画面の改善案レビュー",
  "instructions": "案Aと案Bのどちらを残すかを決めてください。迷う項目は未判定のままでかまいません。",
  "groups": [{"id": "A", "label": "案A"}, {"id": "B", "label": "案B"}],
  "items": [
    {"id": "a-screen", "title": "案Aの画面", "group": "A",
     "description": "初めての利用者が迷わずにログインできそうか。要修正なら、どこで迷うかを書いてください。",
     "files": ["../../designs/a/login.html"]},
    {"id": "b-screen", "title": "案Bの画面", "group": "B",
     "description": "案Aと同じ観点で見てください。",
     "files": ["../../designs/b/login.html", "../../designs/b/notes.md"]}
  ]
}
```

書いたら検査する。形式の誤りや存在しないファイルがここで分かる。

```bash
python <このスキルのフォルダ>/scripts/review_server.py <review.json> --check
```

Windows では `python` を使う（`python3` は Microsoft Store の案内が開くことがある）。`python` が無ければ `py -3`。

### 2. サーバーをバックグラウンドで起動し、利用者に伝える

Bash ツールの `run_in_background: true` で起動する。`timeout` は上限の `7200000`（2時間）を指定する。既定の30分のままだと、利用者がゆっくりレビューしている途中でサーバーが止められてしまうため。

```bash
python "<このスキルのフォルダ>/scripts/review_server.py" "<review.json>"
```

PowerShell ツールの `run_in_background` でも同じように動く（パスに日本語や全角文字があっても文字化けしない）。

起動すると、サーバーはブラウザを自動で開き、標準出力に `URL: http://127.0.0.1:<ポート>/` を出す。既定のポート（3118）が使用中なら空いているポートに切り替わるので、URL はバックグラウンドの出力ファイルを Read して確かめる（起動直後で空なら、少し後にもう一度読む）。ブラウザを開けない環境では URL を出すだけになる。

利用者には、次の3点を短く伝える。

- URL（ブラウザが開かなかった場合に開けるように）
- 何を見て、何を判断してほしいか（項目数と、判定の選び方）
- 終わったら「レビュー完了」を押せば結果が自動でこちらに届くこと。迷う項目は未判定のままでよいこと

伝え方の例：「レビュー画面を開きました（http://127.0.0.1:3118/）。ログイン画面の案が2つあります。それぞれ採用・要修正・不採用を選び、直してほしい点があればコメントに書いてください。迷うものは未判定のままで大丈夫です。最後に右上の「レビュー完了」を押すと、結果が自動でこちらに届きます。」

利用者がレビューしている間は、出力ファイルを繰り返し読んだり sleep で待ったりしない。完了するとバックグラウンドのコマンドが終了し、Claude Code から通知が届く。その間に利用者から話しかけられたら、普通に応じる。

### 3. 完了の通知を受けたら feedback.json を読み、結果を示す

通知が届いたら、まず出力の末尾を見る。

| 出力 | 意味 | すること |
| --- | --- | --- |
| `REVIEW_COMPLETE: <パス>` と `SUMMARY: ...` | 利用者が完了を押した | feedback.json を読んで結果をまとめる |
| どちらも無い（時間切れで止められた、異常終了など） | 利用者はまだ途中の可能性がある | feedback.json の `status` を確かめる。`in_progress` なら、同じコマンドでサーバーを起動し直し、利用者にブラウザの再読み込みを頼む（入力は保存済みなので消えない） |

feedback.json は `reviews` にマニフェストの全項目を含む。判定ごとに項目をまとめ、次のように扱う。

- **採用**（または作業ごとの「残す」側の判定）：そのまま次の工程に進める。コメントがあれば、採用の条件や補足として扱う。
- **要修正**：コメントを修正の指示として扱う。コメントが無い、または指示が曖昧なら、推測で直さずに何を直すかを利用者に確かめる。
- **不採用**：コメントに理由があれば記録に残す（次の版で同じ方向の案を出さないため）。
- **未判定でコメントあり**：判定は迷っているが、コメントには意見がある。コメントの内容を示し、どう扱うかを利用者に確かめる。
- **未判定でコメントもない**：「問題なし」とは扱わない。`viewed: false` なら「見ていない」、`viewed: true` なら「見たが判断しなかった」として、未確認の項目に分けて伝える。利用者が判定しなかったのは、迷ったか見落としたかのどちらかで、エージェントがそれを了承とみなすと、利用者の意思でない決定が次の工程に入ってしまうため。
- **全体へのコメント**（`overall_comment`）：項目をまたぐ指示として、各項目の対応より先に読む。

利用者には、判定ごとの件数、項目ごとのコメントの要約、対応方針を示す。

```
レビューの結果を受け取りました（5件：採用 1・要修正 2・不採用 1・未判定 1）。

全体へのコメント：案Aを基本に進めてほしい

要修正
- 案Aの提案書：目標値の根拠を追記 → 現状値の出典を本文に足します
- 案Aの画面：エラー文が小さい → 文字サイズとアイコンを変えます

不採用
- 案Bの画面：入力欄が多すぎる（理由を記録しました）

未確認
- 案Bのロゴ：画面に表示されていません（見ていない可能性があります）

この方針で案Aを直します。未確認の「案Bのロゴ」は、案Bを不採用にしたので対象外にしてよいですか。
```

判定の選択肢を変えた場合は、各選択肢が次の作業で何を意味するか（「残す」は採用と同じ、など）を review.json を作った時点の意図に合わせて読み替える。

### 4. 次の版をもう一度レビューしてもらう

修正した版を見てもらうときは、新しいフォルダ（`round-2/`）に review.json を作り、前回の feedback.json を指定する。

```json
"previous_feedback": "../round-1/feedback.json"
```

同じ成果物には前回と同じ `id` を付ける。そうすると、各項目に前回の判定とコメントが「前回のレビュー（参考）」として出て、利用者は前回の指摘が直ったかを確かめられる。`description` には「前回の指摘（○○）をこう直した」と書くと、利用者が差分を探す手間が減る。前回不採用になった項目は、改めて見てもらう理由がなければ入れない。

### 5. 終わったらサーバーを止める

完了ボタンが押された場合、サーバーは自分で終了しているので何もしなくてよい。

利用者が完了ボタンを押さずにチャットで「終わった」と言った場合は、feedback.json を読んで手順3と同じように進める（`status` は `in_progress` のままだが、保存済みの内容は最新）。その後、バックグラウンドのタスクを止める（TaskStop ツールにタスク ID を渡す。使えなければ、起動時の出力にあるポートで待ち受けているプロセスを止める）。止めずに次のサーバーを起動しても、ポートは自動で切り替わるので動作はするが、古いサーバーが残り続ける。

## サーバーを使えない場合（--static）

ブラウザとエージェントが別の環境にあるなど、ローカルサーバーに接続できない場合は、1つの HTML ファイルを書き出す。

```bash
python "<このスキルのフォルダ>/scripts/review_server.py" "<review.json>" --static "<出力先>/review.html"
```

利用者にはこのファイルを開いてもらう。入力はブラウザ内に控えられ（再読み込みしても残る）、「レビュー完了」を押すと feedback.json がダウンロードされる。サーバーが無いので完了の通知は届かない。利用者に「完了を押したら知らせてほしい」と伝え、知らせを受けたら、ダウンロードフォルダ（同名のファイルがあると `feedback (1).json` のような名前になる）の場所を確かめてから読む。静的表示では、HTML が相対パスで読む CSS・画像は表示されない。

## 困ったとき

| 状況 | 対処 |
| --- | --- |
| `ERROR:` で起動しない | メッセージに review.json の誤り（id の重複、items が空、JSON の書式）が出る。直して `--check` から |
| 画面に「レビュー対象を読み込めませんでした」 | review.json を書き換えている途中か、壊れている。直してから利用者に再読み込みを頼む |
| 成果物を直したのに画面が古い | 利用者にブラウザの再読み込みを頼む（サーバーの再起動は不要） |
| 画面に「保存に失敗しました」 | サーバーが止まっている。手順3の表のとおり起動し直す。入力はブラウザ内にも控えてある |
| ファイルが大きくて先頭だけ表示される | 仕様どおり（テキストは256KBまで）。画面の「全文を開く」で全体を見られる |

## このスキルのテスト

`tests/test_review_server.py`（標準ライブラリのみ）はサーバーを実際に起動して、保存・ポートの切り替え・完了による終了・`</script>` の埋め込みなどを確かめる。`tests/browser_check.mjs`（Playwright が必要）は、ブラウザで表示・判定・再読み込み後の復元・完了の確認を操作して確かめる。どちらも Windows の Git Bash と PowerShell で通ることを確認済みで、「完了ボタン → サーバー終了 → Claude Code のバックグラウンド通知」の流れも Bash と PowerShell の両方のツールで動作を確認している。
