# 台本からパワポを作る

台本は、話し手が声に出す言葉と、どこでスライドを切り替えるかを決めている。
スライドの役目は、その言葉を目で追える形にすることだ。
だから、スライドに台詞を書き写さない。
台詞は発表者ノートに入れ、スライドには、その区切りで聞き手に見せたいもの（図、比較、表、大きな数字、問い）を置く。

このスキルは、台本の〔スライド：…〕の指示を1枚ずつスライドにし、実際の PowerPoint で全部を画像にして確かめてから渡す。
確かめる手順まで含めるのは、PowerPoint の文字の折り返しや幅は、組み立てるコードからは見えないからだ。
日本語の語の途中での改行や、箱からのはみ出しは、画像を見て初めて分かる。

## 作るもの

- 16:9 の .pptx。表紙1枚と、台本の〔スライド：…〕1つにつき1枚（台本の1枚目の指示が表紙なら、それを表紙にする）。
- スライドの左上には段階名（台本の ### 見出し）を小さく出し、タイトルにはそのスライドで伝えることを短く書く。
- 下の出典の行には、根拠（問題番号、資料名、時点）と、「説明のための例」「仮の数字」などの断りを書く。資料は聞き手に見せてよい名前（「製品資料」「導入企業へのインタビュー」など）で書き、ファイル名やフォルダー名は書かない。スライドは聞き手に映すものだからだ。
- 発表者ノートには、その区切りの台詞を、〔間〕などの指示も含めて台本のまま入れる。話し手は、発表者ビューで台詞を見ながら話せる。
- PowerPoint のセクションを、台本の段階ごとに分ける。
- 保存先は台本と同じフォルダーで、名前は台本の名前から「台本」を除いて「スライド」を付ける（例：`研修_第1回_台本.md` → `研修_第1回_スライド.pptx`）。同じ名前のファイルがすでにあるときは、上書きする前に利用者に聞く。
- Web のサービスに上げたり、公開したりはしない。ファイルとして渡す。

## 手順

### 1. 作業フォルダーを用意する

組み立てには Node.js の pptxgenjs を使い、確かめには Windows の PowerPoint を使う。
一時フォルダー（scratchpad があればその中）に作業フォルダーを作り、次を実行する。

```powershell
& "<このスキルのフォルダー>/scripts/setup.ps1" -WorkDir "<作業フォルダー>"
```

部品（`lib.js`、`inspect.js`、`render.ps1`、`build.ps1`）と見本（`deck-example.js`、`example_script.md`）が写され、pptxgenjs と jszip が入る。
最後に、PowerPoint とフォントが使えるかが表示される。
PowerPoint がないときも組み立てはできるが、画像での確かめはできない。そのことを最後の報告で必ず伝える。

### 2. 台本を読む

台詞だけでなく、台本の表や注記も読む。スライドの中身を決める材料が、そこにあるからだ。

- **発表の条件**：聞き手、場、持ち時間。経営層向けの提案なら文字を減らし、自分で読む復習用なら図に少し説明を足す。
- **〔スライド：…〕の指示**：何を見せるかが書いてある。指示の言葉は、そのスライドで必ず見せるものとして扱う。
- **問いと答え**：「答える段階」が後ろにある問いは、答えをスライドに書かない。答えが先に見えると、問いが成り立たないからだ。答えはノートの台詞に残る。
- **ネタの出どころ**、**確かめてほしいこと**：【仮】の数字や比喩、説明のために作った例、版で変わる事実が書いてある。スライドに載せるときは、出典の行に断りを書く。
- 〔スライド：【仮】…の画面〕のように、手元にない画像を指示している所は、画像の置き場所（`IMGPH`）にして、差し替える画像を書いておく。画面の写真やイラストの指示を、それらしいコードや架空の金額・名前を入れた作り物の画面で埋めない。作り物は、発表の直前に差し替え忘れると、そのまま本物として映るからだ。

### 3. 出どころの資料を確かめる

台本が根拠として資料（問題集、調査結果、データ、仕様書）を挙げていて、それが手元で読めるなら、スライドに載せる部分を原典で確かめる。
スライドは台本より多くのことを目に見える形で載せる（選択肢の判定、ツール名、表の値）ので、台本にない細部を推測で埋めると、間違いがそのまま画面に出るからだ。

- 名前や値は原典の表記に合わせる（例：問題文のツール名や項目名）。
- 台本にも原典にもない事実（画面のメニューの道順、設定の手順、金額や日付）を、親切のつもりで足さない。確かめていない手順がスライドに載ると、聞き手はそれを正しいものとして持ち帰るからだ。足した方がよいと思ったら、スライドには載せず、報告で提案する。
- 判定や分類のラベル（「最善策」「次善策」など）は、原典の記載に合わせる。台本と原典が食い違っていたら原典に合わせ、報告で伝える。
- 原典にない例を図のために作るときは、出典の行に「〇〇は説明のための例」と書く。事実と区別できるようにするためだ。
- 資料が台本の横にないときは、近くのフォルダーを探してよい。見つけて使ったら、どこで見つけたかと、台本と同じ版か確かめてほしいことを報告で伝える。見つからなければ、照合できなかったことを伝え、値は台本のまま載せる。

### 4. スライドの割り方を決める

〔スライド：…〕の指示があれば、1つの指示を1枚にする。指示を足したり、まとめたりはしない。話し手は、指示の所でスライドを進めるつもりで練習しているからだ。

指示が別の書き方（【スライド3】…、（スライド：…）、「スライド：」で始まる行など）なら、それも指示として扱う。
台本の写しを作業フォルダーに作り、その行を〔スライド：…〕の形に置き換えてから組み立てる（`build` が読むのはこの形だけだ）。
指示の中身（何を見せるか）は書き換えない。指示に付いた注記（【スライド6の注記】出典…など）は、そのスライドの出典の行に入れる。
段階の見出しの末尾にある時間の目安（「（0:00〜1:30）」など）は、`build` が段階名から外す。聞き手に見せるものではないからだ。
台本の最初の指示が表紙（タイトルと副題）なら、その指示を `def(…, "TITLE", タイトル, 副題, …)` で作る。自動の表紙は作られず、表紙が二重にならない。

指示がない原稿では、先に割り方を決める。

- 1枚に伝えることは一つ。目安は、講義や提案なら1枚1〜2分、LT なら30秒前後。
- 区切りは、話題が変わる所と、聞き手に何かを見せる所（問い、数字、比較）に置く。
- 台本の写しを作業フォルダーに作り、区切りの所に〔スライド：見せるもの〕の行を入れる。元の台本は変えない。
- 組み立てはこの写しから行い、最後の報告で、どこで区切ったかを一覧で伝える。

### 5. 配色を決める

題材に合った配色を選ぶ。同じ連載（第1回、第2回…）の続きなら、前の回と同じ配色にする。並べたときに一つの連載に見えるようにするためだ。
`createDeck({ theme })` に12色を渡す。色の役目は `lib.js` の既定の配色の注記どおりにする（accent1 は強調、accent2 は良い・正解、accent5 は補足の文字など）。役目を守ると、ラベルや枠の色の意味がスライドをまたいでそろう。

### 6. 各スライドを設計する

[references/design.md](references/design.md) の目次を見て、その区切りで見せたいものに合う型の節だけを読む。
参照資料を最初に全部読むと、その分が後のやり取りのたびに積み上がり、時間と利用量がかさむ。必要になった所だけを読む。
設計で守ることは次のとおり。

- **図が主役**。文章は、図の説明として一、二行にする。台詞を書き写さない。
- **1枚に一つのこと**。タイトルは、そのスライドで伝えることを全角20字前後で書く（32pt で1行に収まる長さ）。
- **比べるものは並べる**。前と後、案と案、正しい形と誤った形は、左右か上下に並べ、良い方に緑の枠を付ける。
- **選択肢の判定**は、ラベル付きの行（`ROWS`）にする。行の間隔は 0.42 インチ以上にする（狭いとラベル同士がくっつく）。
- **名前**（コマンド、設定、項目名）は、チップ（`CHIP`）かコードの箱（`CODE`）に入れ、本文と区別する。
- **大きな数字**は `STAT` で見せ、何の数字かを一行で添える。
- **暗い背景**（`DARK`）は、掴みと回収のように、聞き手の注意を一点に集める所だけに使う。
- 同じ型のスライドでは、タイトルと本文の位置をそろえる。

部品の使い方は `deck-example.js` を見れば足りることが多い。引数や表のセルの書き方で迷ったときだけ [references/components.md](references/components.md) を読む。

### 7. 組み立てて、画像にする

`deck-example.js` を写して `deck.js` を作り、スライドを1枚ずつ `def(…)` で書く。

```js
def("台本の〔スライド：…〕の中身（一字も変えずに）", "CONTENT", "タイトル", "出典の行", (s) => { /* 部品を置く */ });
```

`def` の最初の引数は、台本の指示の文字列と完全に一致させる。`build` は、台本の指示の数と順番が定義と合うかを確かめ、ずれていれば止まる。これで、スライドとノートの台詞が1枚ずれる事故を防げる。

組み立て、中身の確かめ、画像化は、次の一つのコマンドで流す。やり取りの回数が減り、時間も利用量も少なくて済む。

```powershell
& "<作業フォルダー>/build.ps1" -Script "<台本.md>"
```

`out.pptx` ができ、`inspect.js` がスライドごとの本文の先頭とノートの行数を出し、ノートのないスライド、空の表のセル、壊れた文字を最後にまとめる。
続けて、全スライドが `png/` に PNG で書き出され、4枚ずつ並べた `grid01.png`… ができる。

### 8. 画像で確かめる

grid を Read で見て、次の点を確かめる。
1枚ずつの PNG（`s05.png` など）は、grid で判断に迷った所だけを見る。画像は1枚でも grid と同じだけの量を使うので、全スライドを1枚ずつ見ると、grid の4倍かかる。

- 文字が箱や画面の端からはみ出していないか、切れていないか
- 語の途中で改行していないか（「確か／める」「ツー／ル」）。1文字だけが次の行に落ちていないか
- 文字や矢印が、ほかの箱や線に重なっていないか
- 選択肢のラベル同士、行同士がくっついていないか
- 表のセルが空になっていないか
- 暗い背景の上に暗い文字がないか
- 英字の下線（`tool_use` の `_`）が見えているか
- 同じ型のスライドで、タイトルや本文の位置がそろっているか
- 後で答える問いの答えが、スライドに出ていないか

直したら、`build.ps1 -Script "<台本.md>" -Only 3,7` のように直したスライドだけを書き出し直し、grid で確かめる。新しい問題がなくなるまで繰り返す。
問題の原因が分からないときは、[references/pitfalls.md](references/pitfalls.md) で、起きていることと直し方を引く。

### 9. 保存して報告する

`out.pptx` を、台本と同じフォルダーに「作るもの」で決めた名前で写す。写した後のファイルに `node inspect.js` をもう一度流して、枚数とノートを確かめる。
報告には次を書く。

- 保存した場所と枚数（表紙＋指示の数）
- 指示とスライドの対応を確かめたこと、画像で確かめて直したこと（PowerPoint がなかったなら、確かめていないこと）
- 原典に合わせた点、台本と原典が食い違っていた点
- 説明のために作った例と【仮】の所。差し替えるときに見る場所として伝える
- 答えをノートにだけ置いた問い
- 指示のない原稿だった場合は、区切った場所の一覧
- `deck.js` は作業フォルダーにあり、台本を直したら作り直せること。残したいと言われたら、台本の横に置く

## 手直しと作り直し

前に作ったスライドの手直しを頼まれたら、作業フォルダーに `deck.js` が残っていれば、それを直して組み立て直す。
残っていなければ、できている .pptx を `node inspect.js --full` で読み、同じ形の `deck.js` を作り直してから直す。
台本が変わったときは、指示の数と順番が変わっていないかを先に確かめる。`build` が止まった所が、ずれた所だ。
