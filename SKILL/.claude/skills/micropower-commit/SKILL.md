# プロパティ単位のタスク・コミット分割

このスキルは、別のスキルが作った実装計画のタスクを、利用者が決めた粒度に細分化し、コミットも同じ粒度に分ける。
あわせて、細分化したことで初めて見えた考慮漏れを指摘する。
何を作るか、どの設計にするかといった計画の大枠は、spec-kit や superpowers などの別のスキルが決める。
このスキルは、その大枠を変えずに、分割と指摘だけを行う。

## 立ち位置

| 担当 | 扱うこと |
|-|-|
| spec-kit・superpowers（writing-plans）など | 要件・設計・大枠の計画を作る |
| このスキル | 計画のタスクとコミットを分割し、分割で見えた考慮漏れを指摘する |
| speckit.implement・superpowers（executing-plans など） | 分割後の計画に沿って実装する |

計画がまだなく、依頼の範囲が1つの経路より広いときは、先に計画を作るスキルを使うことを一言勧める。
1つの経路で済む小さな依頼なら、依頼文とコードから直接分割してよい。

## 分割の規則

原典は利用者のシートで、写しを `references/source-rule.md` に置いている。
この規則は、計画を作った側のスキルが持つタスクの大きさの基準（superpowers の「新しいレビューアーの関門に値する最小の単位」など）より優先する（2026-11-15 に利用者が決定）。
規則は次の4つである。

1. **1コミット＝1タスク。**
   計画のタスクとコミットを1対1にする。
2. **1つのコミットに1つのプロパティ。**
   プロパティは、経路の上を運ばれるデータ項目（例：書籍ID、書籍名、金額、解説）を指す。
3. **1つのコミットの中で、経路を1回通す。**
   経路は、1つの操作の始まりから終わりまでの処理のつながり（例：フロントエンド→バックエンド→フロントエンド）を指す。
   その後にも続く処理（画面の更新、通知など）があれば、それも同じコミットに含める。
4. **経路の最初のプロパティに限り、責務ごとにさらに分ける。**
   責務は、経路の各段が受け持つ処理（画面での選択、リクエストの送信、コントローラーでの受け取りなど）を指す。
   最初のプロパティは、経路の始まりから終わりまで、すべての段を1段ずつ別のコミットにする。
   終わりの段まで分けることは、2026-11-15 に利用者が決めた。

書籍の登録をリクエストする経路は、次のように分ける。
コミット8は、原典のシートにはない。
最初のプロパティを経路の終わりまで分けるという利用者の決定に合わせて足した。

| コミットに含める文言 | 概念単位 | コミット粒度 | 内容 |
|-|-|-|-|
| `_書籍ID_1_` | 責務単位 | コミット1 | フロントエンドから書籍を選択 |
| `_書籍ID_2_` | 責務単位 | コミット2 | フロントエンドから書籍IDをリクエストで送信 |
| `_書籍ID_3_` | 責務単位 | コミット3 | バックエンド（コントローラー）が書籍IDを受け取る |
| `_書籍ID_4_` | 責務単位 | コミット4 | バックエンド（サービス）が書籍IDを受け取る |
| `_書籍ID_5_` | 責務単位 | コミット5 | バックエンド（リポジトリ）が書籍IDを登録 |
| `_書籍ID_6_` | 責務単位 | コミット6 | バックエンド（サービス）がレスポンスを生成 |
| `_書籍ID_7_` | 責務単位 | コミット7 | バックエンド（コントローラー）がレスポンスを生成 |
| `_書籍ID_8_` | 責務単位 | コミット8 | フロントエンドがレスポンスを受け取る |
| `_書籍名_1_` | 1プロパティ単位 | コミット9 | 書籍名プロパティを追加（フロントエンド→バックエンド→フロントエンド） |
| `_金額_1_` | 1プロパティ単位 | コミット10 | 金額プロパティを追加（フロントエンド→バックエンド→フロントエンド） |
| `_解説_1_` | 1プロパティ単位 | コミット11 | 解説プロパティを追加（フロントエンド→バックエンド→フロントエンド） |

規則4の理由は、シートに書かれていない。
このスキルでは、次のように解釈している。
最初のプロパティのコミットは、経路の骨組み（画面の部品、APIの呼び出し、エンドポイント、サービス、リポジトリ、テーブル）を新しく作る。
骨組みの各段は、それぞれ別の設計判断（APIの形、トランザクションの範囲、エラーの返し方など）を含む。
そのため、段ごとにコミットを分けると、レビューで1段ずつ確かめられ、問題がどの段にあるかも分かる。
骨組みができた後のプロパティの追加は、既存の経路に項目を1つ通すだけなので、1コミットに収めても変更は小さく、経路全体が動く状態を保てる。

### シートに書かれていない場合の解釈

次の解釈は、分割案の「仮置きした解釈」の節に書く。
利用者が違うと言えば、それに従う。

- **新しい経路ごとに規則4を当てはめる。**
  既存の経路にプロパティを足すだけなら、骨組みがすでにあるので、責務ごとには分けない。
  新しい経路でも、変更せずに使う段（例：既存のリポジトリをそのまま呼ぶ）には、コミットを作らない。
- **最初のプロパティは、それがないと経路が成り立たないものを選ぶ。**
  多くは、操作の対象を特定する識別子（例：書籍ID）である。
  選んだ理由を分割案に書く。
- **層の呼び出しは、呼ばれる側のコミットに入れる。**
  例えば、コントローラーからサービスを呼ぶ処理は「サービスが書籍IDを受け取る」コミットに入れる。
  こうすると、どのコミットの時点でも、まだない層を呼ばずに済み、ビルドとテストが通る。
- **テストは、そのテストが確かめる処理と同じコミットに入れる。**
  テストを先に書く手順（TDD）は、1つのコミットの中で守る。
- **データベースの変更も経路の一部にする。**
  テーブルの作成は最初のプロパティの保存の段のコミットに、列の追加はそのプロパティのコミットに入れる。
- **プロパティを運ばない作業**は、次の基準で扱う。扱いがぶれないよう、この順に当てはめて決める。
  1. **リポジトリのファイルを変えない作業**（本番の行数を数える、API の利用者に知らせる、リリースの日を決める、手で確かめる）は、タスクにしない。
     コミットにならないからである。
     代わりに、分割案の「コミット以外の作業」として書き、利用者に示す。
  2. **リポジトリのファイルを変える作業で、あるプロパティの変更がないと意味がないもの**（そのプロパティの列を足す移行のスクリプト、そのプロパティのテスト）は、そのプロパティのタスクに含める。
  3. **リポジトリのファイルを変える作業で、特定のプロパティに属さないもの**（設定、ライブラリの導入、共通部品、適用と切り戻しの手順書をリポジトリに置く）は、小さければそれを最初に必要とするタスクに含め、大きければ1つのタスク（1コミット）にする。
     文言は作業の対象の名前で作る（例：`_適用手順_1_`）。
  4. **リポジトリにある文書が、今回変えるものとコードの食い違いを含むとき**（spec.md、README、API の説明が、変える項目の名前・型・API・上限を違って書いている）は、文書を直すかを利用者に確かめ、直すなら1つのタスク（1コミット）にする（例：`_仕様書_1_`）。
     直さないと決めたときも、考慮漏れの指摘として、その文書が古いことと理由を残す。
     読む人が古い文書を信じて、また同じ誤りを繰り返さないようにするためである。
  単独で残すときの文言は、対象の名前で作る（例：`_認証設定_1_`）。
- **1つのプロパティを足すのに新しい骨組みが要るとき**（例：著者を別のテーブルで持つ）は、それを新しい経路とみなし、責務ごとに分けるかを利用者に確かめる。
- **同じプロパティ名が複数の経路に出るとき**は、計画の中で連番を続け、文言が重ならないようにする。
  例えば、登録の経路で `_書籍ID_1_`〜`_書籍ID_8_` を使ったら、削除の経路は `_書籍ID_9_` から始める。
- **計画の後で同じプロパティにコミットを足すとき**（レビューでの修正など）も、連番を続ける。

## コミットメッセージ

文言は `_<プロパティ名>_<連番>_` とし、連番はそのプロパティの中での順番とする。
プロパティ名は、計画や仕様が使っている名前（例：書籍ID）にそろえる。
メッセージは、文言の後に内容を続ける（例：`_書籍ID_1_ フロントエンドから書籍を選択`）。

リポジトリやチームに別の規則があれば、その規則に従ったうえで文言を加える。
規則は次の順に探し、見つかったものをすべて満たす。

1. 利用者の指示（会話、CLAUDE.md、AGENTS.md）
2. リポジトリの設定（commitlint・commitizen の設定、`.gitmessage`、commit-msg フック、CONTRIBUTING）
3. 計画の中のコミットの書き方（superpowers の計画にある `git commit -m` の例など）
4. 直近のコミット履歴の書き方（`git log --oneline -20`）

| 見つかった規則 | メッセージの例 |
|-|-|
| 規則なし | `_書籍ID_1_ フロントエンドから書籍を選択` |
| Conventional Commits | `feat(book): _書籍ID_1_ フロントエンドから書籍を選択` |
| 英語のみ・ASCII のみ | `feat(book): _bookId_1_ select a book on the frontend`（プロパティ名はコードの識別子にする） |

文言は、種別や範囲（`feat(book):` など）の直後、件名の先頭に置く。
件名の先頭にそろえると、`git log --grep "_書籍ID_"` で1つのプロパティのコミットをまとめて探せる。
件名の長さに上限があるときは、内容を短くし、文言は削らない。
Claude Code が求める帰属表示（`Co-Authored-By` など）は、そのまま末尾に付ける。
どの規則に従ったかと、その出所は、分割案に書く。

## 進め方

### 1. 計画とコードを読む

計画の場所を確かめる。
利用者が示した場所を優先し、示されていなければ次を探す。

- spec-kit：`specs/<機能>/tasks.md`（あわせて plan.md、data-model.md、contracts/）
- superpowers：`docs/superpowers/plans/*.md`（利用者の設定で場所が違うことがある）

次に、コードを読んで、経路の段を実際のファイルで特定する。
段の名前は、一般的な構成から推測せず、このリポジトリにある層から取る。
例えば、サービス層がないリポジトリに「サービスが受け取る」コミットを作らない。
フロントエンドだけのアプリなら、経路は「操作→状態の更新→描画」のようになり、その段ごとに責務を分ける。
コードがまだない新規のリポジトリでは、計画に書かれた構成から段を決め、そのことを仮置きとして書く。

最後に、計画の中の経路（操作）を挙げ、経路ごとに運ばれるプロパティを挙げる。

### 2. 分割案を作る

`assets/slices-template.md` をひな形にして、分割案のファイルを作る。
置き場所は計画と同じフォルダーとし、spec-kit なら `specs/<機能>/slices.md`、superpowers なら `<計画のファイル名>.slices.md` とする。
計画のファイルがないときは `docs/slices/<YYYY-MM-DD>-<機能>.md` に置く。
利用者の指定があれば、それに従う。

分割案には、経路ごとに次を書く。

- 経路の段（始まりから終わりまでと、各段のファイル）
- タスクとコミットの表（利用者のシートと同じ列に、主な変更ファイル・元のタスク・状態を足す）
- コミットメッセージの一覧
- プロパティと段の対応表（次の手順3で使う）

元の計画のタスクと、分割後のタスクの対応を、両方向で確かめる。
元のタスクはすべて、分割後のどれかのタスクに入っているか、「分割に入れなかったタスク」に理由付きで載っている必要がある。
分割後のタスクはすべて、元のタスクか、利用者が取り込みを決めた考慮漏れのどちらかを由来に持つ必要がある。
この確認で、分割の途中で作業が消えることと、計画にない作業が紛れ込むことを防ぐ。

### 3. 分割で見えた考慮漏れを指摘する

大枠の計画は「書籍登録APIを作る」のような単位で書かれるので、段ごと・プロパティごとの扱いまでは書かれていないことが多い。
分割すると、コミットごとに「この段で、このプロパティをどう扱うか」を決める必要が出てくるので、計画に書かれていない扱いが見えるようになる。
このスキルが指摘するのは、この種類の漏れである。

見つけ方は2つある。

- **プロパティと段の対応表の空欄。**
  行がプロパティ、列が経路の段で、各欄に、その段がそのプロパティに何をするか（入力、送信、検証、変換、保存、返却、表示）を書く。
  計画にもコードにも根拠がない欄が、考慮漏れの候補になる。
- **コミットごとの観点。**
  各コミットについて、失敗したとき・値がないとき・重複したとき・既存データがあるときに何が起きるかを確かめる。
  観点の一覧と指摘の書き方は `references/oversight-viewpoints.md` にある。

指摘は、次の3つをすべて満たすものだけを載せる。
観点の一覧を当てはめただけの一般論は載せない。
一般論が混ざると、読む人がどれが本当に問題なのかを判断できなくなるためである。

- どのコミット（文言）の話かが特定できる。
- 具体的に何が起きるかを書ける（例：「存在しない書籍IDを送ると、サービスで例外になり、画面には何も表示されない」）。
- 根拠がある。根拠は、計画やコードの場所（`ファイル:行`）か、「推測」と明記した推論とする。

指摘には、提案（どのコミットに含めるか、新しいタスクにするか、依頼者に確かめるか）を付ける。
取り込むかどうかは利用者が決める。
利用者が決めるまで、考慮漏れを計画のタスクに加えない。

分割そのものの問題も、同じ表に載せる。
例えば、途中のコミットでビルドが通らない順番になっている、元の計画のタスクがどのプロパティにも当てはまらない、計画にある層がコードにない、といった問題である。

### 4. 分割案を見せて、承認を得る

会話では、次を短く示す。

- 経路ごとのコミット数と、タスクとコミットの表
- 考慮漏れの指摘（影響の大きいものから）と、それぞれの提案
- 仮置きした解釈
- 分割案のファイルの場所
- superpowers の計画なら、タスクが増えた分だけ、実装とレビューのサブエージェントが動く回数も増えること

利用者から、分割の承認と、考慮漏れごとの判断（取り込む／別のタスクにする／対象外／依頼者に確かめる）をもらう。
判断は、分割案の「判断」の列に書く。

承認されたら、元の計画のタスクの部分を、分割後のタスクに書き換える。
計画の形式（spec-kit、superpowers など）ごとの書き方は `references/plan-formats.md` にある。
タスク以外の部分（目的、構成、制約など）は変えない。
計画のファイルが git で管理されていないか、未コミットの変更があるときは、書き換える前に同じフォルダーへ写しを取る。

### 5. コミットを分ける

コミットは、利用者に頼まれたとき（このスキルでコミットを分けるよう頼まれたときを含む）だけ行い、push はしない。
コミットする前に、作るコミットの一覧（メッセージと、含めるファイル）を見せて、承認を得る。

**実装しながらコミットする場合。**
1つのタスクを実装し終えたら、そのタスクの変更だけをステージして、分割案のメッセージでコミットする。
コミットの前に `git diff --cached --stat` を見て、別のタスクの変更が混ざっていないことを確かめる。
混ざっているときは、次の手順で分ける。

**まとめて書いた変更を分ける場合。**
複数のタスクの変更が作業ツリーにまとめて入っているときは、`references/commit-splitting.md` の手順で分ける。
同梱の `scripts/slice_commit.py` は、作業ツリーのファイルを変えずに、コミットごとの途中の状態をステージしてコミットし、最後に作業ツリーと一致したかを確かめる。
push していないローカルのコミットを分け直すときも、同じ手順で行う。

コミットするたびに、分割案の「状態」の列にコミットのハッシュを書く。

### 6. 終わったら

分割案の状態を「計画に反映済み」または「コミット済み」にする。
会話では、作ったもの（分割案、書き換えた計画、コミット）と、利用者の判断が残っている考慮漏れを伝える。
