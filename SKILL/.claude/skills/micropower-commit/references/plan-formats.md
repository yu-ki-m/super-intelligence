# 計画の形式ごとの書き換え方

承認された分割を、元の計画に書き戻すときの書き方をまとめる。
どの形式でも、実装を担う次のスキルが、分割後の1タスクを1コミットとして実行できる形にする。
タスク以外の部分は変えない。

## spec-kit（`specs/<機能>/tasks.md`）

spec-kit の tasks.md は、1行に1タスクを `- [ ] T<番号> [P?] [US<n>] <説明>` の形で書き、説明に変更するファイルのパスを含める。
spec-kit の雛形は、ユーザーストーリーの中をモデル→サービス→エンドポイントのように層ごとに並べることが多い。
分割では、この層ごとのタスクを、経路とプロパティの単位に組み替える。

- 説明の先頭を「文言＋内容」にし、その後に変更するファイルのパスを書く。
  例：`- [ ] T012 [US1] _書籍ID_1_ フロントエンドから書籍を選択 in frontend/src/features/book/BookSelect.tsx`
- タスク番号は、書き換えたフェーズ以降を通し番号に振り直す。
  元の番号は、分割案の「元のタスク」の列に残る。
- 同じ経路のタスクは前のタスクに依存するので、`[P]` を付けない。
- 「Tests for User Story N」の節にあるテストのタスクは、そのテストが確かめる処理のタスクに含める。
  テストと実装を同じコミットにするためである。
  constitution や tasks.md の冒頭で、テストを別のタスクにすることが求められているときは、規則が衝突している。
  黙ってどちらかを選ばず、どちらに従うかを利用者に確かめる。
- フェーズ、ユーザーストーリーの見出し、Checkpoint、Dependencies の節は残し、依存関係の記述を新しい番号に合わせる。
- Notes の節に、次の1行を足す。
  「各タスクは1コミットにする。コミットメッセージは slices.md の一覧を使う。」
- `/speckit.analyze` を使っているリポジトリなら、書き換えた後に実行することを勧める。

## superpowers（`docs/superpowers/plans/*.md`）

この節は superpowers 7.0.2 を基準にしている（2026-11-15 に確認）。
superpowers の計画は、`### Task N:` ごとに Files・Interfaces・手順（チェックボックス）を持ち、最後の手順でコミットする。
実装は subagent-driven-development か executing-plans が、タスクごとに行う。
1つのタスクが複数のコミットになってもよく、レビューはタスクを始めた時点のコミットから HEAD までの範囲で行われる。
そのため、1スライスを1タスクにすれば、superpowers の仕組みを変えずに「1タスク＝1コミット」を守れる。

- 分割後の1タスクを、`### Task N: <文言> <内容>` の1つにする。
  例：`### Task 3: _書籍ID_3_ バックエンド（コントローラー）が書籍IDを受け取る`
  見出しの先頭の `Task N:` は変えない。
  補助スクリプト task-brief は、見出しの「Task」と数字を含む ID でタスクを切り出すためである。
- 各タスクに、Files・Interfaces・手順（失敗するテストを書く→失敗を確かめる→実装する→通ることを確かめる→コミットする）を持たせる。
- 元のタスクの手順は、分割後のタスクへ分けて移す。
  7.0.2 の計画は、テストの手順にテスト名とアサーションを、コードの手順にシグネチャ・ファイル・仕様の値を書き、関数の本体はシグネチャとテストで決まらないアルゴリズムに限る。
  他のタスクのコードは繰り返さず、そのタスクの Interfaces で示す。
  分割で関数の本体を各タスクに写すと、writing-plans の「書きすぎ」の見直しに当たるので、写さない。
  （6.3.0 の計画は、各タスクに必要なコードをそのタスクの中に書くよう求めていた。古い版の計画を扱うときは、計画にある書き方に合わせる。）
- コミットの手順には、分割案のメッセージを書く。

  ```bash
  git add <そのタスクのファイル>
  git commit -m "feat(book): _書籍ID_3_ バックエンド（コントローラー）が書籍IDを受け取る"
  ```

- 分割で増えた境界ごとに、Interfaces の Produces と Consumes を書き、前後のタスクで名前と型をそろえる。
  実装のスキルは、Task 1 の前に、この Interfaces を手がかりにタスク間の衝突を調べる。
- 冒頭の見出し、Goal、Architecture、Tech Stack、Spec、Global Constraints は変えない。
- 利用者が取り込むと決めた考慮漏れは、担当のタスクにテストを足し、冒頭の Review Focus にも1行足す。
  executing-plans は、最後のレビューアーに Review Focus をそのまま渡すためである。
- subagent-driven-development は、同じ形の小さな編集（項目の追加など）が複数のタスクに並ぶと、1人の実装者にまとめて渡すことがある。
  2つ目以降のプロパティのタスクはこれに当たりやすいので、各タスクの最後の手順に別々のコミットを書いておく。
  実装の後、コミットがプロパティごとに分かれていなければ、`references/commit-splitting.md` の手順で分け直す。
- タスクが増えると、subagent-driven-development では、タスクごとに実装とレビューのサブエージェントが動くので、時間と利用量が増える。
  分割案を見せるときに、このことを一言伝える。
  利用者が望む場合に限り、元のタスクを残し、その中の手順として分割後のコミットを並べる形にしてよい。

## その他の計画（Markdown のチェックリスト、Issue、依頼文）

- 計画にある書き方（チェックボックス、番号付きの一覧など）に合わせ、1行に1タスクで「文言＋内容」を書く。
- 書き戻す計画のファイルがないときは、分割案のファイルの表を、そのまま計画として使う。
