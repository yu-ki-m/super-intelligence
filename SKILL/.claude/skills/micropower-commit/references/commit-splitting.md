# まとめて書いた変更をコミットに分ける手順

複数のタスクの変更が作業ツリーにまとめて入っているときに、分割案のコミットに分ける手順をまとめる。
`git add -p` は対話の入力が必要なので、このスキルでは使えない。
代わりに、コミットごとに「そのコミットの後のファイルの状態」を作り、それをステージしてコミットする。
作業ツリーのファイルは最後の状態のまま変えないので、途中で失敗しても、書いたコードは失われない。

スクリプトは `scripts/slice_commit.py`（Python 3、標準ライブラリだけ）である。
リポジトリの中で `python <スキルの場所>/scripts/slice_commit.py <サブコマンド>` の形で実行する。

## 0. 前提を確かめる

- `git status` で、マージ・リベース・チェリーピックの途中でないことを確かめる。
- ステージ済みの変更がないことを確かめる。
  ステージ済みの変更があると、最初のコミットに混ざるので、スクリプトは止まる。
  あれば利用者に確かめてから、`git restore --staged .` で外す（作業ツリーのファイルは変わらない）。
- pre-commit・commit-msg のフック（husky、lint-staged、pre-commit など）があるかを確かめる。
  lint-staged のように、ステージしていない変更を一時的に退避して戻すフックは、この手順と相性が悪いことがある。
  フックがあれば利用者に伝え、次の1の退避を必ず取る。

## 1. 退避を取る

```bash
python scripts/slice_commit.py backup
```

変更のあるファイルと未追跡のファイルの写し、追跡済みのファイルの差分（`tracked.patch`）、HEAD の位置を、`.git/slice-backup/<日時>/` に保存する。
あわせて、`refs/slice-backup/<日時>` に、分割を始める前の HEAD を記録する。
`.git` の中に置くので、作業ツリーにもコミットにも入らない。

## 2. 変更をコミットに割り当てる

`git diff HEAD` と、未追跡のファイルの中身を読み、変更の各部分（ハンク、必要なら行）を、分割案のどのコミットに属するかに割り当てる。
どのコミットにも属さない変更が見つかったら、利用者に伝え、扱い（分割案に足す、別のコミットにする、コミットせずに残す）を決めてもらう。

## 3. 途中の状態のファイルを作る

リポジトリの外の一時フォルダー（セッションの作業用フォルダーがあればそこ）に、コミットごとのフォルダー（`c01/`、`c02/` …）を作る。
その中に、そのコミットの後の状態のファイルを書く。

- 既存のファイルは、HEAD の内容（`git show HEAD:<パス>`）から始め、そのコミットまでに属する変更だけを入れる。
- 新しいファイルは、そのコミットまでに属する部分だけを書く。
- あるファイルを最後に変えるコミットでは、途中の状態を書かず、作業ツリーの内容をそのまま使う（指示ファイルで `"worktree": true`）。
  こうすると、そのファイルの最後の状態が作業ツリーと一致することが保証され、書き写しの誤りが入らない。

## 4. 指示ファイルを書く

指示ファイル（JSON）には、コミットの順に、メッセージと含めるファイルを書く。

```json
{
  "commits": [
    {
      "message": "feat(book): _書籍ID_1_ フロントエンドから書籍を選択\n\nCo-Authored-By: ...",
      "files": [
        {"path": "frontend/src/BookForm.tsx", "content_file": "C:/tmp/slices/c01/frontend/src/BookForm.tsx"},
        {"path": "frontend/src/BookSelect.tsx", "worktree": true}
      ]
    },
    {
      "message": "feat(book): _書籍ID_2_ フロントエンドから書籍IDをリクエストで送信",
      "files": [
        {"path": "frontend/src/BookForm.tsx", "worktree": true},
        {"path": "frontend/src/legacyApi.ts", "delete": true}
      ]
    }
  ]
}
```

- `path`：リポジトリのルートからの相対パス（`/` 区切り）。
- `content_file`：手順3で作った、途中の状態のファイル。
- `worktree`：作業ツリーの今の内容を使う。作業ツリーで削除済みのファイルなら、削除になる。
- `delete`：そのコミットでファイルを削除する。

メッセージには、手順の「コミットメッセージ」の節で決めた形と、帰属表示を入れる。

## 5. 試してから、コミットする

```bash
python scripts/slice_commit.py commit spec.json --dry-run
python scripts/slice_commit.py commit spec.json
```

ドライランでは、何も変えずに、次を表示する。

- 指示ファイルの誤り（ファイルがない、同じコミットに同じパスが2回ある、など）。
- 最後のコミットの後も作業ツリーとの差が残るファイル。
  途中の状態のファイルを最後に使っていると、ここに出る。
- どのコミットにも入っていない変更。

コミットするときは、コミットごとに、ステージした内容が指示ファイルのパスだけであることを確かめてからコミットする。
フックがコミットを拒んだら、そこで止まり、それまでに作ったコミットは残る。
最後に、変更が残っているファイルを表示する。
指示ファイルにあるパスで変更が残っていたら、途中の状態か割り当てに誤りがあるので、利用者に伝える。

## 6. 途中のコミットを確かめる（任意）

各コミットの時点でビルドやテストが通るかを確かめるときは、作業ツリーに変更が残っていない状態で、次を実行する。

```bash
git rebase --exec "<ビルドやテストのコマンド>" <分割を始める前の HEAD>
```

この形のリベースは、コミットを書き換えずに、各コミットを順に取り出してコマンドを実行する。
コマンドが失敗したコミットで止まるので、`git rebase --abort` で元に戻してから、そのコミットの途中の状態を直し、分割をやり直す。
テストに時間がかかるときは、ビルドだけ、または型の検査だけにする。
確かめなかったときは、確かめていないことを利用者に伝える。

## 7. やり直す・元に戻す

分割で作ったコミットを取り消すときは、次を実行する。

```bash
git reset --soft refs/slice-backup/<日時>
git restore --staged .
```

1行目は、HEAD を分割を始める前の位置に戻す。
ファイルの内容は変わらず、分割した変更がステージされた状態になる。
2行目でステージを外すと、分割を始める前と同じ状態に戻る。

## push していないコミットを分け直す

すでにあるローカルのコミットを分け直すときは、次の順に行う。

1. 分け直すコミットが push されていないことを確かめる。
   `git log @{u}..` に、分け直すコミットがすべて出ていればよい。
   push 済みなら、履歴の書き換えになるので、利用者の明示の承認なしには進めない。
2. 退避を取る（手順1）。
   `refs/slice-backup/<日時>` に、分け直す前の HEAD が記録される。
3. `git reset --mixed <分け直す範囲の直前のコミット>` で、コミットを作業ツリーの変更に戻す。
   ファイルの内容は変わらない。
4. 手順2から同じ手順で分ける。

分け直す前のコミットに戻すときは、`git reset --soft refs/slice-backup/<日時>` を実行する。
分割後の最後のコミットと、分け直す前の HEAD は、ファイルの内容が同じなので、作業ツリーは変わらない。
