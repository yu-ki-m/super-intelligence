# 稼働規模と成果の測定

目標は、50人規模の専門チームに分担させるような仕事の範囲と処理量をAIによって実現することである。この目標を、50個の役職名を作ることや、50体を同じ討論に参加させることに置き換えない。50役割は初期の業務分担設計であり、人間50人分の生産性を達成した証拠ではない。

本スキルの対象はプロダクトブランディングと、その判断に必要な調査・制作・検証準備である。事業全体の開発・営業・経理・本番運営をすべて代行するとは説明しない。

## 分けて報告する数

次の数はそれぞれ別のものであり、混ぜて報告しない。`capacity.md` と `summary.md` に分けて出力される。

| 数 | 意味 | 記録の場所 |
| --- | --- | --- |
| 役割数 | 定義された業務分担の数（50） | `graphs/roles.json` |
| 起動した役割 | 実際に呼び出しがあった役割 | `instances` |
| インスタンス数 | 起動した独立のセッションの数 | `instances` |
| 同時実行数 | 同時に動いた数の最大と、設定した上限 | `peak_concurrency`、`settings` |
| 呼び出し数 | エージェントへの依頼の回数と結果の内訳 | `attempts` |
| 完了した仕事の数 | 品質ゲートを通過した作業の数 | `tasks` |

依頼範囲に該当する仕事がない役割は起動しない。起動しなかった数が多いことは、それ自体では問題ではない。

## 記録する値

品質検査に合格した成果物数、初回合格率、手戻り件数、完了までの時間、人間の確認・修正時間、実際に取得できたAIの使用量と費用を記録する。調査表と短い紹介文のように異なる種類の成果物を単純合算して生産性を比較せず、作業種別（品質契約の種類）ごとに集計する。

Agent ツールの方式では、ハーネスは費用を取得できないので「取得できなかった」と報告する。`claude -p` の方式では、`claude -p` が報告する値を使う。確認した結果、この値はセッション内の累計なので、セッションごとの差分を試行の費用として記録する。また `costBasis` が `list` であり、API 定価換算の値である。定額プランでは実際の請求額ではないので、そのように表示する。取得できなければ「取得できなかった」と報告し、推定で埋めない。

人間の介入時間は自動では測れない。依頼者や確認者の時間を `python pbteam.py log-human --run-dir <run> --minutes 30 --activity "内容の確認"` で記録する。記録がなければ未測定と表示する。

## 50人分という目標の検証方法

評価の前に、対象期間、対象業務、人間が行う場合の比較条件、必要な品質を決める。例えば、次のような形で決める。

> 架空の例：対象期間は1か月、対象業務は新製品1件の紹介ページ・営業原稿・FAQの作成と根拠の整理とする。比較条件は、社内の担当者が過去に同じ種類の成果物を作った実績の作業時間（過去3件の工数記録）とする。必要な品質は、品質契約の合格に加えて、担当者が修正なしで使えると判断することとする。

人間の所要時間が不明なら、50人分を達成したと報告しない。完了成果物、人間の介入時間、AI費用など測定できる値を報告する。

人間の基準時間がある場合は、同じ範囲・品質の完了作業に対応する基準時間の合計から、実際の人間の介入時間を差し引き、代替できた時間の推定値として示せる。ハーネスの `harness/report.py` の `replacement_estimate` は次の形の基準を受け取り、`measured` が真の作業種別だけを計算に使う。

```json
{"landing_page": {"minutes_per_item": 120, "measured": true, "basis": "過去3件の工数記録の平均"}}
```

これは実測された前提に依存する推定であり、出力数に任意の時間を掛けて50人分と称してはならない。AI費用は別に示す。

同時実行数を上げれば処理量は増えるが、検査待ちが増えるなら、完了した仕事は増えない。待機作業が多いときは依存関係を見直し、検査待ちが多いときは検査へ稼働を配分する。

## 確認できないこと

模擬実装での負荷試験は、作業の欠落、二重完了、合流の早すぎる開始、停止後の再開がないことを確かめるものであり、人間50人分の品質や生産性の証明ではない。小規模の実行が成功しても、50人分の生産性や長期運用が検証済みになったとは報告しない。

比較評価（`evals/results/`）は一つの架空の題材での結果であり、一般化できない。評価者もAIなので、同じモデルに由来する誤りを共有する可能性がある。顧客の実際の反応は含まれていない。
