# 説明の方針とブランド検討項目

この文書は二つの内容を持つ。前半は、スキル作成者が書く文書と、完成したスキルがエージェント間で共有し依頼者に提示する説明・質問・成果物の両方に適用する説明の方針である。後半は、討論で扱うブランド検討項目と工程間の関係である。依頼者に「なぜこの論点を検討するのか」「どの判断に使うのか」と尋ねられたら、後半の該当する工程の説明を、対象の製品に当てはめて答える。各項目の問いはAI同士で検討する問いであり、そのまま依頼者への質問票にしない。

## 説明の方針

依頼者は、個々の言葉を理解できても、暗黙の前提や概念間の関係が省略されていると内容を理解できない場合がある。ブランディングの専門知識があるとは限らないため、工程名や質問を列挙するだけで進行しない。

### 内容と構成

依頼の目的、論点、条件を維持する。理解に必要な説明の追加、文章の分割・統合、順序の調整は行ってよいが、単なる要約や別の主張への変更はしない。内容に適した説明形式を選び、すべての説明を同じ数の見出しや同じ順序に当てはめない。冒頭の結論や要約は必須にしない。全体の中で現在の工程が何を決める工程かを示し、各作業について、目的、使用する情報、具体的な作業、得られる結果、次の工程での使い方を説明する。

### 前提と論理

専門用語は、この討論での意味を説明し、別の専門用語に置き換えるだけで説明を終えない。ある前提から次の判断へ進む理由を示す。「必要」「改善できる」「価値になる」と述べる場合は、誰にとって、なぜそう言えるのかを説明する。

原因、製品の働き、人の行動、結果を分け、機能の存在から成果の達成へ直接飛躍しない。成立条件や結果を妨げる要因が判断に影響する場合は併記する。主語と対象を明確にし、「管理する」「対応する」だけで済ませず、誰が何を記録・確認・判断・変更するのかを書く。ただし、明白な主語の反復や論理の過剰な説明は避ける。新しい概念を導入するときは、それまでの検討との関係を示す。比較では対象、基準、成立条件、判断に必要な情報を明確にする。

### 抽象と具体

理解しにくい抽象的な説明には、原則として同じ段落で具体例を添える。例は人物や組織、状況、行動、判断、結果が想像できるものとする。架空例と確認された事実を分け、仮定の数字には仮定と明記する。計算や評価の根拠が必要な場合は条件を示す。可能な範囲で同じ具体例を継続使用し、工程間のつながりを示す。理解に役立たない例や不要な設定を追加しない。

### 文章と表現

自然な日本語の説明文を中心とし、説明は常体を基本とする。問いかけは自然な表現とし、既存の引用文の文体は維持する。段落は話題単位で構成し、一文ごとに不必要に改行せず、同じ論点の説明、理由、例をできるだけ同じ段落にまとめる。箇条書きは記入項目、手順、比較対象などの整理に使い、背景や因果関係を箇条書きの列挙だけで済ませない。見出しは実際の説明対象を簡潔に表し、感想、宣言、呼びかけ、煽り、不必要な疑問形を避け、機械的に増やさない。

「つまり」「要するに」や対比構文は、理解に必要なときだけ使う。説明者の行為や説明の親切さを強調する導入・自己評価を追加しない。対象や動作が曖昧になる比喩（`tests/test_docs.py` に一覧がある）を避ける。「柔軟」「高度」「効率的」「最適化」のような言葉は、何がどう変わるかを具体化する。不必要な感嘆符、絵文字、誇張したキャッチコピーを説明に加えない。顧客向けメッセージ案を作る場合も、根拠を超えた誇張をしない。

### 表・図・正確性

比較には共通の観点を持つ表を使い、表だけでは理解できない理由や条件を文章で補う。構成や情報の流れを図示する場合は、要素と矢印が何を表すかを明示する。装飾のために図表を追加しない。確認された事実、一般的な考え方、推論、仮定を区別し、一般的な傾向を例外のない規則として扱わない。最新情報が必要なら、利用可能な情報源を確認する。

手段と目的を分ける。説明の理解、試用、購入、継続利用は異なる結果であり、一つが確認されたことを他の達成の証拠にしない。理解に必要な情報や制約を削らず、無関係な周辺知識を大量に加えない。各工程で求めた範囲を超える行動計画やチェックリストを機械的に追加しない。

出力前には、内容と意図の維持、必要な前提と用語、主語と対象、因果関係、具体例、全体と部分の関係、比較基準、自然な見出しと文章、事実と仮定の区別、長さの妥当性、不要な削除・装飾・繰り返しの有無を内部で確認する。この内部確認の結果は依頼者への応答に出力しない。

## この検討で使う言葉

「顧客からの認識」とは、顧客が製品を何のためのものと理解し、どのような場面で役立つと考え、何を期待するかを指す。例えば、同じ問い合わせ管理製品でも、「履歴を保存する道具」と理解される場合と、「担当者が不在でも経緯を確認できる道具」と理解される場合では、顧客が検討する場面や期待する使い方が異なる。この例は認識の違いを説明する架空例であり、どちらが売れるかを示すものではない。

製品の説明は、顧客が利用前に期待を持つ材料になる。利用開始後は、実際にできたことや支援を受けた経験も、その製品への認識を形成する材料になる。そのため、伝える言葉と、それを裏づける提供実態を一緒に検討する。ただし、提供側が意図したとおりの認識が必ず形成されるわけではないため、実際の受け止め方は別途確認する。

「ブランドの仮説」は、今ある情報に基づく暫定的な説明である。例えば、機能の動作を確認済みでも、顧客がその機能を重視するかは未確認かもしれない。「カテゴリー」は、「問い合わせ管理サービス」のように、何の用途の製品かを理解する手掛かりとなる分類を指す。顧客が知らない独自名称を付けただけで理解されたとは扱わない。「接点」は、顧客が製品や提供企業に関する情報・サービスに触れる場を指し、例えば紹介ページ、商談、初期設定画面、問い合わせ窓口が該当する。

## 討論で扱う工程と、工程間の関係

以下の工程は、次の問いに答えられるようにするためにある。誰が、どのような状況でこのプロダクトを思い出し、検討し、選ぶことを目指すか。顧客は現在どのように対処し、何に不満や不安を感じているか。利用者、購入決定者、導入に関わる人がそれぞれ何を判断するか。競合製品、内製、手作業、現状維持と比べてどの点が選ぶ理由になるか。プロダクトは何を約束でき、その根拠は何か。どのように理解・記憶されたいか、現在の認識とどのような差があるか。どの接点で何を伝え、どの体験で約束を裏づけるか。30日間で何を確かめ、その結果から何を修正するか。

名称、ロゴ、キャッチコピーの作成だけで完了させない。購入前の説明、導入、日常利用、サポートなどで、伝えた価値を実際に提供できるかまで扱う。ただし、事業計画全体、詳細な製品要件、デザイン制作まではこの討論の完了条件にしない。必要な検討は別の課題として記録する。

### 工程1：目的と対象の共有

今回どの製品の、どの認識を検討するかをそろえる。対象や検討目的が異なるまま議論すると、例えば新規顧客向けの説明と既存顧客向けの説明を同じ条件で判断してしまう。ここで定めた目的と制約を、後の候補選定の基準にする。

何を対象とし、なぜ今ブランドを考えるのかを確認する。検討の契機を、立ち上げ、価値が伝わらない、比較で違いが伝わらない、期待と体験が違うなどから具体化する。今回決めたいこと、既に決まっている制約、判断する人を確認する。企業ブランドと製品ブランド、個別機能の名称が混ざっていれば、今回の対象を定める。企業全体のブランドとの関係は、検討に必要な範囲で確認する。

### 工程2：選択の場面と説明の関係を確認

工程1で定めた目的に対して、顧客のどの場面と説明を結びつけるかを各担当が検討する。同じ機能でも、相手の状況によって意味が異なるためである。実際の対象製品の資料を優先し、次の例は理解を補う場合だけ使う。

架空の問い合わせ管理製品では、履歴保存という機能を「記録を残せる」と説明する案と、「担当者不在でも経緯を確認できる」と説明する案が考えられる。後者は利用場面を想像しやすい一方、情報が記録されていることと閲覧権限があることが必要になる。各担当は、何が伝わりやすくなり、どの条件が省略されやすいかを批評する。この検討だけで顧客に伝わったとは判定しない。工程3では、この場面が実際の対象顧客に存在するか、資料からどこまで確認できるかを検討する。

### 工程3：顧客・利用状況・現状の認識を整理

前の検討で扱った「相手の状況と説明の関係」を、対象プロダクトに当てはめる。誰のどの困りごとを扱うかが不明なままでは、製品の特徴がその人にとって価値になるかを判断できない。そこで利用や購入の場面と現在の対処を整理し、工程4で比較する選択肢と判断基準を得る。

具体的な利用や購入の場面を1〜3件扱い、次を整理する。誰が、何をしようとしているか。どの出来事をきっかけに、課題を意識し、対処方法を探すか。現在は何を使って、どう対処しているか。何が負担、不安、不満になっているか、放置すると何が起こるか。どのような状態になれば本人にとって改善と言えるか。実際に使う人、購入を決める人、導入を審査・支援する人は誰か、それぞれ何を重視するか。B2Cなどで同一人物なら無理に分けない。顧客は現在この製品をどのようなものと捉えているか。

年齢や企業規模だけで顧客像を完成させず、選択につながる状況を具体化する。現状の認識が未調査なら、チームが期待する認識で埋めない。候補が複数ある場合は、課題の切実さ、提供できる価値、根拠、接触可能性から、今回の優先対象を仮決めする。

### 工程4：代替手段と選択理由を整理

工程3で顧客の課題を特定しても、それだけで自社製品を選ぶ理由は確定しない。例えば、顧客がメール管理に不便を感じていても、製品を導入する設定や教育の負担を大きいと考えれば、現在の方法を続ける可能性がある。そこで現在の対処を含む選択肢を比較し、どの条件で自社製品を選ぶ理由が成立するかを整理する。その結果を工程5の価値と選択理由の材料にする。

競合製品だけでなく、手作業、内製、外注、既存ツールの組み合わせ、何もしないことを扱う。比較表の列は、代替手段、顧客がそれを選ぶ理由、顧客にとっての不足や負担、自社製品を選ぶ理由になり得る違い、その違いが重要になる状況、自社製品への変更負担・弱点・適さない条件、比較の根拠と未確認事項とする。

顧客が比較している選択肢と、チームが競合だと考える選択肢を区別する。選択理由を「利用の前提となる条件」と「候補の中から選ぶ理由」に分ける。例えば、必要なセキュリティ条件を満たすことが参加条件であり、導入時の負担が小さいことが選択理由になる場合がある。常にそうなるとは決めつけない。独自機能がなくても、特定業務への適合、導入支援、使い続けられる運用などに根拠があれば検討する。優位性がない・不明な場合は、その状態を保持する。

### 工程5：ブランドの仮説づくり

工程3の顧客の状況と工程4の比較結果を使い、誰に何を約束でき、どのように認識されたいかを文章にする。各主張の確認状態を保ったまま整理し、工程6で対外説明と実際の体験に照らして検討する。

整理するのは、優先対象と選択のきっかけ、カテゴリー、顧客の課題と望む状態、主要な代替手段、提供価値とそれを実現する仕組み、選ぶ理由となる違い、信頼の根拠と提供条件、顧客に覚えてほしい認識、表現や対応の姿勢、約束しないことと適さない条件である。仮説文の型は次のとおりである。

> 「【状況】にある【対象】にとって、【製品名】は【カテゴリー】であり、【方法】によって【価値】を提供する。【代替手段】との比較では【選ぶ理由】があり、その根拠は【証拠】である。このため、【覚えてほしい認識】として認識されたい。」

全項目を一文に詰め込む必要はない。内部で判断をそろえるための文章と、顧客向けの短い説明を分ける。未確認の比較優位を対外説明に転記しない。

例えば、架空製品で担当者と対応状況が正しく記録され、責任者が一覧を確認する運用があるとする。この条件では、責任者は担当者が決まっていない依頼を見つけ、割り当てを判断できる。このように、機能が何を表示し、人が何を判断するかを介して価値を説明する。「担当者と対応状況を一覧化する」は機能、「未対応の依頼を確認できる」は価値、「部署への依頼を見失わないためのサービス」は認識の仮説として区別できる。ただし、実際の確認作業や運用が必要なら「対応漏れゼロ」などの保証に変えない。候補は必要に応じて2〜3案を作り、対象への適合、根拠、代替との差、提供可能性、伝わりやすさで比較する。裏づけのない採点で勝者を確定しない。

### 工程6：伝え方と利用体験の整合性を確認

工程5の仮説を顧客向けの説明に変換し、その説明を信じた顧客が何を期待するかを考える。そのうえで現在の製品や支援で期待に応えられるかを確認する。提供できない価値を説明で約束してしまうと、伝わりやすくても期待との不一致が残るためである。説明案と提供条件を整理した後、工程7で他者が実際にどう理解するかを確認する。

作成するものは二つある。一つ目のメッセージ案は、誰向けの何であるかを伝える1文、顧客の状況・価値・方法・根拠を含む30秒程度の説明、主要な価値に対する根拠と提供条件、使う表現と避ける表現とその理由である。二つ目の接点と体験の対応表は、列を「接点／顧客が知りたい・したいこと／伝える約束／実際に必要な体験／現状／差分／対応担当・次の行動」とする。接点は、製品を知る段階、比較、商談・購入、導入、日常利用、サポート、継続・再購入などから対象に合うものを選ぶ。

例えば「すぐ使い始められる」と伝えるなら、導入設定、データ移行、教育に何が必要かを確認する。現状と一致しなければ、説明に条件を加える、約束を修正する、体験を改善する、のいずれかを検討する。名称・ロゴ・色・語調は、狙う認識との関係が必要な場合に検討し、見た目だけで価値の問題が解決したと扱わない。製品やサービスの改善が必要なら、コミュニケーションだけの課題にせず、改善案を担当者が検討する課題として記録する。

### 工程7：説明の解釈と異論を確認

説明案を整えても、受け手が同じ意味を理解するとは限らない。ブランド・表現担当以外のエージェントも、説明案からどの対象、価値、利用条件が読み取れるかを返す。ただし、資料を共有したAIは初見の顧客ではない。その解釈を、顧客による理解確認の代わりにしない。

確認するのは、誰のどの状況に向く製品と読めるか、どのような変化や体験を期待させるか、現在の方法を変える理由は説明されているか、原資料を知らない人にはどの前提が不足するか、反論を受けた修正で元の具体的な長所が消えていないか、である。AIによる解釈、資料にある実際の顧客反応、今後確認すべきことを別々に記録する。「説明の理解」「価値への関心」「信頼」「試用や購入などの行動」を混同しない。顧客確認がなければ未実施とする。

### 工程8：30日間の検証計画

ここまでで整理した主張のうち、どれが未確認で、その誤りがどの判断を変えるかを確認する。例えば、顧客の課題が違うなら対象や価値を見直す必要があるが、課題と価値が合っていて用語だけ伝わらないなら説明の修正を検討できる。この違いを判断できるように、確認する仮説と観察方法を対応させる。30日間は最初の確認期間として置いた目安であり、ブランドの確立や売上効果を30日で証明する期限ではない。

決めるのは、最も判断に影響する未確認の仮説、何を学ぶための確認か、対象者の条件と接触方法、提示する説明・試作品・体験など、実施方法と担当者と期限、確認する発言・理解・行動・利用結果、結果に応じて維持・修正・保留する判断の基準、振り返る日である。

理解確認なら、説明後に本人の言葉で価値を説明してもらう。課題確認なら、過去の具体的な行動と現在の対処を聞く。行動の確認なら、試用開始や導入相談など、対象に適した行動を観察する。購入意思を尋ねただけで売上が見込めると断定しない。

例えば、最初の週に対象条件に合う候補者を募り、翌週に普段の依頼管理方法を聞く。その後、説明案を提示し、誰向けの何と理解したかを本人の言葉で確認する。可能なら試用時に未対応の依頼を確認できるかを観察し、30日目に説明・対象・体験のどれを変更するか判断する。これは探索的な確認例であり、少人数で市場性を証明したとは扱わない。

表示回数や好意度だけに限定せず、今回の仮説と結びつく確認方法を選ぶ。短期間で確認できることと、中長期の認知・継続・売上への影響を分ける。この工程では計画を作成する。顧客への連絡、投稿、公開、広告出稿、価格・製品変更などの実行は別の依頼として扱う。

## 工程と作業の対応

工程はハーネスの作業として実行される。次の表は、工程がどのノードで実行されるかを示す。`standard` は50役割のグラフ、`minimal` は最小構成である。工程1は親の会話が `brief.json` にまとめる。工程2は候補の作成と相互批評の中で検討する。

| 工程 | `standard` のノード | `minimal` のノード |
| --- | --- | --- |
| 工程1 目的と対象 | 依頼の整理、`work_plan`、`B06` | 依頼の整理 |
| 工程2 場面と説明 | `cand_a`、`cand_b`、`debate_target` | `cand_a`、`cand_b`、`debate_strategy` |
| 工程3 顧客 | `C01`〜`C07` | `customer` |
| 工程4 代替手段 | `M01`〜`M07`、`B03` | `alternatives` |
| 工程5 仮説 | `B01`〜`B08`、`debate_*`、`compare`、`select` | `cand_a`、`cand_b`、`debate_strategy`、`select` |
| 工程6 伝え方と体験 | `P01`〜`P07`、`D01`〜`D08`、`V05` | `product`、`intro_page` |
| 工程7 解釈と異論 | `V04`、`debate_integration`、`final_check` | `final_check` |
| 工程8 検証計画 | `C08`、`validation_plan` | `validation_plan` |
