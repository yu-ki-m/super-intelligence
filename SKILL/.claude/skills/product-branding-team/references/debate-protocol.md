# 相互批評の進め方

相互批評は、判断が分かれる箇所で行う。全員を同じ会議へ集めず、論点ごとに提案者、反対意見を持つ担当、関係する実務担当、評価担当を選ぶ。人数は通常3〜6役割を目安とする。議論を狭めるためではなく、相手の主張へ具体的に応答できる単位にするためである。各エージェントが一度だけ所見を出し、親がまとめる形は相互批評として扱わない。

## 発言の受け渡しの仕組み

実接続では、サブエージェント同士が直接通信する機能を使わない。ハーネスが実際の発言を保存し、宛先のインスタンスへ全文を転送して、応答を取得する。親の会話は依頼をサブエージェントへ渡すだけで、相手の回答を代作しない。各発言には試行IDとセッションIDが記録され、実行記録からたどれる。

インスタンスは次のように割り当てる。候補の作成者と批評者は、同じ論点の間は同じインスタンスで続ける。以前の自分の発言を踏まえて応答するためである。Agent ツールの方式では、ハーネスがそのインスタンスの以前の依頼と結果のファイルを新しいサブエージェントに順に読ませる。`claude -p` の方式では、同じセッションを `--resume` で続ける。セッションが失われた場合は新しいインスタンスで継続し、役割、以前の提案、受け取った批判、未回答事項を渡して、新しいインスタンスであることを記録する。検査担当は、作成者や討論の経緯を知らない新しいインスタンスにする。

| 環境の状態 | 動作 |
| --- | --- |
| 起動・再開・結果取得を確認できた | ハーネスが発言を転送して実討論を行う |
| 直接通信の機能がある基盤へ接続する場合 | `adapters/` に実装を追加する。親が記録を保持する点は変わらない |
| 独立したサブエージェントを起動できない | 実討論を実施できないと明示して終了する。単一エージェントの模擬会話へ切り替えない |
| 同時実行数が少ない | 役割を維持して順番に呼び出す。並列実行と複数エージェントの討論は別の要件である |

## 一巡の流れ

1. 独立した候補を作る担当には同じ版の基礎資料を渡し、他の案は見せない。最初に示された案に全員が追従することを避けるためである。依頼文に含めないだけでなく、インスタンスごとに作業フォルダーを分け、ファイルとしても読めないようにしている。
2. G04 が争点を設定する。各候補に異なる観点の評価を少なくとも2つ割り当てる。
3. 批評者が案を評価し、発言を送る。批判には重大度と論争の種類を付ける。修正しても残すべき長所は `keep_strength` に書く。
4. 提案者がすべての批判に応答する。受け入れて修正する、条件を限定する、根拠を示して反論する、撤回する、情報不足として保留する、のいずれかである。「参考になる」で済ませることはできない。修正するときは案の全文を返し、新しい版として登録される。
5. 批判者が応答を読み、自分の批判ごとに解消、部分解消、未解消、撤回を理由つきで判断する。反論が正しければ撤回する。意見を変えることを敗北として扱わない。
6. 未解消の重大な批判が残れば次の巡へ進む。既定の上限は3巡である。

## 発言の記録

発言は自然な文章を基本とし、記録には次を添える。発言の各項目を機械的に埋めることは求めないが、誰の何に答えたか、なぜそう判断したかは省略しない。共有するのは検討に必要な主張、根拠、判断理由、変更内容であり、非公開の内部思考の逐語的な開示は求めない。

発言ID、発言者、宛先、対象の論点・主張・提案版。提案、支持、批判、質問、応答、修正、撤回などの発言種別。対象となる主張の引用または正確な要約。評価、理由、根拠ID、成立条件、反例。求める修正、維持したい長所、判断が変わる条件。応答先の発言IDと、新しい提案版への参照。

## 批評の書き方

遠慮のない批評を行う。根拠のある強い否定や明確な不採用判断を、協調のために弱めない。同時に、優れた点は具体的に認め、修正時にも残す。「良いところを褒め、悪いところをけなす」は、案の内容と論理を率直に評価する意味である。人格への罵倒、根拠のない悪口、怒っている演技は、改善すべき箇所を特定できないため不要である。

例えば「これは弱い案だ。『使いやすい』が誰のどの操作を指すか不明で、今の方法から変更する理由を説明できていない」と述べてよい。一方、「素晴らしい」「駄目だ」だけで評価を終えない。称賛も「担当者不在という利用場面を特定した点は良い。そのため、履歴保存が誰の判断に役立つか説明できている」のように、対象と理由を示す。

批判の前後に必ず称賛を挟むルールは設けない。褒める点や反論が見つからないときに作らせない。討論の激しさや発言数を品質指標にしない。全員に提案、具体的な称賛、批判、反論、修正の権限があり、提案する人と否定する人を固定しない。評価・反証・検証の担当も良い案を認め、自分の批判が誤っていれば撤回する。親の案や統合結果も批判の対象である。

## 論争の種類と解決の方法

論争は、種類によって解決の方法が違う。声の強さや多数決で解決したことにしない。

| 種類 | 値 | 解決の方法 | ハーネスの動作 |
| --- | --- | --- | --- |
| 事実の不一致 | `fact` | 資料を確認する | 次の巡で根拠を示す。解消しなければ未解決として提出する |
| 推論の不一致 | `inference` | 成立条件や反例を検討する | 次の巡へ進む |
| 判断基準の違い | `criteria` | 依頼目的と照合する | 次の巡へ進む。解けなければ条件別の候補を残す |
| 情報不足 | `info_missing` | 外部確認事項にする | 追加の討論を行わず、外部確認へ送る |

## ハーネスが受理しない発言

形式面の検査はハーネスがコードで行う。意味の妥当性はここでは判断せず、参加者の相互評価と検査担当に委ねる。

| 状況 | 動作 |
| --- | --- |
| 対象の主張や理由がない発言、「駄目だ」「素晴らしい」だけの発言 | 受理せず、理由を添えて1回だけ再依頼する |
| 提案者が一部の批判に応答しない | 受理せず再依頼する。それでも応答がなければ未回答として残す |
| 受け入れると答えたのに修正した本文がない | 受理せず再依頼する |
| 修正した案が形式検査を通らない | 受理せず再依頼する |
| 批判者が応答を踏まえず同じ指摘を繰り返す | 受理せず、応答のどこが足りないかと新しい根拠を求める |
| 批評者全員が批判なしで、支持にも根拠の参照がない | 検討済みとして扱わず、論点を未解決にする |

## 終了条件

全員一致は終了条件ではない。依頼された成果物が検査に合格し、重要な批判に応答があり、統合案への最終確認が済み、残った対立が外部の証拠や依頼者の方針なしには解けない状態になれば終了できる。上限到達時は「検討途中」「未解決」を明示して提出する。

未回答の重大な批判がある間は、その主張を確定扱いにしない。統合の成果物は、未解決の異論と残すべき長所を `structured.carried_forward` に記録する。抜けていれば形式検査で拒否される。統合の成果物にも批判と別担当の検査を行い、親の判断も例外にしない。

## 根拠の強さの扱い

役割を分けても、同じ資料やモデルに由来する誤りを共有する可能性はある。そのため、賛成人数を証拠の強さに換算しない。同一資料を複数の担当が引用しても、独立した複数件の証拠にはならない。ハーネスは同じ資料の同じ引用を一つの根拠として登録する。

顧客視点を担当するAIも実際の顧客ではない。「私は買う」「顧客は必ず評価する」といった発言を実需要の証拠として扱わない。事実、顧客の実発言、AIの推論、依頼者の希望を区別する。引用と要約、現在の機能と開発予定、競合の未確認事項と確認済み情報も混同しない。

## 失敗したときの対応

エージェントが応答しない、停止する、資料の取得に失敗する場合は、取得済みの結果を保存し、同一処理の再試行を既定で1回まで行う。それでも失敗した場合は未実施の役割と評価を記録する。欠けた発言を生成して埋めず、取得済みの結果で条件付きの提案を作れるかを統括が判断する。提案者の応答が得られなかった重大な批判が残った場合、成果物が合格していても実行全体を完了扱いにしない。

利用上限など実行環境の制約で止まった場合は、再試行の回数を消費せず一時停止する。再開すると、未送達の発言は再度転送され、応答済みの批判は再び転送されない。

討論記録は実際に送受信した発言に基づき、後から迫力のある会話へ脚色しない。全文と要約は区別し、引用には発言IDを付ける。架空の対話例（`examples/sample-debate.md`）を実行証跡として使わない。
