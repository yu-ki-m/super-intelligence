# product-branding-team

このスキルは依頼を受け付ける入口である。作業の順序、状態、発言の受け渡し、検査は `pbteam.py` のハーネスが管理し、各作業は親の会話が Agent ツールで起動するサブエージェントが行う。親の会話はハーネスが出した依頼をそのまま渡すだけで、依頼文や結果を読まず、書き換えない。親の会話が複数人の会話を創作することはなく、親の判断で完了状態を書き換えることもない。

ここでのプロダクトブランディングとは、誰の、どのような状況で選ばれたいかを定め、提供価値、その根拠、伝え方、利用体験を通じて、顧客からの認識を形成していくことを指す。完成するのは「ブランドの仮説」である。チーム内の合意やAIの評価で、需要や差別化が検証されたとは報告しない。

依頼者は目的や資料を提供する人であり、各工程の回答者や議論の仲介者ではない。依頼者への説明は `references/discussion-guide.md` の方針に従う。特に、工程名や質問を列挙するだけで進めず、今の作業が全体の何を決めるかを説明する。

## 進め方の全体

親の会話が行うのは、依頼の整理、ハーネスの開始と確認、サブエージェントの起動と完了の連絡、結果の説明である。

```
依頼の整理（brief.json）→ 実行環境の確認（probe）→ 実行の作成（init）→ 実行（run）→ 確認（status / export）→ 説明
```

ハーネスは親の会話の外のプロセスで動くので、Agent ツールを直接呼べない。そのため probe と run の間は、ハーネスが依頼をファイルに書き、親の会話がそれを受け取ってサブエージェントを起動する。手順は「サブエージェントの起動」の節に書く。サブエージェントは親の会話と同じ接続先と認証で動くので、Bedrock などでも親の会話が動けば動く。

以下、`<skill>` はこのファイルのあるフォルダーを指す。コマンドは Bash または PowerShell で実行する。

### 1. 依頼を整理する

対象プロダクト、今回決めたいこと、参照資料、制約、提供段階を確認する。既に与えられた情報は再質問しない。方向を大きく左右する情報が欠ける場合だけ、まとめて一度に尋ねる。他の不足は未確認のまま進め、条件別の仮説を作る。実績や顧客の声を補作しない。

提供段階は次の4つから選ぶ。段階によって根拠の扱いが変わるためである。

| 値 | 段階 | 根拠の扱い |
| --- | --- | --- |
| `concept` | 構想 | 顧客課題と提供価値を仮説として扱い、課題の観察、試作品、実現可能性の確認状況を整理する |
| `pilot` | 試験提供 | 試用者の反応を市場全体へ一般化せず、無償利用と支払い意思を分ける |
| `offering` | 提供中 | 商談、受注・失注、利用状況、問い合わせ、継続・解約から、認識と提供実態を整理する |
| `redefine` | 再定義 | 新たに目指す認識と既存顧客が評価する価値を分け、変更で失う期待も検討する |

整理した内容を `brief.json` に書く。形式は `schemas/brief.schema.json`、記入の考え方は `templates/product-brief.md` を見る。`deliverables` にはグラフで決まった名前だけを書く。`minimal` では「紹介ページ」「検証計画」、`standard` ではこれに加えて「短い紹介文」「営業資料」「デモ」「FAQ」「事例」「視覚表現」「接点表」「価格比較」「ブランド関係」が使える。違う名前は実行の作成時に拒否される。製品の種別は、他社へ販売する製品なら `B2B`、個人へ販売する製品なら `B2C`、自社の社員だけが使う製品なら `internal` とする。`planned_features` には開発予定の機能を登録する。提供中のように書いた文章を機械検査で拒否するために使う。複数の製品の資料を一つの実行に混ぜない。製品ごとに実行を分ける。

### 2. 実行環境を確かめる

`probe` をバックグラウンドで実行し、「サブエージェントの起動」の手順で、出された2件の依頼にサブエージェントを起動する（`--run-dir` には `.pbteam-probe` を指定する）。

```bash
python <skill>/pbteam.py probe --workdir .pbteam-probe          # バックグラウンドで実行する
python <skill>/pbteam.py pending --run-dir .pbteam-probe --wait 90
```

サブエージェントの起動、結果の取得、以前の依頼と結果を引き継いだ継続、発言の受け渡しを実際に確かめ、結果を `.pbteam-probe/capability.json` に書く。`debate_possible` が `false` なら実討論は実施できない。その旨を依頼者に伝え、単一エージェントの模擬会話へ黙って切り替えない。作成できるのは設計資料だけだと明示する。サブエージェントが結果のファイルを書けずに失敗した場合は、権限の設定で実行フォルダーへの書き込みを許可するよう依頼者に伝える。

### 3. 実行を作り、開始する

```bash
python <skill>/pbteam.py init --brief brief.json --graph minimal --run-dir .product-branding-team/<製品ID> --concurrency 1 --probe-dir .pbteam-probe
python <skill>/pbteam.py run --run-dir .product-branding-team/<製品ID>      # バックグラウンドで実行する
```

`init` は `probe` の結果（`--probe-dir`）を使う。`run` を始めたら、「サブエージェントの起動」の手順を繰り返す。

`--graph` の選び方は次のとおりである。呼び出し数の上限の目安は開始時に表示される。

| グラフ | 内容 | 向いている依頼 |
| --- | --- | --- |
| `minimal` | 根拠、利用者業務、代替手段、日常利用、候補2案、相互批評、採用、紹介ページ、検証計画、横断検査 | まず一つの利用場面で確かめたい、依頼範囲が紹介ページ程度 |
| `standard` | 50役割を成果物と依存関係で結ぶ | 営業資料、デモ、FAQ なども含めて広く検討したい |

始める前に、この方式の費用と効果を依頼者に伝える。架空の小さな題材（資料3点、紹介ページと検証計画）での比較では、単一担当、一度だけ分担して統合する方式、本方式のいずれも事前に定めた15基準をすべて満たし、成果物の品質に差は測れなかった。本方式は呼び出しが26回、時間が約25倍、API 定価換算の費用が約60倍だった（`evals/results/README.md`、`claude -p` の方式で測定）。Agent ツールの方式では、ハーネスは費用を取得できないので、提出物の費用欄は「取得できなかった」になる。本方式で増えるのは、主張と根拠の対応、実際の批判と応答の記録、別担当の検査と差し戻しの記録、資料の更新に対する影響の追跡である。これらの記録が判断や説明に必要な依頼、資料が多く担当間の食い違いが起きやすい依頼に向く。記録が要らず資料も少ない依頼なら、本方式を使わない選択も示す。

`standard` は `brief.json` の `deliverables` に書かれた成果物に絞って起動し、該当しない役割は理由を記録して起動しない。依頼者が予算を指定していれば `--max-calls` で上限にする。同時実行数は利用環境の上限に合わせる。利用上限に当たりやすい定額プランでは 1 から始める。

実行には時間がかかるので、`run` はバックグラウンドで実行する。止まっても状態は保存されている。待機の通知を重ねて出さない。検討中の重要な対立、案の変更、残る不確実性が分かった時点で依頼者へ報告する。

### サブエージェントの起動

`probe` と `run` の間、親の会話は次を繰り返す。`<run>` は実行フォルダー（`probe` のときは `.pbteam-probe`）である。

1. `python <skill>/pbteam.py pending --run-dir <run> --wait 90` を実行する。出力の `new` が、起動するサブエージェントの一覧である。
2. `new` の各依頼について Agent ツールを1回ずつ起動する。`subagent_type`、`model`、`description`、`prompt` は出力の値をそのまま渡す。`model` が `null` なら指定しない。親の会話は依頼文や結果のファイルを開かない。結果がサブエージェント自身の出力であることを保つためと、親の会話の文脈を節約するためである。
3. 起動したら、完了の通知を待つ。通知が来たら `python <skill>/pbteam.py done --run-dir <run> --attempt <attempt_id>` を実行する。サブエージェントが利用上限や起動の失敗などで作業できなかったときは、`--error` にそのエラー文を渡す。
4. 1 に戻る。`pending` が「ハーネスは動いていない」と返したとき、またはバックグラウンドの `run` の終了が通知されたときは、`status` で状態を確かめる。

サブエージェントは、依頼文を読み、結果を実行フォルダーの `exchange/<作業>/result.json` に書き、「提出した：<作業>」とだけ返す。形式の検査、受理、差し戻しはハーネスが行う。同じ担当の続きの作業では、ハーネスが以前の依頼と結果のファイルを読ませるので、同じサブエージェントへ SendMessage で続けない。

親の会話が依頼を受け取らないまま数分たつと、ハーネスは `paused` になる。再試行の回数と呼び出しの予算は消費しない。`run` で再開し、上の手順を続ける。

端末だけで、親の会話なしに動かす場合は、`init` と `probe` に `--adapter claude_cli` を付けると、ハーネスが `claude -p` を別プロセスとして起動する。この方式では、設定ファイルに書いた接続先（Bedrock など）や `apiKeyHelper` などが子のプロセスに届かず、Claude のログインか OS の環境変数で渡した認証だけで動く。

### 4. 確認し、再開する

```bash
python <skill>/pbteam.py status --run-dir <run>        # 現在地
python <skill>/pbteam.py run --run-dir <run>           # 続きから再開
python <skill>/pbteam.py stop --run-dir <run>          # 実行中の呼び出しの後で一時停止
python <skill>/pbteam.py update-source --run-dir <run> --source S1 --file 新しい資料.md   # 資料の更新
python <skill>/pbteam.py export --run-dir <run>        # 提出物の書き出し
python <skill>/pbteam.py log-human --run-dir <run> --minutes 30 --activity "内容の確認"
```

再開では、完了した作業を再実行せず、実行中だった作業、未送達の発言、未検査の成果物だけを復旧する。再開を頼まれたら `status` で現在地を確かめ、現在地と次の作業を短く示してから `run` する。資料が更新された場合は `update-source` を使う。変更された根拠を引用する成果物と、一式の横断検査だけが再確認の対象になる。

利用上限で `paused` になったら、上限が解除されてから `run` で再開する。上限を理由に検査を省略しない。

### 5. 結果を説明する

`export` は `<run>/output/` に次を書き出す。

| ファイル | 内容 |
| --- | --- |
| `summary.md` | 要点の1ページ。未確認の状態と提供条件を残す |
| `brand-proposal.md` | 依頼で求められる20シートの全体 |
| `debate-log.md` | 実際に送受信した発言。誰のどの発言に誰が応答したかを追える |
| `quality-review.md`、`rejection-trace.md` | 検査の結果と、拒否から修正・再検査までの経路 |
| `cross-document-review.md` | 資料横断の検査 |
| `task-board.md`、`session-state.md`、`evidence-register.md`、`capacity.md` | 作業台帳、実行の状態、主張と根拠、稼働実績 |

依頼者へは次を区別して伝える。

終了状態は、品質契約充足、仮説案の契約充足、資料不足による保留、予算上限による未達、実行失敗、中止のいずれかである。途中結果を提出できても完了状態を偽らない。修正上限や予算に達したことを品質達成と同一視しない。

実施の水準は、設計のみ、模擬実行済み、実エージェント接続済み、内容品質評価済み、規模検証済みを分ける。`mock` で動かした結果は状態制御の確認であり、内容の品質や実接続の証拠にならない。

50人分という目標については、`references/capacity-evaluation.md` の方法で測れる値だけを報告する。人間の基準時間が実測されていなければ「50人分を達成した」とは報告せず、完了成果物、人間の介入時間、AI費用を作業種別ごとに示す。

実際の顧客の反応がなければ、需要や理解は未確認として報告する。顧客への連絡、投稿、公開、広告出稿、価格・製品変更は実行せず、計画までとする。製品の改善が必要なら、根拠となる顧客価値、現状との差、受入条件を引き渡し事項にする。
