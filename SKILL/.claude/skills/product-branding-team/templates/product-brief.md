# 依頼の整理

親の会話がこの内容を確かめ、`brief.json`（形式は `schemas/brief.schema.json`）に書く。既に与えられた情報は再質問しない。方向を大きく左右する情報が欠ける場合だけまとめて尋ね、他は未確認のまま条件別の仮説を作る。実績や顧客の声を補作しない。

| 項目 | `brief.json` の項目 | 書くこと |
| --- | --- | --- |
| 依頼目的 | `goal` | 今回決めたいこと。例：試験提供の後、誰に何を約束して提供を始めるかの仮説を決める |
| 検討の契機 | `trigger` | 立ち上げ、価値が伝わらない、比較で違いが伝わらない、期待と体験が違う、など |
| 製品 | `product` | ID、名称、種別、概要。種別は、他社へ販売するなら B2B、個人へ販売するなら B2C、自社の社員だけが使うなら internal（社内向け）。企業ブランド・製品ブランド・機能の名称が混ざっていれば対象を定める |
| 提供段階 | `stage` | `concept`（構想）、`pilot`（試験提供）、`offering`（提供中）、`redefine`（再定義） |
| 判断する人 | `decision_maker` | 結論を判断する人。分からなければ未確認と書く |
| 制約 | `constraints` | 既に決まっている制約。例：顧客への連絡はしない |
| 依頼範囲の成果物 | `deliverables` | グラフで決まった名前だけを書く。紹介ページ、検証計画、短い紹介文、営業資料、デモ、FAQ、事例、視覚表現、接点表、価格比較、ブランド関係。違う名前は拒否される。空ならグラフの全成果物 |
| 開発予定の機能 | `planned_features` | 名称と、本文での言い方（`keywords`）。提供中のように書いた文章を機械検査で拒否するために使う |
| 資料 | `materials` | ID、パスまたは本文、題名、確認日。別の製品の資料を混ぜない |
| 未確認事項 | `unknowns` | 依頼時点で分かっていないこと |
| 追加調査 | `allow_research` | 不足を追加で調べてよいか |

## 記入例（架空）

```json
{
  "product": {"id": "hikitsugi", "name": "ヒキツギ帳（架空）", "type": "B2B"},
  "goal": "試験提供の後、誰に何を約束して提供を始めるかの仮説を決める",
  "stage": "pilot",
  "trigger": "試験提供が終わり、紹介ページを用意する段階になった",
  "decision_maker": "企画責任者",
  "constraints": ["顧客への連絡や公開は行わない"],
  "deliverables": ["紹介ページ", "検証計画"],
  "planned_features": [{"name": "担当者の自動割り当て", "keywords": ["自動で割り当て", "自動割り当て"]}],
  "materials": [{"id": "S1", "path": "docs/observation.md", "title": "窓口の観察記録", "retrieved_at": "2026-09-20"}],
  "unknowns": ["試用後に支払う意思があるか"]
}
```
