# 検査結果

`python pbteam.py export` が `output/quality-review.md` に書き出す。内容検査の担当の出力形式は `schemas/output_review.schema.json` で定義している。

## 一件の検査に含まれるもの

検査対象は成果物の版とハッシュで特定する。v2 に対する合格は v3 へ流用されない。判定は「検査担当の判定」と「ゲートの判定」を分けて記録する。検査担当が合格と書いても、重大な欠陥や基準の未達があればゲートは合格にしない。点数は使わない。

| 項目 | 内容 |
| --- | --- |
| 対象 | 成果物IDと版 |
| 検査の種類 | `machine`（形式検査）、`content`（内容検査）、`upstream`（下流の欠陥による差し戻し） |
| 検査担当 | 役割ID。作成者の名前や討論の多数意見は渡していない |
| 検査担当の判定 | `pass`、`fail`、`hold` |
| ゲートの判定 | `pass`、`fail`、`hold`、`invalid_review`（検査の不備）、`needs_second_check`（別担当の再確認）、`superseded`（対象の版が現行でない） |
| 合否基準ごとの判定 | 全基準への回答。未達には該当箇所と理由 |
| 認めた長所 | 該当箇所と理由。修正で失われないように修正担当へ渡す |

## 欠陥

軽微な改善点（`minor`）と、判断を誤らせる重大な欠陥（`major`）を分ける。重大な欠陥は他の評価で相殺しない。必須項目の欠落、根拠の捏造、未提供機能の断定、未解決の重大な矛盾、依頼した制作物の未作成は不合格である。

| 項目 | 内容 |
| --- | --- |
| 欠陥ID | 同じ欠陥が残っていれば同じIDのまま回数が増える |
| 分類 | 情報不足、推論の誤り、対象選択の問題、制作不足、成果物間の矛盾、検査の誤り |
| 該当箇所、引用 | どこの何か |
| 理由 | なぜ欠陥か |
| 修正条件 | 何をもって解消とするか |
| 回数 | 2回続くと原因診断へ移る |
| 状態、解消の記録 | `open`、`resolved`。解消の判定は次の検査担当が書く |

## 修正依頼と再検査

修正担当は欠陥IDごとに何を変えたかを `changes` に書く。指摘が誤っていると考えるなら `rebuttals` に根拠を書く。次の検査担当は未解決の重大欠陥すべてに `resolved_defects` で判定を返す。語句が変わっただけなら解消としない。

## 未解決事項

上限に達して未解決のまま残った欠陥は、状態 `open` のまま記録に残り、作業は失敗または保留で終わる。完了状態へは移らない。経路の全体は `output/rejection-trace.md` でたどれる。
