# 実行例：調査から討論、制作、検査、修正、提出まで

この文書は二つの部分からなる。前半は実エージェントで行った実行の記録からの抜粋であり、後半はその実行を読む手順の説明である。題材の製品「ヒキツギ帳」と資料（`evals/fixtures/hikitsugi/`）は評価のために作った架空のものだが、以下に引用する発言、判定、版、費用は、2026-11-06 に `python evals/run_e2e.py --name e2e_real_4` で実際に記録された値である。全記録は `evals/results/e2e_real_4/` にある。

## 実行の条件

| 項目 | 値 |

## 1. 不良成果物の拒否（機械検査）

`alternatives` の最初の出力として、現状維持や手作業を含まない比較表を差し込んだ（記録の `injected_output`）。形式検査が「比較に手作業・内製・現状維持など、製品以外の選択肢がない」として拒否し（R3）、欠陥 D6 を記録した。分類が制作不足なので、同じ作成担当（M03）のセッションへ修正を依頼した。修正版 v2 は現状維持を含み、別のインスタンスの V03 が合格とした（R5）。

## 2. 中断と資料の更新

9件の結果で中断し、プロセスを閉じた。資料 S3 の「2024年3月の価格」の文を「2026年10月の価格と移行機能の追加」に置き換え、`update_source` で登録した。引用が消えた根拠は E24 の1件だけで、それを引用する3つの成果物（代替比較、根拠台帳、製品の整理）の合格だけが取り消された。顧客分析は E24 を引用していなかったので、このとき再確認の対象にならなかった。再開後、検査担当は3つとも「根拠 E24 は最新の資料から引用できない」と指摘して差し戻し、各担当が新しい資料で書き直した。

## 3. 実際の相互批評

二つの候補は別々のインスタンスが、互いの案を見ずに作った。論点「現在の方法から変える理由は十分か、その約束を提供できるか」について、V03 と P04 が批評した。以下は記録された発言の全文からの抜粋である。

> **M1　V03（I-V03-4）→ B08　批判・重大（candidate_a v1）**
> 現状維持の側から見ると、この約束は共有表と区別できない。C社は共有表に備考欄を足して経緯を書いているのに、口頭説明が残っている。つまり「経緯を誰かが書く」ことは現状でも可能で、書かれない・読まれない点が問題のはずである。（以下略）

> **M15　B08（I-B08-1）→ V03　応答・受け入れて修正（M1 への応答、案を v2 にした）**
> C社は備考欄に経緯を書いているのに口頭説明が残っている(E23,E6)。（中略）備考欄で足りなかった理由(記入漏れか、探しにくさか)は資料にない。そこで「共有表より記録しやすい」と読める表現を避けると明記し、備考欄の記入実態と足りなかった理由の確認を「次に確かめること」に加えた。

> **M27　V03（I-V03-4）→ B08　再評価・解消（M1 について、M15 を読んだうえで）**
> candidate_a v2 は、備考欄で足りなかった理由が資料にないと認めた。「共有表より記録しやすい」「読まれやすい」を約束しない項目に加え、認識の仮説でも差は未確認と明記した。（中略）求めた修正はすべて反映されている。

M1 と M27 は同じインスタンス（I-V03-4）、同じセッション（`c3b10753…`）の発言である。批評者は自分の批判を覚えたまま、提案者の応答と修正版を読んで判断している。候補の作成と応答も同じセッション（I-B08-1）が続けている。この論点では批判11件、質問1件、応答12件、再評価11件が記録され、重大な批判はすべて解消と判定された。P04 の批判 M8「1日10分の短縮が導入設定約40分と再登録と履歴入力の負担に見合うかを示していない」を受けて、案は「変える理由は十分とは言えない」と結論を弱めた。

## 4. 不良な紹介ページの拒否（内容検査）

紹介ページの最初の出力として、機械検査は通るが内容に欠陥がある文章を差し込んだ。欠陥は事前に二つ定めてある。引用は絞り込み表示の機能しか述べていないのに「対応の抜けが減る」と結論している点と、管理者の設定が必要なのに「設定はほとんど不要」と書いている点である。V05 は次の理由で拒否した（R20、記録からの抜粋）。

> 一覧で担当未定の依頼を確認できる機能(E11)から、対応の抜けが減るという成果へ飛躍している。確認後の割り当て・対応の根拠はなく、対応漏れは未測定(E16)。

> E13は管理者による担当者登録と権限設定が必要（1か所で約40分）、E20は進行中の依頼の手での再登録が必要と示す。

修正版は「始める前に必要な作業」の節を設け、成果の主張を機能の記述に限った。次の検査担当は欠陥ごとに解消を判定し、例えば D35 について「語句の置換ではなく、約束の範囲が変わっている」と記録した。

## 5. 資料横断の検査で止まった理由

個別の資料はすべて合格したが、横断検査が3回とも不合格になり、上限に達して「予算上限による未達」で終わった。記録を読むと、内容検査（V08）は3回とも「整合している」と判定し、機械検査の指摘の多くを「用途の違いであり矛盾ではない」と退けていた。不合格の原因は、当時の機械検査が対象の文言や成立条件の文を文字列で比べ、言い方の違いを矛盾と断定していたことにある。これはハーネスの設計の誤りであり、修正した（文字列の比較による指摘は内容検査への確認依頼に変えた。`architecture.md` と `evals/results/README.md` を参照）。上限に達しても完成扱いにしなかった点は、設計どおりの動作である。

## 記録の読み方

実行フォルダーで次を実行すると、ここに書いた内容をすべて確かめられる。

```bash
python pbteam.py status --run-dir evals/results/e2e_real_4/run
python pbteam.py export --run-dir evals/results/e2e_real_4/run --out <出力先>
```

`debate-log.md` で発言と応答の関係を、`rejection-trace.md` で差し込みから拒否・修正・再検査までの順番を、`quality-review.md` で欠陥ごとの解消の判定を確かめる。各発言の試行IDに対応する `run/raw/<試行ID>.json` が、実行基盤の応答そのものである。
