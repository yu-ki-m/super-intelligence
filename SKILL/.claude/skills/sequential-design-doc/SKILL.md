# 逐次処理の詳細設計書（sequential-design-doc）

ソースコードを解析し、**プログラム言語を日本語に置き換えるように**、実行される処理の順序・条件・データの変化を忠実に書いた詳細設計書（単一 HTML）を作る。
一般的な設計書のような機能単位の要約・処理の共通化・クラス構成の説明はしない。読者がコードを読まずに、実行順序・分岐・データの変化・入出力・副作用を具体的に理解できることを目指す。

最優先の品質基準は**ソースコードと文書の意味的な同等性**。文書を短くすることや、見た目をきれいにすることは目的ではない。

スキルのディレクトリを `${CLAUDE_SKILL_DIR}` と書く（このファイルがあるディレクトリ）。

## 原則

1. **実行順に、実行される処理そのものを書く。** 1 行 = 1 つの実行単位（代入・判定・SQL・外部通信・例外・トランザクション操作・応答）。各行で入力・実行条件・処理内容・結果が分かるようにする。
2. **呼び出し先を展開する。** 「共通認証処理を呼び出す」「Repository を使用して取得する」のような構造の説明で済ませず、呼び出し先で実行される処理を呼び出し位置に書く。同じ処理が複数の経路・エンドポイントで実行されるなら、それぞれに書く。メソッド名は根拠欄に置く。
3. **制御の流れを木の形で書き、曖昧にしない。** 分岐の下には結果ごとに「〜のとき」行を必ず置き（├─）、その結果の処理を 1 段下げる。繰り返し・try はブロックの終わりの行で閉じる（└─）。try・catch・finally は日本語にせずキーワードのまま書く。行き先は処理内容に「→ NN」で書き、例外は通過する finally・ROLLBACK・選ばれるハンドラー・応答まで書く。フレームワークが暗黙に行う処理（入力検証・トランザクション・ORM の SQL・例外ハンドラー）も、結果に影響するものは書く。
4. **SQL は全文を残し、データを表で示す。** SQL の行の中に、項目（1. 2. …）として SQL・バインド変数・取得データ／更新前後／登録データ／削除対象・件数ごとの処理を並べる。項目は No.29.3 のように参照できる。ORM から推定した SQL は「参考SQL」と明示し、実行SQL と区別する。
5. **事実と推定を分ける。** コードで確認したことは根拠（ファイル:行）付きで書き、フレームワーク仕様からの推定は〔推定〕、確定できないことは〔未確認〕にして未確認事項に載せる。推測で穴埋めしない。
6. **表を活用し、余白を削る。** 逐次処理表は No.・処理内容・根拠の 3 列。項目・データ・判定・エラーは表に、実行順序は逐次処理の行に。罫線・縦線・枝・字下げはテンプレートの CSS（13px・セル余白 3〜6px・装飾なし・印刷対応）に任せ、独自の装飾を足さない。
7. **リクエスト・レスポンスは JSON の形でも見せる。** ボディが JSON なら、項目の表の前に実際の形の JSON の例（シナリオの値）を置く。異常時は形ごとに 1 つ。外部 API の送受信も同じ。
8. **処理が複数なら、タブで切り替え、関心事でまとめる。** 1 つの文書に複数のエンドポイント・ジョブを入れるときは、処理ごとにタブにし（build が作る）、タブを関心事のグループ（対象の業務・参照と変更など）でまとめる。

## 進め方

### 1. 範囲と出力先を決める

- 起点（エンドポイント・ジョブ・メッセージハンドラー）を特定する。依頼から特定できない場合だけ、候補（パス・メソッド・ファイル:行）を挙げて確認する。複数の起点を 1 つの文書にしてよい（処理ごとに節を分け、build が処理ごとのタブにする）。
- 複数の起点を扱うときは、関心事のグループ（例：「タスクの参照」「タスクの変更」、「注文」「返金」）を決め、処理をグループごとに並べる（`html-rules.md` 10 章）。
- 出力先は、利用者の指定が無ければ作業ディレクトリの `design-docs/<名前>/`。ここに成果物 `<名前>.html`、台帳 `<名前>.trace.md`、部品 `parts/`、スクリーンショット `shots/` を置く。

### 2. 解析する

`references/analysis-guide.md` を読み、その手順で進める。フレームワークの暗黙の動作は `references/framework-notes.md` の該当する章を読む。

- 起点の前後（フィルター・ミドルウェア・入力検証・トランザクション・例外ハンドラー・コミット後の処理）を先に洗い出す。
- 起点から深さ優先で追跡し、メソッドを 1 つ読み終えるたびに台帳 `<名前>.trace.md` に書く（すべてに `ファイル:行`）。追跡するメソッドが少なければ台帳は省略してよいが、大きいコードベースでは必ず作る。
- 追跡するファイルの注目行を一覧にし、台帳に漏れが無いか照合する：
  `python "${CLAUDE_SKILL_DIR}/scripts/ddoc.py" inventory <ファイル|ディレクトリ>... --src-root <ソースのルート>`
- 例外ごとの伝わり方、トランザクションの範囲、並列・非同期、データの流れを台帳にまとめる。

### 3. 書く

`references/writing-rules.md`（逐次処理の書き方）、`references/sql-rules.md`（SQL とデータの表）、`references/html-rules.md`（HTML の部品）を読む。

```bash
python "${CLAUDE_SKILL_DIR}/scripts/ddoc.py" init <出力先>/parts [--procs <処理の数>]
```

- 雛形の部品ファイル（概要・逐次処理・例外経路・レスポンス・未確認事項・検証記録）を、台帳をもとに埋める。部品に `<html>`・`<style>` は書かない。
- 逐次処理表は 3 列（No.・処理内容・根拠）。字下げ（`class="i1"`〜）で木の形にし、分岐の結果・catch・finally は `tr.arm` の行、SQL・外部 API・判定表は処理の中の項目（`<ol>`）にする（`html-rules.md` 4・5 章）。
- 入力項目・レスポンス・外部 API の送受信の表の前に、JSON の例（`pre.json`）を置く（`html-rules.md` 3・5・7 章）。
- 処理が複数なら、各 `section.proc` に `data-group`（グループ名）と `data-tab`（タブの名前）を書き、`00-toc.html` に一覧と共通の前提を書く。処理の外から行を指すときは `p2 No.05`（`html-rules.md` 10 章）。
- 文書全体で 1 つの代表的なシナリオを決め、値の例（架空）をリクエストから応答まで一貫させる。
- 書き方に迷ったら実例を見る：`examples/ticket-status-update/parts/`（Spring・JWT フィルター・行ロック・状態遷移・楽観ロック・例外ハンドラー）、`examples/member-signup/parts/`（NestJS・ORM の参考SQL・トランザクション・キューと別プロセスのワーカー）。

### 4. 組み立てて機械検査する

```bash
D="${CLAUDE_SKILL_DIR}/scripts/ddoc.py"
python "$D" build <出力先>/parts -o <出力先>/<名前>.html --title "詳細設計書：<処理名>（<メソッド> <パス>）" \
    --meta "作成日 YYYY-MM-DD" --meta "対象 <ソースのルート>" --src-root <ソースのルート>
python "$D" check <出力先>/<名前>.html --src-root <ソースのルート> --coverage
python "$D" check <出力先>/<名前>.html --refs
python "$D" render <出力先>/<名前>.html --shots <出力先>/shots
```

- build・check の **ERROR は 0 件になるまで直す**。WARN は 1 件ずつ読み、直すか正しい理由を確認する。
- `--coverage` の INFO（根拠から参照されていない注目行）を確認し、書き漏れを追記する。
- `--refs` の一覧（No.29.3 などの参照と参照先の文）を読み、番号のずれ・まとめの表との食い違いを直す。
- render の ERROR（横スクロール・はみ出し）を直し、スクリーンショットを Read で見て、崩れ・読みにくい表が無いか確認する。タブのある文書は `--tab p1` のように 1 つのタブを撮って、タブの並びとグループも確かめる。

### 5. ソースと照合して検証記録を書く

`references/verification.md` の 11 の観点で、ソースを開き直して照合する。問題は直して再度 build する。
検証記録（`95-verification.html`）に観点ごとの結果と確認内容を書く。未確認事項が 1 件でもあれば検証状態は「未完了」。NG を残したまま出力しない。

### 6. 報告する

次を簡潔に伝える：HTML のパス、対象の処理（起点）と行数（逐次処理・例外経路・非同期経路）、SQL の数（実行SQL・参考SQL）、機械検査の結果、検証状態、利用者に確認してほしい未確認事項、扱わなかった範囲。

## ddoc.py

```
python ddoc.py init      <dir> [--procs N]
python ddoc.py build     <部品|dir>... -o OUT.html --title T [--meta M]... [--src-root DIR] [--no-check] [--no-tabs]
python ddoc.py check     OUT.html [--src-root DIR] [--coverage] [--refs] [--json]
python ddoc.py inventory <file|dir>... [--src-root DIR]
python ddoc.py render    OUT.html [--widths 1280,1600] [--no-print] [--shots DIR] [--parts N] [--focus SELECTOR]... [--tab ID] [--pdf OUT.pdf] [--browser PATH]
```

終了コード：0 = 問題なし、1 = エラーあり、2 = 引数・入力の誤り、3 = ブラウザが見つからない（`--browser` か環境変数 `DDOC_BROWSER` で指定）。
