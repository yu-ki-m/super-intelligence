# 検証手順

生成した HTML がソースコードと意味的に同じであることを確かめ、結果を「検証記録」節に残す。
検証で見つけた問題は直してから記録する。直せない・確かめられないものは〔未確認〕として残し、検証状態を「未完了」にする。

目次
1. 機械検査（build / check / render）
2. ソースとの照合（11 の観点）
3. 独立レビュー（任意）
4. 検証記録の書き方

---

## 1. 機械検査

```bash
D="${CLAUDE_SKILL_DIR}/scripts/ddoc.py"
python "$D" build <作業ディレクトリ> -o <出力.html> --title "…" --src-root <ソースのルート>   # エラー 0 件まで直す
python "$D" check <出力.html> --src-root <ソースのルート> --coverage                          # 未参照の注目行を確認
python "$D" check <出力.html> --refs                                                           # No. の参照と参照先の一覧（整合の確認）
python "$D" render <出力.html> --shots <出力先>/shots                                          # 表示の検査とスクリーンショット
```

| 検査 | 見るもの | 対応 |
|---|---|---|
| build / check の ERROR | 列数（3 列）・No. の形式と順序・参照先の有無（No.29.3 を含む）・分岐の「〜のとき」行（結果ごとに 1 つ、合計 2 つ以上、「とき」の形）・処理の無い「〜のとき」行の行き先・SQL の必須表・`data-kind`・根拠の行番号の範囲・未確認事項と検証状態の整合 | すべて直す |
| check の WARN | 抽象的な表現（ABSTRACT）、字下げ（木）の崩れ（TREE）、繰り返しの対応（LOOP）、SQL の列と表の不一致（SQLCOL・SQLBIND）、根拠の欠落（SRC）、項目の `<ol>` が 2 つ以上（ITEM）、JSON の例が無い・JSON として正しくない・表に無い項目がある（JSON）、複数の処理に data-group・data-tab が無い（TAB） | 1 件ずつ読んで直すか、正しい理由を確認する |
| check --refs の INFO（REFMAP） | 「No.29.3」「→ 13」などの参照と、参照先の行・項目の文の一覧 | 参照元で書いた内容と参照先の文が合っているか読む。番号を振り直した後・行を足した後は必ず確認する（入力項目表・まとめの表・未確認事項の No. がずれやすい） |
| check --coverage の INFO（UNCITED） | 根拠で参照した関数の中で、どの行からも参照されていない注目行（分岐・例外・SQL など） | 書き漏れなら追記する。対象外（呼ばれない分岐ではなく、追跡範囲外の関数など）なら理由を確認する。**分岐・例外・SQL の行を理由なく残さない** |
| render の ERROR | 横スクロール、要素のはみ出し | 長い語の折り返し、表の列の見直し（CSS は変えない） |
| render の WARN | 文字サイズ・セル余白・装飾 | テンプレートから外れた書き方（`style=""` など）を戻す |
| スクリーンショット | 表示の崩れ、読みにくい表、詰まりすぎ・空きすぎ | Read で画像を見て確認する。`--focus "pre.sql"` などで特定の箇所も撮れる |

ブラウザが無い環境では render を実行できない。その場合は検証記録の「視認性」に「ブラウザでの確認は未実施（理由）」と書く。

## 2. ソースとの照合（11 の観点）

台帳と HTML を並べ、ソースを開き直して確認する。記憶ではなく、ソースの該当行を読んで確かめる。

| 観点 | 確認の手順 |
|---|---|
| 処理網羅性 | 追跡した各メソッドの注目行（`inventory`・`--coverage`）が、すべていずれかの行の根拠になっているか。フレームワークの前処理・後処理（`analysis-guide.md` 2 章）が入っているか |
| 実行順序 | 呼び出しを展開した結果の行の順が、実行時の順と一致するか。特に、finally の位置、遅延 SQL（flush）の位置、並列処理の開始と待機、コミット後の処理 |
| 分岐網羅性 | すべての分岐の行に、結果ごとの「〜のとき」行があり、処理の無い結果には行き先があるか。else が無い if の不成立側、switch の default、短絡評価、三項演算子、NULL 合体演算子、Go の `if err != nil` も |
| 終了条件 | return・throw・raise・exit・応答のすべての位置が書かれ、それぞれの行き先（終了・経路）が正しいか |
| データ整合性 | 値の例が、リクエスト → 変数 → SQL → 計算 → 更新後 → レスポンスで一貫しているか。変数の格納先と利用箇所の No.（No.29.3 など）が正しいか。JSON の例（リクエスト・レスポンス・外部 API）の値がシナリオの値・項目の表と同じか、キーの名前と順がコード（シリアライズの順）どおりか。**まとめの表（異常時の応答・データ変更とトランザクション・未確認事項）の内容が、逐次処理・例外経路の行と食い違っていないか**（まとめの表は最後に、行を見ながら作り直すつもりで照合する） |
| SQL整合性 | SQL の全文がソースと一致するか（1 文字ずつ照合）。バインド変数の数と表の行、取得列と `rows`、SET 列と `upd`、INSERT 列と `ins` が一致するか。参考SQL が実行SQL として書かれていないか |
| 例外処理 | 例外の型・発生条件・捕捉の有無・通過する finally・選ばれるハンドラー・応答が正しいか。暗黙の例外（NULL、キーなし、型変換、制約違反、タイムアウト）を書いたか |
| トランザクション | 開始・COMMIT・ROLLBACK の位置、伝播属性、別トランザクション・トランザクション外の操作、ROLLBACK で取り消されないもの（外部 API・送信済みメッセージ）が正しいか |
| 共通化の排除 | 「〜を呼び出す」「共通処理」「〜サービスで」だけの行が無いか（ABSTRACT 警告）。共通の手順を、各経路・各エンドポイントで展開しているか |
| 視認性 | render の結果とスクリーンショット。過剰な余白・装飾が無く、表が読みやすいか。処理が複数なら、タブのグループ分けが関心事として自然か（`--tab` で撮って確認） |
| 根拠 | 根拠の `ファイル:行` を抜き取りで開き、その行に書いた処理があるか（行番号のずれ）。〔推定〕〔未確認〕の付け方が正しいか |

## 3. 独立レビュー（任意）

サブエージェントを使える環境で、利用者・実行環境の方針が許す場合は、文書を作っていない別のエージェントに、ソースと HTML を照合してもらうと見落としが減る。
依頼するときは、ソースのパス・HTML のパス・この文書（verification.md）の 2 章を渡し、「欠落・順序の誤り・分岐の誤り・データの不整合を、ファイル:行と No. を付けて列挙する」よう頼む。
指摘は自分でソースを読んで確かめてから反映する。実施しなかった場合は、検証記録に「独立レビューは未実施」と書く。

## 4. 検証記録の書き方

- 11 の観点を 1 行ずつ。結果は「OK」「未確認あり（U1, U3）」「対象外（理由）」のいずれか。
- 「確認した内容」に、何をどう確かめたかを具体的に書く（例：「coverage の未参照行 14 件を確認。refund_service.py:37-38 の分岐を追記、残り 12 件は追跡範囲外の関数」）。
- **NG を残したまま出力しない。** 見つけた問題は直してから OK にする。
- 検証状態（`p.vstatus`）：未確認事項が 1 件でもあれば `data-status="open"`「検証状態：未完了（未確認事項 N 件）」。すべて確認できた場合だけ `done`「検証状態：完了」。
- 解析できなかった箇所があるのに「完了」としない。
