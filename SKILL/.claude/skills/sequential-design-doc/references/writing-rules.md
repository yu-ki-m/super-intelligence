# 逐次処理の記述規則

逐次処理表（文書の中心）の書き方。HTML の部品と書式は `html-rules.md`、SQL は `sql-rules.md` を参照。

目次
1. 判断基準
2. 1 行の単位と、処理の中の項目（1. 2. …）
3. 処理内容の書き方（結果・行き先も処理内容に書く）
4. 呼び出し先の展開（共通化・メソッド構造を書かない）
5. 制御構造を木の形で書く（分岐・繰り返し・try・並列）
6. 例外・中断・終了（例外経路）
7. トランザクションとロック
8. 値の例（シナリオ値）
9. 表にするもの・文章にするもの
10. 確認済み・〔推定〕・〔未確認〕
11. 書き換え例

---

## 1. 判断基準

読者はコードを開かずに、この文書だけで「どの順に・どの条件で・どのデータが・どう変わり・何を返し、何が副作用として残るか」を知る。
迷ったときは **「この記述だけから元のロジックを書き直せるか」** で判断する。書き直せないなら粒度が粗い。

文書を短くすること、きれいに見せることは目的ではない。処理を省略したり、「など」でまとめたりして短くしない。
一方で、同じ情報を何度も書く必要はない。順序は逐次処理の行、構造化できる値は項目の中の表、と役割を分ける。

## 2. 1 行の単位と、処理の中の項目（1. 2. …）

逐次処理表の 1 行（No. の付いた行）は、次のいずれか 1 つ。

| 行にするもの | 例 |
|---|---|
| 値の取得・変換・計算・代入 | `email` を前後の空白を除いて小文字にし、`email` に格納する |
| 判定（分岐）1 つ | `stock.available` が `line.quantity` 未満か判定する |
| 繰り返しの開始・終端 | `command.lines` の要素ごとに 39〜45 を繰り返す ／ 次の要素があれば 39 へ戻る |
| try の開始・終端 | 16 を実行する（try） ／ finally の後、例外が残っていれば E7 へ |
| SQL 1 文（ORM の操作 1 回） | `stocks` の在庫数を減らす UPDATE を実行する |
| 外部との通信 1 回 | 決済代行の返金 API に POST する |
| 例外の送出 | `OutOfStockException` を送出する |
| トランザクションの開始・確定・取り消し、ロックの取得 | トランザクションを開始する（`@Transactional`、伝播 REQUIRED） |
| 非同期処理の起動・完了待ち | 与信照会を別スレッドで開始する |
| ログ出力 | WARN ログ「payment declined: order={id}」を出力する |
| 応答の生成・返却、処理の終了 | ステータス 201 で応答する |

**処理の中の項目**：1 行の中に、さらに分けて示すべき内容がある場合は、処理の文の後に `<ol>` で **1. 2. …** と番号を付けて並べる。
項目は処理の文より 1 段下がって表示され、ほかの場所から **No.29.3**（No.29 の項目 3）のように参照できる。

- SQL の行：1. 実行SQL（または参考SQL） 2. バインド変数 3. 取得データ／更新内容／登録データ／削除対象 4. 件数ごとの処理（`sql-rules.md`）
- 外部 API の行：1. 送信内容（URL・ヘッダー・タイムアウト） 2. 送信データ 3. 受信データ 4. 応答ごとの処理
- 複数の確認をまとめて行う行（JWT の検証の「署名・発行者・有効期限」、入力検証の注釈など）：確認ごとに 1 項目
- 判定表・状態遷移表・変換の対応表：その判定・変換の行の項目にする
- 1 つの式・1 つの代入で済む行には項目を作らない。

**粒度**

- まとめてよいのは、分岐も副作用も例外の可能性もない、連続した値の詰め替えだけ（DTO からコマンドへの変換など）。この場合も、変換の対応表を項目に置き、項目名を省略しない。
- ライブラリの定型の繰り返し（DB の結果を 1 行ずつ読み込んで配列に追加する、配列を `map` で変換する）は、繰り返しの中に分岐・副作用・例外が無ければ 1 行で書いてよい。「取得した各行を `Order` に読み込み、`orders` に追加する（読み込みの失敗 → E3）」。
- フレームワークの内部の動作は、**この処理の結果（応答・データ・行き先）を変えるものだけ**を行にする。結果に影響しない細部（キャッシュのヘッダー、内部のバッファリングなど）は書かないか、必要なら未確認事項・注記に回す。

## 3. 処理内容の書き方（結果・行き先も処理内容に書く）

- 文末は「〜する。」の常体。主語（システム）は省略する。
- 対象を具体的に書く。変数名・項目名・テーブル名・列名は原文のまま `<code>` で書き、必要なら日本語の意味を添える。
- **結果**（何に格納したか・値の例）は文の中に書く：「`token` に格納する（例 `eyJhbGci…`）。」
- **行き先**は文の最後に「→ NN」で書く：「`ForbiddenException` を送出する。→ E5」「… を作って `user` に格納する。→ 14」。
  行き先が書かれていない行は、次の番号の行へ進む（凡例に明記済み）。次の行ではない行へ進むときは、必ず「→ NN」を書く。
- 失敗したときの行き先も文の中に書く：「数字でない場合は `NumberFormatException` → E1」。
- 終了は「401 応答で<span class="end">終了</span>」のように書く。
- 計算は式そのものを書く（端数処理・型変換・上限下限・ゼロ除算の扱いまで）。比較は演算子の意味を正確に（「より大きい」「以上」「未満」）。
- 定数・列挙値・設定値は、名前ではなく値を書く（`REFUNDABLE` →「SHIPPED または DELIVERED」）。値がコードの外にある場合は、キー名を書き〔未確認〕にする。
- ライブラリの呼び出しは、入力・出力・失敗時の動作を書く（「`dto.password` を bcrypt（コスト 12）でハッシュ化し、`passwordHash` に格納する。」）。
- ほかの行の値を使うときは、出どころを No. で示す：「`count`（No.29.3）が 0 以下か判定する。」

## 4. 呼び出し先の展開（共通化・メソッド構造を書かない）

この文書は**実行される処理**を説明するもので、クラス構成やメソッド構成を説明するものではない。

- 関数・メソッドを呼ぶ行を作らず、**呼び出し先で実行される処理を、呼び出し位置に展開して**書く。呼び出し先の中でさらに呼ぶものも同じように展開する。
- インターフェース・抽象クラスは、実行時に使われる実装を特定して展開する（決められなければ〔未確認〕）。
- 次の書き方をしない（`ddoc.py check` が警告する）：「共通認証処理を呼び出す」「入力検証処理を実行する」「チケット更新サービスを呼び出す」「Repository を使用してデータを取得する」「〜を呼び出す。」で終わるだけの行（システムの外との通信を除く）。
- メソッド名・クラス名は**根拠欄**に書く（例：`InventoryService.java:23-37 allocate`）。
- 同じ関数が 1 つの処理の中で何度も呼ばれる場合、それぞれの位置で展開して書く。複数のエンドポイントで使われる場合も、エンドポイントごとに展開する。
- 展開しない（できない）もの：言語標準・外部ライブラリの内部（入力・出力・失敗時の動作だけ）、フレームワークの内部（結果に影響する動作だけ、〔推定〕）、提供されていないコード（〔未確認〕）。

## 5. 制御構造を木の形で書く（分岐・繰り返し・try・並列）

### 5.1 種別タグ

処理内容の先頭に、制御・副作用を示すタグを付ける（`<span class="k">分岐</span>`）。普通の代入・計算には付けない。

| タグ | 付ける行 |
|---|---|
| 分岐 | if / else if / switch / match / 三項演算子 / 短絡評価による条件実行 / Go の `if err != nil` |
| 繰返 / 繰返終端 | 繰り返しの開始 / 終わり（戻り先と抜け先を書く行） |
| try / try終端 | try 文の開始 / 終わり（finally の後の行き先を書く行。必要な場合だけ） |
| 並列 / 待機 | 並列実行の開始 / 完了待ち |
| 非同期 | 呼び出し元が完了を待たない処理の起動（別スレッド・キュー投入・イベント発行） |
| SQL / API | DB 操作（ORM を含む）／ システムの外との通信 |
| TX | トランザクションの開始・COMMIT・ROLLBACK |
| ロック | アプリ側の排他制御（SELECT … FOR UPDATE は SQL タグで本文に明記） |
| 例外 | 例外の送出（`<span class="k x">例外</span>`） |
| 応答 / 終了 | 応答の生成・返却 ／ 処理の終了（`<span class="k x">終了</span>`） |
| ログ | ログ出力 |

### 5.2 木の形（字下げ・縦線・枝）

制御構造は、ソースの入れ子をそのまま **木の形** で表す。字下げは処理内容の欄に `class="i1"`〜`"i8"` で付け、build と CSS が縦線と枝を描く。

- **見出しの行**（分岐・繰返・try・並列、コールバック型のトランザクション）の内側の行は、見出しより 1 段深くする。見出しの下から縦線が下りる。
- **分岐の結果**・catch・except・finally・並列の各処理の区切りは「〜のとき」行（`tr.arm`、No. なし）にし、見出しの 1 段下に置く。縦線から横の枝（├─）が出る。
- その結果で実行される行は、「〜のとき」行よりさらに 1 段深くする（自分の縦線を持つ）。
- **ブロックの終わり**を示す行（繰返終端・待機・try終端）は、見出しの 1 段下に置く。縦線がそこで止まる（└─）。
- 字下げは 1 段ずつ深くする（2 段以上いきなり深くしない）。見出しでない行の次で字下げを深くしない。
- 横の罫線はブロックの間にだけ自動で引かれる。ブロックの内側の行は 1 つのまとまりとして表示される。

```
 28 │ [分岐] user.roles に TICKET_ADMIN が含まれないか判定する。
    │ ├─ TICKET_ADMIN が含まれないとき（No.28 が成立）
 29 │ │   │ [SQL] project_member の件数を count に格納する。
 30 │ │   │ [分岐] count が null または 0 以下か判定する。
    │ │   │ ├─ count が null または 0 以下のとき（No.30 が成立）
 31 │ │   │ │   │ [例外] ForbiddenException を送出する。→ E5
    │ │   │ ├─ count が 1 以上のとき（No.30 が不成立） → 32
    │ ├─ TICKET_ADMIN が含まれるとき（No.28 が不成立） → 32
 32 │ ticket.status を previousStatus に格納する。
```

### 5.3 分岐

- 判定行には、条件の意味（日本語）と原文の式（`<code>`）の両方を書く。
- **すべての分岐について、結果ごとに「〜のとき」行を置く**（`ddoc.py check` がエラーにする）。成立・不成立の両方、switch のすべての case と default、3 方向以上の判定のすべての結果。
  - 「〜のとき」には条件の中身を日本語で書く（「`stock` が null のとき（在庫の行が無いとき）」）。その後に `<span class="of">（No.40 が成立）</span>` と、どの分岐のどちらの結果かを添える。
  - その結果で実行される処理があれば、「〜のとき」行の下に 1 段下げて書く。
  - 処理が無く次へ進むだけの結果は、「〜のとき」行の文の最後に行き先を書く：「`stock` が null でないとき（No.40 が不成立） → 42」。
- 分岐の結果の処理の最後の行から、分岐の後の行ではない所へ進む場合は、その行に「→ NN」を書く。
- else if の連鎖は、1 つの分岐の行として「〜のとき」行を評価順に並べるか、ソースどおりに入れ子の分岐にする。評価順（前の条件が不成立のときだけ次を評価する）が分かるようにする。
- 短絡評価（`a or b`、`a && b`）は評価順を書く。左の条件で結果が決まると右は評価されないこと、右に副作用・例外の可能性がある場合はその点も書く。
- switch / match は case ごとに「〜のとき」行（「`status` が OPEN のとき」）。fall-through と default の有無を書く。

**判定表**（条件が 3 つ以上組み合わさる、状態遷移、許可・不許可の表）：分岐の行の項目（1. 2. …）として置く。
表の直前に原文の条件式と評価順を書き、行は評価順に並べ、最後に「その他（上記以外）」の行を置く。表を置いても「〜のとき」行は省略しない（表は判定の中身、「〜のとき」行は行き先）。

### 5.4 繰り返し

- 開始行（繰返タグ）：何の要素を（コレクション・範囲・条件）、どの変数に入れ、どの順で、何行目から何行目を繰り返すか。0 件のときの行き先も書く（「0 件のときは → 47」）。
- 本体の行は 1 段深くする。
- 終端行（繰返終端タグ）を本体と同じ深さの最後に置く：「次の要素があれば 39 へ戻る。無ければ 47 へ進む。」break・continue・return による途中終了の行き先も書く。
- while・do-while：継続条件と、条件を変化させる処理（カーソル・ページ番号の更新など）、上限（無ければ「上限なし」）を書く。
- 繰り返しの中の DB 操作・外部通信は、1 回分の内容と、何回実行されるか（「明細の件数だけ」）を書き、項目の表に 2 回分程度の値の例を示す。

### 5.5 try・catch・finally

try・catch・finally は**日本語にせず、ソースの言語のキーワードのまま**書く。

- try の開始行：タグ `try`。何行目を実行するか、どの例外を捕捉するか、捕捉しない例外はどうなるか（呼び出し元へ伝わる）。
- catch・except・finally は「〜のとき」行と同じ `tr.arm` の行にし、見出し（try）の 1 段下に置く。文はキーワードのまま `<span class="kw">catch (JwtVerificationException e)</span>`、`<span class="kw">except PaymentGatewayError as e</span>`、`<span class="kw">finally</span>` とし、後に `<span class="of">（No.15。16 で 400 以上の応答があったとき）</span>` と、いつ実行されるかを添える。
- catch・finally の中の処理は、その行の下に 1 段下げて書く。
- try 文の後の行き先が経路によって違う場合（finally の後に例外が残る・残らない）は、try の 1 段下の最後に「try終端」の行を置き、行き先を書く：「finally の後、19 で送出した例外が残っていれば → E7 ／ 残っていなければ → 22」。
- finally の中で例外が起きると元の例外が置き換わることなど、言語の決まりで結果が変わる点を書く。
- Go の `if err != nil { return … }` は try ではなく分岐として書く（「`err` が nil でないとき」）。

### 5.6 並列・非同期・待機

- 並列タグの行：同時に開始する処理と、実行場所（スレッドプール名・イベントループ・goroutine）。
- 並列に実行される各処理は「〜のとき」行と同じ `tr.arm` の行で区切る：「(A) 与信照会（`orderExecutor` の別スレッド）」「(B) 見積計算（同）」。それぞれの処理は 1 段下げる。
- 待機タグの行を並列の 1 段下の最後に置く（縦線を閉じる）：何の完了を待つか、タイムアウト、**一方が失敗した場合の動作**（もう一方は止まるか、例外がどう包まれて伝わるか）。
- スレッド・プロセスが変わると、トランザクション・ロック・認証情報・リクエストスコープの値が引き継がれないことがある。影響がある場合は書く。
- 呼び出し元が完了を待たない処理は、起動する行に「非同期」タグを付け、起動された処理を **A 経路**（`A1-01`…）として別の表に書く。

## 6. 例外・中断・終了（例外経路）

- 例外の送出行：送出する例外の型と、渡す値（コード・メッセージ）を書き、最後に行き先の経路を書く（「→ E1」）。
- 送出後に実行される処理は **例外経路**（E1, E2…）の表に書く。例外が伝わる順に、通過する finally・catch（その中の処理も展開する）、抜けるトランザクション境界（ROLLBACK と、取り消されるデータ・取り消されないデータ）、選ばれる例外ハンドラー、応答（ステータス・ボディ）と終了を、1 行ずつ書く。
- 経路の見出し：「E1：No.08 で `OrderNotFound` が送出された場合」。
- **合流**：送出位置が違っても、その後に実行される処理とデータの状態が完全に同じ場合だけ、同じ経路に合流させてよい。見出しに合流元の No. をすべて書く。finally を通るか、どのデータが確定・送信済みか、が 1 つでも違えば経路を分ける。
- コードに書かれていない例外も書く（NULL 参照、キーが無い、型変換の失敗、一意制約違反、タイムアウト、HTTP エラー、件数が想定外）。捕捉されず 500 応答になるものも「想定外の例外」として経路を書く。
- catch で握りつぶして処理を続ける場合は、例外経路に分けず、try・catch の木の中に書いて続行先を書く。

## 7. トランザクションとロック

- 開始行：方式（アノテーション・コンテキストマネージャー・明示的な begin・コールバック）、伝播属性、分離レベル・読み取り専用（コードにあれば）。コールバック型（`dataSource.transaction(async (manager) => …)`）は TX タグの見出しにして、コールバックの中を 1 段下げ、COMMIT の行を 1 段下の最後に置いてよい（`tr` に `class="close"` を付けると縦線が閉じる）。
- COMMIT 行：どこで確定するか、その時点で発行される遅延 SQL（ORM の flush）。
- ROLLBACK 行：どの例外で行われるか（ロールバック規則）、**取り消されるデータ**と**取り消されないデータ**（別トランザクション、外部 API の実行結果、送信済みのメッセージ・メール）。
- 別トランザクション（REQUIRES_NEW・自動コミット・別コネクション）は、その開始と確定を書き、外側の結果に関係なく確定することを書く。
- ロック：対象、保持期間、競合したときの動作。タイムアウト値がコードに無ければ〔未確認〕。
- 処理ごとに「データ変更とトランザクション」節に、トランザクションごとの範囲・操作・正常時・例外時の表を置く。

## 8. 値の例（シナリオ値）

- 文書全体で代表的な正常系のシナリオを 1 つ決め、その値を一貫して使う。リクエストの値 → バインド変数 → 取得した値 → 計算結果 → 更新後の値 → レスポンス、が数値まで矛盾なくつながるようにする。
- 異常系の説明に別の値が必要な場合は、その場で「（例：`available` = 1 の場合）」と条件付きで書く。
- 値の例は説明用の架空の値。実在しそうな個人情報・本番の値を推測して書かない。
- 型・桁・NULL 可否はコード・エンティティ・DDL から取る。分からなければ〔未確認〕。

## 9. 表にするもの・文章にするもの

| 表にする（項目の中、または節の表） | 文章（逐次処理の行）にする |
|---|---|
| 入力項目、レスポンス項目、エラー一覧（節の表） | 実行される順序そのもの |
| SQL のバインド変数・取得データ・更新前後・登録データ・削除対象・件数ごとの処理（SQL の行の項目） | 判定と、結果ごとの「〜のとき」行 |
| 外部 API の送受信データ、応答ごとの処理（API の行の項目） | 繰り返しの範囲と戻り先 |
| 判定表、状態遷移、変数と値の対応、配列・オブジェクトの構造（その行の項目） | 例外の伝わり方 |
| トランザクションのまとめ、未確認事項、検証記録（節の表） | |

補足の表は、該当する行の**項目**として置く（離れた場所に置かない）。表にすると実行順序が分かりにくくなる場合は表にしない。

## 10. 確認済み・〔推定〕・〔未確認〕

| 印 | 意味 | 根拠欄 |
|---|---|---|
| なし | コードで確認した事実 | `ファイル:行` |
| `<span class="inf">〔推定〕</span>` | コードに書かれていないが、フレームワーク・ライブラリの仕様から導いた動作 | 根拠になる注釈・設定の位置と「FW 仕様」 |
| `<span class="uv">〔未確認: U1〕</span>` | 提供されたコードからは確定できない | 分かる範囲の位置 |

- 〔未確認〕は必ず「未確認事項」の表に ID・内容・影響する No.・確認方法を書く。
- 推測した値・動作を、印を付けずに確定事項のように書かない。
