# ソースコードの解析手順

目次
1. 範囲を決める
2. 入口の前と後を洗い出す
3. 深さ優先で追跡する
4. 台帳（解析ノート）に書きながら進める
5. 注目行の一覧で漏れを防ぐ
6. 例外の伝わり方を解析する
7. トランザクション・ロックを解析する
8. 並列・非同期を解析する
9. データの流れを解析する
10. 大きなコードベースでの進め方
11. 分からないとき

---

## 1. 範囲を決める

- **起点**：エンドポイント（ルーティングの定義・`@PostMapping`・`router.post`・`@app.post`）、バッチの main・ジョブ定義、メッセージの受信ハンドラー、スケジューラー。
  依頼から起点が特定できない場合は、候補（メソッド・パス・ファイル:行）を挙げて利用者に確認する。
- **終点**：HTTP 応答がクライアントに返るまで（例外ハンドラー・シリアライズを含む）。バッチは終了コードを返すまで。
- **含めるもの**：起点の前に実行されるフィルター・ミドルウェア・インターセプター・ガード・パイプ・入力検証、
  コミット後や非同期に実行される処理（イベントリスナー・キューのワーカー）。非同期の処理は A 経路として書く。
- **含めないもの**：フレームワーク・ライブラリの内部実装、アプリの起動処理（ただし、処理に影響する設定値は書く）。
- 含めない・分からないものは、未確認事項か概要に明記する。黙って外さない。

## 2. 入口の前と後を洗い出す

コードの起点のメソッドより前・後に、フレームワークが実行する処理がある。読み落としやすいので最初に洗い出す（詳細は `framework-notes.md`）。

| 位置 | 探すもの |
|---|---|
| 前 | サーブレットフィルター・Spring Security、ミドルウェア（`app.use`）、インターセプター、ガード、パイプ、`Depends`、デコレーター、AOP（`@Around`・`@Before`）、引数の変換（パス変数の型変換）、入力検証（`@Valid`・Pydantic・class-validator・FormRequest） |
| 起点 | `@Transactional` などのプロキシ（メソッドの開始時にトランザクション開始） |
| 後 | トランザクションの COMMIT / ROLLBACK、例外ハンドラー（`@ExceptionHandler`・`exception_handler`・エラーミドルウェア・例外フィルター）、レスポンスの変換（`response_model`・シリアライザー）、コミット後のイベント |

探し方の例：`Grep` で `@Component.*Filter|OncePerRequestFilter|app\.use\(|add_middleware|@UseGuards|APP_GUARD|useGlobal|@ControllerAdvice|exception_handler|errorHandler|@Aspect`。

## 3. 深さ優先で追跡する

1. 起点のメソッドを**全体**読む（Read で該当範囲を行番号付きで読む）。
2. 上から順に、呼び出し・分岐・繰り返し・例外・return・代入・DB・外部通信を拾い、台帳に書く。
3. 呼び出しに出会ったら、その呼び出し先を開いて 1 に戻る（深さ優先）。呼び出し先を読み終えたら、呼び出し元の次の行へ戻る。
   - インターフェース・抽象メソッド：実装クラスを探す（`implements X`、`extends X`、DI の設定、`@Primary`、`@Qualifier`、プロファイル）。
   - ラムダ・コールバック：いつ実行されるか（即時・別スレッド・トランザクション内・後で）を確認する。
   - 継承したメソッド・デフォルトメソッド・ミックスイン：親クラスも読む。
   - 同じクラス内の呼び出し（`this.method()`）は Spring のプロキシを通らない（`@Transactional`・`@Async` が効かない）。
4. 1 つのメソッドを読み終えるたびに台帳を更新する（記憶に頼らない）。
5. 同じメソッドを 2 回目に読むときも、呼び出し位置ごとに台帳へ書く（引数の値が違えば分岐の行き先も違う）。

## 4. 台帳（解析ノート）に書きながら進める

追跡するメソッドがおおむね 10 以上、または複数の処理を書く場合は、出力先に台帳 `<名前>.trace.md` を作り、解析しながら書き足す。
HTML は台帳から書く。会話の文脈が長くなって途中が要約されても、台帳を読み直せば解析を続けられる。

```markdown
# 台帳：注文登録（POST /api/orders）
## 範囲
- 起点：OrderController.java:31-38 createOrder ／ ソースのルート：order-system/src/main
- 前処理：@Valid（CreateOrderRequest.java:13-18）。フィルターは見当たらない（Grep 済み）
- 後処理：GlobalExceptionHandler.java、OrderNotificationListener（AFTER_COMMIT・@Async）
## 追跡キュー
- [x] OrderController.createOrder 31-38
- [x] OrderServiceImpl.registerOrder 47-85
- [ ] PricingService.quote 26-41  ← 別スレッドで実行（No.08 の並列）
## 実行イベント（実行順。字下げ＝内側）
- @Valid 検証 … CreateOrderRequest.java:14-17 → 違反時 MethodArgumentNotValidException（ハンドラーなし → 400〔推定〕）
- TX 開始 REQUIRED … OrderServiceImpl.java:48
- SQL customers 主キー検索（JPA findById・参考SQL） … :51
  - 0 件 → CustomerNotFoundException … :52 → 例外経路（404）
- 分岐 customer.isSuspended()（status == "SUSPENDED"） … :53, Customer.java:17-19
  - 成立 → CustomerSuspendedException … :54 → 例外経路（409）
- 並列 supplyAsync ×2（orderExecutor） … :58-61
  - (A) GET {credit}/v2/customers/{id}/credit … CreditCheckClient.java:16-21
  - (B) products findAllById（別スレッド・TX 外〔推定〕） … PricingService.java:28
## 例外と伝わり方
| 送出 | 位置 | 通過する catch / finally | TX | ハンドラー | 応答 |
## トランザクション・ロック
## DB 操作（SQL 全文の位置）
## 外部通信
## 変数（生成・変更）
## 未確認
- U1 与信照会 API のタイムアウト設定（RestClient の Bean 定義が無い）
```

書き方は自由でよいが、**すべての項目に `ファイル:行` を付ける**。行番号は Read・Grep -n で確かめた値だけを書く。

## 5. 注目行の一覧で漏れを防ぐ

追跡するファイルが決まったら、注目行（分岐・繰り返し・例外・捕捉・return・SQL・DB・TX・外部・非同期）を一覧にする。

```bash
python "${CLAUDE_SKILL_DIR}/scripts/ddoc.py" inventory <ファイルまたはディレクトリ>... --src-root <ソースのルート>
```

関数ごとに注目行が並ぶので、追跡したメソッドの注目行がすべて台帳に入っているか照合する。
HTML を作った後は `ddoc.py check --coverage` で、根拠欄から参照されていない注目行を確認する（`verification.md`）。
一覧は正規表現による簡易抽出なので、拾いすぎ・拾い漏れがある。最終的な判断はコードを読んで行う。

## 6. 例外の伝わり方を解析する

例外を送出しうる位置（`throw`・`raise`・ライブラリの例外・フレームワークの検証）ごとに、次を順に確かめる。

1. 送出位置から呼び出し元へさかのぼり、間にある `try` の `catch` / `except` が**その型を捕捉するか**（型の継承関係を確認）。
2. 通過する `finally`（その中の処理も実行される。finally の中で例外が起きると元の例外は置き換わる）。
3. 抜けるトランザクション境界でのロールバックの有無（ロールバック規則：Spring は既定で RuntimeException と Error、`rollbackFor`・`noRollbackFor`）。
4. 包まれるかどうか（`CompletionException`・`ExecutionException`・`UndeclaredThrowableException`・`raise … from e`）。
5. どの例外ハンドラーが選ばれるか（最も近い型、原因例外のたどり方、ハンドラーが無い場合の既定の応答）。
6. 応答（ステータス・ボディ）と、その時点で確定済み・送信済みのデータ。

同じ型の例外でも、送出位置によって 2・3・6 が違えば、例外経路を分ける。

## 7. トランザクション・ロックを解析する

- 開始と終了の位置（アノテーションのメソッドの入口と出口、`with`・`using` ブロック、`BeginTx` と `Commit`、コールバックの範囲）。
- 伝播属性（REQUIRED・REQUIRES_NEW・MANDATORY・NESTED）と、呼び出し元のトランザクションとの関係。
- 同じトランザクションに入る DB 操作と、入らない DB 操作（別スレッド・別コネクション・自動コミット・REQUIRES_NEW）。
- ORM の遅延 SQL が発行される位置（flush・commit）。
- ロックの取得位置・対象・解放位置。ロックを持ったまま外部通信をしていないか。
- ROLLBACK で取り消されないもの：外部 API の実行結果、送信したメッセージ・メール、別トランザクションで確定した行、ファイル。

## 8. 並列・非同期を解析する

- 何がどこで実行されるか：スレッドプール（Bean 名・設定）、イベントループ、goroutine、別プロセス（キューのワーカー）。
- 呼び出し元が完了を待つか（join・await・Wait）、待たないか（fire-and-forget）。
- 失敗の伝わり方：一方の失敗で全体がどうなるか、もう一方は止まるか、例外がどう包まれるか、握りつぶされるか。
- 実行されるタイミング：コミット後（`AFTER_COMMIT`）、応答の後、遅延・再試行（キューの `attempts`・`backoff`）。
- 引き継がれないもの：トランザクション、ロック、セキュリティコンテキスト、リクエストスコープ、MDC。

## 9. データの流れを解析する

- 入力（リクエスト）の各項目が、どの変数・どの SQL のバインド変数・どの外部送信項目・どのレスポンス項目になるかを追う。
- 取得した値（DB・外部 API）が、どの判定・計算・更新に使われるかを追う（SQL の `rows` 表の「後続の利用箇所」になる）。
- 変数が変化する位置（再代入・属性の変更・コレクションへの追加）を拾う。特に ORM のエンティティの属性変更は、後で UPDATE になる。
- 値の例（シナリオ値）は、この流れに沿って一貫させる。

## 10. 大きなコードベースでの進め方

会話の文脈の量に解析の質を左右させないための進め方。

- **台帳を正とする**：解析結果はすぐ台帳ファイルへ書く。HTML は台帳から書く。
- **必要な範囲だけ読む**：`Grep -n` で定義と呼び出し位置を探し、Read は `offset`・`limit` でメソッドの範囲だけ読む。巨大なファイルを丸ごと読まない。
- **追跡キュー**：未読のメソッドを台帳のキューに積み、読んだら [x] を付ける。中断・再開してもキューから続けられる。
- **処理ごとに分ける**：複数のエンドポイントを書く場合は、1 つずつ「解析 → 台帳 → 部品ファイル」を終えてから次へ進む。
- **部品ファイルに分けて書く**：逐次処理が長い場合は部品を分け（`html-rules.md` 1 章）、1 回の書き込みを小さくする。
- **サブエージェント**：使える環境で、利用者・実行環境の方針が許す場合は、独立した部分木（例：非同期のワーカー、別モジュールの処理）の解析を任せ、結果を台帳の形式で返してもらってよい。統合と最終確認は自分で行う。

## 11. 分からないとき

- 定義が見つからない（import 先のファイルが無い、生成コード、外部ライブラリ）：分かる範囲を書き、〔未確認〕にする。
- 値がコードの外で決まる（環境変数・設定ファイル・DB のマスター）：キー名と使われ方を書き、〔未確認〕にする。設定ファイルが提供されていれば読む。
- DB の型・制約が分からない（DDL・マイグレーションが無い）：エンティティの型から書けるものは書き、残りは〔未確認〕。
- フレームワークの版で動作が変わる：〔推定〕とし、前提とした版・仕様を根拠欄に書く。
- 推測で穴埋めしたものを確定事項として書かない。
