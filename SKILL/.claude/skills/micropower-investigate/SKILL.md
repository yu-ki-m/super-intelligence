# 実装タスクの徹底調査

このスキルは、実装に入る前に、要求から1コミット単位のタスクまでを1本の追跡でつなぎ、どの層にも漏れと誤りがないかを徹底的に調べる。
調べた結果は、TOON 形式の台帳（ファイルの集まり）に残し、最後に台帳から人が読む HTML を作る。
コードの修正、コミット、計画の道具のファイルへの書き込みはしない。
書くのは台帳のフォルダーの中だけである。

## 層の定義

| 層 | 意味 | 例 |
|-|-|-|
| 要求 | 誰が・どの場面で・何を・なぜ達成したいか | 書店員が、入荷したときに、書籍を在庫に登録したい（在庫数を正しく保つため） |
| 要件 | 要求を満たすためにシステムが満たすべき条件と理由 | 同じ書籍IDの書籍を二重に登録しないこと |
| 仕様 | 外から観察できる具体的な振る舞い（親の要件は1つ） | 登録済みの書籍IDで登録すると「すでに登録されています」と表示し、登録しない |
| 経路の設計 | 仕様を、コードのどの段で、どのプロパティについて実現するか（段×プロパティの表） | サービスの段で、書籍IDについて、登録済みかを確かめる |
| 影響範囲 | 変更する既存の箇所から逆にたどった、変更の影響を受ける箇所と、その対応 | 書籍の一覧画面は同じデータを表示するので、一覧が変わらないことを回帰として確かめる |
| タスク | 粒度の規則で切った1コミット分の作業 | `_書籍ID_4_` バックエンド（サービス）が書籍IDを受け取る |

仕様は振る舞いごとに、タスクはプロパティと段ごとに切るので、両者は多対多になる。
経路の設計の表を間に置くと、タスクを規則どおりに機械的に切り出せ、タスクの漏れが表の空欄として見える。

## 決まりごと

- **粒度。** 1タスク＝1コミット、1コミット＝1プロパティで経路を1回通す、新しい経路の最初のプロパティだけ経路のすべての段を1段ずつ別のコミットにする。
  詳細・解釈・コミットメッセージの決め方は `references/granularity-rule.md` にある。
  この規則は、計画の道具が持つタスクの大きさの基準より優先する。
- **根拠は既存のコードが最優先。** spec.md・plan.md・設計書などの文書は保守されていない前提で扱い、コードで確かめるまで事実にしない。
  用語集は無いものとし、プロパティの名前はコードから取る。
  事実には、コードのファイル・行・引用（そのままの文字列）を付け、スクリプトで照合する。
- **確からしさを混ぜない。** 台帳の行に、fact（事実）・claim（申告）・hypothesis（推測）・decided（決定）・unconfirmed（未確認）を付ける。
  数値・保存期間・承認者・契約を作らない。
- **空欄を残さない。** 発見の表は、すべての欄に「該当あり・不要（理由）・対象外・未確認」のどれかを書く。
  空欄や未確認が、未検討の箇所として見えるようにするためである。
- **両方向にたどる。** 子のない親は下の層の漏れ、親のない子は上の層の漏れ（または頼まれていない追加）である。
  上の層に足したら、そこから下の層を導き直す。
- **影響範囲は機械で記録して全件判断する。**
  変更する箇所を一覧にし、それぞれをリポジトリ全体で逆引きして、当たった行をスクリプトがすべて記録する。
  git の履歴で一緒に変更されてきたファイルも挙げる。
  Claude はそのすべてを1件ずつ判断し、要変更の影響先は仕様とタスクに、回帰確認の影響先は回帰を確かめる仕様につなぐ。
- **検証は徹底的に行う。** 規模によらず、8つの役割の独立した検証、机上実行、直した後の再検証を省かない。
- **「漏れはない」と言わない。** 確かめた枠・観点・範囲と、確かめていない範囲を書く。

## 成果物

台帳の置き場所は、利用者の指定を優先し、なければ対象のリポジトリの `docs/task-investigation/<YYYY-MM-DD>-<題目>/` にする。
既に別の調査の台帳があるフォルダーは上書きしない。

| ファイル | 中身 |
|-|-|
| progress.toon | 進み具合（再開の起点） |
| scope.toon | 依頼の原文、範囲、調べた版、コミットメッセージの形 |
| sources.toon | 調べた情報源と、その信頼の扱い |
| current.toon | 現状の調査（調査台帳、入口、現行の仕様と処遇、影響先） |
| needs.toon | 関係者、場面、要求、関係者×場面の表 |
| requirements.toon | 要件、要求との対応、要求×観点の表 |
| quality.toon | 605の品質観点と確認項目の判定 |
| specs.toon | 経路、プロパティ、仕様、受入ケース、状態遷移、決定表、CRUD、エラー |
| design.toon | 経路の段、段×プロパティの表 |
| impact.toon | 変更する箇所、逆引きの検索と当たり（全件）、一緒に変更されてきたファイル |
| tasks.toon | タスク（文言、内容、ファイル、テスト、コミットメッセージ）、タスクと仕様の対応 |
| reviews.toon | 検証の回、役割、指摘、机上実行、確かめた範囲 |
| decisions.toon | 利用者・依頼者に決めてもらう事項と答え |
| reconcile.toon | （任意）道具の成果物との突き合わせ |
| validation.toon | 最後の機械検査の結果（スクリプトが書く） |
| report.html | 人が読む HTML（スクリプトが台帳から作る。手で直さない） |

各ファイルの列と値は `references/ledger-schema.md`、TOON の書き方は `references/toon-writing.md` にある。

## スクリプト

スクリプトは Python 3 の標準ライブラリだけで動く。
Bash から `python -X utf8 "${CLAUDE_SKILL_DIR}/scripts/<名前>.py" …` で実行する（Windows では `python`、ほかは `python3`）。
パスは二重引用符で囲む。

| コマンド | 役目 |
|-|-|
| `ledger.py init <台帳> --topic <題目> --repo <リポジトリ> --kind new\|change\|mixed --request "<原文>"` | 台帳を作る（既にあれば止まる） |
| `ledger.py validate <台帳> [--gate <段階>\|--final] [--write]` | 構造、追跡、表の空欄、粒度、根拠の引用を検査する。エラー0件で終了コード0 |
| `ledger.py derive-tasks <台帳>` | 段×プロパティの表から、規則が求めるタスクの行と対応を足し、文言を振り直す |
| `ledger.py stage <台帳> <段階> <状態> [--next "…"]` | 進み具合を書く |
| `ledger.py status <台帳>` | 件数と未回答の確認事項を見る |
| `ledger.py fmt <台帳>` | TOON を正しい形に整える |
| `quality.py init／show／set／summary` | 品質の観点の台帳を扱う（`references/stage-guide.md` の「品質の観点」） |
| `impact.py search <台帳> --change <ID> --term <名前> --variants` | 変更する箇所をリポジトリ全体で逆引きし、当たりを全件記録する（`--print` は台帳に書かずに表示だけ） |
| `impact.py classify <台帳> …` | 当たりの判断を書く（ファイルのパターンでまとめてもよい） |
| `impact.py cochange <台帳>` | git の履歴から、変更するファイルと一緒に変更されてきたファイルを記録する |
| `impact.py summary <台帳>` | 変更する箇所ごとの判断の件数を見る |
| `render_html.py render <台帳>` | report.html を作る |
| `render_html.py check <台帳>` | report.html が今の台帳から作ったものと一致するかを確かめる |
| `toon.py check <ファイル…>` | TOON として読めるかを確かめる |

スクリプトの検査は構造の検査である。
通っても、中身が正しいことは保証しない。
中身の正しさは、検証の段階で確かめる。

## 進め方

段階は次の順に進む。
各段階の詳しい手順は `references/stage-guide.md` にある。
各段階の終わりに `validate --gate <段階>` を通し、`stage <段階> done --next "…"` で進み具合を書いてから、次へ進む。

```
準備 → 現状の調査 → 要求 ◆ → 要件 ◆ → 品質の観点 → 仕様 ◆ → 経路の設計 → 影響範囲 → タスク ◆ → 検証 ◆ → 出力
（◆ は利用者の承認・判断を求める所）
```

1. **開始・再開。**
   台帳の置き場所に progress.toon があれば、再開する（下の「長い作業を途切れさせない」）。
   なければ `ledger.py init` で作る。
2. **準備。**
   依頼の原文、範囲、新規か改修か、調べた版、コミットメッセージの形を scope.toon に書く。
3. **現状の調査。**
   `references/methods/investigation.md` に従い、入口・現行の仕様・影響先を、コードの根拠付きで記録する。
   新しい機能でも、段をコードの層から決めるために行う。
4. **要求。**
   関係者×場面の表を全部埋め、依頼・表・現行の仕様の処遇・当たり前の品質から要求を出す。
   要求の一覧と範囲の承認を得る。
5. **要件。**
   採用した要求ごとに6観点（機能・データ・品質・運用・移行・制約）の表を埋め、検証できる要件にする。
   要件の一覧の承認を得る。
6. **品質の観点。**
   605観点を全部一次選別し、適用あり・不明の観点の確認項目を判定する。
   要件が足りなければ要件に戻る。
7. **仕様。**
   経路、プロパティ（名前はコードから）、仕様（親は1つ）、受入ケース、状態遷移、決定表、CRUD、エラーを作る。
   業務のルールを利用者に決めてもらい、仕様の一覧の承認を得る。
8. **経路の設計。**
   経路ごとに、コードの層から段を決め（戻りの段とその後の処理まで）、段×プロパティの表の全欄を埋める。
   仕様のない作業が見つかれば仕様に戻る。
9. **影響範囲。**
   変更する箇所を一覧にし、`impact.py search` で全件逆引きし、`impact.py cochange` で一緒に変更されてきたファイルを挙げて、すべて判断する。
   影響先を仕様につなぎ、仕様が足りなければ仕様と経路の設計に戻る（`references/methods/investigation.md` の「影響範囲の確定」）。
10. **タスク。**
   `derive-tasks` でタスクを切り出し、内容・ファイル・テスト・コミットメッセージを埋める。
   最初のプロパティの選び方と規則の解釈を、利用者に確かめる。
11. **検証。**
    `references/verification-protocol.md` に従い、8つの役割の独立した検証、机上実行、直した後の再検証を行う。
12. **出力。**
    `validate --final --write` を通し、`render_html.py render` と `check` で HTML を作って一致を確かめる。
    この後で台帳を直したら、検査と HTML をやり直す。

各段階で使う分析の手法（目的からの分解、シナリオ、状態遷移、条件の組合せ、データの一生、インターフェース、故障からの逆算、脅威）は `references/methods/analysis-methods.md`、品質と業務の横断の組合せは `references/methods/cross-checks.md`、暗黙の期待は `references/methods/implicit-quality.md` にある。

## 質問の仕方

`references/questions-and-records.md` に従う。
要点は次のとおりである。

- 各層は Claude が先に下書きを作り、利用者には反応してもらう。
- 事実（コードや設定を見れば分かること）は聞かずに調べる。
- 聞くのは、答えで台帳の中身が変わる業務の判断だけにし、1回のメッセージで1問にする。
  問いには、聞く理由、Claude の見立て（推奨と理由）、選択肢を添える。
- 問いと答えは decisions.toon に残し、答えは利用者の言葉のまま書く。
- 利用者が答えられない事項は保留（deferred）にし、関係する項目を未確認のまま targets に入れる。

## 長い作業を途切れさせない

この調査は長く、途中で会話が要約されたり、PC が止まったりすることがある。
記憶に頼らず、台帳のファイルを正とする。

- 表を1つ書き終えるたびに、ファイルに書く。
  まとめて最後に書かない。
- 段階を終えるたびに `stage` で進み具合と、次にやること（初めて読む人が続けられる具体さで）を書く。
- 会話が要約された後や、「続き」「再開」と言われたときは、`ledger.py status <台帳>` と progress.toon を読み、このファイルの「決まりごと」と、次の段階の手引きを読み直してから続ける。
- scope.toon の git_commit と今のコミットが違えば、変わったファイルを確かめ、影響を受ける根拠と分析をやり直す。

## 道具の成果物との突き合わせ

この台帳を入力にして、spec-kit・superpowers・mattpocock-skills などが仕様・計画・タスクを作った後に呼ばれたら、`references/stage-guide.md` の「道具の成果物との突き合わせ」を行う。
道具のファイルは読むだけで書き換えず、結果は reconcile.toon に書く。

## 完了の判断

- `validate --final` がエラー0件で、`render_html.py check` が一致を返したときに、成果物を渡す。
- 未確認・保留が残るときは、progress の status を provisional にし、何が確定できないかを伝える。
  未確認を確定のように見せない。
- 最後の返答では、report.html と台帳のフォルダーの絶対パス、要求・要件・仕様・タスクの件数、残った確認事項、確かめていない範囲を短く伝える。
  HTML の内容を返答に貼り直さない。
