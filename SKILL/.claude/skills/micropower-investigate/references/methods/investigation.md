# 現状の調査（既存コードを最優先の根拠にする）

既存の機能を変える、または既存の機能の隣に新しい経路を足すときに、現状を事実として固める手引きである。
analyze-requirements-and-specs スキルの「既存コード精査と調査完了条件」と「調査と判断の観点」を取り込み、このスキルの決まりに合わせて直した。

## 根拠の優先順位

- 現行の振る舞いの事実は、既存のコード（設定、スキーマ、テストを含む）を最優先の根拠にする。
- spec.md、plan.md、設計書、README などの文書は、保守されていない前提で扱う。
  文書に書かれたことは「確かめるべき仮説」であり、コードで確かめるまで事実（`fact`）にしない。
  文書を根拠にするときは、`ev_path` を `doc:<相対パス>` と書き、確からしさを `hypothesis` にする。
  `ledger.py` は、文書を根拠にした `fact` をエラーにする。
- 用語集（GLOSSARY.md など）は無いものとし、プロパティや概念の名前はコードから取る（`references/granularity-rule.md` の「名前の出所」）。
- 会話で聞いたことは `ev_path: conversation` とし、発言をそのまま `ev_quote` に書く。
  確からしさは `claim`（申告）か、利用者が決めたことなら `decided` にする。
- コードの動作は「今そう動いている」という事実であり、正しい将来の要件とは限らない。
  維持するか変えるかは、処遇（`treatment`）として別に決める。

## 根拠の書き方

事実として記録する行（入口、現行の仕様、影響先、既存のプロパティ、既存の段）には、次の3つを必ず書く。

- `ev_path`：リポジトリのルートからの相対パス（`/` 区切り）。
- `ev_line`：根拠の行番号（1から）。
- `ev_quote`：その行（前後3行の範囲）にある文字列を、そのまま写したもの。
  要約や言い換えをしない。
  空白の違いは無視して照合されるが、文字は1字も変えない。

`ledger.py validate` は、ファイルの存在、行番号の範囲、引用がその行の前後3行にあるかを機械で照合する。
照合に通っても、引用が主張の根拠として正しいかは別の問題なので、検証の段階で根拠の検証役が確かめる。

## 調査台帳（`current.toon` の investigations）

調べた範囲ごとに1行を書き、状態（done／partial／not_done／out_of_scope）を付ける。
partial・not_done・out_of_scope には、調査を止めた境界と理由を必ず書く。
「検索で見つからない」だけで影響なしとしない。

1. 対象の版を固定する（`git rev-parse HEAD` と `git status --porcelain` を `scope.toon` に記録する）。
   未コミットの変更があれば、作業ツリーを調べたことを記録し、変更を戻さない。
2. ルーティング、画面の操作、ジョブの登録、イベントの購読から、入口を列挙する（`entrypoints`）。
   画面だけでなく、API、一括処理、CSV、管理画面、外部連携、非同期のイベントも探す。
3. 入口→入力の検証→権限→業務の判定→保存→戻り値→後続の処理の順に読む。
   例外の経路、早期の return、トランザクションの境界も追う。
4. 呼び出し元、同じ共通処理の利用先、同じデータを読み書きする箇所を逆にたどる。
   直接の参照だけでなく、DI の登録、設定、動的な呼び出し、イベントの対応も調べる。
   追跡できないものは、不明として調査台帳に残す。
5. 判定を、状態・権限・設定・入力・データの世代に分け、正常・拒否・失敗・競合のときの結果を列挙する。
6. テストと履歴（`git log`、`git blame`）は、必要に応じて照合する。
   履歴のコメントだけで意図を断定しない。
   動作の確認と、目的の確認を分けて記録する。
7. 影響が伝わる先を繰り返し追い、各境界で止めた理由を残す（`impacts`）。
   no_impact には、影響が伝わらない根拠を書く。

## 現行の仕様（`behaviors`）と処遇

見つけた振る舞いを1行ずつ書き、次を問う。

- 誰の、どの業務の成果や不変条件を守るのか（`purpose`）。
- その目的は、明記された事実か、複数の証拠に基づく推定か、不明か。
- 今もその利用者・依存先・前提・制約は残っているか。
- 目的は有効でも、実現の手段だけが古くなっていないか。
- 他の仕様が代わりに保証しているか。
  重複を除くと、保証が欠けないか。

処遇（`treatment`）は、keep（維持）・change（変更）・remove（廃止）・unconfirmed（未確認）から選ぶ。
keep・change・remove のどれも、要求につなぐ（`needs.toon` の current_links）。
維持する振る舞いは、暗黙の要求として要求一覧に入れる。
廃止は、目的の失効、代わりの保証、実際の利用、互換性、移行、復旧、決める権限を調べてから提案し、利用者に決めてもらう。
負債である、複雑である、検索で見つからない、という理由だけでは廃止しない。

## 影響と暗黙の要求の観点

| 領域 | 調べること |
|-|-|
| 業務 | 前後の工程、取消、訂正、承認、手動の介入、例外、責任の分界 |
| 経路 | 画面、API、一括、バッチ、管理、連携、イベント、再実行 |
| 条件 | 状態、権限、所属、契約、設定、データの有無、世代、境界値 |
| データ | 意味、必須、既定値、整合性、制約、履歴、削除、保持期間 |
| 共有 | 呼び出し元・先、共通部品、共有テーブル、集計、キャッシュ、検索索引 |
| 時間 | 判定の時点、同時更新、排他の外部保証、順序、重複、冪等性 |
| 失敗 | 成功の単位、部分更新、タイムアウト、再送、補償、復旧 |
| 接点 | 入出力の契約、通知、エラーの意味、互換性、利用者の次の行動 |
| 品質 | 性能と負荷の条件、容量、可用性、認証と認可、分離、秘密情報、監査 |
| 導入 | 既存データの移行、新旧の混在、適用の順序、処理中のデータ、切り戻し |
| 運用 | 監視、問い合わせ、手動の復旧、教育、費用、担当者 |

適用しない観点にも理由を付ける。
すべてに新しい機能を足さない。
今満たしている保証を維持する要件も含める。

## 影響範囲の確定（経路の設計の後）

現状の調査の時点では、何を変えるかがまだ決まっていない。
そのため、経路の設計で変更する段とプロパティが決まった後に、影響範囲の段階で、変更する箇所から逆にたどって影響範囲を確定する。
記録は `impact.toon` に置き、`scripts/impact.py` で機械的に作る。
人が当たりを選り分けて記録すると、取りこぼしや作り話が入る余地があるため、当たりはスクリプトがすべて記録し、Claude は1件ずつ判断だけを書く。

1. **変更する箇所を一覧にする（changes）。**
   変更する段のファイル（`design.toon` の steps で origin が changed）、経路の段×プロパティの表で作業が要る既存のプロパティ（フィールド、列）、テーブル、API のパス、メッセージのキー、設定のキー、画面の部品などを1行ずつ書く。
   既存のものは、根拠（ファイル・行・引用）を付ける。
   `ledger.py validate --gate impact` は、変更する段のファイルと、作業が要る既存のプロパティの識別子が、この一覧から漏れていないかを照合する。
2. **逆引きする（searches、hits）。**
   既存の変更する箇所ごとに、`impact.py search <台帳> --change <ID> --term <名前> --variants` でリポジトリ全体を検索する。
   検索は、追跡中と未追跡のファイル（.gitignore で除外したものを除く）の全部が対象で、台帳のフォルダーは除く。
   `--variants` は、camelCase・snake_case・kebab-case・PascalCase・UPPER_SNAKE の書き方を足す（例：`bookId` → `book_id`、`book-id`、`BOOK_ID`）。
   コード以外（SQL、テンプレート、設定、メッセージの定義、OpenAPI、スクリプト、帳票の定義）も同じ検索で当たる。
   名前が文字列の組み立てで作られる箇所（動的な呼び出し、リフレクション、文字列で書いたルーティング）を見つけるため、識別子の一部や、テーブル名・API のパスでも検索する。
3. **当たりを1件ずつ判断する。**
   判断は、impact（影響先。current.toon の impacts に足して ID を書く）、same_change（変更する箇所の中）、test（テスト）、definition（定義そのもの）、irrelevant（名前が一致するだけ。理由必須）のどれかである。
   `impact.py classify` で、ファイルのパターンごとにまとめて判断してよいが、まとめる前にそのパターンの当たりを読む。
   test と判断したテストは、回帰を確かめる対象として、影響先と同じく仕様や受入ケースに反映するかを考える。
4. **一緒に変更されてきたファイルを調べる（cochanges）。**
   `impact.py cochange <台帳>` は、git の履歴から、変更するファイルと同じコミットで2回以上・20%以上一緒に変更されてきたファイルを挙げる。
   名前の検索では見つからない結びつき（同じ規則を別々に実装したファイル、出力の定義、移行のスクリプト、文書）を見つけるためである。
   すべてを、impact・checked_no_impact（確かめて影響なし。理由必須）・same_change・irrelevant（理由必須）のどれかに判断する。
   git のリポジトリでないときは、調べられないことが調査台帳に記録される。
5. **リポジトリの外の利用者を調べる。**
   検索では見つからない利用者（他のサービスやリポジトリ、データベースを直接読む集計・帳票・BI、ファイルや API を受け取る外部の連携先、利用者の手作業や Excel）を、調査台帳に「リポジトリの外の利用者」という範囲の1行として必ず記録する。
   調べ切れないときは partial か not_done にし、止めた境界と理由を書き、確認先を確認事項（decisions）に載せる。
6. **影響先を仕様につなぐ。**
   要変更（must_change）の影響先は、実装が要る仕様（`implementation: needed`）につなぐ（impacts の specs）。
   その仕様は経路の設計とタスクに落ちるので、影響先の対応がタスクから漏れない。
   維持・回帰確認（keep_regression）の影響先は、回帰を確かめる仕様（既存で満たすなら `already_satisfied`、受入ケース付き）につなぐ。
   仕様が足りなければ、仕様の段階に戻って足し、経路の設計とタスクを導き直す。
7. `impact.py summary` で残りを確かめ、`ledger.py validate --gate impact` を通す。

## 調査の完了の判断

重要な入口・分岐・依存先に未調査があるときは、現状の調査を完了にしない。
調べた件数だけで完了と判断しない。
経路と業務の条件を網羅した根拠、証拠、矛盾の解消、影響への対応を確かめる。
静的に読んだのか、動かしたのか、テストで確かめたのかを、調査台帳の method で区別する。
