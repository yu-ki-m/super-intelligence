# タスクとコミットの粒度

このスキルが切り出すタスクの粒度の規則である。
原典は利用者のシート（private-wiki の `4.ナレッジストック/9999_9999｜1｜XXXXXXX/index.html`、Excel風HTML の Sheet1）で、2026-11-15 に写した。
この規則は、計画の道具（superpowers の「新しいレビューアーの関門に値する最小の単位」など）が持つタスクの大きさの基準より優先する（2026-11-15 に利用者が決定）。

## 原文（基本的な考え方）

- 1コミット＝１タスク
- コミット粒度は１つのコミット１つのプロパティ
- コミット内に１パスは通る（例：フロントエンド→バックエンド→フロントエンド....それ以降もワンパスを通す何かがあるなら、続きも出す）
- 最初のコミットに限り、１つのコミット１つのプロパティ　に加えて、責務単位でさらに細かくコミットする

## 原文の例：書籍の登録をリクエスト

| コミットに含める文言 | 概念単位 | コミット粒度 | （内容） |
|-|-|-|-|
| _書籍ID_1_ | 責務単位で実装を分ける | コミット1 | フロントエンドから書籍を選択 |

## 利用者が決めたこと（2026-11-15）

- 最初のプロパティを責務ごとに分ける範囲は、経路のすべての段とする。
  シートの例はコミット7「コントローラーがレスポンスを生成」で終わっているが、フロントエンドがレスポンスを受け取って表示する段なども、責務ごとのコミットにする。
- コミットメッセージは、その時のほかのコミットメッセージの規則を考慮しつつ、文言（`_書籍ID_1_`）と内容を加える。
- プロパティの名前の出所は、既存のコードを最優先にする。
  spec.md などの文書は保守されていない前提で扱い、GLOSSARY.md のような用語集は無いものとする。

## 台帳での表し方

規則は、経路の設計（`design.toon`）の段×プロパティの表から、機械的にタスクを切り出す形で守る。
表の欄の「要る作業」が `change`（新規か変更が要る）の欄だけがタスクになる。
`ledger.py derive-tasks` が、次の規則で必要なタスクの行を足し、文言の連番を振る。

| 経路の種類 | 最初のプロパティ | ほかのプロパティ |
|-|-|-|
| 新しい経路（`new`） | `change` の段ごとに1タスク（責務単位）。段の順に並べる | `change` の欄が1つでもあれば1タスク（1プロパティ単位）。全段を通す |
| 既存の経路の変更（`change`） | 1タスク（1プロパティ単位） | 同じ |

新しい経路では、最初のプロパティの責務のタスクを、ほかのプロパティのタスクより先に並べる。
`ledger.py validate --gate tasks` が、足りないタスク、余分なタスク、順番、文言の形と連番、コミットメッセージに文言が入っているかを検査する。

## 規則4（最初のプロパティだけ段ごとに分ける）の理由の解釈

シートには理由が書かれていない。
このスキルでは、次のように解釈している。
最初のプロパティのコミットは、経路の骨組み（画面の部品、API の呼び出し、エンドポイント、サービス、リポジトリ、テーブル）を新しく作る。
骨組みの各段は、それぞれ別の設計判断（API の形、トランザクションの範囲、エラーの返し方など）を含む。
そのため、段ごとにコミットを分けると、レビューで1段ずつ確かめられ、問題がどの段にあるかも分かる。
骨組みができた後のプロパティの追加は、既存の経路に項目を1つ通すだけなので、1コミットに収めても変更は小さく、経路全体が動く状態を保てる。

## シートに書かれていない場合の解釈

次の解釈は、台帳の確認事項（`decisions.toon`）に「Claude の仮置き」として残し、利用者が違うと言えば従う。

- **新しい経路ごとに、最初のプロパティを段ごとに分ける。**
  既存の経路にプロパティを足すだけなら、骨組みがすでにあるので、段ごとには分けない（経路の種類を `change` にする）。
  新しい経路でも、変更せずに使う段（例：既存のリポジトリをそのまま呼ぶ）は、その欄を `existing_ok` にし、タスクを作らない。
- **最初のプロパティは、それがないと経路が成り立たないものを選ぶ。**
  多くは、操作の対象を特定する識別子（例：書籍ID）である。
  選んだ理由を `path_properties` の reason に書く。
- **層の呼び出しは、呼ばれる側のコミットに入れる。**
  例えば、コントローラーからサービスを呼ぶ処理は「サービスが書籍IDを受け取る」コミットに入れる。
  こうすると、どのコミットの時点でも、まだない層を呼ばずに済み、ビルドとテストが通る。
- **テストは、そのテストが確かめる処理と同じコミットに入れる。**
  テストを先に書く手順（TDD）は、1つのコミットの中で守る。
  `tasks` の tests 列に、同じコミットに入れるテストを書く。
- **データベースの変更も経路の一部にする。**
  テーブルの作成は最初のプロパティの保存の段のコミットに、列の追加はそのプロパティのコミットに入れる。
  既存の行に入れる値（移行）も、そのプロパティのコミットに含め、プロパティ定義の existing_data に書く。
- **プロパティを運ばない作業**は、次の基準で扱う。評価ごとに扱いがぶれたため、この順に当てはめて決める。
  1. **リポジトリのファイルを変えない作業**（本番の行数を数える、API の利用者に知らせる、リリースの日を決める、手で確かめる）は、タスクにしない。
     コミットにならないからである。
     代わりに、仕様（運用の仕様）か確認事項（decisions）に書き、HTML の仕様か確認事項の表に載るようにする。
  2. **リポジトリのファイルを変える作業で、あるプロパティの変更がないと意味がないもの**（そのプロパティの列を足す移行のスクリプト、そのプロパティのテスト）は、そのプロパティのタスクに含める。
  3. **リポジトリのファイルを変える作業で、特定のプロパティに属さないもの**（設定、ライブラリの導入、共通部品、適用と切り戻しの手順書をリポジトリに置く）は、小さければそれを最初に必要とするタスクに含め、大きければ `non_property` のタスク（1コミット）にする。
     文言は作業の対象の名前で作る（例：`_適用手順_1_`）。
  4. **リポジトリにある文書が、今回変えるものとコードの食い違いを含むとき**（spec.md、README、API の説明が、変える項目の名前・型・API・上限を違って書いている）は、文書を直すかを確認事項にし、直すなら `non_property` のタスクにする（例：`_仕様書_1_`）。
     直さないと決めたときも、その文書を影響先（impacts）に keep_regression ではなく no_impact か unconfirmed として載せ、理由を書く。
     読む人が古い文書を信じて、また同じ誤りを繰り返さないようにするためである。
  単独で残すときの文言は、対象の名前で作る（例：`_認証設定_1_`）。
- **1つのプロパティを足すのに新しい骨組みが要るとき**（例：著者を別のテーブルで持つ）は、それを新しい経路として扱うかを利用者に確かめる。
- **同じプロパティ名が複数の経路に出るとき**は、計画の中で連番を続け、文言が重ならないようにする（`derive-tasks` が実装の順に振る）。
  例えば、登録の経路で `_書籍ID_1_`〜`_書籍ID_8_` を使ったら、削除の経路は `_書籍ID_9_` から始まる。

## 名前の出所

文言に使うプロパティの名前（`properties.name`）は、次の順に決める。

1. 既存のコードで、そのプロパティに付いている日本語の表示名（画面の項目名、メッセージの定義、列のコメント、型の注釈のコメント）。
2. それがなければ、既存のコードの識別子（例：`bookId`）。
3. 新しいプロパティは、仕様で決めた名前。
   決めた名前と、予定する識別子を記録し、利用者に確かめる。

既存のプロパティは、識別子を `code_name` に書き、それが現れるコードの行を根拠にする。
`ledger.py validate` は、`code_name` が根拠の行の前後にあるかを確かめる。
spec.md や設計書に書かれた名前は、コードと食い違うことがあるので、名前の出所にしない。

## コミットメッセージ

文言は `_<プロパティ名>_<連番>_` とし、連番はそのプロパティの中での実装の順番とする。
メッセージは、文言の後に内容を続ける（例：`_書籍ID_1_ フロントエンドから書籍を選択`）。

リポジトリやチームに別の規則があれば、その規則に従ったうえで文言を加える。
規則は次の順に探し、見つかったものをすべて満たす。
見つけた形を `scope.toon` の commit_format に、出所を commit_format_source に書く。

1. 利用者の指示（会話、CLAUDE.md、AGENTS.md）
2. リポジトリの設定（commitlint・commitizen の設定、`.gitmessage`、commit-msg フック、CONTRIBUTING）
3. 直近のコミット履歴の書き方（`git log --oneline -20`）

| 見つかった規則 | メッセージの例 |
|-|-|
| 規則なし | `_書籍ID_1_ フロントエンドから書籍を選択` |
| Conventional Commits | `feat(book): _書籍ID_1_ フロントエンドから書籍を選択` |
| 英語のみ・ASCII のみ | `feat(book): _bookId_1_ select a book on the frontend`（プロパティ名はコードの識別子にする） |

文言は、種別や範囲（`feat(book):` など）の直後、件名の先頭に置く。
件名の先頭にそろえると、`git log --grep "_書籍ID_"` で1つのプロパティのコミットをまとめて探せる。
件名の長さに上限があるときは、内容を短くし、文言は削らない。
