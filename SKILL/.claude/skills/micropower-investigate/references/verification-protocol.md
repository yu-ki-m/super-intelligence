# 検証の手順（漏れと誤りを徹底的に見つける）

台帳を作った本体（このセッションの Claude）が自分で読み直すだけでは、同じ文脈と同じ仮定から生まれた見落としが残る。
そのため、台帳を作っていない新しいエージェントに、役割を変えて台帳を読ませ、漏れ（omission）と誤り（error）を探させる。
検証は規模によらず全部行い、省かない（利用者の決定）。

## 前提

- タスクの段階まで終わり、`ledger.py validate <台帳> --gate tasks` がエラー0件であること。
  構造の誤りが残ったまま人や別のエージェントの目を使わない。
- 検証の記録は `reviews.toon` に書く。
  役割ごとのエージェントの出力は、台帳のフォルダーの `review-work/` に置く（台帳のファイルではない作業用のファイル）。

## 役割

| 役割（role） | 見ること |
|-|-|
| 作り手（builder） | 台帳だけで、各タスクを迷わず実装できるか。変更するファイル、段、仕様、データの制約が足りているか。タスクどうしの食い違い。呼び出しを呼ばれる側のコミットに入れているか、各コミットの時点でビルドとテストが通る順番か。 |
| テスト担当（tester） | すべての仕様に、最終のデータ・応答・表示まで決まる受入ケースがあるか。境界値、否定のケース、0件・1件・多数件。各タスクのテストが、そのコミットの変更を確かめているか。 |
| 運用担当（operator） | 既存データの移行、新旧の混在、適用の順序、切り戻し、監視とログ、障害時の復旧、問い合わせへの対応、設定。 |
| 利用者（end_user） | 関係者×場面の各欄の要求について、利用者が目的を最後まで達成できるか。失敗したときに何が見え、次に何をすればよいか分かるか。 |
| 反証役（adversary） | 仕様と設計を壊す具体的な反例を探す。同時操作、順序の逆転、権限の迂回、不正な入力、途中の失敗、再送、同じデータに触れる別の入口。`references/methods/cross-checks.md` の組合せ。 |
| 根拠の検証役（evidence_auditor） | 事実（fact）として書いた行のすべてについて、根拠のファイルの行を開き、書いた主張が本当にコードで裏付けられているかを確かめる（引用がそこにあるだけでは足りない）。確からしさの付け方、名前がコードから取られているか、文書を事実の根拠にしていないか。 |
| 追跡の検証役（trace_auditor） | 意味の追跡。要件が本当にその要求に役立つか、仕様の理由が親の要件の条件に対応するか、仕様にだけ現れる義務が要件になっているか、品質の観点（quality.toon）の not_applicable と out_of_scope から副特性ごとに抜き取り、理由がその観点に固有の根拠になっているか、段×プロパティの欄が仕様と食い違わないか、タスクの内容が仕様と合うか、規則の解釈が守られているか。 |
| 影響範囲の検証役（impact_auditor） | 台帳の changes を見ずに、仕様と経路の設計から変更する箇所を自分で洗い出し、`impact.py search <台帳> --change <任意の ID> --term <名前> --variants --print`（台帳に書かない）で自分で逆引きして、impact.toon と impacts に無い影響先を探す。irrelevant と判断された当たりと、checked_no_impact の共起から抜き取って、判断が正しいかを確かめる。要変更の影響先が仕様とタスクまで届いているか。 |

## 回の進め方

### 1回目（独立した検証、kind independent）

1. `reviews.toon` の rounds に 1回目を書く。
2. 8つの役割のエージェントを、Agent ツールで起動する。
   利用上限が心配でなければ、8つを1つのメッセージで同時に起動する。
   心配なら、1つずつ順に起動する。
   どの場合も、ある役割に、他の役割の指摘を渡さない（独立性を保つため）。
3. 各エージェントの指示は、下の「指示の雛形」から作る。
   エージェントは会話の文脈もこのスキルも引き継がないので、必要なパスと規則をすべて書く。
4. 返ってきた出力ファイルの指摘を、本体が1件ずつ確かめる。
   - 正しい指摘：台帳を直す（必要なら上の層から導き直す）。
     `reviews.toon` の findings に、指摘した役割の ID、状態 fixed、対処を書く（verified_by は再検証で埋める）。
   - 誤った指摘：状態 rejected にし、なぜ誤りかを根拠付きで書く。
     却下も再検証で確かめる。
   - 利用者にしか決められない指摘：状態 escalated にし、確認事項（decisions）に載せて targets に指摘の ID を入れる。
5. reviewers に8つの役割を、状態 done（失敗したら failed にして起動し直す）で書く。

### 机上実行（kind desk）

経路ごとに、正常・拒否・境界値・既存データ・同時操作・途中の失敗・権限の7つの場面で、経路を段ごとにたどる。
各段で、そのプロパティに何が起き、最後にどのデータが残り、どの応答が返り、画面に何が表示されるかを、台帳の仕様と表だけから決める。
一意に決まれば determined、決まらなければ undetermined にして、その原因を指摘として findings に足す。
その場面が経路にあり得ないときは not_applicable にして理由を書く。
机上実行は、本体が行っても、テスト担当の役割に頼んでもよい。

### 再検証（kind reverify）

直した後、新しいエージェント（追跡の検証役。直した層によって他の役割も足す）を起動する。
渡すのは、直した指摘と却下した指摘の一覧（指摘・対処・直した台帳の箇所）と、台帳のパスである。
再検証のエージェントは、次を確かめる。

- 直した指摘それぞれが、本当に解消しているか。
  解消していれば、本体がその指摘の verified_by に再検証のエージェントの ID を書く。
- 却下した指摘それぞれの理由が、根拠として妥当か。
  妥当でなければ、指摘を開き直す。
- 直したことで、新しい漏れや誤りが入っていないか（直した箇所の周りと、それに依存する下の層）。

新しい指摘が出たら、直して、もう一度再検証の回を足す。
再検証を3回繰り返しても指摘が残るときは、それ以上は回さず、残った指摘を escalated にして利用者に判断を求める。
回すたびに `ledger.py validate <台帳> --final` で機械の検査も通す。

### 確かめた範囲を書く

最後に、`reviews.toon` の coverage に、領域ごとに「確かめたこと」と「確かめていないこと」を書く。
確かめていないことがなければ「なし」と書く。
「漏れはない」とは書かず、確かめた枠・観点・範囲を書く。

## 指示の雛形

```
あなたは「〔役割の名前〕」として、実装に入る前の調査の台帳を検証する。
台帳を作ったのは別のエージェントで、あなたは作成に関わっていない。
目的は、実装のタスクに漏れと誤りが起きないよう、台帳の漏れ（omission）と誤り（error）を見つけることである。

## 読むもの
- 台帳のフォルダー：〔台帳の絶対パス〕（TOON 形式。各ファイルの列の意味は 〔スキルの絶対パス〕/references/ledger-schema.md）
- 対象のリポジトリ：〔repo_root の絶対パス〕（読むだけ）
- 粒度の規則：〔スキルの絶対パス〕/references/granularity-rule.md
- 〔役割ごとの追加の資料。例：反証役は references/methods/cross-checks.md、根拠の検証役と影響範囲の検証役は references/methods/investigation.md〕
- 〔影響範囲の検証役だけ：自分で逆引きするときは python -X utf8 〔スキルの絶対パス〕/scripts/impact.py search 〔台帳の絶対パス〕 --term 〔名前〕 --variants --print を使う。--print は台帳に書かない〕

## あなたの役割で見ること
〔上の「役割」の表の、この役割の行を写す〕

## 決まり
- リポジトリと台帳のファイルは変更しない。書いてよいのは、下の出力ファイルだけである。
- 他のエージェントやサブエージェントを起動しない。
- 一般論の指摘はしない。指摘は、どの台帳の項目（ID）についてか、具体的に何が起きるか（入力と結果）、根拠（コードの `ファイル:行` か台帳の項目）を書けるものだけにする。
- 推測の指摘は、推測であると evidence に書く。
- spec.md などの文書は保守されていない前提で扱い、コードと食い違ったらコードを事実とする。
- 重さ：critical（誤った振る舞いを実装する、データを失う、安全に関わる）、high（要件・仕様・タスクが欠けて、ある場面が成り立たない）、medium（解釈が分かれ、手戻りになりうる）、low（書き方の小さな問題）。

## 出力
〔台帳の絶対パス〕/review-work/round〔回〕-〔役割の英名〕.toon に、次の TOON を書く（指摘がなければ findings: []）。
findings[N]{layer,targets,kind,severity,statement,scenario,evidence}:
- layer：scope / current / need / requirement / quality / spec / design / task / evidence のどれか
- targets：対象の台帳の ID（空白区切り）
- kind：omission / error / contradiction / ambiguity / unsupported / granularity / other のどれか
- 値にカンマ・コロン・角かっこ・波かっこを含めるときは二重引用符で囲む
書いたら、python -X utf8 〔スキルの絶対パス〕/scripts/toon.py check 〔出力ファイル〕 で読めることを確かめる。

最後の返答は、出力ファイルのパスと、重さごとの件数だけにする。
```

## 本体の取り込み

各エージェントの出力（`review-work/` の TOON）を読み、指摘ごとに `reviews.toon` の findings に1行を足す。
ID は本体が振り（FD001 から）、round と reviewer（reviewers の ID）を書く。
同じ内容の指摘が複数の役割から出たら、1行にまとめ、対処の欄にまとめたことを書く。
指摘を取り込まずに捨てない。
誤った指摘も rejected として残す。
