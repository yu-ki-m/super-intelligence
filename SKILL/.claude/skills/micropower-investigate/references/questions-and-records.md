# 質問の仕方と記録の分け方

planning-requirements-dialogue スキルの、確からしさの分け方と記録の決まりを取り込み、このスキルに合わせた。

## 確からしさ（confidence）

台帳の行には、確からしさを5つのどれかで付ける。
混ぜないことで、何が確かで何が仮置きかを、読む人が見分けられる。

| 値 | 意味 | 根拠の書き方 |
|-|-|-|
| fact（事実） | コード・設定・スキーマ・テストで確かめた | コードの `ファイル:行` と引用 |
| claim（申告） | 人が言ったが、確かめていない | `conversation` と発言そのまま |
| hypothesis（推測） | 証拠からの推定。文書（spec.md など）に書かれていたことも含む | 推定の根拠。文書なら `doc:相対パス` |
| decided（決定） | 利用者・依頼者が決めた | `conversation` と発言、または確認事項の答え |
| unconfirmed（未確認） | まだ分からない | 確認事項（decisions）の targets に入れる |

数値・保存期間・承認者・契約上の義務を作らない。
分からないものは unconfirmed にし、確認事項にする。

## 聞く前に下書きを出す

- 各層（要求、要件、仕様など）は、Claude が先に下書きを作り、利用者には反応してもらう。
  利用者に一から書かせない。
- 事実（コードや設定を見れば分かること）は、利用者に聞かずに調べる。
  調べる範囲が広ければ、サブエージェントに調べさせ、その間も調べた結果に依存しない作業を進める。
- 書き出す場所、ファイルの名前、調べ方などの進め方は、Claude が決めて、決めたことを伝える。

## 聞くこと

聞くのは、答えで台帳の中身が変わり、コードにも会話にも答えがない業務の判断だけにする。
例：拒否するか上書きするか、上限の値、対象外にするか、既存の振る舞いを廃止するか、規則の解釈。

1回のメッセージで聞くのは1問だけにし、次の形で書く。

```
〔問い〕
- 聞く理由：答えで何が変わるか（どの要件・仕様・タスクに効くか）
- Claude の見立て：推奨する答えと、その理由
- 選択肢：（決められた選択肢があれば。自由に答えてよい）
```

- 問いは、聞く前に `decisions.toon` に status open で書く（layer、why、options、recommendation、targets）。
- 答えを受けたら、利用者の言葉をそのまま answer に書き、status を answered、answered_by を user にする。
  要約しない。
  後で解釈を見直せるようにするため。
- 答えを、関係する台帳の行に反映し、その行の確からしさを decided にする。
- 利用者が「分からない」「依頼者に聞く」と答えたら、status を deferred にする。
  関係する行は unconfirmed のまま targets に入れ、先へ進める行は Claude の仮置き（answered_by claude_provisional、status provisional）で進めて、そのことを書く。
- 黙っていることを、業務の判断への同意とみなさない。

## 段階の承認

要求・要件・仕様の各段階の終わりに、その層の下書きを短くまとめて見せ、承認を求める。
まとめには、件数、主な項目、仮置きした解釈、未確認の項目を入れる。
台帳の表をそのまま貼らない。

承認も `decisions.toon` に1行として残す（例：「要件の一覧はこれでよいか」→ 答え「はい」）。
直すように言われたら、直してから、もう一度承認を求める。
