# 内容レビュー

## 手順

作成者としての説明を一度離れ、実例を入力として成果物をたどる。新たな情報が出たら表現だけではなく要件・境界・推奨そのものを変える。正式の規模では、サブエージェントが利用でき、利用規約上許可されている場合は、生の案件情報（資料・コード）と成果物の草稿を渡して独立レビューを依頼する。作成者は自分の前提に沿って読むため、不具合や例外の経路を見落としやすい。依頼では、作成者の結論や推奨の理由を先に伝えず、材料から確かめてもらう。返ってきた指摘は、コードや資料で確かめてから反映する。利用できなければ自ら役割を分けて点検する。未実施の独立レビューを報告しない。

| 観点 | 確認 | 問題があった場合の戻り先 |
|---|---|---|
| 事業 | 機能から成果までの因果を説明できるか。非開発案を無視していないか | 目的・インパクト |
| 利用者 | 標準手順だけでなく待ち・例外・取消に対応できるか | シナリオ・要件 |
| ドメイン | 同じ語の意味や不変条件が境界内で一貫しているか | 言語・境界 |
| 組織 | 所有チームと専門家が実在し、変更を判断できるか | 体制・契約 |
| データ | 正本と更新責任、コピーの許容用途が分かるか | 所有・移行 |
| 品質 | 6観点を扱い、測定方法があるか | 品質条件・実験 |
| 選択 | 比較条件は公平か。必須制約の違反を点数で隠していないか | 比較・ADR |
| 運用 | 非同期処理や段階移行が失敗した場合の着地点があるか | 実験・移行 |
| 根拠 | 事実・仮説・提案・承認が区別されているか | 証拠台帳 |
| 整合 | 目標、要件、図、ADR、実験のID・用語が一致するか | 関連成果物全体 |

## 反例

以下から案件に関係するものを選び、具体的な開始状態・操作・結果を示す。
- 需要はあるが利用者が行動を変えない。
- サービス分離後も全チームが同時リリースする必要がある。
- 通知が2回来る。順序が逆転する。送信は成功したが応答が失われる。
- 承認済みの処理が外部障害で完了しない。
- 権限が途中で取り消される。削除済みデータが再処理で復活する。
- 移行先で更新した後、旧系に戻す必要が生じる。
- 担当チームが新方式を運用できない。
- 想定より負荷が小さく、分散コストが利益を上回る。

## 他者の構成案をレビューする

他者が作った構成案は、作り直さずに、案が自分の主張をどこまで支えているかを確かめる。作り直した案だけを返すと、作者は自分の案のどこが問題だったのかを知ることができず、案の良い部分まで失われるためである。

1. 案を「目的・前提・提案する構成・期待する効果・移行の手順」に分け、それぞれの根拠が案のどこに書かれているかを探す。根拠が見当たらない場合は「案には記述がない」と書く。作者が別の資料に根拠を持っている可能性があるため、欠けていると断定せず、確認事項にする。
2. 上の観点表と反例を案に当てる。特に次を確かめる。目的と手段の混同（「マイクロサービス化」自体が目標になっていないか）。比較の欠落（現状維持やモジュール型モノリスと比べたか）。事業成果への因果の飛躍。組織の現実との不一致（例：3人のチームで9つのサービスと専用のデータベースを運用する）。データの正本と、移行時の復帰方法の欠落。
3. 指摘ごとに、重大度、案の該当箇所の引用、問題が起きる具体的な状況、代案または修正の方向を書く。重大度は「採用の判断を変える」「条件付きで判断を変える」「表現や記録の改善」の3段階とし、重い順に並べる。同じ重大度の中では、放置したときの損失が大きく取り返しにくいものを先に置く（例：案自身が定めた業務規則を守れない問題は、目的の書き方の問題より先）。指摘の一覧表には修正の方向の列を設け、一覧だけで直し方の見当が付くようにする。
4. 判断に関係する良い点も書く。残すべき部分が分からないと、修正のときに良い部分まで変えられてしまうためである。
5. 方式が組織で決まっている場合は、方式の是非ではなく、その方式の中での構成・段階・統合方式を指摘の対象にする。ただし、方式の固定によって満たせない目標があれば明記する。
6. 最後に、案の作者が次に確かめるべきこと（判断を変える不明点）と、案が「仮説段階」「判断可能な提案」のどちらにあると読めるかを示す。

## 完了の扱い

構造検査合格だけで完了にしない。重大な矛盾を解消するか、具体的な未決事項にして判断に与える影響を表示する。未決事項には確認先、期限または契機、解消方法を持たせる。

仮説段階でも成果を返せる。ただし採用確定や移行可能とは宣言しない。暫定推奨、判断を変える条件、最初の行動があれば、情報不足の中でも有用な提案となる。
