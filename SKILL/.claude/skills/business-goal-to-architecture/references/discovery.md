# 目的・要求・学習の探索

## 情報不足の案件

最初に「直近の具体例」「誰がいつ困るか」「変えられない条件」を調べる。抽象的な理想像を求めるより、最近の1件を業務の開始から終了まで再現する。資料に答えがあれば利用者に同じ質問をしない。

問いの例：
- 最近、その手順を省けずに待った場面は何か。誰の判断を待ち、何を確認していたか。
- システム外のメモや一覧は、何を補うために存在するか。それがないと何が起きるか。
- この機能をなくしても同じ結果が得られるなら、何を変えられるか。
- 現行仕様は何を防ぐために作られたか。導入時と現在で何が変わったか。
- 指標が改善しても現場が困るとすれば、どんな状態か。

原因は観測から区別する。例：「承認に2日かかる」は観測候補、「承認画面が悪い」は原因仮説である。権限の不在、判断材料不足、まとめて処理する習慣という別原因も調べる。

## インパクトマップの例（架空）

| 種類 | 内容 | 状態・検証 |
|---|---|---|
| 目標G1 | 申請者が必要なサービスを利用開始するまでの待ち時間を短縮する | 利用者の目的。現状値と目標値は未確認 |
| アクター | 申請者、承認者、権限管理者 | 関係者候補。担当者確認が必要 |
| 行動変化I1 | 承認者が不足情報を追加質問せずに判断できる | 判断材料不足が主因という仮説 |
| 要件R1 | 申請時に判断に必要な情報が揃い、承認者が根拠を確認できる | 必須項目は案件調査で確定 |
| 手段案 | 入力改善、案内の変更、事前相談、承認条件の整理 | 画面実装は選択肢の1つ |
| 反証 | 材料が揃っても待ち時間が変わらない | 権限者不在等の別原因に戻る |

「自動承認を実装する→生産性向上」は中間が欠ける。自動化する判断が安定しているか、例外時の責任と引継ぎ、誤処理の費用を調べる。目標値を勝手に20%などと埋めない。

## 不確実性に応じた行動

Cynefinの区分を使う。案件全体を単一ラベルに固定せず、論点ごとに判断する。

| 状況 | 次に行うこと | 避けること |
|---|---|---|
| Clear：関係が自明 | 既知の手順と適用条件を確認する | 全部を新規実験にする |
| Complicated：分析で解ける | 専門家・ログ・コードで比較分析する | 専門家の好みを証拠にする |
| Complex：試して初めて分かる | 小さく可逆な実験で観測する | 詳細計画で未知を消した扱いにする |
| Chaotic：緊急の混乱 | 許可範囲で安定化を優先し、後で分析する | 大規模な再設計を先に始める |
| Disorder：状況が分からない | 論点を分け、判別に必要な情報を集める | 自分が得意な手法に全件を当てはめる |

## 実験カード

仮説ID／影響する判断ID／根拠／代替説明／対象／最小操作／観測方法／開始前の基準／成功条件／反証条件／期間・費用・影響範囲の上限／停止条件／責任者／実測結果／結果別の次の判断。

実験を「PoCを行う」だけで済ませない。例：性能が論点なら、本番相当のデータ量・競合・処理構成をどう再現するか、比較対象と計測区間を指定する。顧客需要が論点なら負荷試験で代用しない。

## 決定を遅らせる条件

保留判断には、何を知りたいか、誰が取得するか、いつまでに必要か、待つことで失われる選択肢、暫定対応を付ける。情報が十分になれば決める。全判断を常に最後まで遅らせない。
