# ドメインモデルと境界

## 全体像から始める

1. 開始と終了が分かる業務シナリオを選ぶ。日常の実例と対象外を示す。
2. 起きた出来事を過去形で並べる。「申請する」はコマンド、「申請が受理された」はイベントである。「申請テーブル」はイベントではない。
3. 並びを専門家と確認し、分岐・待機・外部からの入力・期限・例外・取消を加える。
4. 必要な出来事に、実行する役割、コマンド、前提条件、判断規則、保護する不変条件、状態を持つ対象を付ける。
5. 表示情報とその鮮度、業務上の問題、機会、未解決の意味を記録する。
6. 用語・責任・知識・変更理由の変わる箇所から境界候補を作り、実例を通して修正する。

役割／コマンド／規則／状態変更／イベント／次の反応を区別する。色を使う場合も種類名とIDを記す。業務イベントすべてを外部公開イベントにする必要はない。

## 境界の診断

| 着眼点 | 境界候補を検討する証拠 | 誤った決め方 |
|---|---|---|
| 言語 | 同じ「顧客」が販売と請求で異なる状態・規則を持つ | 同じ名詞だから共通巨大モデルを作る |
| 不変条件 | 一度の更新で守るべき業務規則がある | テーブル数やコード行数で分ける |
| 変更理由 | 価格規則と請求規則が別の理由で変更される | 部署名をそのままサービス名にする |
| 所有 | 正しさを説明し、変更を判断する専門家が異なる | 全部を共通チームに任せる |
| 相互依存 | 同時変更や往復呼び出しが多い | ネットワーク分離すれば疎結合と思う |

サブドメインは事業の問題領域、境界付きコンテキストは特定の言語・モデルが通用する範囲、モジュールは実装の区画、デプロイ単位は配置・更新の単位である。対応関係は示すが同義語にしない。

コアは差別化への寄与、支援的は固有だが直接の競争優位ではないもの、汎用的は既製手段の利用可能性で検討する。業務の重要性と独自開発の必要性は別である。認証等を一律に軽視しない。分類は事業モデルと時点に依存する。

## 境界カード

境界ID／名称／目的／業務専門家／担当チーム／サブドメインと分類／業務能力／用語と他境界との差／受け取るイベント／公開するイベント／コマンド／主要な状態・集約／業務規則／表示・照会／協調相手と関係／機会／問題。

カードでは業務の意味を中心にする。クラウド製品やランタイムの細部は別の配置図で表す。コンテキスト・サブドメイン・業務能力の1対1対応が崩れている場合は、理由、影響、調整候補を明示する。

## コンテキストマップ

現状の関係と望ましい関係を別に描く。すべての連携に提供元／利用側／契約／言語変換／データ正本／許容遅延／運用責任を付ける。上流・下流はモデルへの影響関係であり、HTTPの呼出し方向だけで決めない。

| パターン | 判断の焦点 | 代償・注意 |
|---|---|---|
| Partnership | 両チームが協調して同時に成功する必要 | 計画・リリース調整の負担 |
| Shared Kernel | 意味も共有する小さなモデルを共同管理 | 変更合意と共同テストが必要 |
| Customer-Supplier | 利用側の要求を提供側の計画に反映できる | 優先順位と契約の交渉が必要 |
| Conformist | 提供側のモデルを受け入れる利益が大きい | 自分のモデルと変更自由度への影響 |
| Anticorruption Layer | 外部の意味から内部モデルを保護する | 翻訳・保守の費用 |
| Open-Host Service | 複数利用側に安定した接点を提供する | 内部データ構造を無制限に露出しない |
| Published Language | 交換情報の意味と形式を明文化する | バージョンと互換性を管理する |
| Separate Ways | 統合利益より結合費用が大きい | 重複知識・不一致の影響を管理する |

これらは排他的な8択ではない。組織関係・公開接点・交換言語・翻訳は併用できる。イベントの交換だけでShared Kernelと判断しない。

## 例（架空）：申請の承認と権限の付与

「申請が承認された」と「権限が付与された」は別の事実である。承認済みでも外部の権限サービスが停止していれば付与は終わらない。承認コンテキストが承認判断を所有し、権限管理側が実際の付与状態を所有する案を考えられる。ただし専門家の会話と規則で確認する。

同じ承認通知の再受信、付与後の取消、申請中の所属変更をたどる。結果として、重複付与を防ぐ識別、付与失敗の可視化、取消時点の状態確認が必要になる場合がある。これらを暗黙の技術詳細にせず、必要な業務結果として要件へ戻す。
