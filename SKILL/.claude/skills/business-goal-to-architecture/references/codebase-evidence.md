# コードと記録から境界の証拠を集める

既存改善と移行判断では、「この2つの機能は密に結合している」「このテーブルの正本が曖昧だ」といった主張が、境界の切り方と移行の順序を左右する。これらを印象で書くと、読み手は確かめようがなく、反対意見との議論も平行線になる。そこで、リポジトリと運用記録から観測できる事実を集め、場所（ファイルと行、コミット、実行したコマンド）を付けて証拠台帳（evidence）に載せる。

観測と解釈は分けて書く。「注文と請求のモジュールが、過去1年のコミットの4割で同時に変更されている」は観測事実である。「だから両者は同じ変更理由を持ち、境界の切り方が誤っている」は原因仮説であり、一括のリファクタリングや共通部品の更新という別の説明もありうる。原因仮説には、代替説明を確かめた結果を添える。

## 調べる観点

| 知りたいこと | 見る場所 | 調べ方の例 | 読み取りの注意 |
|---|---|---|---|
| 変更理由の近さ | git の履歴 | `scripts/co_change.py` でモジュール間の同時変更を数える | 同時変更が多いことは、変更理由が境界をまたいでいる兆候であり、証明ではない。一括整形・依存更新・名前変更のコミットは除く |
| 依存の向きと量 | import / require / using、DIの設定、パッケージ定義 | Grep で他モジュールへの参照を集め、モジュール間の依存の表を作る | コードの依存は呼び出しの向きを表す。業務上の上流・下流とは別に判断する |
| データの共有と正本 | スキーマ、マイグレーション、ORMのモデル、SQL | テーブルごとに、書き込むモジュールと読むモジュールを一覧にする | 複数のモジュールが同じテーブルに書き込むなら、正本と更新責任が曖昧な兆候である。ビュー、バッチ、他システムからの直接参照も探す |
| 一貫性の範囲 | トランザクションの境界（`@Transactional`、`BEGIN`/`COMMIT`、Unit of Work など） | 1つのトランザクションで更新されるテーブルの組を書き出す | この組を別々のサービスに分けると、整合を保つ仕組み（補償処理や照合）が新たに必要になる |
| 言葉の意味の違い | クラス名、カラム名、画面の文言、仕様書、問い合わせの記録 | 同じ名詞（例：顧客、注文）が、モジュールごとに異なる属性・状態・規則を持つかを比べる | 名前が同じでも意味が同じとは限らない。意味が分かれる箇所は境界の候補になる |
| 実際の所有 | CODEOWNERS、ディレクトリごとの変更者 | `git shortlog -sn -- <ディレクトリ>` で主な変更者を見る | 組織図と一致しなければ、現実の所有を記録する。個人名を成果物に載せる必要があるかは利用者に確認する |
| リリースの待ちと衝突 | CI/CDの設定、デプロイの履歴、ブランチの運用、リリースノート | 他チームの変更を待ったリリースの頻度を調べる | 記録がなければ、利用者への確認事項にする |
| 負荷と障害の偏り | 監視、ログ、障害報告 | 機能ごとの負荷と、障害の影響範囲を調べる | コードからは分からない。記録が手元になければ計測計画に回し、推定値を事実として書かない |
| 例外の経路 | 境界をまたぐ処理のコード | 値がない（NULL、行が存在しない）、同じ操作が2回行われる、2つの操作が同時に行われる、順序が逆になる、の4つの場合にコードがどう動くかを追う | 正常系だけを読むと、分離や移行で表に出る不整合を見落とす。見つけた不具合は、構成の判断とは別に直すべきものとして分けて書く |

すべての観点を毎回調べる必要はない。今回の判断（例：注文と請求を分離するか）を左右する観点から調べる。

## 同時変更の数え方

```bash
python -X utf8 "${CLAUDE_SKILL_DIR}/scripts/co_change.py" <リポジトリ> --since 2025-01-01 --depth 2
```

- `--depth` は、パスの先頭から何階層をモジュールとみなすかを指定する。`src/orders/service.py` は `--depth 2` で `src/orders` になる。
- 技術レイヤごとにディレクトリを分けた構成（例：Rails の `app/models/`、`app/controllers/`）では、ディレクトリ単位の同時変更はレイヤ間の結合を表すだけで、業務の境界は見えない。その場合は `--map` に、パスのパターンと業務上のモジュール名の対応を書いたJSONを渡す。例：`[["app/*order*", "注文"], ["app/*invoice*", "請求"]]`。パターンの `*` は `/` もまたぐ。最初に一致した行が使われる。
- 変更したファイルが `--max-files`（既定50）を超えるコミットは、一括の変更とみなして数えない。ロックファイルや生成物は `--exclude "*.lock"` のように除く。
- `--path src` のように指定すると、そのディレクトリの下だけを数える。
- 出力の「結合度」は、2つのモジュールが同時に変更されたコミット数を、変更回数が少ない方のコミット数で割った値である。0.5なら、変更が少ない方のモジュールは、変更の半分で相手も同時に変更されている。
- 期間と除外の条件は、結果と一緒に報告書に書く。条件によって数値が変わるためである。

## 証拠台帳への載せ方

例（架空）：

```json
{"id":"E3","locator":"git log 2025-01-01..2025-12-31（co_change.py --depth 2、50ファイル超のコミットを除外）","claim":"src/billing を変更した112件のコミットのうち47件で src/orders も同時に変更された（結合度0.42）"}
```

この観測を根拠にする要件や判断では、原因仮説として扱い、代替説明（共通部品の更新、一括の名前変更など）を確かめたかを本文に書く。
