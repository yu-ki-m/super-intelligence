# 予約SaaS「サロンブック（仮称）」システム構成案 v0.3

作成：開発チーム　　レビュー予定：来週の設計レビュー

## 1. 目的

最新のアーキテクチャを採用し、将来の急成長にも耐えられるスケーラブルなシステムを作る。

## 2. 前提

- 対象：美容室・ネイルサロン向けの予約受付と事前決済
- 開発体制：エンジニア3名（バックエンド2名、フロントエンド1名）。インフラ専任はいない
- リリース目標：4か月後にMVPを公開し、初年度に50店舗の導入を目指す
- 想定利用量：1店舗あたり月200件程度の予約

## 3. 構成

次の9つのマイクロサービスに分割する。各サービスは専用のPostgreSQLを持ち、他サービスのデータベースには直接アクセスしない。

| サービス | 責務 |
|---|---|
| 認証 | ログイン、店舗スタッフと来店客のアカウント |
| 店舗 | 店舗情報、営業時間 |
| スタッフ | スタッフ情報、シフト |
| メニュー | 施術メニュー、所要時間、料金 |
| 予約 | 予約の受付・変更・取消 |
| 顧客 | 来店客の情報、来店履歴 |
| 決済 | オンライン事前決済（外部の決済代行を利用） |
| 通知 | メール・LINEでの予約確認とリマインド |
| 分析 | 店舗向けの売上・予約の集計 |

- サービス間の通信はすべてKafkaのイベントで行う（同期のAPI呼び出しは使わない）。
- 全サービスでイベントソーシングとCQRSを採用する。監査に対応でき、将来の分析にも使えるため。
- Kubernetes（EKS）上で稼働させ、Istioでサービスメッシュを構成する。

## 4. 主要な処理

### 予約の受付

1. 来店客が日時・メニュー・スタッフを選ぶ。
2. 予約サービスは、スタッフサービスが発行する「シフト更新イベント」から作った読み取りモデルと、自身の予約一覧の読み取りモデルから、空き枠を判定する。
3. 空いていれば「予約受付済みイベント」を発行する。
4. 決済サービスが「予約受付済みイベント」を受けて事前決済を実行し、「決済完了イベント」を発行する。
5. 通知サービスが予約確認を送る。

同じスタッフの同じ時間帯に2件の予約が入ってはならない。予約サービスの空き枠判定でこれを防ぐ。

### 予約の取消

来店客が取り消すと、予約サービスが「予約取消イベント」を発行し、決済サービスが返金する。

## 5. 期待する効果

- サービスごとに独立してデプロイできるため、開発スピードが上がる。
- 負荷が増えたサービスだけをスケールできる。
- イベントソーシングにより、全ての変更履歴を監査に使える。

## 6. スケジュール

| 期間 | 内容 |
|---|---|
