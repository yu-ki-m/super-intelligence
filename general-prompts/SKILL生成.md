「ユーザーが与えた目的を、検証可能な完了状態まで確実に持っていく」ための汎用Agent Skillを設計・実装してください。

私は、単なるTODO実行スキルや「最後まで頑張る」という精神論を求めていません。

このスキルの目的は、

「要求を理解する」
→「完了条件を定義する」
→「計画する」
→「実行する」
→「成果物を検証する」
→「不足を発見する」
→「修正する」
→「独立した観点から再検証する」
→「完了条件を満たしたことを証明する」

という閉ループを、AIエージェントに強制することです。

# 最重要原則

AI自身の「終わりました」という自己申告を、完了の根拠として認めないでください。

完了とは、

「事前に定義された完了条件について、客観的な証拠を使って、すべて満たしていることを確認できた状態」

と定義してください。

成果物を作ったことと、目的を達成したことを区別してください。

例えば、

- コードを書いた
- ファイルを作った
- テストを書いた
- コマンドを実行した
- 文書を作成した

だけでは完了としてはいけません。

それらがユーザーの目的を本当に満たしていることまで検証してください。

# このスキルが解決すべき問題

AIエージェントには、以下の失敗が頻繁に発生します。

- 途中まで実行して完了したと判断する
- 要求の一部を忘れる
- 実装しただけで動作確認しない
- テストを書いただけで実行しない
- テストが通っただけで要求を満たしたと思う
- 正常系だけ確認する
- 失敗系・境界値を確認しない
- 自分が書いたコードを自分で評価して問題なしと判断する
- 「おそらく動く」「たぶん問題ない」で終了する
- エラーを回避しただけなのに原因を解決したと思う
- TODOや未実装を残したまま終了する
- サブタスクを完了したことで全体目的も完了したと誤認する
- コンテキスト圧縮などによって当初要求を忘れる
- 修正によって別の場所を壊す
- ユーザーが指定した方法を実行しただけで、本来の目的達成を確認しない
- 途中でツール/APIが失敗すると、そのまま作業を縮退させる
- 「できなかったこと」を明示せず成功扱いする
- 証拠を提示せず完了宣言する

これらを構造的に防止してください。

# 必須設計

## 1. Goal Contract

開始時にユーザー要求を以下へ変換してください。

- Goal
- Deliverables
- Acceptance Criteria
- Constraints
- Non-Goals
- Required Evidence
- Unknowns
- Risks

ユーザーが明示していない完了条件も、目的達成に不可欠なら推定候補として提示してください。

ただし、推定した要求を勝手に確定しないでください。

重大な解釈差が発生する場合だけ確認してください。

## 2. Completion Ledger

要求を追跡可能な台帳として管理してください。

各要求について最低限、

- ID
- Requirement
- Status
- Evidence
- Verification Method
- Remaining Work

を保持してください。

Statusは最低でも、

- PENDING
- IN_PROGRESS
- BLOCKED
- IMPLEMENTED_NOT_VERIFIED
- VERIFIED
- FAILED
- NOT_APPLICABLE

を区別してください。

IMPLEMENTED_NOT_VERIFIED を VERIFIED と同一視してはいけません。

## 3. Plan

要求とタスクの対応関係を明示してください。

各タスクが、どのAcceptance Criteriaを満たすためのものか追跡可能にしてください。

要求に紐づかない作業を大量に増やさないでください。

逆に、タスクに変換されていない要求が残っていないか確認してください。

## 4. Execution Loop

以下をループしてください。

PLAN
→ EXECUTE
→ OBSERVE
→ VERIFY
→ GAP ANALYSIS
→ REPLAN
→ EXECUTE

「一度実装して終わり」にしないでください。

検証で不足を発見した場合、その不足を新しいタスクとしてCompletion Ledgerへ戻してください。

## 5. Independent Verification

成果物を作ったコンテキストと、検証するコンテキストを可能な限り分離してください。

サブエージェントが利用できる場合、

実装担当
と
検証担当

を分けてください。

検証担当には、実装担当の自己評価を渡さず、

- 元の要求
- 完了条件
- 成果物
- 実行結果

を中心に渡してください。

検証担当は「問題を発見すること」を役割としてください。

単なる追認者にしないでください。

## 6. Adversarial Verification

正常に動くことだけではなく、

「どのように失敗し得るか」

を検証してください。

最低でも必要に応じて、

- 正常系
- 異常系
- 境界値
- 空入力
- 大量入力
- タイムアウト
- 部分失敗
- 再実行
- 重複実行
- 中断→再開
- 外部依存失敗
- 権限不足
- 不正入力
- 既存機能への回帰
- 並行実行
- 状態不整合

などを検討してください。

すべてを機械的に実行するのではなく、対象に relevant なものを選択してください。

## 7. Counterfactual Verification

「成功した」という仮説だけを検証しないでください。

最低限、

「もしこの成果物が要求を満たしていないとしたら、どこに問題がある可能性が高いか」

という逆方向の検証を行ってください。

さらに、

- 別の入力では壊れないか
- 別の環境では壊れないか
- 偶然テストが通っただけではないか
- モックによって問題を隠していないか
- テスト対象そのものが間違っていないか
- 検証方法に盲点がないか

を確認してください。

## 8. Evidence-First Completion

完了宣言には証拠を要求してください。

例えばソフトウェアなら、

- 実行したコマンド
- テスト結果
- lint/build結果
- 実際の出力
- 差分
- 該当ファイル
- 期待値と実測値

などです。

文書なら、

- 要求項目との対応
- 欠落チェック
- 矛盾チェック
- 必須章の存在
- 引用元確認

などを証拠として扱ってください。

「確認しました」という文章だけをEvidenceとして認めないでください。

## 9. Regression Guard

修正によって元々動いていたものを壊していないことを確認してください。

局所テストだけではなく、必要に応じて関連範囲の回帰確認をしてください。

## 10. Stop Condition

以下をすべて満たすまで正常終了しないでください。

- Acceptance Criteria がすべて VERIFIED または明示的な NOT_APPLICABLE
- PENDING が0
- IMPLEMENTED_NOT_VERIFIED が0
- 未解決の重大な FAILED が0
- BLOCKED が存在する場合、その理由と影響をユーザーへ明示
- 独立検証が完了
- 重大なRegressionがない
- Required Evidenceが揃っている

「時間がかかった」
「かなり作業した」
「主要部分はできた」

などを終了条件にしないでください。

# 完遂性

途中で失敗した場合でも、即座に作業全体を終了しないでください。

回復可能な失敗なら、

原因分類
→ 再試行
→ 別手段
→ スコープ再評価
→ 再検証

を行ってください。

ただし無限ループは禁止します。

再試行回数だけではなく、

「同じ失敗を同じ方法で繰り返していないか」

を判断してください。

同一原因で再試行しても成功可能性が上がらない場合、別アプローチへ変更してください。

# ユーザー指示との関係

ユーザーが指定した手段と、ユーザーの目的を区別してください。

ユーザーの手段が明らかに目的達成に不利であり、

- 効果
- コスト
- 安全性
- 実行可能性
- 保守性

のいずれかで重大な問題がある場合、

実行前に代替案とトレードオフを提示してください。

ただし、「本当はこうしたいはず」と勝手に目的を書き換えないでください。

# 不確実性

確認できていないことを、確認済みとして扱わないでください。

以下を区別してください。

- FACT
- INFERENCE
- ASSUMPTION
- UNKNOWN

UNKNOWNが重要な完了条件に影響する場合、完了宣言を禁止してください。

# コンテキスト喪失対策

長時間タスクでも要求を失わないよう、

Goal Contract
Completion Ledger
重要な設計判断
未解決事項
次のアクション

を永続的な作業状態として管理する仕組みを設計してください。

コンテキスト圧縮・サブエージェント委譲・セッション長期化後にも復元できる形式にしてください。

# サブエージェント

利用可能な場合は積極的に利用してください。

特に以下は分離してください。

- 実装
- 調査
- テスト
- 要求照合
- 反証
- 回帰確認
- 最終監査

ただし、サブエージェントを増やすこと自体を目的にしないでください。

サブエージェントの結果も無条件で信用せず、統合時に検証してください。

# 最終監査

終了直前に、実装担当とは別の視点で最終監査を実施してください。

最終監査では、

「この仕事を失敗扱いにするとしたら、その理由は何か？」

から開始してください。

その後、

1. 元の要求を再読する
2. Acceptance Criteriaを1件ずつ確認する
3. 成果物との対応を見る
4. Evidenceを確認する
5. 未検証箇所を探す
6. 回帰を探す
7. 暗黙の未完了を探す
8. TODO/FIXME/仮実装/モック/ハードコードを確認する
9. ユーザー要求からの逸脱を確認する
10. 完了宣言が証拠によって成立するか判定する

という工程を必須化してください。

# 出力時の完了報告

完了時には単に

「完了しました」

と書かないでください。

最低でも、

- 何を達成したか
- 何を検証したか
- Acceptance Criteriaの達成状況
- 主要なEvidence
- 残存リスク
- 未完了事項の有無

を簡潔に報告してください。

未完了がある場合は「完了」と表現しないでください。

# スキル自体の品質要求

このSkill自体についても、

「このSkillが本当にエージェントの途中終了・自己評価バイアス・検証不足を防げるか」

を検証してください。

単なる長いSKILL.mdを作るだけで終わらせないでください。

以下も作成してください。

- SKILL.md
- 必要なreferences
- 必要ならscripts
- 状態管理テンプレート
- Completion Ledgerテンプレート
- Verification Checklist
- Final Audit Checklist
- 使用例
- 失敗例
- テストシナリオ

さらに最低20種類程度の異なるタスクを想定して、Skillの設計を机上検証してください。

例:

- 小規模コード修正
- 大規模リファクタリング
- バグ修正
- 複数コミット調査
- API統合
- インフラ変更
- 文書作成
- 調査レポート
- データ分析
- UI変更
- 移行作業
- テスト追加
- 性能改善
- セキュリティ修正
- 障害原因調査
- 長時間タスク
- 外部API失敗を含むタスク
- 複数エージェントタスク
- ユーザー要求が曖昧なタスク
- 一部しか検証できないタスク

これらを使って設計上の欠陥を洗い出し、Skillを改善してください。

# 証跡要求(設計観点一覧)

以下の観点で、どう設計したが証跡のファイルを以下の形式で残してください。  

ファイル名：`design_evidence_YYYYMMDD_hhmmss.md`  

``` md
## 1. 目的・対象範囲・完了条件

| No. | 設計観点 | 設計時に決めること |
|---:|---|---|
| 1 | 利用者と用途 | 誰が、どの場面で成果物を使い、何を判断するのか。利用者と最終判断者が異なる場合は、両者を明確にする。 |
| 2 | 答えるべき問い | どの問いに、どの証拠を使って答えるのか。たとえば「障害が起こり得るか」はコードから判断できる場合があるが、「実際に起きたか」には実行記録などの証拠が必要になる。 |
| 3 | 対象範囲 | 対象とする顧客、期間、環境、システム、データの範囲はどこまでか。途中で対象を追加できる条件と、その判断者を決める。 |
| 4 | 成果物と提出先 | 誰に、何を、どの形式で渡すのか。受け手がAIとの会話を閲覧できない場合は、チケットや報告書だけで判断できる内容を定める。 |
| 5 | 完了・部分完了・保留 | どの証拠や成果物がそろえば完了か。一部を取得できない場合、確認済みの範囲を報告して終了するか、追加情報を待つかを決める。 |
| 6 | 誤りの影響 | 見逃し、誤検出、誤操作、遅延が、それぞれ誰にどの程度影響するか。重大な誤りについては、公開や実行の前に必要な検査を決める。 |

## 2. 起動・受付・実行単位

| No. | 設計観点 | 設計時に決めること |
|---:|---|---|
| 7 | 起動条件 | 手動依頼、定期実行、PR更新、外部通知など、何を契機に開始するのか。対象外のイベントや、権限のない主体からの依頼をどう識別するか。 |
| 8 | 実行単位と重複受付 | 何を1件の仕事として識別するか。同じ通知の再送と、利用者が意図して行った新しい依頼をどう区別するか。 |
| 9 | 同期・非同期 | 利用者が完了まで待つ必要があるか。非同期なら、受付番号、進捗の確認方法、完了通知、結果の受取先を決める。 |
| 10 | 優先度と依頼の競合 | 即時対応と夜間処理が同じ実行枠を使うとき、どちらを優先するか。同じ対象に新しい依頼が来た場合、古い実行を継続するか取り消すか。 |

## 3. 処理の分解・分岐・統合

| No. | 設計観点 | 設計時に決めること |
|---:|---|---|
| 11 | コード・モデル・人の分担 | 型検査や金額比較などの規則はコードで処理できるか。文章の解釈や仮説の作成はモデルに任せるか。業務上の承認を誰が行うか。 |
| 12 | 分解の必要性と単位 | 1回の処理で目的を達成できるか。分ける場合は、ファイル、機能、仮説、成果物のどれを単位にすると、担当範囲と結果を検証しやすいか。 |
| 13 | 順序と依存関係 | 後続作業を始めるには、前段で何が確定している必要があるか。前段が終了しただけで開始できるか、結果の妥当性も確認する必要があるか。 |
| 14 | 固定手順と途中の判断 | どの手順をあらかじめ固定し、どの判断を実行時に行うか。たとえば調査の順序は固定し、次に読む資料だけを途中の発見に応じて選べる。 |
| 15 | 分岐条件 | 何を根拠に次の処理を選ぶか。複数条件が同時に成立した場合、どれも成立しない場合、情報不足で判定できない場合の行き先を決める。 |
| 16 | 並列化と担当範囲 | 互いの結果を待たずに開始できる作業は何か。複数担当が同じファイルや記録を更新する場合、変更の所有者を誰にするか。 |
| 17 | 追加調査と停止条件 | どんな発見があれば調査を追加するか。すでに確認した対象の再調査をどう防ぐか。新しい証拠が得られない場合の終了条件を決める。 |
| 18 | 並列作業の終了待ち | 全担当の完了が必要か、一部の結果で次へ進めるか。担当の時間切れ、途中の失敗、報告確定後に届いた結果をどう扱うか。 |
| 19 | 結果の統合 | 別々の担当が調べた結果を何に基づいて対応付けるか。重複・欠落・矛盾を誰が解消するか。同じ資料を複数担当が引用したとき、独立した証拠として数えない仕組みがあるか。 |
| 20 | 委譲する権限と責任 | 担当には作業だけを任せるのか、追加調査の決定や他の担当への再委譲も任せるのか。範囲変更と最終報告について誰が責任を持つか。 |

## 4. 段階間の入出力・情報・証拠

| No. | 設計観点 | 設計時に決めること |
|---:|---|---|
| 21 | 入力契約 | 各段階が必要とする項目、型、単位、タイムゾーン、対象期は何か。項目不足や不正値を受け取ったら、補完・照会・停止のどれを選ぶか。 |
| 22 | 出力契約 | 次の担当に渡す結果・根拠・処理状態をどう表現するか。「検索結果が0件」「未調査」「取得失敗」を区別できるか。 |
| 23 | 正式な情報源 | 情報源の内容が食い違った場合、どの記録を判断根拠にするか。たとえばチケットに書かれた承認の主張を、正式な承認記録と区別できるか。 |
| 24 | 情報の版・時点・鮮度 | いつの仕様、コミット、取引状態を対象にしたか。各担当が異なる時点の情報を取得した場合、比較可能かを確認する方法はあるか。 |
| 25 | 担当間の引き継ぎ | 元の会話を参照できない担当に、目的、対象ID、制約、確認済みの事実、取得失敗、未解決事項のどれを渡すか。 |
| 26 | 検索・選別・要約 | 必要な資料をどう取得するか。モデルに渡せる情報量を超えた場合、例外条件、根拠の位置、対象外にした資料をどう記録するか。 |
| 27 | 段階ごとの妥当性検証 | 出力形式に加えて内容をどう検査するか。参照先が実在することと、参照先が実際に主張を裏付けることを区別して確認できるか。 |
| 28 | 識別子と対応関係 | 業務対象のID、ワークフローの実行ID、ツールの呼び出しIDをどう区別するか。複数回の呼び出しが同じ業務対象に対応する場合に識別できるか。 |
| 29 | 網羅性と不確実性 | 調査予定の対象と、実際に確認できた対象を照合できるか。観測した事実、そこから導いた判断、未確認事項を成果物で区別できるか。 |

## 5. 実行状態・待機・取消

| No. | 設計観点 | 設計時に決めること |
|---:|---|---|
| 30 | 状態と遷移 | 受付、実行中、承認待ち、部分完了、失敗、取消、完了のうち、業務に必要な状態はどれか。誰がどの条件で状態を変更できるか。 |
| 31 | 状態の保存と再開位置 | プロセスや端末が停止しても、完了済みの段階と次の作業を特定できるか。中間成果物と実行状態をいつ保存するか。 |
| 32 | 外部イベント待ち | 承認、外部処理の完了通知、利用者の返答を待つ間、どう休止するか。重複、遅延、順序が逆転した通知を正しい実行に対応付けられるか。 |
```
